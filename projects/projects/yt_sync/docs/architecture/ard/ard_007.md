# ADR 007: Intelligent Adoption and Repair of Untracked Files

**Date**: 2025-06-23

**Status**: Accepted

---

### 1. Context

The `--audit` command has revealed that user libraries can contain hundreds of video files that are not tracked by the application's download archive (`.metadata/downloads.txt`). This occurs for two main reasons:
1.  Files were downloaded by other tools or previous versions of this project.
2.  Filenames do not follow the project's standard `Title [ID].ext` convention, making them invisible to the existing `auto_import` logic.

Currently, the only way to "fix" these files is to manually delete them and let the application re-download them, which is extremely inefficient in terms of bandwidth and API quota usage.

### 2. Decision

We will introduce a new, explicit "repair mode" to intelligently discover, verify, and adopt these untracked files into the managed library. This feature will be triggered by a dedicated command-line flag, `--repair`, and will **not** run as part of the standard `--sync` operation to ensure user intent and system predictability.

The core logic for the repair process will be as follows:

### 3. Action Plan & Design Mitigations

To ensure the feature is robust, user-friendly, and safe, the implementation will adhere to the following principles derived from a SWOT analysis:

1.  **User Control & Transparency:**
    *   A `--dry-run` flag will be implemented for the repair mode (`--repair --dry-run`). This will simulate the entire process and output a detailed report of all proposed actions (ADOPT, QUARANTINE, SKIP) without modifying any files.
    *   Logging for quarantined files will be verbose, explicitly stating which verification check failed (e.g., `Reason: Duration mismatch`).

2.  **Configurability & Heuristics:**
    *   The "title similarity" check will use a robust library (e.g., `thefuzz`) to handle complex strings.
    *   The similarity score threshold will be user-configurable in `config.yaml` to accommodate diverse libraries, defaulting to a balanced value (e.g., `0.4`).

3.  **Performance & Stability:**
    *   The verification process for a large number of files will be parallelized using a `ThreadPoolExecutor` to improve performance.
    *   A `rich.progress` bar will provide real-time feedback to the user during long-running repair operations.
    *   All file system operations (rename, move) will be wrapped in `try...except` blocks to gracefully handle potential file locks (e.g., a file being in use) and permission errors.
    *   The repair process will perform a pre-flight check for the `ffprobe` executable and fail fast with an actionable error message if it is not found.

### 4. Consequences

*   **Positive**:
    *   Dramatically improves the tool's utility by allowing users to import and manage existing archives without costly re-downloads.
    *   Actively improves library health by identifying and quarantining corrupt or low-quality files.
    *   Positions the project as a more advanced and intelligent library management solution.
    *   Maintains a clear separation of concerns between the "sync" and "repair" operations.

*   **Negative**:
    *   Introduces a new dependency for fuzzy string matching (e.g., `thefuzz`).
    *   Adds complexity to the codebase, which must be managed with clean encapsulation in a new `yt_sync/repair.py` module.
    *   Requires clear and thorough documentation to manage user expectations about what the repair tool can and cannot do.
