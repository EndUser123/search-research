### Document Analysis

In `docs/roadmap.md`, under the completed **PHASE 1-7**, it states:

### The Discrepancy

This reveals a critical issue:
1.  **The Requirement Exists:** The roadmap, which acts as our high-level product plan, explicitly states that a "local file cache for metadata" is a completed feature.
2.  **The Implementation is Incomplete:** Our detailed analysis of the `yt_sync/metadata.py` source code has shown that **only the in-memory part was implemented.** The persistent, on-disk local file cache that survives between application runs **does not exist**.

You are correct. We do not need a new PRD because the requirement is already documented and considered part of the core product. The problem is that the implementation does not match the documentation.

### The Path Forward

This isn't a new feature request; it's a **bug fix** to bring the implementation in line with the established product requirements.

However, because the implementation is missing, we still need to make a formal architectural decision about *how* to build it correctly this time. Creating an ADR is the right process for this. It will serve two purposes:
1.  It documents the specific design for the persistent cache (e.g., location, format, read/write strategy).
2.  It serves as a record that we are now correcting the discrepancy between the roadmap and the code.

Therefore, my recommendation stands, but with a clearer justification:

**We must create `ADR 008: Implement Persistent, On-Disk Metadata Cache` not to invent a new feature, but to formally design the implementation of a feature that is required by the project roadmap but was never fully built.**

This ensures we build it correctly and have a paper trail explaining the decision.
