## Intent Summary

Design proposal for an ADR verification system that creates automated test coverage from Architecture Decision Records, linking architectural decisions to implementation via pytest tests and deviation detection hooks. Spans modifications to `/planning`, `/code`, `/verify` skills plus new scripts and a hook.

## Health Score: 50% — Warning

The proposal addresses a real architectural gap but has 2 HIGH-severity prerequisite blockers and 1 MEDIUM calibration issue. The design is directionally sound but not yet implementable without resolving foundational schema issues first.

## Logical Gaps & Inconsistencies

1.1. [HIGH] **No ADR markdown schema** (source: adversarial-compliance)
   - The existing ADR at `P:/__csf/arch_decisions/2025-03-08_python_tree_sitter_integration.md` has no `## Acceptance Criteria` section — only prose rationale and architectural decisions. The proposal assumes `## Acceptance Criteria` with parseable `- AC1: testable statement` format, but no ADR in the repo uses this format.
   - Without this schema, `adr_to_tests` cannot extract ACs from any existing ADR. Only future ADRs would benefit.
   - Verification: `P:/__csf/arch_decisions/2025-03-08_python_tree_sitter_integration.md:1-60` — no structured AC section exists.

1.2. [HIGH] **AUDIT phase mechanism unspecified** (source: adversarial-critic)
   - `/code` Phase 7 AUDIT (`P:/.claude/skills/code/SKILL.md:1798`) runs ruff, mypy, pylint — no ADR verification exists. The proposal says "verify ADR ACs are still satisfied" but gives no execution mechanism.
   - Must choose: (a) subprocess pytest, (b) `/verify adr:<id>` invocation, (c) direct import. This is a prerequisite-blocking integration decision.
   - Severity calibrated to HIGH (equivalent to schema issue — both block implementation).

## Hidden Assumptions & Fragile Dependencies

2.1. [MEDIUM] **Prose ACs cannot be parsed into pytest** (source: adversarial-critic)
   - The existing ADR's criteria are architectural rationale ("Use `tree-sitter-language-pack` over alternatives"), not testable assertions. These cannot become failing tests without manual translation.
   - The 30-50% ambiguity estimate in Phase 1 is realistic for natural language ADRs.

2.2. [MEDIUM] **`/planning` trigger mechanism undefined** (source: adversarial-critic, Phase 2 recall failure)
   - "At acceptance time" implies automatic generation, but `/planning` has no step that generates test stubs. The ADR-aware behavior (lines 145-160 of `/planning` SKILL.md) creates a plan from an ADR but emits no test file.
   - Is the trigger an explicit command (`/adr_to_tests 0001`), automatic on `status → implementation-ready`, or a manual step in `/planning` workflow? This must be defined before the design is implementable.

2.3. [LOW] **ADR version lifecycle undefined** (source: adversarial-critic)
   - When an ADR is revised, should old tests be overwritten, archived, or kept? No protocol specified.

## Missing Obvious Actions / Best Practices

3.1. [HIGH] **Existing ADRs retroactively unparseable** (source: Phase 2 recall failure)
   - The 3 existing ADRs in `P:/__csf/arch_decisions/` use prose criteria. For these to have ADR test coverage, someone must manually convert prose to testable ACs. The proposal offers no path for this.
   - Without this, the system only works for new ADRs — existing architectural debt remains unverified.

3.2. [MEDIUM] **Commit-level ADR ID linking absent** (source: Phase 2 recall failure)
   - The proposal mentions "ADR-to-code linking in commit messages" but doesn't specify format. Without `ADR-0001` in commit footers, there is no audit trail connecting code changes to architectural decisions.
   - Recommend: `git commit -m "feat: description\n\nADR-0001` convention, enforced by a `commit-msg` hook.

## Risks and Edge Cases

4.1. [MEDIUM] **ADR test maintenance overhead for solo dev** (source: adversarial-critic)
   - Every ADR with test coverage becomes a ongoing maintenance obligation. For a solo dev, this could become burdensome — particularly if many ADRs are "important enough" to cover but complex enough that their tests frequently break on refactors.
   - No guidance provided on when ADR test coverage is warranted vs. prose-only.

4.2. [LOW] **Circular dependency in file tracking** (source: adversarial-compliance)
   - ADR registry and test infrastructure files should be excluded from "ADR-covered files" to avoid self-referential triggers. Trivial to fix but needs explicit mention.

## Concrete Recommendations

5.1. [HIGH] **Define ADR markdown schema first** (source: adversarial-compliance)
   - Create `P:/__csf/docs/adr_schema.md` with required format:
     ```markdown
     ## Acceptance Criteria
     - AC1: [imperative, testable statement]
     - AC2: [must map to pytest function name: test_<adr_id>_ac1()]
     ```
   - Require AC numbering and imperative mood. Non-compliant ADRs cannot be processed by `adr_to_tests`.

5.2. [HIGH] **Specify `/planning` test stub generation trigger** (source: adversarial-critic)
   - Choose one: (a) explicit command after ADR acceptance, (b) automatic on status change, (c) explicit step in `/planning` workflow. Recommend (c) — add a step in `/planning` after `implementation-ready` status is set.

5.3. [HIGH] **Define AUDIT phase integration mechanism** (source: adversarial-critic)
   - Recommend: invoke `/verify adr:<id>` from `/code` AUDIT phase when plan has ADR-linked tasks. This reuses existing `/verify` infrastructure rather than building new subprocess logic.

5.4. [MEDIUM] **Schema-validate ADR_REGISTRY.json** (source: adversarial-compliance)
   - Add JSON Schema as inline comment header in the registry file, not a separate doc. Solo-dev project: fewer files is better.
   ```json
   { "// JSON Schema": "v1 - { adr_id: { covers: string[], test_file: string, status: string } }" }
   ```

5.5. [MEDIUM] **ADR deprecation protocol** (source: adversarial-compliance)
   - On deprecation: rename test file to `test_adr_<id>_DEPRECATED.py`, add `@pytest.mark.skip("ADR deprecated")` to all tests. Do not delete — history has value.

## Open Questions / Unknowns

6.1. [LOW] **ADR test location** — `tests/adr/` at repo root vs. alongside ADR file? Recommend repo root `P:/__csf/tests/adr/` since ADR tests are cross-cutting.

6.2. [LOW] **Fallback for unparseable ACs** — If `adr_to_tests` cannot parse an AC into a valid pytest name, emit skeleton with `@pytest.mark.skip("TODO: manual AC")` rather than failing.

6.3. [LOW] **Threshold for ADR test coverage** — What makes an ADR "significant enough" for test coverage? Recommend: only when ACs are objectively testable (not architectural rationale).
