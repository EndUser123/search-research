## Missed Blind Spots

1.1. **[HIGH recall failure] — Existing ADRs are prose, not parseable** — Neither specialist examined the existing ADRs at `P:/__csf/arch_decisions/`. The ADR for tree-sitter integration has acceptance criteria written as prose decisions (e.g., "Use `tree-sitter-language-pack` over `py-tree-sitter-languages`"). These are not `pytest`-compatible statements. The `adr_to_tests` script cannot generate meaningful failing tests from prose ACs — it would need to infer testable assertions from architectural rationale, not from structured ACs. **This is the core feasibility gap: the proposal assumes future ADRs will be written in parseable format, but existing ADRs are not and cannot be retroactively normalized.**

1.2. **[HIGH recall failure] — `/planning` integration trigger is unspecified** — The proposal says `/planning` should generate test stubs "at acceptance time" but doesn't specify what user action or status transition triggers this. Is it:
   - An explicit `/adr_to_tests 0001` command after ADR acceptance?
   - Automatic when ADR status changes to `Accepted`?
   - A step in the `/planning` workflow phase?
   Without this, the "at acceptance time" claim is hollow — nothing enforces it.

1.3. **[MEDIUM recall failure] — CI/execution frequency not defined** — The proposal mentions `/verify_all_adrs` as a "nightly cron" but doesn't address when ADR tests should fire during normal development. Should `PostToolUse_adr_deviation_check` run on every `git commit` touching ADR-governed files? On every `Bash` tool call that modifies a covered file? The hook design is mentioned but the trigger condition is unspecified.

1.4. **[MEDIUM recall failure] — ADR-to-code linking in commit messages is missing** — The proposal mentions commit-level hooks but doesn't specify the commit message format. Without ADR ID in the commit (e.g., `ADR-0001` in footer), there is no audit trail linking code changes to architectural decisions. This is the "implementation audit trail" the user wanted.
