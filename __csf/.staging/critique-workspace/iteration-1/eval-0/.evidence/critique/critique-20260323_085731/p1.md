## Brief Intent Summary

The /critique skill is a Three-Phase Adversarial Review workflow that orchestrates two parallel critique agents (Phase 1: initial expert review; Phase 2: meta-critique of Phase 1) followed by a synthesis phase (Phase 3). It is designed to critique any work product — plans, designs, documents, policies, prompts, or skills — using severity-tagged findings and a recommended next-steps schema. The skill also includes a Phase 7 execution protocol for auto-implementing fixes when the user responds with 0.

## Logical Gaps & Inconsistencies

1. The SKILL.md workflow references its own phase template paths using two different root paths: Step 3 launches agents that are told to read from 'P:/.claude/skills/critique/phases/' (the LIVE path), not the BASELINE path. This means the skill cannot critique itself using its own phase templates in an evaluation context — it always defers to the live version. (SKILL.md:79, 91 — inconsistency: Step 3 says 'Read P:/.claude/skills/critique/phases/' but the SKILL.md is itself the work being critiqued in an eval context)

2. The Phase 1 prompt template (p1_initial_review.md) requires the reviewer to 'establish a clear model of the target' but the workflow never specifies how the agent should resolve which version of the target to critique when the target name matches multiple locations (e.g., '/critique' skill exists in both .claude/skills/critique/ and __csf/.staging/.../baseline/). This creates an ambiguity in the evaluation workflow. (p1_initial_review.md:9 — 'Verify this understanding against the actual content before critiquing' but no path resolution mechanism exists)

3. Step 7 (Handling 0 — Do ALL) is labeled 'Step 7' in the SKILL.md output structure section and 'Step 7 Execution Protocol' in the body, but in the Phase 7 sub-section it is called 'Phase 7a/7b/7c' etc. Inconsistent numbering — the execution protocol uses 'Phase 7a/7b/7c' but the main workflow labels it as Step 7. This is self-referential confusion in a process document. (SKILL.md:174 vs SKILL.md:181)

4. The workflow in Step 3 says 'Spawn two background agents simultaneously' but provides inline bash commands for the agents to execute, not actual spawn mechanisms. The skill assumes an agent spawning capability that is not defined or verified in the skill itself. No subagent_type, prompt, or description parameters are specified for the Task tool. (SKILL.md:73 — 'Spawn two background agents' with no defined spawn mechanism)

5. The skill's Phase 3 output schema requires GTO v2 style RNS format (Recommended Next Steps with domain ordering), but the Phase 3 prompt (p3_synthesis.md) says to use the 'RNS (Results/Next Steps) format familiar from /gto' — however /gto's format is not referenced or linked. A reviewer cannot verify the expected format without external knowledge. (p3_synthesis.md:3)

## Hidden Assumptions & Fragile Dependencies

1. The skill assumes CritiqueSession.write_work() will always receive non-empty content, but Step 6's validation only runs AFTER the session is created and work is supposedly written. If sys.argv[1] is empty, write_work() silently writes an empty file and the validation in Step 6 could fire but the session already exists. (SKILL.md:56-68 — no early validation before session.setup())

2. The session cleanup path in Step 6 says sessions persist at 'P:/.claude/.evidence/critique/' but CritiqueSession defaults to STAGING_ROOT = Path(__file__).parent.parent.parent / '.evidence' / 'critique' which resolves to a path under the staging root, not the documented cleanup location. The actual session was created under the staging root, not P:/.claude/.evidence/critique/. This means the documented cleanup path and the actual path diverge. (critique_io.py:32 STAGING_ROOT vs SKILL.md:126)

3. The skill requires Python with the critique_io module in sys.path at 'P:/.claude/skills/critique/lib'. If this path doesn't exist or the module is not importable, the entire workflow fails silently or with an unhelpful error. No fallback or error handling is described. (SKILL.md:59-68 — single hardcoded path with no validation)

4. Phase 2 meta-critique is described as 'NOT the original work' (SKILL.md:95) but the Phase 2 template (p2_meta_critique.md:17) says to read the original work AND the Phase 1 critique. The Phase 2 template includes reading the original work, which the SKILL.md workflow step explicitly says NOT to do. Contradiction between SKILL.md workflow description and the actual Phase 2 template instructions. (p2_meta_critique.md:17 vs SKILL.md:95)

5. The 'Context-Aware Resolution' in Step 1 uses conversation context as a signal, but the skill has no access to conversation history — it can only work with args. This makes the second priority ('Recent session focus') effectively unimplementable without additional context-passing. (SKILL.md:41-47 — no mechanism for accessing session context)

## Missing Obvious Actions / Best Practices

1. No validation that the target work/product actually exists before launching phases. If the user types '/critique on /nonexistent', the workflow proceeds through all 3 phases before failing or producing meaningless output. (SKILL.md:39-52 — no existence check on resolved target)

2. No timeout or deadline for phase completion. Background agents could run indefinitely and the workflow would never proceed to Step 4. No mechanism described for detecting stalled or failed phases. (SKILL.md:73-102 — no timeout, no polling, no completion signal)

3. No output format validation between phases. Phase 1 could output anything and Phase 2 would attempt to critique it regardless. Phase 3 would then synthesize potentially malformed input. No schema enforcement. (SKILL.md:102-118 — no cross-phase validation)

4. The 'Cleanup' step (Step 6) is labeled Step 6 in the workflow but Step 7 in the output structure section. This numbering mismatch means the numbered steps are out of sync with the Output Structure section. (SKILL.md:124 vs SKILL.md:128-172)

5. No description of what happens if the user responds with something other than '0' to the final output. Does non-zero input acknowledge and dismiss? Does it re-trigger critique? The interface contract is incomplete. (SKILL.md:169 — only '0' is handled)

## Risks and Edge Cases

1. If two terminals run the same skill simultaneously, they both create sessions with different timestamps, but nothing prevents them from overwriting each other's work.md if using the same timestamp pattern. Critically, CritiqueSession does not use file locking for session creation. (critique_io.py:60 — session_dir.mkdir() without locking, concurrent execution risk)

2. The inline python -c commands for file writing (SKILL.md:65, 85, 98, 117) are fragile: if the critique content contains single quotes, the shell command breaks. The use of heredoc-style input redirection (< your_critique) also assumes bash availability, which may not be consistent across platforms. (SKILL.md:85 — python -c '...' < file pattern vulnerable to quoting issues)

3. Phase 1 and Phase 2 are launched 'in parallel' but the skill provides no mechanism for waiting for both to complete before proceeding to Phase 3. The workflow says 'Wait for both agents to complete' but there is no described synchronization primitive. (SKILL.md:102 — 'Wait for both agents to complete' with no wait mechanism)

4. If the Phase 3 synthesizer (Step 4) finds that p1.md or p2.md are empty or missing, the skill provides no error handling — it would produce an empty or broken p3.md. (SKILL.md:104-118 — no missing file guards)

5. The Phase 7 execution protocol says 'do not re-critique' and 'do not expand scope', but if a fix reveals new issues that are direct consequences of the original design, the constraint is unrealistic. Phase 7c says to mark DEFERRED but the original item was the scope — new issues from the fix are by definition outside the original scope. (SKILL.md:221-223)

## Concrete Recommendations

1. Replace hardcoded path 'P:/.claude/skills/critique/lib' in Step 2 with a variable derived from the SKILL.md's own location, so the skill is location-agnostic and can critique older versions of itself. (SKILL.md:60)

2. Add explicit subagent spawn commands using the Task tool with proper subagent_type='general-purpose', prompt='...', and description='...' parameters so the spawn mechanism is verifiable and not just described in prose. (SKILL.md:77-100)

3. Add a session_dir parameter to the workflow so evaluators can specify which session directory to use, enabling comparison between baseline and optimized versions. Currently the session dir is auto-generated and not passed between steps. (SKILL.md:56 — CritiqueSession() with no session_dir override)

4. Add a 'target_version' or 'target_path' parameter to differentiate between multiple versions of the same skill being evaluated, to prevent the path resolution ambiguity identified in Logical Gap #1. (SKILL.md:39-52 — context resolution has no version awareness)

5. Synchronize the step numbering between the Workflow section and the Output Structure section — remove the numbering from Output Structure or align it with the Workflow steps. (SKILL.md:124-172)

## Open Questions / Unknowns

1. What is the expected format of the Phase 3 RNS output if /gto is not available or has a different format than assumed? The skill references /gto format but doesn't define it. (p3_synthesis.md:3)

2. How does the skill handle it if the work being critiqued is the critique skill itself and the phase templates contain instructions that contradict the skill's own workflow description? (SKILL.md vs p2_meta_critique.md — the recursive self-reference is not handled)

3. What determines the 'Health Score' threshold values (80%/50%)? Are these empirically derived or arbitrary? The skill doesn't explain the basis for these specific cutoffs. (p3_synthesis.md:33 — 'Healthy >=80%, Warning 50-79%, Critical <50%' with no justification)

4. How should evaluators handle the case where Phase 1 and Phase 2 produce conflicting assessments of the same issue? Does Phase 3 arbitration have a defined method or is it ad hoc? (SKILL.md:104-118 — no conflict resolution mechanism described)

5. The skill is marked 'enforcement: advisory' (SKILL.md:11) but describes a fully blocking sequential workflow. Is the 'advisory' tag referring to the skill's role in the broader system, or the internal workflow? The distinction is unclear. (SKILL.md:11)
