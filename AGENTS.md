## Search Topology (read before any existence/absence claim)

`P:\` is a multi-root workspace. Code for one subsystem is split across these
roots - a search scoped to only one of them proves nothing:

| Root | What lives there |
|------|------------------|
| `P:\.claude\hooks\` | User-level hooks (dispatched from `~/.claude/settings.json`) |
| `P:\.claude\scripts\` | Maintenance/audit scripts (e.g. `hooks_audit.py`) |

| `~\.claude\plugins\cache\` | Version-keyed plugin CACHE - generated, never edit; may lag source |
| `P:\.claude\worktrees\`, `P:\worktrees\`, `P:	mp\` | Stale copies/experiments - exclude from truth claims |

**Absence rule:** never claim a file, hook, or module "does not exist" until you
have searched BOTH live roots. Canonical command:

```
rg --files -g "*<name>*" P:/.claude/hooks P:/.claude/scripts P:/packages/.claude-marketplace/plugins
```

(`rg` respects .gitignore, so node_modules/.venv noise is excluded automatically.)
For hook ground truth, prefer running the audit over searching by hand:
`python P:/.claude/scripts/hooks_audit.py --packages P:/packages/.claude-marketplace/plugins`

If a spec names a file you can't find in one root, check the other root before
concluding the spec is wrong.

This workspace runs on **Grok Build**. Many conventions here originated in
Claude Code (CLAUDE.md, `.claude/` directories, hook patterns), and the

Before assuming a Claude Code feature works identically here, verify against
`~/.grok/docs/user-guide/`. Known differences:

| Area | Claude Code | Grok Build |
|------|-------------|------------|
| Hook types | `command`, `prompt`, `agent` | `command`, `http` only |
| Hook discovery | `~/.claude/settings.json` + plugins | `~/.grok/hooks/*.json` + scans Claude/Cursor locations for compat |
| Slash commands | `.claude/commands/` | `.grok/commands/` (different resolution) |

| MCP dispatch | Native | Via `use_tool` / `server__tool` qualified names |
| Session ID env | `$CLAUDE_SESSION_ID` | `$GROK_SESSION_ID` (Claude alias still set) |

**Rule:** when proposing any hook, command, or skill mechanism, cite the
Grok Build doc that confirms it works here. If only Claude Code docs support
it, flag it as unverified and check `~/.grok/docs/user-guide/` first.

**Session start — read the active-surface snapshot:** before assuming any
documented enforcement is active, read `~/.grok/active-surface.last.md`.
The snapshot is generated by a Grok-native SessionStart hook and enumerates
what is *actually firing* in this runtime: compat flags, active plugins,
active hooks (filtered by `~/.grok/disabled-hooks`), permission deny rules,
user-disabled hooks, and dynamically enumerated Claude-side hook files that
are NOT firing. Trust the snapshot over documentation when they conflict.
Note: the snapshot cannot enumerate active MCP servers (the hook fires
before the system reminder exists) — for MCP, read the session's system
reminder. The snapshot reflects config state at SessionStart; if config
changes mid-session, re-run `python ~/.grok/hooks/scripts/active_surface_snapshot.py`.

## Delegation signal — prepare, don't implement

When the user's prompt connects a task to a **future or separate session**,
the default disposition is **prepare the task for delegation**, not implement
it. Implementing in the current session is the override, not the default.

**Trigger phrasings** (any one is sufficient):

- "X for a fresh cold start LLM"
- "X for next session"
- "X to be picked up cold"
- "X for a fresh agent / fresh session / cold start"
- A task description paired with "for <recipient> where recipient is not the current session"

**Default disposition when triggered:** produce a delegation packet —
objective, scope, acceptance criteria, relevant file paths, constraints,
and any open questions — written to a durable path the future session can
read. Do NOT start implementation. Do NOT modify production code.

**Override phrasings** (any one flips back to implement-now):

- "do this now"
- "implement here"
- "in this session"
- "ship it"
- "go ahead"

**Why this rule exists:** delegation prompts and implementation prompts look
similar from the model's side; the difference is whether the work belongs to
*this* session or a *different* one. When the model wrongly implements a
delegated task, the cost is wasted work plus the user having to undo it
(plus, if the implementation was destructive, potential state damage). When
the model wrongly prepares-for-delegation an implementation task, the cost
is one clarifying question. The asymmetry favors defaulting to delegation
when the signal is present.

**Applies across all entry points:** `/plan`, `/go`, plain prompts, plan mode.
The rule is about reading the user's intent correctly, not about which
command was invoked.

**Falsifier:** if the rule causes the model to ask "delegate or implement?"
on every implementation request, the trigger phrasings are too broad and
should be narrowed. If the rule fails to fire when the user says "for a
fresh cold start LLM," the trigger phrasings are too narrow and should be
expanded.

## Direct-answer default — answer the question, don't substitute process

When the user asks a question — whether about a fact, a state, a preference,
or a decision — answer it. **Action** (research, code, tool calls,
implementation) is justified only when the user explicitly asks for it or
the question is unanswerable from session context.

This rule mirrors `/tp`'s "evidence-first" rule (`C:\Users\brsth\.grok\skills\tp\SKILL.md`)
without requiring the user to invoke `/tp` explicitly. Its core: "Provide
useful provisional conclusions first; ask a blocking question only when
unresolved ambiguity would materially change the decision, exceed
authority, make action unsafe, or prevent any grounded analysis."

**What "answer the question" means:**
- A question is a request for information, not an invitation to perform.
- Read available context (files, conversation history, prior turns,
  AGENTS.md, prior-session notes) before forming the answer.
- If the answer is supportable from context, produce it. Cite the source.
- If context is partial, state what is supportable and label what is not
  (`[FACT]` / `[INFERENCE]` / `[UNKNOWN]`).
- Do not chain *investigation → options → meta-questions → implementation*
  before answering. That chain is the failure mode this rule exists to
  prevent.

**What this rule does NOT mean:**
- Refusing to act when the user explicitly asks for action. The
  "delegation signal — prepare, don't implement" rule above handles
  *implicit* delegation cues; this rule handles *implicit* action cues
  (questions that aren't actually questions).
- Suppressing `/tp`, `/red-team`, `/aar`, or any other skill when
  explicitly invoked. Skills are user-initiated; this rule only governs
  default behavior when no skill is invoked.
- Eliminating clarification entirely. If the question is genuinely
  unanswerable from context (missing information, blocked by authority,
  depends on inaccessible state), ask **one focused** clarifying question
  and stop. Do not chain multiple clarifications.

**Symptom this rule prevents — "meta-question-loop":**
1. User asks a question.
2. Model asks 2–3 meta-questions back ("which subset?", "what threshold?",
   "which approach do you prefer?").
3. User pushes back: "answer the question" / "stop asking" / "just tell me."
4. Model treats the push-back as authorization to act (implements, ships,
   edits files) when the user only wanted an answer.
5. User pushes back again: "I asked a question, I didn't tell you to do
   anything."
6. Model performs another round of meta-questions about what to do.

The fix: at step 2, recognize the meta-question pattern and answer with
what is supportable from context. Treat push-back at step 3 as
information about the user's preference for terseness, not as a green
light to act.

**Cross-reference:** `/tp`'s failure-mode 4 ("solution vending") and failure-mode
2 ("premature solutioning") name the same pattern with different vocabulary.
This workspace rule is the always-on version; `/tp` is the explicit
invocation path when the user wants the full critical-friend protocol.

## Proactive verification suggestions

When you complete or ship work that crosses a verification threshold,
**proactively tell the user** — do not wait for them to think of it. Surface
the suggestion as a short note at the end of your turn, with the specific
skill named. Do not auto-invoke the skill; recommend it.

**Suggest `/check` when:**
- Work touched ≥2 distinct concerns or files in different domains
- You made claims about runtime behavior (what's firing, what's installed,
  what's enabled) that you did not directly verify in this turn
- You are about to claim work is "done," "complete," "fixed," or "shipped"
- The work was delegated to you and you're handing back

**Suggest `/review` (or `/code-review` / `/user:code-review` — all aliases
for the same skill per the user-guide) when:**
- Work touched hooks, plugins, schemas, contracts, dispatch chains,
  settings.json, or other load-bearing infrastructure
- Work introduced new enforcement (a new hook, a new rule, a new gate,
  a new permission)
- Work modified shared infrastructure that other sessions or terminals
  depend on
- Work refactored code that has multiple consumers
- Work changed the runtime's active surface (enabled/disabled plugins,
  compat flags, hook wiring)

**Form factor:** one line at the end of the turn, e.g.:
> **Verification suggestion:** this work touched a Grok-native hook and
> AGENTS.md — recommend `/review` before relying on it.

**Do NOT suggest when:**
- The work is trivial (single-line typo, one doc edit, reversibility ≤1.25)
- You already ran the relevant verification skill in this turn
- The user explicitly said "quick" or "don't verify"

**Falsifier:** if the rule fires on every turn (noise), the triggers are too
broad — narrow to "load-bearing" or "multi-file." If the rule fails to fire
after a multi-file hook change, the triggers are too narrow.

- **Staleness rubric** (applied to wiki content before deciding to trust it):
  - Library/API/framework docs: fresh for 6-12 months
  - Tool comparisons: fresh for 6 months
  - Code examples: fresh until the underlying API changes
  - Best practices / patterns: fresh for 1-2 years
  - Architectural principles: fresh for 5+ years
  - Research papers: never stale (but check for retractions or newer work)
  - Vulnerability / security info: fresh for 3-6 months
- **Validation + disconfirmation framing:** run at least 2 searches — one
  for evidence supporting the emerging design, one for evidence against.
  Do not run only confirmation searches.

## Narrative-as-signal (anti-dismissal rule)

When you find yourself constructing a plausible narrative for why something
**can't be done, can't be found, or doesn't exist**, treat that narrative as
the **signal to read documentation** — not as the answer.

**Why this rule exists:** the model repeatedly dismisses correct findings
because it constructs a plausible story ("enumeration is structurally
impossible," "the hooks are wired so they must be firing," "this can't be
in static config"). The story feels sufficient, the model stops
investigating, and the story turns out to be wrong. Every instance traced
back to the same pattern: **plausible narrative substituted for
verification.**

**Worked example (2026-07-20 session):** another LLM reported that MCP
servers weren't being enumerated from `[mcp_servers]` in config.toml.
The model checked config.toml, found no `[mcp_servers]` section, and
concluded "the data doesn't exist in any static config." It then
constructed a narrative ("the hook fires before MCP servers connect, so
enumeration is structurally impossible"). Both were wrong: MCP config
IS in static files — `~/.claude.json` (3 servers) and `~/.claude/.mcp.json`
(1 server) — documented at `~/.grok/docs/user-guide/07-mcp-servers.md:200-213`.
The model didn't read the documentation until the user told it to.

**Rule:** the moment you think "this can't be done because X," check:
1. Have you read the documentation for the system in question?
2. Have you checked the obvious config locations the docs name?
3. Are you conflating the finding with the proposed fix? (A wrong fix
   does not invalidate a correct finding.)
4. Is your narrative grounded in observed evidence, or in inference?

If the answer to (1) or (2) is "no," read the docs first. The narrative
is the trigger to investigate, not the substitute for it.

**Separate findings from fixes.** When evaluating an external review or
critique, evaluate the finding and the proposed fix independently. A wrong
fix does not invalidate a correct finding. If the finding says "X is
broken" and the fix says "change Y," check whether X is actually broken
before checking whether Y is the right change. The MCP instance: the
finding (MCP not enumerated) was correct; the fix (read `[mcp_servers]`)
was wrong because that section doesn't exist. The model dismissed both.

## Observe-Before-Propose (anti-oscillation rule)

When proposing any structure — file layout, artifact lifecycle, format discipline,
naming scheme, storage location, or process design — you MUST first inspect the
user's existing patterns for that class of decision and cite what you found.

**Why this rule exists:** the model has a documented failure mode of inventing a
plausible-sounding structure, defending it with abstract reasoning, then collapsing
when the user pushes back. The user has a trust bias and may not catch the defense
in time. The structural fix is to make evidence-gathering physically precede
proposal, so the model cannot anchor on an uninformed first answer.

**Required sequence:**

1. **Observe** — grep/list/read the user's existing workspace for how they already
   solve this class of problem. For storage/location questions: check the wiki
   (`P:/.data/wiki/concepts/`), package `docs/`, and any prior decisions. For
   format/process questions: check existing skills and artifacts that do similar
   work. Name what you found, with paths.
2. **Reflect** — does the user's existing pattern already answer the question? If
   yes, propose formalizing that pattern, not inventing a new one.
3. **Propose** — only after observation and reflection, and only if the existing
   patterns are genuinely insufficient. Cite the observation that motivates the
   proposal.
4. **Falsifier** — name what would make the proposal wrong, including "the user's
   existing pattern actually handles this and I missed it."

**Forbidden:** proposing a structure in the same turn as the question is asked,
without any tool call to inspect existing patterns. If your first response to a
"where should X go?" or "how should X be structured?" question contains a proposal
but no `grep`/`list_dir`/`read_file` of the user's workspace, stop and do the
observation first.

**Applies to:** storage locations, artifact lifecycles, file layouts, naming
schemes, format disciplines, process steps, skill structure, agent selection
logic — any time you're proposing *how* something should be organized or
structured.

## Review Discipline

For non-trivial analysis, proposals, mechanism investigations, benchmark
interpretations, or decision packets, separate verified facts, measured metrics,
inferences, hypotheses, historical context, and unsupported claims.

Do not promote an inference or hypothesis into an implementation decision, live
run authorization, or `ready_for_parent_review` handoff. If a new explanation is
only inferred, the next allowed action is evidence gathering.
