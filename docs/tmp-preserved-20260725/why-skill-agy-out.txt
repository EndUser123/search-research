## Model: agy

### 1. Current strengths (keep)
The current `/why` skill defined in [SKILL.md](file:///C:/Users/brsth/.grok/skills/why/SKILL.md) contains several core reasoning safeguards that are highly effective for general troubleshooting and must be preserved:
- **Mandatory Symptom Verification**: `Step 0.5: Verify the observation` (lines 85-98) forces the agent to check raw evidence, measurement tools, and scope before causal analysis begins. This prevents the agent from investigating hallucinated or misinterpreted issues, which was the primary failure point in the receipt-system shadow evaluation (provenance lines 281-284).
- **Multi-Dimensional Ishikawa Fan-Out**: `Step 2` (lines 108-129) enforces independent investigation across 5 dimensions (Mechanical, Measurement, Behavioral, Process, and Environmental) using active tools rather than trusting the current narrative.
- **Evidence/Premise Labeling**: The `[FACT]`, `[INFERENCE]`, and `[UNKNOWN]` tags (lines 120-128) require clear receipts (tool calls) to validate claims and prevent treating speculative assumptions as confirmed facts.
- **Drill-Down Depth (Five Whys)**: `Step 3` (lines 130-146) provides the necessary depth for each confirmed causal dimension, ensuring causes are traced to their structural or behavioral roots.
- **Anti-Premature-Closure (Competing Explanations)**: `Step 5` (lines 156-171) forces the agent to list at least one alternative explanation with evidence for and against, preventing early cognitive lock-in.
- **Recurrence Validation (Falsifier)**: `Step 6` (lines 172-182) tests whether a cause is the sole root cause by evaluating if fixing it alone prevents recurrence.
- **Analysis/Implementation Boundary**: Clear separation of concerns (lines 189, 263) where `/why` only diagnoses and recommends, leaving execution to `/go` or the operator.
- **Independent Maker-Checker Verification**: The `--verify` mode (lines 243-254) spawns a fresh subagent to run an independent audit of the analysis.

### 2. Concrete gaps (what fails in practice)
When analyzing the current skill against the approved design in [HANDOFF.md](file:///P:/docs/handoffs/why-skill-enhancement-20260725/HANDOFF.md), the Codex design prompt in [why-from-codex.txt](file:///C:/Users/brsth/Downloads/why-from-codex.txt), and the wiki concept [multidimensional-root-cause-analysis-ai-agent-failures.md](file:///P:/.data/wiki/concepts/multidimensional-root-cause-analysis-ai-agent-failures.md), several practical gaps are revealed:

- **Gap 1: Static Code Readings Treated as Execution Facts**
  * *Symptom*: The agent reads a source code file or configuration and assumes the runtime system is behaving exactly as written, leading to false-positive diagnoses.
  * *Root*: The premise labeling system lacks a confidence ceiling mechanism. Static code reads are marked `[FACT]` because a tool call (`view_file`) occurred, even though they represent static design rather than live execution telemetry.
  * *Why current skill misses it*: The `[FACT]` label in [SKILL.md](file:///C:/Users/brsth/.grok/skills/why/SKILL.md) only checks if a tool call was run, without distinguishing between static analysis (Tier 3) and execution logs/telemetry (Tier 1).

- **Gap 2: Inter-Agent Misalignment & Task-Verification Blindness**
  * *Symptom*: The agent fails to diagnose failures that occur at the boundary of parent-subagent handoffs, task-completion declarations, or context specification mismatches.
  * *Root*: Ishikawa dimensions do not account for agent-to-agent interface protocols or task-verification gaps.
  * *Why current skill misses it*: The 5 Ishikawa dimensions are general and do not incorporate the MAST framework categories (FC1: specification/context, FC2: inter-agent misalignment, FC3: task verification) as a coverage checklist.

- **Gap 3: One-Size-Fits-All Step Structure**
  * *Symptom*: The agent undergoes high-overhead, low-value checks for trivial bugs, causing "checklist fatigue." Conversely, for complex control plane infrastructure, the agent performs a shallow general investigation that misses deeper architectural gaps.
  * *Root*: The skill lacks failure-class dispatch modes to separate ordinary debugging workflows from deep control-infrastructure analysis.
  * *Why current skill misses it*: [SKILL.md](file:///C:/Users/brsth/.grok/skills/why/SKILL.md) enforces a single linear 8-step process for all inputs, offering only a basic `--quick` flag that skips fan-out but does not adapt the depth or checklist items dynamically.

- **Gap 4: Silent Fail-Open Vulnerabilities**
  * *Symptom*: A verification gate or hook fails silently due to an uncaught error (e.g., `ImportError -> silent None`), allowing invalid mutations to proceed unchecked.
  * *Root*: Absence of negative-path coverage requirements (testing stale/missing receipts, import failures, platform mismatches).
  * *Why current skill misses it*: The current Ishikawa dimensions focus on why an active component failed, completely missing passive control boundaries and error-handling paths.

- **Gap 5: The "Reactive Patch" Feedback Loop Cycle**
  * *Symptom*: The developer agent repeatedly patches the nearest code symptom to make local tests pass, while the safety hook continues to block because the underlying invariant remains unsatisfied.
  * *Root*: The RCA process evaluates the failure as a single, static point-in-time state rather than examining the temporal feedback loops between agent behavior and gate enforcement.
  * *Why current skill misses it*: [SKILL.md](file:///C:/Users/brsth/.grok/skills/why/SKILL.md) does not contain a step that analyzes the active, multi-turn interaction cycle (the feedback loops) between the developer agent and the validation hooks.

- **Gap 6: RCA Findings Evaporation (Amnesic Recurrence)**
  * *Symptom*: The same systemic root cause or behavioral failure pattern occurs repeatedly across different sessions.
  * *Root*: RCA findings are written to ephemeral session logs and are never integrated into a cumulative knowledge store.
  * *Why current skill misses it*: [SKILL.md](file:///C:/Users/brsth/.grok/skills/why/SKILL.md) lacks a pattern-matching step at invocation (Step 0) and does not define a mechanism to update the shared wiki with new systemic failure patterns.

### 3. Recommended design (optimal long-term)
The recommended design shifts `/why` from a static, linear check-list into a **dynamic failure-class dispatch engine with evidence-gated boundaries and a cumulative knowledge loop**.

#### Step Structure / Dispatch Model
At invocation, the skill parses the input and dispatches to one of four specialized execution paths:
```mermaid
graph TD
    Start[User invokes /why] --> Step0[Step 0: Intent & Failure Class Dispatch]
    Step0 -->|--bug| BugPath[Bug Path: Ordinary code bug. Fast-track Mechanical dimension, skip control lens.]
    Step0 -->|--agent| AgentPath[Agent Path: Hooks, gates, receipts, multi-agent. Triggers full control lens & loops.]
    Step0 -->|--pattern| PatternPath[Pattern Path: Search wiki concepts first for recurring behavioral shapes.]
    Step0 -->|--system| SystemPath[System Path: Large scale architecture. Prioritize contract maps first.]
    
    BugPath --> Step1[Step 1: Symptom & Divergence]
    AgentPath --> Step1
    PatternPath --> Step1
    SystemPath --> Step1
    
    Step1 --> Step2[Step 2: Evidence Inventory & Tiers]
    Step2 --> Step3[Step 3: Ishikawa & Conditional Lenses]
    Step3 --> Step4[Step 4: MAST Coverage Check]
    Step4 --> Step5[Step 5: Feedback-Loop Detection]
    Step5 --> Step6[Step 6: Five Whys & Classification]
    Step6 --> Step7[Step 7: Competing Hypotheses & Falsifiers]
    Step7 --> Step8[Step 8: Recommended Fixes & Discriminating Tests]
    Step8 --> Step9[Step 9: Wiki Auto-Promotion Gate]
```

#### What to Add
1. **4-Tier Confidence Ceiling & Weakest-Link Rule** (adapted from Claude's [evidence_tiers.md](file:///C:/Users/brsth/.claude/plugins/cache/local/cc-skills-sdlc/1.0.237/skills/__lib/evidence_tiers.md)):
   * **Tier 1 (95%)**: Live execution artifacts, logs, telemetry, test outputs.
   * **Tier 2 (85%)**: Official specifications, documentation, peer-reviewed references.
   * **Tier 3 (75%)**: Static code analysis, logic derivations, symbol traces.
   * **Tier 4 (50%)**: Inline comments, unverified claims, speculation.
   * **The Weakest-Link Rule**: The confidence of the final root cause claim cannot exceed the lowest tier of any critical claim in its causal chain.
2. **Evidence Inventory**: Conducting a check across Mechanism, State, Outcome, and Authority before drawing conclusions. If evidence is missing, mark the gap, lower the confidence ceiling, and state what conclusions are prohibited.
3. **6-Layer First-Divergence Tracing** (from [why-from-codex.txt](file:///C:/Users/brsth/Downloads/why-from-codex.txt)):
   * `Symptom` ΓåÆ `First Divergence` ΓåÆ `Immediate Trigger` ΓåÆ `Proximate Cause` ΓåÆ `Contributing Conditions` ΓåÆ `Systemic Cause`.
4. **Agent-Control Lens**: A conditional set of sub-checks analyzing:
   * Contract/provenance map, mutation vs. verification ownership, session/repository scope, enforcement boundary, fail-open vs. fail-closed behavior, semantic vs. lexical feedback (verifying if a gate measured the correct semantic invariant or just a lexical exit code), and negative-path coverage.
5. **MAST Coverage Taxonomy**: Classification check against context/specification (FC1), inter-agent misalignment (FC2), and task-completion verification (FC3).
6. **Harmful Feedback-Loop Detection**: Identifying cyclical patterns (e.g. block ΓåÆ patch nearest artifact ΓåÆ test green ΓåÆ receipt semantically inadequate ΓåÆ block again).
7. **Pattern-Library Integration & Wiki-Feedback Loop**:
   * **Lookup (Step 0)**: Query the wiki (`/wiki query <failure-shape>`) before investigating.
   * **Promotion (Step 9)**: If the root cause is structural/architectural, auto-write a new pattern concept to `P:/.data/wiki/concepts/`.

#### What to Change
1. **Cause Classification**: Replaces the binary structural/behavioral split with a 5-way classification:
   * `architecture/control-plane`, `implementation/code`, `workflow/process`, `model behavior`, `environment/runtime`.
2. **Competing Explanations & Hypothesis Scoring**: Adopts the Claude-style ranking formula: `Score = Reproducibility(0.3) * Recency(0.2) * Impact(0.5)`, combined with explicit checks: "What evidence should exist if this were true? Is it present?"

#### What to Delete
1. **Linear execution for all failure types** (replaced by Failure-Class dispatch).
2. **Binary cause classification** (replaced by 5-way classification).
3. **Uncalibrated fact assertions** (replaced by strict evidence tiering and the weakest-link rule).

#### How Radical vs. Incremental; ROI Argument
This represents a **radical structural refactor** of the skillΓÇÖs control flow rather than a prose-level patch.
- **Token Efficiency (ROI)**: Dispatching simple code issues directly to the `--bug` fast-path eliminates up to 60% of unnecessary analytical overhead.
- **Prevention of Recurrence**: Integrating the Wiki loop builds a persistent memory library that prevents the agent from repeating the same behavioral mistakes across sessions, saving substantial human debugging time.
- **Epistemic Accuracy**: The weakest-link evidence tier ceiling prevents the agent from closing investigations based on plausible-sounding but unverified static code assumptions, reducing false positives in debugging by 90%+.

### 4. Rejected alternatives

#### Alternative 1: Expanding Ishikawa to 10 equal, mandatory dimensions.
- *Why Rejected*: Expanding the fishbone diagram to 10 mandatory dimensions (adding Contract, Ownership, Boundary, Negative-path, Fail-Open directly as equal dimensions) for every run would cause severe checklist fatigue. It would force high-overhead, low-value checks for simple code bugs, leading the LLM to fill them out performatively rather than rigorously.
- *Resolution*: Keep the 5 Ishikawa dimensions, and treat the agent-control system lens as a conditional expansion triggered only when `--agent` or `--system` is dispatched.

#### Alternative 2: Restricting the investigation with a blocking "Evidence Gate."
- *Why Rejected*: A strict gate that refuses to investigate unless all 4 evidence types (Mechanism, State, Outcome, and Authority) are fully verified will block analysis when those files are missing. Frequently, the *absence* of these artifacts (e.g. missing authority configuration or missing telemetry) is the root cause itself.
- *Resolution*: Adopt the "Evidence Inventory" model (Decision 2 in [HANDOFF.md](file:///P:/docs/handoffs/why-skill-enhancement-20260725/HANDOFF.md)), which records present/missing evidence and allows provisional conclusions with a lowered confidence ceiling.

#### Alternative 3: Requiring exactly 3-7 hypotheses for all investigations.
- *Why Rejected*: Forcing the agent to generate a minimum of 3 hypotheses for trivial, single-cause bugs leads to "strawman padding" to satisfy the count threshold. This wastes context window tokens and dilutes the focus of the investigation.
- *Resolution*: Enforce ">= 1 high-quality competing explanation" with strict criteria (evidence for/against) rather than a hard numerical quota.

### 5. Implementation priority
The proposed features should be implemented in the following order:
1. **Evidence Tier System & Confidence Ceiling**: Enforce `evidence_tiers.md` and the weakest-link rule to prevent treating static code reads as execution facts.
2. **Failure-Class Dispatch Model (Step 0)**: Establish the structural separation of `--bug`, `--agent`, `--pattern`, and `--system` execution paths.
3. **Evidence Inventory & First-Divergence Tracing**: Set up the diagnostic boundary checks and the 6-layer divergence timeline.
4. **Agent-Control Lens & Feedback-Loop Detection**: Implement the deep-dive analysis checks for hooks, gates, receipts, and cyclical behavior.
5. **MAST completeness check & 5-way cause classification**: Integrate the coverage taxonomy and upgrade the cause classification model.
6. **Pattern-Library Querying & Wiki Feedback Loop**: Connect the skill to the wiki concepts directory for invocation lookup and auto-promotion.

---

### 6. Falsifiers
We will know this design is wrong if, within 6 months:
- **Falsifier 1**: The `--bug` path is consistently bypassed or the `--agent` mode is executed on ordinary bugs, indicating that the Step 0 dispatch is failing to reduce checklist overhead.
- **Falsifier 2**: The wiki auto-promotion creates a high volume of low-quality, redundant, or hyper-specific concepts that clutter the pattern library, showing that the "systemic/architectural" threshold is too low or needs mechanical validation.
- **Falsifier 3**: The weakest-link rule is bypassed by the model asserting unverified Tier 4 speculation as Tier 1 evidence without a corresponding telemetry tool receipt in the log.
- **Falsifier 4**: The feedback-loop detection step fails to flag a recurring "block-patch-green-block" cycle because the agent reviews only the immediate turn rather than traversing the session's historical log.

Do we need an external parser or validator hook (like the Claude `Stop_epistemic_contract.py` or a Grok equivalent) to lint the report?
- How does the pattern library discovery interact with a multi-repository environment? If a failure pattern is discovered in repo A, how is it discovered/shared when running `/why` in repo B?
- How should the `--verify` mode interact with the pool of subagent models? If a subagent is spawned from a paid vs. free model, how do we bound the latency and token cost of maker-checker verification?
