# Handoff: Extend skill graph to track finding-routing coverage

## Problem

The skill graph (`P:/.data/wiki/concepts/skill-graph.md`, generated by `P:/.data/wiki/scripts/build_skill_graph.py`) tracks dependencies, providers, and capabilities — but does not track which skills produce findings and whether those findings get routed to `/handoff`. This gap meant `/dream` was missing handoff routing and nobody noticed until the operator caught it manually. A simple graph query ("which skills produce findings but don't route to /handoff?") would have surfaced it immediately.

## Current state

The skill graph extracts from SKILL.md frontmatter:
- `depends_on` — skill-to-skill dependencies
- `consumes` — MCP/CLI tool consumption
- `provides` — declared capabilities
- `domain` — lifecycle domain

Individual SKILL.md files already have the data needed — it's just not extracted into the graph:
- `remediation_mode: surface-only | auto-act` (in close-check's classification matrix, not standardized in frontmatter)
- Post-output routing sections (added to 9 skills this session: /tp, /aar, /friction, /capture, /why, /red-team, /model-web, /behave, /dream)
- `solves:` frontmatter field (partially present)

## Proposed changes

### 1. Standardize frontmatter fields

Add two fields to SKILL.md frontmatter for finding-producing skills:

```yaml
produces_findings: true      # this skill surfaces findings that need disposition
post_output_routing: handoff  # unresolved findings are routed to /handoff
```

Skills that don't produce findings omit these fields (default: false/none).

### 2. Extend build_skill_graph.py

Extract the two new fields and add a "Finding routing coverage" table to the graph output:

```markdown
## Finding routing coverage

Which skills produce findings and whether unresolved findings are routed:

| Skill | Produces findings? | Routes to /handoff? | Status |
|-------|-------------------|---------------------|--------|
| /tp | yes | yes | ✅ complete |
| /aar | yes | yes | ✅ complete |
| /friction | yes | yes | ✅ complete |
| /capture | yes | yes | ✅ complete |
| /why | yes | yes | ✅ complete |
| /red-team | yes | yes | ✅ complete |
| /model-web | yes | yes | ✅ complete |
| /behave | yes | yes | ✅ complete |
| /dream | yes | yes | ✅ complete |
| /harvest | yes | — (consumes findings, doesn't produce new ones) | N/A |
| /notice | yes (T11/T12) | routes to /slc | ✅ different route |
| /check | yes (verifier concerns) | no | ❌ gap |
```

This makes gaps visible at a glance. Any skill with `produces_findings: true` and no `post_output_routing` is a gap.

### 3. Validation gate

Add a check to `index_skills.py --audit` that flags skills with `produces_findings: true` but no `post_output_routing`. This catches the gap mechanically on every catalog refresh.
