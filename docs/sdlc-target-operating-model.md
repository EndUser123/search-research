## Part 0: Governing Invariants

### 0.1 Multi-terminal Isolation and Stale-Data Immunity

Every mutable `/go` artifact, discovery record, risk review, approval record, check result, handoff, candidate learning, pointer, gate input, and worktree MUST be isolated to the authoritative current session/run by default. Shared state requires a specific justified consumer and concurrency design.

**Identity model — three levels:**

| Identity | Purpose | Scope | Generated by | Authority |
|---|---|---|---|---|
| `session_id` | Authoritative current logical session identity | One Claude Code session | Hook payload (`session_id` field) | Verified invocation payload |
| `run_id` | One `/go` execution and its run-scoped artifacts | Single `/go` invocation | Generated fresh per `/go` start: `go-<session_id>-<timestamp>-<suffix>` | Created by current run |
| `workspace_id` / `worktree_id` | Longer-lived identity for a reusable isolated worktree belonging to one workstream | One workstream (may span multiple runs) | At worktree creation; derived from workstream intent, not from run_id | Persisted in ownership record |
| `lease_id` | Current exclusive write lease held by one active run | One active run | Generated per lease acquisition | Recorded in worktree ownership metadata |

**Rules:**

| Rule | Applies to | Behavior |
|---|---|---|
| Foreign run/session state fails silent | Artifacts keyed by session_id+run_id | Different session_id or run_id → IGNORE. No warning, no merge, no fallback. |
| Foreign state readable only when necessary | Discovery, risk import | If a current-run decision cannot be made without prior evidence, foreign state may be read with provenance noted. Explicit justification required. |
| Ambiguous state blocks | All identity lookups | If session_id, run_id, or workspace_id cannot be positively verified → BLOCK. Guessing prohibited. |
| "Newest artifact" / directory-wide fallback prohibited | All artifact lookups | Reader must use exact identity keys. Wildcard or mtime-based fallback not allowed. |
| Session-analysis skills never search parallel terminals | recap, rns, gto, why | Current logical session chain only. |
| Cross-run aggregation is deliberate reader operation | GTO, reporting | Aggregation is a READER operation, not shared mutable writer state. |
| Only one active run may hold the write lease for a worktree | Worktree access | Lease is checked before writes. |
| Sequential related runs may acquire the lease and reuse the same compatible worktree | Worktree creation | Earlier lease released → new run may acquire. |
| Concurrent or foreign runs may NOT write to a leased worktree | Worktree access | BLOCK if lease held by different active run. |
| Missing, foreign, stale, or ambiguous lease must NOT be guessed or overridden | Lease resolution | Present evidence; ask user. |
| Read-only explorers do NOT acquire a write lease | Exploration subagents | No lease check needed; no write capability. |

### 0.2 Worktree Lifecycle and Anti-Sprawl Policy

**Principles:**
- Redundant safety checks are encouraged.
- Redundant worktree creation is not.
- Reuse a compatible worktree already owned and leased by the current run's workspace.
- Never modify, clean, reset, merge, rebase, prune, or remove a foreign or ambiguously owned worktree.
- Never use age alone as authority to remove a worktree.

#### Worktree compatibility

A worktree is compatible with a new `/go` run when ALL of the following are true:

- Same repository (verified by `git rev-parse --show-toplevel`)
- Same intended branch or workstream lineage (the worktree branch is the same as or a descendant of the current run's intended branch)
- Compatible base ancestry (current run's base_revision is an ancestor of the worktree HEAD, or the worktree is clean and at the base revision)
- Current worktree state is understood (clean or dirty with known files)
- No foreign active write lease (no other active `/go` run holds the lease)
- No conflicting target or clean-baseline requirement (the worktree is not part of a run that required a clean baseline while this run tolerates dirty state, or vice versa)
- No evidence that reuse would mix unrelated work (the worktree branch does not contain commits unrelated to the current workstream)

The contract fingerprint is authoritative for the current run's scope, approval, and artifacts, but is only ONE input to worktree compatibility.

#### Inventory before creation

Record:
- parent repository path, branch, HEAD, dirty state
- `git worktree list --porcelain`
- Each candidate: path, branch, HEAD, clean/dirty, untracked files, workspace_id (if available), lease_id (if available), active/inactive status, merged/unmerged, pushed/unpushed

#### Creation decision

| Disposition | When | Next action |
|---|---|---|
| `USE_CURRENT_ISOLATED_WORKTREE` | Already in an owned worktree with valid lease | Proceed |
| `REUSE_OWNED_WORKTREE` | Compatible worktree exists, no foreign active lease | Acquire lease; bind |
| `CREATE_NEW_WORKTREE` | No compatible worktree, write isolation needed | Create + record workspace_id + lease |
| `READ_ONLY_NO_WORKTREE_NEEDED` | Read-only task | Proceed in-place; no lease |
| `BLOCKED_WORKTREE_OWNERSHIP_AMBIGUOUS` | Worktree exists but ownership unclear | Block; ask user |
| `BLOCKED_NO_SAFE_WORKTREE` | All candidates foreign or dirty | Block; present evidence |

A new worktree requires an ownership record containing:
- repository, worktree path, branch, base revision
- **workspace_id** (stable workstream identity, NOT the run_id)
- **lease_id** (current exclusive write lease)
- session_id (creating session), run_id (creating run)
- contract fingerprint (creating contract)
- created time, lifecycle status

Use `P:\.worktrees` root unless live discovery proves a newer canonical location.

#### Worktree lease lifecycle (ordered)

```
created
→ leased_active            [write lease acquired by one run]
→ implementation_complete
→ check_complete
→ artifacts_finalized
→ lease_released            [run releases write lease]
→ cleanup_eligible           [no other live lease verified]
→ removed | preserved | reclaim_candidate
```

**Required ordering:**
1. Finish implementation and `/check`.
2. Persist final evidence and handoff/completion state.
3. Classify branch, commit, push, merge, dirty, untracked, and ignored state.
4. Release the current run's write lease.
5. Revalidate that no other live lease exists (no active run holds lease_id).
6. Only then classify as cleanup-eligible.
7. Remove only after all removal proofs pass.

An interrupted run retains lease metadata with lifecycle_status=`active`. A later operation may classify it as abandoned or reclaimable ONLY through a separate bounded recovery process. Never silently steal an active lease.

#### Terminal classification

At every complete, blocked, failed, or interrupted end state:

| Classification | Meaning |
|---|---|
| `KEEP_ACTIVE` | Work in progress; preserve |
| `READY_TO_MERGE` | Completed, clean, user may merge |
| `PRESERVE_FOR_REVIEW` | Completed but needs review |
| `SAFE_TO_REMOVE` | Clean, merged, no untracked/ignored content |
| `BLOCKED_DIRTY` | Uncommitted changes |
| `BLOCKED_UNTRACKED_CONTENT` | Untracked files present |
| `BLOCKED_UNMERGED` | Unmerged branches |
| `BLOCKED_UNPUSHED` | Unpushed commits |
| `FOREIGN_OWNER_IGNORE` | Not owned by this session/run; do not touch |
| `STALE_RECLAIM_CANDIDATE` | Old worktree, no live lease, clean; eligible for explicit reclamation |

#### Ignored and generated-file safety (required before removal)

Before any worktree removal, inventory:
```powershell
git status --short --untracked-files=all
git ls-files --others --ignored --exclude-standard
```

Classify ignored content:
- **Proven generated and safely reproducible** — may be removed
- **Known runtime state** — may be removed if acceptable
- **Preserved evidence or recovery material** — preserve
- **Unknown** — BLOCKS removal

Unknown ignored content blocks removal. Do not use broad `git clean`, filesystem deletion, or `--force` removal to bypass unknown ignored content.

#### Removal and reclamation

Removal requires proof of ALL:
1. Authoritative ownership OR explicit user approval
2. No live owning run (lease released or abandoned)
3. Clean status
4. All untracked and ignored content classified (no unknowns)
5. Branch and commit state understood
6. Intended changes merged, committed/preserved, or explicitly abandoned
7. Rollback or recovery path documented
8. Exact target path known

Use normal Git worktree removal. Verify result. Prune only verified stale metadata. Never run broad filesystem deletion.

Reclamation of old worktrees is a SEPARATE BOUNDED OPERATION. Surface candidates, evidence, and disposition. Do NOT remove ambiguous candidates automatically.

#### Enforcement checkpoints

1. `/go` preflight (Step 1 — worktree compatibility)
2. Before first write (Step 5 pre-write — lease still valid?)
3. When scope or repository changes
4. Before `/check` (Step 6 — worktree still owned?)
5. At Stop/completion (classify, order lease release)
6. At session startup when reclaimable candidates exist

These checks should share one canonical mechanism. Extend existing `/go` worktree-safety and Stop-gate mechanisms rather than creating new hooks.

## Part II: `/go` Lifecycle

### Mandatory Sequence

```
STEP 1: ESTABLISH CONTRACT
  - State goal, authorization source, contract boundary
  - Record session_id (from hook payload), run_id (generated fresh)
  - Record repository, base_revision, worktree_path
  - Record or establish workspace_id (reuse existing or create new)
  - Compute contract_fingerprint (see Part IIa)
  - Preflight: worktree compatibility check (Part 0.2)

STEP 2: DISCOVERY
  - Proportionate mandatory discovery (see Part III)
  - All evidence scoped to session_id + run_id
  - Foreign state IGNORED unless explicit justification
  - Disposition vocabulary. New mechanism requires proof that existing
    mechanisms cannot satisfy the goal.
  - Record: consumed paths, dispositions, evidence citations,
    affected_surfaces_fingerprint (SHA256 of discovered surfaces)

STEP 3: PRODUCE OR VALIDATE IMPLEMENTATION PLAN
  - Plan references discovery evidence
  - ALREADY_EXISTS / NO_CHANGE → document and stop

STEP 4: PROSPECTIVE RISK REVIEW
  - Run or import prior risk reviews (see Part V — incremental flow)
  - Bound to run_id + contract_fingerprint + affected_surfaces_fingerprint
  - Present risks, mitigations, adopted/deferred, residual risk
  - Automatic proceed only when: already authorized, preserves contract,
    no new behavior/functionality/architecture/authority/
    persistence/routing/scope requires approval

STEP 5: IMPLEMENT
  - Execute approved plan in selected worktree
  - Pre-write: revalidate worktree path, branch, HEAD, lease, contract
  - No externally observable changes without approval
  - NO_CHANGE / ALREADY_EXISTS / reuse / repair / simplification /
    removal of proven duplicate are valid outcomes

STEP 6: VERIFY — invoke canonical /check
  - Automatic; must not be skipped
  - Pre-check: revalidate worktree lease and contract
  - Must include: verification, review, falsification of completion,
    goal matching, residual gaps
  - Strong single-agent preference; escalate only for security,
    large/cross-cutting changes, conflicting evidence, high blast
    radius, or explicit user request

STEP 7: REPORT
  - Completion evidence, residual uncertainty, rollback information
  - Record [GTO_CANDIDATE] observations (see Part VIII)
  - Artifacts scoped to session_id + run_id
  - Classify worktree, order lease release (see Part 0.2)

STEP 8: EMIT HANDOFF OR COMPLETION SIGNAL
  - Handoff: structured with session_id, run_id, workspace_id, contract
  - Complete: completion signal with evidence summary
```

### Exemptions
- **Emergency revert** — may skip Steps 2-4; must run Steps 6-7.
- **User explicitly confirms** bounded fix without full discovery — record skipped step.

### Failure Behavior

| Condition | Behavior |
|---|---|
| Step 1 contract unclear | BLOCKED — clarify with user |
| Step 2 BLOCKED_DISCOVERY_INCOMPLETE | BLOCKED — expand discovery |
| Step 4 risk review missing/stale/identity-mismatch | BLOCKED — run or refresh |
| Step 4 affected_surfaces_fingerprint changed from discovery | BLOCKED — re-discover |
| Step 5 pre-write worktree/lease revalidation fails | BLOCKED — worktree no longer valid |
| Step 6 verification fails | FAIL — present evidence |
| Step 6 required phase cannot run | Report missing phase; no full completion |
| Step 3 plan contradicts Step 2 discovery | BLOCKED — return to Step 2 |
| Worktree lease held by another active run | BLOCKED — cannot acquire lease |
| Ignored content unknown before removal | BLOCKED — classify first |

## Part IIa: Canonical Contract Fingerprint

### Definition

One stable canonical representation used everywhere contract identity is required.

```
contract_fingerprint = SHA256(
  canonical(goal) +
  canonical(authorization) +
  canonical(in_scope) +
  canonical(out_of_scope) +
  canonical(must_not_change) +
  canonical(target_repository) +
  canonical(target_workstream)
)
```

Where `canonical()` means:
- **goal** and **authorization**: whitespace-normalized string (trimmed, single spaces)
- **in_scope**, **out_of_scope**, **must_not_change**: deterministically sorted list, each item whitespace-normalized, joined by `\n`
- **target_repository**: `git rev-parse --show-toplevel` output
- **target_workstream**: empty string if none

### Separate affected-surfaces fingerprint

Discovery produces an `affected_surfaces_fingerprint` derived from the consumed paths, registrations, and entry points found in Step 2.

```
affected_surfaces_fingerprint = SHA256(
  canonical(sorted_discovered_paths) +
  canonical(sorted_discovered_entry_points) +
  canonical(sorted_registrations)
)
```

Changing discovered surfaces invalidates affected discovery and risk evidence WITHOUT pretending the original authorization changed.

## Part III: Discovery Contract

### Purpose

Incomplete system understanding is a proven source of destructive LLM changes. All discovery evidence is scoped to `session_id` + `run_id`. Foreign or ambiguous state does not satisfy discovery requirements.

### Mandatory Scope

| Question | Evidence required |
|---|---|
| What capability already exists? | File paths, entry points, SKILL.md names, triggers |
| Does it exist under another name or mechanism? | Alias search, NLP trigger search, router inspection |
| Complete/partial/dormant/duplicated? | Status docs, git history, cache comparison, registration |
| Exact consumed source and runtime path? | SHA256 cache-vs-source, settings.json, hooks.json, router |
| Entry points and registrations? | SKILL.md frontmatter, settings.json, hooks.json, router.py |
| Inbound consumers? | Grep imports, trigger refs, SKILL.md name |
| Outbound dependencies? | Imports, subprocess, SKILL.md suggests/blocks |
| State/artifacts? | File writes, env vars, artifact dirs |
| Tests? | test_*.py, __lib/*test* |
| Configuration? | settings.json, plugin.json, env vars |
| Documentation/prompts? | SKILL.md, references/, CLAUDE.md |
| Compatibility surfaces? | Public contracts, output formats, hook protocols |
| Provenance of removal target? | Git log, author, purpose |
| Runtime/live evidence needed? | Hook registration, dynamic imports, env-conditional code |
| Current repo/worktree state? | HEAD, branch, dirty files, cache version, cache-vs-source |
| session_id, run_id, workspace_id? | From Step 1 contract |
| Material unknowns? | Explicit list with suggested investigation |

### Path Tracing

`user intent → public entry point → registration/router → implementation → storage/state → reader/consumer → authority → freshness → failure behavior`

Each link verified by direct inspection. Identity recorded at each hop.

### Refresh Conditions

Discovery stale and must be refreshed when:
- New subsystems or file families enter scope
- The target contract changes (contract_fingerprint changes)
- New public behavior is proposed
- New registration or persistence surface touched
- The implementation plan materially changes
- The worktree or repository revision changes
- Affected surfaces expand from initial discovery (affected_surfaces_fingerprint changes)

After implementation, repeat relevant checks for: stale refs, duplicate paths, obsolete registrations, compatibility gaps, unreachable replacements, cache/source divergence.

### Prohibitions

- Absence of runtime observation NEVER proves dead code.
- New mechanism NOT justified until discovery shows why existing mechanisms cannot satisfy the goal.
- Discovery by naming convention alone is insufficient.
- Foreign session/run state does not satisfy discovery.
- "Newest artifact" / directory-wide fallback prohibited for identity.

### Dispositions

ALREADY_EXISTS, NO_CHANGE, CLARIFY_EXISTING, REUSE_EXISTING, EXTEND_EXISTING, REPAIR_EXISTING, SIMPLIFY_EXISTING, REMOVE_DUPLICATE, DEPRECATE_FIRST, NEW_MECHANISM_JUSTIFIED, BLOCKED_DISCOVERY_INCOMPLETE.

## Part V: Risk-Review Contract

### Incremental flow (not binary reuse/refresh)

1. **Locate** prior reviews relevant to the same proposal, solution family, or affected surfaces.
2. **Import** them as provenance-bound evidence (retain original session_id, run_id, contract_fingerprint, affected_surfaces_fingerprint, revision).
3. **Compare** assumptions, implementation approach, affected surfaces, revision, and unresolved findings.
4. **Reuse** findings whose basis remains valid.
5. **Refresh** findings whose basis changed or is uncertain.
6. **Produce** a new current-run risk result bound to the current `run_id`, contract_fingerprint, affected_surfaces_fingerprint, revision, and worktree.

Foreign or old reviews inform the new review but NEVER substitute for current-run validation.

### Report structure

- Findings reused unchanged (with provenance)
- Findings refreshed (with before/after comparison)
- New findings (not present in any prior review)
- Invalidated findings (with reason)
- Residual risk

### Presentation requirements

Material risks, mitigations, adopted recommendations, deferred recommendations (with reason), residual risk.

### Automatic proceed conditions

ALL must be true:
- Implementation already authorized
- Mitigations preserve the approved contract
- No new behavior, functionality, architecture, authority, persistence, routing, or scope requires approval

### Blocked conditions

If not yet authorized, or risk review surfaces a change requiring new approval → BLOCK.

## Part VIII: Self-Learning and `/gto`

### Posture

Advisory and human-governed. Never automatically changes prompts, skills, hooks, policies, routing, or stable-core behavior.

### Candidate marker

During `/go`, the system may emit:

```
[GTO_CANDIDATE]
  observation: ...
  evidence: ...
  scope: ...
  confidence: HIGH | MEDIUM | LOW
  suggested_review: ...
```

### Candidate accumulation (run-scoped)

**Storage path:** `~/.claude/.artifacts/go-runs/<session_id>/<run_id>/gto-candidates.jsonl`

**Format:** JSONL, append-only within run file. Each entry carries session_id, run_id, timestamp.

**Foreign-state behavior:** A non-`/gto` reader encountering a different session_id or run_id MUST NOT read it. `/gto` is the only deliberate cross-run aggregator.

### `/gto` aggregator contract

`/gto` may deliberately read candidate files across completed sessions and runs. Cross-session aggregation is allowed ONLY as an explicit reader operation with:

- Preserved `session_id`, `run_id`, repository, revision, contract, and evidence provenance for every candidate
- No mutation of source candidate files
- No automatic authority over the current `/go` run
- No foreign candidate silently entering current implementation scope
- User-visible inclusion and exclusion rules

**Inclusion:** `/gto` does NOT exclude a candidate merely because it originated in another session. `/gto` does NOT require the candidate's contract fingerprint to match the current invocation. Systemic lessons often arise across different contracts.

**Exclusion rules apply only when:**
- Candidate has no provenance metadata (ambiguous origin)
- Candidate is from an incomplete run (no Step 6/7 completion signal)
- Candidate is a duplicate (same observation hash, same session+run)
- Candidate claims current-state authority but the source revision is too old for that claim type (see claim-aware freshness, Part VIIIa)

### Promotion path

```
/go observation → [GTO_CANDIDATE] → run-scoped JSONL → /gto aggregates across eligible completed runs
→ human review → separate authorized /go change
```

Current `/go` runs do NOT inherit scope or authority from imported GTO candidates. A candidate must go through human review and a separate `/go` change to become actionable.

### Prohibitions

Candidate learnings must NOT automatically change prompts, skills, hooks, policies, routing, or stable-core behavior.

## Part VIIIa: Claim-Aware Freshness (replaces revision-age rejection)

Do not discard a candidate solely because its base revision is old. Classify each candidate claim:

| Claim class | Meaning | Freshness behavior |
|---|---|---|
| `HISTORICAL_OBSERVATION` | Evidence that an event or failure occurred; remains historically valid regardless of revision | Retained permanently with original revision and timestamp |
| `CURRENT_STATE_CLAIM` | Must be re-verified against current source/runtime state | Flagged stale when revision diverges. Must be re-verified before use as evidence. |
| `SYSTEMIC_HYPOTHESIS` | Pattern hypothesis retained for comparison with later evidence | Retained. May gain or lose confidence as more evidence accumulates. |
| `RESOLVED_CANDIDATE` | Preserved with resolution evidence; not promoted again unless recurrence occurs | Preserved permanently. Suppressed from promotion unless new contradictory evidence emerges. |
| `SUPERSEDED_OR_CONTRADICTED` | Preserved with the newer evidence that displaced it | Preserved permanently with superseding evidence citation. Not promoted. |

Old evidence loses authority over current state but does NOT lose historical or systemic value. `/gto` reports classification counts alongside aggregated candidates.

## Part IX: Scope Pattern

### Default evidence horizon

Session-analysis skills (`/recap`, `/rns`, `/gto`, `/why`): entire current logical session chain from its first linked turn through now.

**`/gto` also reads candidate files across sessions.** This is the ONLY exemption to the foreign-session prohibition, and it is a deliberate reader operation with provenance preservation (see Part VIII). The normal transcript evidence horizon remains the current session chain. Candidate-ledger aggregation is a separate capability.

### Prohibitions

- Never inspect foreign terminal sessions
- Never guess other session IDs
- Never merge parallel terminal transcripts unless user explicitly supplies them
- Never use "newest artifact" or directory-wide fallback for identity

### Full-session context guard

Full-session context must not silently broaden authorized implementation, review target, or risk target.

## Part XIII: Independently Implementable Workstreams

### Workstream A-p: Prompt-level discovery contract

Prompt-contract change to `/go` SKILL.md Step 2. Adds mandatory discovery instructions, path-tracing, dispositions, refresh conditions. LLM-enforced. No deterministic guarantee.

### Workstream B0: Minimal identity and worktree-disposition foundation

**What:** Establish minimal identity infrastructure WITHOUT automatic worktree creation or removal:
- Acquire verified `session_id` from hook payload
- Generate `run_id` per invocation
- Identify repository and current worktree
- Inventory all worktrees (`git worktree list --porcelain`)
- Establish or read `workspace_id`
- Determine lease status (active/released/absent)
- Return a worktree disposition from Part 0.2's creation decision
- Do NOT automatically create, remove, clean, reset, merge, rebase, or prune worktrees

**Extends existing mechanisms:**
- `/go` already has `go_delegation_enforce_PreToolUse.py` — worktree/run-context checks could be added here
- `classify_complexity.py` already produces a model-selection JSON — analogous identity envelope

## Part XIV: First Implementation Recommendation

### Three candidates compared

| Dimension | A-p: Prompt discovery | B0: Identity+worktree foundation | A-p + B0: Combined |
|---|---|---|---|
| **Prevents destructive duplicate implementation?** | Yes — LLM sees existing mechanism before creating new one | Indirect — identity alone doesn't prevent duplicates | Yes — discovery + identity |
| **Multi-terminal isolation?** | No — prompt-only, no identity mechanism | Yes — session_id + run_id + workspace_id + lease | Yes |
| **Stale-data immunity?** | No — no fingerprint to check | Yes — contract_fingerprint + affected_surfaces_fingerprint | Yes |
| **Worktree-sprawl prevention?** | No — no worktree inventory | Yes — inventory + lease + compatibility | Yes |
| **Extends existing /go mechanisms?** | Yes — SKILL.md workflow_steps | Yes — PreToolUse, classify_complexity patterns | Yes — both |
| **Implementation complexity** | Low — SKILL.md prose | Medium — identity envelope + inventory patterns | Medium — both, but natural sequence |
| **Risk if done alone** | Discovery depends on LLM compliance; no identity safeguards | Identity exists but nothing enforces its use in discovery | Neither gap remains |
| **Live-testable?** | LLM compliance hard to measure | trivially — run_id uniqueness, worktree inventory | Both |
| **Rollback** | Revert SKILL.md | Revert identity instructions | Revert all |

### Recommendation

**Candidate A-p + B0 combined as the first workstream.**

Rationale:
1. A-p alone would introduce prompt-level discovery instructions but produce artifacts with ambiguous identity — violating the governing invariant that all solutions are multi-terminal isolated and stale-data-safe by default.
2. B0 alone would establish identity infrastructure but nothing would use it for discovery.
3. Combined, they form a coherent minimal foundation: the LLM knows what to discover AND every artifact carries verifiable session/run identity. Neither gap compromises the other.
4. The combined workstream extends existing `/go` mechanisms (workflow_steps for discovery, PreToolUse/delegation patterns for identity) rather than creating parallel mechanisms.
5. The combined workstream does NOT introduce new state that depends on ambiguous workspace identity — identity is derived from the verified hook payload and git state.
6. No automatic worktree creation or removal is included in this combined workstream — those are deferred to later workstreams (B0 explicitly excludes auto-creation/removal).

### What would falsify this recommendation

- Evidence that the `/go` SKILL.md discovery instructions are LLM-ignored at high rates AND concurrent-run corruption is also frequent → Implement a deterministic enforcement hook.
- Evidence that the user's primary frustration is worktree proliferation, not discovery failures → Prioritize worktree lifecycle enforcement (Workstream G) before discovery contract.
- Evidence that existing `/go` worktree-safety and run-context mechanisms already provide sufficient identity isolation → B0 may be partially covered already; audit those mechanisms first.

### Explicit exclusions from first implementation

- No automatic worktree creation or removal
- No deterministic enforcement hooks
- No new schemas beyond the identity envelope
- No discovery tool installation
- No changes to skills other than `/go` (A-p) and identity patterns (B0)

## Part XV: Live Acceptance Scenarios

**Scenario 1 — Two terminals, distinct run IDs**
Two terminals run `/go` concurrently. Each generates a different `run_id`. Each writes under `go-runs/<own_session_id>/<own_run_id>/`. **Expected:** Distinct run IDs, no collision.

**Scenario 2 — Two concurrent write-capable runs cannot lease the same worktree**
Terminal A acquires lease on worktree W with lease_id=la1. Terminal B cannot acquire lease on W while A holds it. **Expected:** BLOCKED_WORKTREE_LEASE_HELD.

**Scenario 3 — Later related run reuses compatible workspace after lease released**
Run 1 releases lease on workspace W. Run 2 (same repository, compatible branch, compatible ancestry, no foreign lease) acquires lease and reuses W. **Expected:** REUSE_OWNED_WORKTREE.

**Scenario 4 — Unrelated run does not reuse that workspace**
Run 2 (different repository, incompatible branch, or unrelated workstream) cannot REUSE_OWNED_WORKTREE. Must CREATE_NEW_WORKTREE or BLOCK. **Expected:** Not reused.

**Scenario 5 — Ten sequential related runs reuse one worktree**
Ten runs in the same workspace sequentially acquire, use, and release the lease on one worktree. **Expected:** Exactly 1 worktree after 10 runs. No unbounded growth.

**Scenario 6 — Stale lease from interrupted run surfaced, not stolen**
Run 1 crashes mid-implementation. Lease remains active. Run 2 starts. Worktree inventory shows active lease. Run 2 cannot acquire lease. Surfaces: "Worktree W has active lease from interrupted run 1. Abandon? Release?" **Expected:** Not silently stolen.

**Scenario 7 — Foreign newer artifact ignored**
Terminal B's artifacts (different session_id) have newer mtime than Terminal A's. Terminal A's discovery does not read them. **Expected:** Foreign state fails silent.

**Scenario 8 — Same-session artifact with wrong identity rejected**
Artifact exists with same session_id but different run_id, different contract_fingerprint, different base_revision, or different affected_surfaces_fingerprint. Current discovery does not treat it as current evidence. **Expected:** Rejected by identity mismatch.

**Scenario 9 — Prior risk findings selectively reused and selectively refreshed**
Prior risk review R1 (from earlier run) exists. Current run locates R1, imports with provenance. Finding "auth token exposure" has same basis → reused. Finding "cache drift" has different affected surfaces → refreshed. New finding "lease collision" → new. **Expected:** Report shows reused, refreshed, and new findings.

**Scenario 10 — `/gto` aggregates candidates across completed sessions with provenance**
Session A, run a1 produces candidate C1. Session B, run b1 produces candidate C2. `/gto` aggregates both. Each candidate displayed with its session_id, run_id, revision, contract_fingerprint. **Expected:** Cross-session aggregation with provenance. No candidates excluded solely for foreign session.

**Scenario 11 — Old historical candidate visible, current-state claim re-verified**
Candidate from 3 weeks ago: "Auth token rotation pattern fails for short-lived tokens" (HISTORICAL_OBSERVATION). Retained. Same candidate's CURRENT_STATE_CLAIM "this is still broken" flagged as stale — must be re-verified. **Expected:** Historical observation retained; current claim flagged for re-verification.

**Scenario 12 — Current `/go` run does not inherit scope or authority from GTO candidates**
`/gto` aggregates candidate "refactor the auth module." Current `/go` run's contract is "fix the login button." **Expected:** No scope creep. Candidate requires separate `/go` authorization.

**Scenario 13 — Worktree cleanup only after lease release and evidence persistence**
`/go` completes implementation and `/check`. Before lease release: worktree NOT cleanup-eligible. After lease release: eligible. After removal proofs: removed. **Expected:** Ordered lifecycle enforced.

**Scenario 14 — Unknown ignored worktree contents block removal**
Worktree has `.direnv/` directory not in `.gitignore`. `git ls-files --others --ignored --exclude-standard` shows it as ignored but classification is "unknown." **Expected:** BLOCKED_IGNORED_UNKNOWN.

**Scenario 15 — Clean generated contents removable only when proven reproducible**
Worktree has `node_modules/` (proven generated — `npm install` reproduces it). Removable. Worktree has `.artifacts/report.pdf` (generated but not proven reproducible in this environment) → not removable. **Expected:** Classification-dependent removal.

**Scenario 16 — Reclamation remains separate bounded operation**
Fifteen stale worktrees exist. Reclamation is invoked as separate command. It inventories, classifies, and presents candidates. Does NOT remove automatically. **Expected:** Separate bounded operation; no automatic removal.

**Scenario 17 — Selected first implementation extends existing mechanisms rather than creating parallel ones**
A-p extends `/go` SKILL.md workflow_steps. B0 extends identity patterns available in existing PreToolUse delegation gates and classify_complexity.py. No new hooks created. **Expected:** No parallel mechanisms.
