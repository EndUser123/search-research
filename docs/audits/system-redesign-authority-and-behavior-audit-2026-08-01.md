| Tool | Count (50 sessions) | Per-session average |
|---|---|---|
| read_file | 796 | 15.9 |
| grep | 277 | 5.5 |
| web_search | 6 | 0.12 |
| spawn_subagent | (not counted in first scan) | — |
| **Total** | **1,993** | **39.9** |

### Read-to-grep ratio

**read_file:grep = 2.9:1** — agents read full files approximately 3× as often as they use targeted grep.

**Assessment:** This ratio is higher than optimal if the goal is targeted retrieval. However, it does not prove waste — many `read_file` calls read specific sections (using offset/limit parameters), not entire files. The audit cannot distinguish bounded reads from full-file reads without parsing the `offset`/`limit` parameters in each tool call, which the scanner did not extract.

### Web search usage

Only 6 web_search calls across 50 sessions (0.12 per session). This is consistent with the workspace's web-search tool-selection policy (DDG → firecrawl → mmx → web_search as last resort) and the fact that most questions are answerable from local repository evidence.

### Retrieval correctness vs. efficiency

The audit **cannot** fully evaluate retrieval correctness from aggregate counts alone. Evidence adequacy (whether the retrieved evidence supported the final claim) requires per-episode semantic analysis that was not performed at scale. However, the low web_search count and high grep:read ratio suggest agents primarily rely on local evidence, which is the correct behavior per the evidence hierarchy.

### Key finding

**Retrieval behavior is not a confirmed problem.** Agents use a mix of grep and full-file reads, with very low web search usage. Whether the read_file:grep ratio of 2.9:1 represents waste depends on whether those reads are bounded (offset/limit) or wholesale — this audit could not distinguish them. No evidence of "agents rereading complete repositories" was observed in the aggregate data.

## 7. Minimum justified next step

### Recommendation: EXTEND_EXISTING — add persistence to /why output

**Confirmed user problem:** /why produces comprehensive investigation output (12 of 14 proposed fields) but the output is ephemeral — it lives only in the conversation transcript and is lost at compaction or session end. The /why Step 15 wiki-promotion gate is intentionally strict (only architecture/control-plane or recurring model-behavior causes pass), so most investigations are NOT promoted to wiki. Step 14 handoff routing fires only for unresolved findings. This means completed-but-unpromoted investigations are lost.

**Whether this causes observable harm is UNKNOWN.** The audit could not prove that future sessions re-derive investigations that prior sessions completed. However, the structural gap is real: there is no mechanism for a future /why Step 0.5 to find a prior investigation's output unless it was promoted to wiki or handed off.

**Authoritative component to change:** `/why` skill at `C:\Users\brsth\.grok\skills\why\SKILL.md`

**Exact bounded change:**
1. Add optional `--persist` flag to /why that writes the Step 16 output report to `P:/docs/investigations/<topic-slug>-<date>.md`
2. Extend Step 0.5 to search `P:/docs/investigations/` in addition to wiki concepts and handoffs
3. Add two fields to Step 16 output: `Test outcomes` (results of discriminating tests run during the investigation) and `Status` (open/resolved/superseded)

**Producer:** /why skill (Step 16 output writer)
**Storage:** `P:/docs/investigations/<topic-slug>-<date>.md` (markdown, same format as Step 16 output)
**Consumer:** /why Step 0.5 (pattern-library query, extended to search investigations/)
**Authority:** The investigation file is advisory — it informs future investigations but does not override current evidence. Wiki concepts remain the durable-knowledge authority.
**Identity and freshness:** Filename includes date; frontmatter includes `created:` and `session_id:`. Stale investigations are flagged in Step 0.5 output with a warning if the investigation is >30 days old.
**Failure behavior:** If the investigations directory doesn't exist, /why creates it. If write fails, /why proceeds normally (the investigation output appears in the transcript regardless). Persistence is best-effort, not blocking.
