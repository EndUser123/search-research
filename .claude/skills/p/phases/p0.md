# Phase 0: Scaffold

## Purpose

Set up correct **project structure and tooling** before any code is written or tested. This is the zeroth phase of the Code Maturation Pipeline (`/p0` -> `/p1` -> `/p2` -> `/p3` -> `/p4`).

**Core question this phase answers:** "Is the project structured correctly?"

**When this runs:** Only when `/p` detects no `pyproject.toml` or no recognizable source structure. Skipped entirely for existing projects.

## What This Phase Does

1. Detect what project structure exists (if any)
2. Scaffold missing essentials (only what's missing)
3. Configure tooling (uv, ruff, mypy, pytest)
4. Verify the scaffold works (imports resolve, tools run)
5. **[From /problem-statement]** If no clear project purpose exists, prompt for problem documentation before scaffolding

## Your Workflow

When `/p --phase=0` is invoked:

### Step 1: Detect Existing Structure and Type

```bash
# Check for project type
ls SKILL.md 2>&1

# Check for project config
ls pyproject.toml setup.py setup.cfg 2>&1

# Check for source layout
ls src/ 2>&1
ls tests/ 2>&1

# Check for tooling
which uv ruff mypy 2>&1
ls .python-version 2>&1
```

### Step 1a: Branch by Type

**If SKILL.md exists → SKILL WORKFLOW** (skip to Step 2S below)

**If no SKILL.md → PACKAGE WORKFLOW** (continue to Step 1.5 below)

## SKILL WORKFLOW (Step 2S+)

**For skills with SKILL.md, use skill-specific validation:**

### Step 2S: Validate SKILL.md Quality

```bash
# Check SKILL.md frontmatter
head -30 SKILL.md | grep -E "^(name:|description:|category:|triggers:|aliases:)"
```

**Validate frontmatter completeness:**
- [ ] `name` present
- [ ] `description` present and ≤ 100 chars
- [ ] `category` present
- [ ] `triggers` list exists
- [ ] `aliases` list exists
- [ ] `suggest` list exists (related skills)

**Validate Constitution links:**
- [ ] Has "Constitution/Constraints" or "Constitutional links" section
- [ ] References specific PARTs (e.g., "PART T: Truthfulness", "PART E: Evidence-first")

### Step 3S: Check Skill Structure

```bash
# Check for skill directories
ls scripts/ references/ assets/ tests/ 2>&1
```

**Optimal skill structure:**
```
skill-name/
├── SKILL.md              # Required: skill documentation
├── scripts/              # Optional: executable code
│   └── *.py, *.sh
├── references/           # Optional: docs loaded as needed
│   └── *.md
├── assets/               # Optional: files for output
│   └── templates/, icons/
└── tests/                # Recommended: skill validation tests
    ├── __init__.py
    ├── conftest.py
    └── test_{skill}_skill.py  # Test triggers work
```

### Step 4S: Skill Quality Assessment

Based on `skill-development` and `testing-skills` best practices:

**Frontmatter quality:**
- [ ] Description concise and specific (≤ 100 chars enforced by registry)
- [ ] Triggers match actual invocation patterns
- [ ] Suggest links to related skills

**Content quality:**
- [ ] Progressive disclosure (metadata → SKILL.md body → bundled resources)
- [ ] Clear purpose section
- [ ] Execution directive (if EXECUTION type skill)
- [ ] Workflow steps with success criteria

**Constitution alignment:**
- [ ] Declares which PARTs it extends
- [ ] Constitutional constraints documented

### Step 5S: Recommendations

**If skill has issues, suggest:**

1. **Quick fixes** — Add missing Constitution PART references
2. **Restructure** — Move scripts to `scripts/`, add `tests/`
3. **Validate** — Run `/testing-skills {skill_name}` for full validation
4. **Improve** — Run `/av {skill_name}` for automatic hook generation and improvements

### Step 6S: Exit Criteria (Skills)

Phase 0-Skill is complete when:
- [ ] SKILL.md frontmatter complete (name, description, triggers, aliases)
- [ ] Description ≤ 100 characters
- [ ] Constitution PARTs referenced (if applicable)
- [ ] Bundled resources properly organized (scripts/, references/, assets/)
- [ ] Tests directory exists (recommended for skills with complex scripts)

### Step 7S: Return Result

```
PHASE_RESULT: PASS
PHASE: 0-SKILL
SUMMARY: Skill validation complete — SKILL.md quality: {assessment}, Structure: {structure}
```

Or if issues found:
```
PHASE_RESULT: HALT
PHASE: 0-SKILL
REASON: Skill validation issues — see findings above
BLOCKING_COUNT: 0
SUMMARY: {brief description of issues}
```

### Step 1.5: Problem Documentation (if needed)

**[From /problem-statement]** If the project lacks clear purpose documentation:

Before scaffolding, capture the problem context:
```markdown
## Problem Statement: [Topic]

### Context
- What you're working on
- Your role and goal
- What led to this problem

### Problem Description

- Actual behavior
```

### Step 2: Scaffold Missing Essentials

Only create what doesn't exist. Never overwrite existing files.

**Minimum viable project structure:**
```
project/
  pyproject.toml          # Project metadata + tool config (uv, ruff, mypy, pytest)
  src/
    package_name/
      __init__.py
      py.typed              # PEP 561 marker
  tests/
    __init__.py
    conftest.py
  .gitignore
```

**pyproject.toml essentials:**
- `[project]` with name, version, requires-python >= "3.12"
- `[tool.ruff]` with target-version = "py312", line-length = 99
- `[tool.mypy]` with strict = true
- `[tool.pytest.ini_options]` with testpaths = ["tests"]
- `[build-system]` with hatchling or setuptools

### Step 3: Initialize Tooling

```bash
# Create virtual environment and install dev deps
uv sync 2>&1

# Verify tools work
uv run ruff check . 2>&1
uv run mypy src/ 2>&1
uv run pytest --collect-only 2>&1
```

### Step 4: Verify Scaffold

Confirm the scaffold is functional:
- `uv run python -c "import package_name"` succeeds
- `uv run pytest --collect-only` finds the test directory
- `uv run ruff check .` runs without config errors
- `uv run mypy src/` runs without config errors

## Exit Criteria

Phase 0 is complete when:
- [ ] `pyproject.toml` exists with tool configuration
- [ ] `src/` layout with `__init__.py` and `py.typed`
- [ ] `tests/` directory with `conftest.py`
- [ ] `.gitignore` covers `__pycache__`, `.venv`, `*.egg-info`
- [ ] `uv sync` succeeds
- [ ] All tools (ruff, mypy, pytest) run without config errors

## Phase Progression

When exit criteria are met:
```
Ready for /p1 (Build) - make the code work with test-first discipline
```

## Usage

```
/p --phase=0                    # Auto-detect and scaffold what's missing
/p --phase=0 <project-name>     # Scaffold with explicit project name
```

## What This Does NOT Do

- Does not write application code (that's your job, then `/p1`)
- Does not write tests (that's `/p1`)
- Does not review code (that's `/p2`)
- Does not overwrite existing configuration — only fills gaps
- Does not choose frameworks or libraries — only sets up tooling
