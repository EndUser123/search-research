# Phase 3: Validate

## Purpose

**Prove** the code is trustworthy through a gated validation pipeline. This is the third phase of the 4-phase Code Maturation Pipeline (`/p1` → `/p2` → `/p3` → `/p4`).

**Core question this phase answers:** "Can I prove it works?"

**Prerequisite:** `/p2` exit criteria met (0 CRITICAL/HIGH adversarial findings).

## Semantic Ownership in P3

P3 owns deterministic semantic gate enforcement:
- blocking: migration rollback parity, unsafe/unbounded data-job timeout defaults
- warning (blocking with `--publish`): env default safety and license-header/context compliance

P3 consumes semantic intent findings from P2 and verifies closure before pass.

## Decomposition Ownership (opt/opts)

P3 owns deterministic validation of optimization/opportunity outcomes:
- complexity, integration, security, coverage, and semantic gate checks on post-fix code
- publish-mode strictness (`--publish`) for warning-to-blocking escalation

P3 does not run exploratory option generation (`/s`) or deterministic recommendation synthesis (`/r`).

## Decomposition Ownership (verify)

P3 owns former `/verify` tiered implementation verification (UAF-style), mapped directly into pipeline stages:
- **Tier 1 (syntax):** Stage 1
- **Tier 2 (types/lint):** Stages 2, 2.8, 7
- **Tier 3 (tests):** Stages 4, 4.5, 5

Scope handling:
- default scope is target inferred from this terminal session context
- explicit `/p --phase=3 <target>` overrides inference
- warning-tier findings remain non-blocking unless `--publish` is used

Standalone `/verify` is deprecated; use `/p --phase=3` for authoritative verification.

## Decomposition Ownership (analysis-profile)

P3 owns deterministic performance validation signals previously surfaced by `/analysis-profile`:
- baseline/bottleneck identification for the promotion target
- executor/concurrency anti-pattern checks as validation evidence

These signals complement (not replace) existing Stage 2.1 complexity and AID performance checks.

## Decomposition Ownership (ddd)

P3 owns deterministic due diligence validation for deployment readiness:
- Technical implementation completeness (code quality, error handling)
- Testing & validation sufficiency (coverage, edge cases)
- Business & requirements alignment (scope, documentation)
- Deployment & operations readiness (environment, monitoring)
- Risk assessment verification (technical debt, constitutional compliance)

These DDD-derived checks run as Stage 9 (non-blocking, blocking with --publish) and inform final HALT decision.

## AID Integration (Validation)

P3 owns performance risk validation via:
- `aid_performance_analysis` on the promotion target

Run this on every `/p3` invocation. Use output as additional validation evidence in Stage 2.1/2.5 decisions and final HALT logic.

## Architecture Validation (archlint)

P3 integrates architectural linting via the `archlint` module to validate compliance with SOLID principles, Clean Architecture, DRY, KISS, and other architectural patterns.

**Available in:** `scripts/archlint/`

**Usage during P3 validation:**
```bash
# Run architectural validation as part of Stage 2
python -m p.scripts.archlint.cli /path/to/target --rulesets solid,clean
```

**Integration points:**
- **Stage 2.5** - Architectural layering and dependency rules
- **Stage 2.7** - SOLID principles compliance
- **Stage 2.9** - Code duplication detection (DRY)

**Rulesets:**
| Ruleset | Purpose | Stage |
|---------|---------|-------|
| `solid` | Single Responsibility, Open/Closed, Liskov, Interface Segregation, Dependency Inversion | 2.5, 2.7 |
| `clean` | Layer separation, dependency rules | 2.5 |
| `dry` | Code duplication detection | 2.9 |
| `kiss` | Complexity and simplicity | 2.1 |

archlint runs as part of the standard P3 validation pipeline and findings are merged with other validation evidence for the HALT decision.

## Usage

```
/p --phase=3 <target>                  # Validate explicit target
/p --phase=3                           # Infer target from context
/p --phase=3 <target> --publish        # Halt on warnings (perfect for publishing)
/p --phase=3 <target> --stage=N        # Resume from stage/group checkpoint (after fixing)
```

**FLAGS:**
| Flag | Effect | Use Case |
|------|--------|----------|
| `--publish` | Treat non-blocking warnings as blocking | Perfect for publishing - no outstanding issues |
| `--stage=N` | Resume from stage/group checkpoint after fixing | Continue from halted stage |

**CRITICAL RULES:**
1. Execute stage GROUPS in parallel (see Parallel Execution below)
2. HALT on CRITICAL/HIGH from blocking stages
3. With `--publish`: HALT on any warning (including non-blocking stages)
4. Show ACTUAL tool output, not summaries
5. Every finding MUST include a concrete **Next Action** (exact fix command or edit location)

## Your Workflow (PARALLEL EXECUTION)

When `/p --phase=3` is invoked with a target, execute stages in **parallel groups** for ~2x speedup.

**Architecture:** 3 independent groups run concurrently as Task subagents, then Stage 3 (adversarial) runs after all groups pass.

## Resume Semantics (`--stage=N`)

Parallel execution changes resume behavior from single-stage restarts to checkpoint restarts.

| `--stage` value | Resume behavior |
|-----------------|-----------------|
| `1`, `1.5`, `2`, `2.1`, `2.5`, `2.55`, `2.6`, `2.7`, `2.8`, `2.9`, `4`, `4.1`, `4.5`, `5`, `6`, `7`, `7.5`, `7.6`, `8` | Re-run **Step 1 + Step 2** (all Groups A/B/C), then continue |
| `3` | Re-run **Step 3 only** IF a complete, passing Step 2 result exists for current target/session; otherwise re-run Step 1 + Step 2 first |

**Why:** grouped parallel runs produce a single merged gate decision; partial single-stage restarts are not deterministic across groups.

## STEP 3: Adversarial Review (Stage 3)

**Only runs if Step 2 passes with no HALT.**

This is the only stage that benefits from knowing all other stages passed. It runs its own internal parallelism.

**CRITICAL:** HALT decision is based on FILTERED findings ONLY, not raw adversarial output.

**CRITICAL: Execute ALL layers in sequence. NO shortcuts.**

**Stage 3 Flow:**
1. Launch 4 parallel adversarial agents → RAW findings
2. Layer 1: Filter to changed files only
3. Layer 2: Filter against architectural pillars + Constitutional filtering
4. Layer 3: Validate test quality metrics
5. **Layer 4: Quality Gate (confidence ≥80%)** → FILTERED findings
6. **HALT decision based on FILTERED findings**

**DO NOT HALT until Layer 4 completes.**

### Mechanical Checklist

- Run 4 adversarial agents (parallel)
  - adversarial-security, adversarial-performance, adversarial-quality, adversarial-testing

- Write findings to JSON files
  - `P:/.claude/state/p3_findings/{terminal_id}/adversarial-{agent}-{terminal_id}.json`

- Layer 1: `python P:/.claude/skills/p/scripts/stage3_layer1_delta.py --no-git <findings.json> [...]`

- Layer 2: `python P:/.claude/skills/p/scripts/stage3_layer2_pillars.py <layer1_output.json>`

- Layer 3: `python P:/.claude/skills/p/scripts/stage3_layer3_assertions.py <layer2_output.json> --test-files <test_files>`

- Layer 4: Invoke quality-gate subagent
  ```python
  Task(
      subagent_type="general-purpose",
      prompt="""Read P:/.claude/skills/solo-dev-authority/SKILL.md and validate these adversarial findings:

  FINDINGS:
  {layer3_filtered_findings}

  Output to: P:/.claude/state/p3-solo-dev-check-{terminal_id}.json
  """,
      description="Layer 4 quality gate - confidence filtering"
  )
  ```

- Read `P:/.claude/state/p3-solo-dev-check-{terminal_id}.json`

- HALT based on filtered findings (>=1 CRITICAL OR HIGH = HALT)

| Condition | Action |
|-----------|--------|
| 0 CRITICAL AND 0 HIGH (**filtered**) | `✅ PASS` → Proceed to Step 4 |
| ≥1 CRITICAL OR ≥1 HIGH (**filtered**) | `🛑 HALT` → Stop pipeline |

**DO NOT present adversarial findings before Layer 4 completes.**

## Stage Reference (Thresholds & Details)

These thresholds are used by the evaluation in Step 2:

### Syntax (Stage 1)
- Exit 0 = PASS, Exit ≠ 0 = FAIL

### Naming (Stage 1.5)
- Non-blocking. Warnings = WARN (HALT with --publish)

### Quality (Stage 2)
- Pylint ≥ 7.0 = PASS, < 7.0 = WARN, tool fails = FAIL

### Complexity (Stage 2.1)
- CC 1-10 (A-B) = PASS, CC 11-20 (C) = WARN, CC >= 21 (D-F) = FAIL

### Integration (Stage 2.5)
- INTEGRATED = PASS, PARTIAL = WARN, NOT_INTEGRATED/NO_REQUIREMENTS = FAIL

### Logging (Stage 2.6a)
- Non-blocking. Missing logging = WARN (HALT with --publish)

### Dead Code (Stage 2.6b)
- Non-blocking. Dead code found = WARN, vulture missing = FAIL (HALT with --publish)

### Security (Stage 2.7)
- No issues = PASS, Medium = WARN, High/Critical = FAIL

### Formatting (Stage 2.8)
- Non-blocking. Needs formatting = WARN (HALT with --publish)

### Duplication (Stage 2.9)
- Non-blocking. Duplicates = WARN, pylint missing = FAIL (HALT with --publish)

### Unit Tests + Branch Coverage (Stage 4+4.1)
- All pass + coverage ≥ 80% = PASS, coverage < 80% = WARN, coverage < 50% = FAIL, tests fail = FAIL

### Regression Tests (Stage 4.5)
- All pass = PASS, failures = FAIL, no tests = WARN

### Integration Tests (Stage 5)
- All pass = PASS, failures = FAIL, no tests = WARN

### Documentation (Stage 6)
- Non-blocking. Missing docstrings = WARN (HALT with --publish)

### Pre-commit (Stage 7)
- Non-blocking. Errors = WARN (HALT with --publish)

### CVE Scan (Stage 7.5)
- No CVEs = PASS, Low/Medium = WARN, High/Critical = FAIL

### Library Freshness (Stage 7.6)
- Non-blocking. Major behind = WARN, deprecated = WARN (HALT with --publish)

### Deploy Verification (Stage 8)
- Non-blocking. Uncommitted changes = INFO (HALT with --publish)

## Handling Halts

When the pipeline halts at a blocking stage:

1. Read the halt output — it includes specific findings with file:line references
2. Fix findings using `/tdd`:
   ```
   /tdd Fix <finding>
   ```
3. Re-run `/p --phase=3` with `--stage=N` to resume from the halted stage/group checkpoint:
   ```
   /p3 <target> --stage=N
   ```

## Halt Output Format

When HALT occurs, output:

```
## Current Status Summary

- ✅ Stage 1: SYNTAX - PASS
- ✅ Stage 1.5: NAMING - PASS
- ⚠️ Stage 2: QUALITY - WARN (score)
- ✅ Stage 2.5: INTEGRATION - PASS
- [Other stages completed before HALT...]
- 🛑 Stage {N}: {NAME} - HALT

## VALIDATION PIPELINE HALTED

## Status: 🛑 HALTED at Stage {stage_number}

**Reason:** {Summary of findings}

## Next Steps

1 - /tdd Fix {specific_finding_id} only
2 - /tdd Fix CRITICAL findings
3 - /tdd Fix HIGH findings
4 - /tdd Fix all filtered findings
x - /tdd All findings

Then re-run: /p3 <target> --stage={N}
```

When validation COMPLETES successfully, output:

```
## Current Status Summary

[All stages with their status]

## VALIDATION PIPELINE COMPLETE

## Status: ✅ COMPLETE

**Summary:** {Brief summary}

## Next Steps

1 - Format code: ruff format <target>
2 - Add docstrings: /refactor <target>
3 - Address remaining MEDIUM findings
4 - Or: Proceed with deployment/usage
```

## Coverage Threshold

The coverage target is **dynamic**, read from `.claude/state/pipeline-{terminal_id}.json`:

```json
{ "coverage_threshold": 70 }
```

| Threshold | Stage 4.1 Behavior |
|-----------|-------------------|
| Below 50% | FAIL (always — hard floor) |
| Below `coverage_threshold` | WARN — pass but flag for improvement |
| At or above `coverage_threshold` | PASS |

- **Default:** 70% (balances rigor with pragmatism for solo dev)
- **Hard floor:** 50% (never passes below this regardless of setting)
- **Configurable:** Set in `pipeline.json` or via `/p --set-coverage <N>`

## Exit Criteria

Phase 3 is complete when:
- [ ] Pipeline passes all blocking stages
- [ ] Unit test coverage meets dynamic threshold (default 70%, min 50%)
- [ ] No CRITICAL/HIGH security findings
- [ ] No known CVEs in dependencies
- [ ] (Optional) `/p5` certification report generated

## Phase Progression

When exit criteria are met:
