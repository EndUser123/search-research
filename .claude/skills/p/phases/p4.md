# Phase 4: Publish

## Purpose

Make the code **presentable and deployable** — generate portfolio artifacts, clean git history, and verify deploy readiness. This is the final phase of the 4-phase Code Maturation Pipeline (`/p1` → `/p2` → `/p3` → `/p4`).

**Core question this phase answers:** "Can others use it?"

**Prerequisite:** `/p3` exit criteria met (validation pipeline passes, no blocking findings).

## What This Phase Does

1. Detect missing portfolio artifacts (README, LICENSE, badges, CI/CD, etc.)
2. Generate only what's missing — no fabrication
3. Clean git history for public consumption
4. Verify deploy readiness
5. Final secret scan before publishing

## Semantic Ownership in P4

P4 owns publish-surface semantic alignment only:
- cloud/deploy metadata alignment (tags/policy docs match deployment reality)
- artifact-level compliance wording (README/CHANGELOG/license narrative consistency)

P4 does not rerun P2/P3 semantic code checks; it verifies public-facing consistency.

## Decomposition Ownership (value/value-maximization)

P4 applies publish-surface value capture before completion:
- detect leverage-point artifact improvements (README clarity, examples, deployment docs)
- avoid silent scope cuts in publish artifacts
- disclose excluded HIGH/MEDIUM-value publish items for user trade-off decisions

## AID Integration (Publish Artifacts)

P4 owns documentation generation via AID:
- `aid_generate_docs` for scoped documentation output
- `aid_multi_file_docs` for cross-file documentation workflows

P2 findings that passed the 4-layer filter and were fixed are already in git history. Use commit messages from P2 fix iterations to populate CHANGELOG entries.

### Step 0.5: Code Simplification (Pre-Publish Polish)

Before generating portfolio artifacts, run code simplification to polish the code:

```
Agent(subagent_type="pr-review-toolkit:code-simplifier", description="Simplify and polish code for clarity and maintainability in <target>")
```

**What this does:**
- Reviews code for clarity, consistency, and maintainability
- Suggests simplifications that preserve all functionality
- Focuses on readability improvements (naming, structure, flow)
- Removes unnecessary complexity while preserving behavior

**When to run:**
- Always run before P4 artifact generation
- Only applies to code that passed P2 (Review) and P3 (Validation)
- Skip if target is EXPLORATORY code (see P2 context classification)

**Integration notes:**
- Run this agent AFTER P3 validation completes
- Apply simplifications only if they:
  - Preserve all functionality (no behavior changes)
  - Pass constitutional filter (no enterprise patterns)
  - Have confidence >= 80% (quality gate)
- If simplifications are suggested, apply them and re-run P3 validation
- Only proceed to Step 1 when code is clean and simplified

**Rationale:** Code simplification before publishing ensures the codebase is in its cleanest, most maintainable state before generating portfolio artifacts. This prevents generating documentation for code that will be refactored.

### Step 1: Portfolio Artifact Generation

Run the portfolio skill to detect and fill artifact gaps:

```
/portfolio prepare
```

The portfolio skill (verified: `portfolio/SKILL.md:1-6`) detects gaps across:
- README (problem statement, quick start, usage, architecture)
- LICENSE (MIT or Apache 2.0 for portfolio work)
- Badges (coverage, version, license, CI status)
- CI/CD pipeline (GitHub Actions for tests, linting, type checks)
- Documentation (API docs, contributing guide)
- Examples (examples/ directory or inline in README)
- CHANGELOG (from git commit history)
- Demo (extracted from E2E tests if available)
- Metrics (coverage %, quality score)
- Secret scan (no .env, credentials, or secrets in repo)

It generates only what's actually missing.

### Step 1.5: AID Documentation Pass

Run both for the promotion target on every `/p4` invocation and feed outputs into README/docs artifacts:

```bash
aid_generate_docs(target_path=<target>, doc_type="technical")
aid_multi_file_docs(target_path=<target>)
```

Rules:
- Keep generated docs aligned with verified behavior from P1-P3 outputs.
- Do not fabricate APIs or capabilities not present in code.
- If an AID call fails/conflicts, continue `/p4` and emit an explicit degraded-docs note in publish output.

### Step 2: Review Generated Artifacts

Review each generated artifact for accuracy:
- README reflects actual functionality (not aspirational)
- Badges show real metrics (from `/p3` validation output)
- CI/CD config matches actual test/lint commands used
- Examples actually run

### Step 3: Git History Cleanup

Clean up messy development history for public presentation.

**Safety guardrails (mandatory):**
1. **Never rewrite main/master history** — only feature branches
2. **Confirm with user before any history-rewriting operation** (squash, rebase, filter-branch)
3. **Create a backup tag** before rewriting: `git tag backup-pre-cleanup-<date>`
4. **Never force-push without explicit user approval**

Operations:
- Squash WIP commits on feature branches (after user confirmation)
- Ensure meaningful commit messages on main
- Verify no secrets in git history

### Step 4: Deploy Readiness Check

Run the ship skill to verify everything is ready:

```
/ship pre
```

This aggregates (verified: `ship/SKILL.md:42-49`):
- Git cleanliness (via `/vdate-deploy`)
- Verification status (via `/p3`)
- QA certification status (via `/p5`)
- CI/CD pipeline status
- Runtime health signals (if applicable)

Produces a verdict: **Ready** / **Caution** / **Blocked**

### Step 5: Final Secret Scan

Before any public publishing:
- Scan for `.env` files, API keys, tokens in repo
- Check `.gitignore` covers sensitive patterns
- Verify git history is clean of accidental secret commits

### Loop Condition

**Repeat Steps 1-5 until:**
- All artifact gaps filled
- No secrets detected in repo or history
- `/ship pre` verdict is "Ready"

## Exit Criteria

Phase 4 (and the full pipeline) is complete when:
- [ ] README exists with problem statement, quick start, usage examples
- [ ] LICENSE file present
- [ ] CI/CD pipeline configured and passing
- [ ] No secrets in repo or git history
- [ ] `/ship pre` returns "Ready" verdict
- [ ] (Optional) CHANGELOG, badges, contributing guide, examples/ directory

## The Full Pipeline

```
/p --phase=1 (Build)    → Does it work?         → Tests pass, bugs fixed
/p --phase=2 (Review)   → What's wrong with it? → 0 CRITICAL/HIGH findings
/p --phase=3 (Validate) → Can I prove it works? → Pipeline passes all gates
/p --phase=4 (Publish)  → Can others use it?    → Artifacts complete, ready to ship
```

## Usage

```
/p --phase=4 <target>           # Full publish workflow
/p --phase=4 prepare            # Artifact generation only (delegates to /portfolio prepare)
/p --phase=4 readiness          # Deploy check only (delegates to /ship pre)
/p --phase=4                    # Infer from context
```

## What This Does NOT Do

- Does not write tests (that's `/p1`)
- Does not find code problems (that's `/p2`)
- Does not run validation pipeline (that's `/p3`)
- Does not fabricate metrics — all numbers come from actual tool output
- Does not push to remote or publish — that's a manual decision
