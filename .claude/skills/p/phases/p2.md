# Phase 2: Review

## Purpose

Find **all the problems** in code that already works. Pure analysis with iterative fixing. This is the second phase of the 4-phase Code Maturation Pipeline (`/p1` → `/p2` → `/p3` → `/p4`).

**Core question this phase answers:** "What's wrong with it?"

**Prerequisite:** `/p1` exit criteria met (tests pass, core logic covered, no known bugs).

## What This Phase Does

1. **Pre-check eligibility** — skip if code is not ready for review (closed, draft, trivial, already reviewed)
2. **Gather context** — collect CLAUDE.md guidelines and git history for target files
3. Collect findings: adversarial review + synergy detection + duplicate detection + git history analysis
4. **[From /slc]** Run solo-dev compliance checks:
   - Complexity justified by value?
   - Complete solutions only (no dead code)?
   - Evidence verified (proofs shown)?
   - Local/portable (no infra/lock-in)?
5. Run semantic intent review (decomposed from former semantic scanner)
6. **HALT and filter** findings through 5-layer pipeline (delta → pillars → assertions → quality-gate → constitutional)
7. Fix filtered findings in priority order: correctness > security > clarity > style
8. Re-run review to confirm fixes and catch new issues
9. Repeat until clean

## Incremental Findings (Session-Scoped)

P2 tracks findings within a single `/p` invocation to survive context compaction. Findings do NOT persist across different `/p` runs.

**Session-scoped findings tracking:**
- Each `/p` invocation starts with a fresh findings state
- Findings are tracked in-memory for the current session
- When context compacts, the findings file helps resume the review

**Findings file:** `.claude/findings/p2-{terminal_id}-{target_hash}.json`
- `terminal_id` = detected terminal ID for multi-terminal isolation
- `target_hash` = first 8 chars of SHA256 of the sorted target file list
- Compute terminal_id: use `detect_terminal_id()` from hooks/terminal_detection.py (canonical source)
- Compute target_hash: `echo -n "file1.py file2.py" | sha256sum | cut -c1-8`

**File structure:**
```json
{
  "target": "src/module.py",
  "target_files": ["src/module.py"],
  "terminal_id": "console_123abc",
  "target_hash": "a1b2c3d4",
  "session_id": "uuid-v4-generated-on-start",
  "agents_completed": ["security", "performance"],
  "raw_findings": [...],
  "filtered_findings": null,
  "status": "in_progress",
  "reported_findings": ["file:42:type", "file:123:type"]  // Layer 1 deduplication
}
```

**Write protocol:**
1. Detect terminal_id using `detect_terminal_id()` from hooks/terminal_detection.py (canonical source)
2. Generate new `session_id` (UUID v4) on `/p` invocation
3. Check if findings file exists with matching `terminal_id` and `target_hash` → resume from `agents_completed` if same session
4. If different terminal, different session, or no findings → start fresh
5. After each agent returns, append its findings to `raw_findings` and its name to `agents_completed`, then write file to disk
6. After filtering, write `filtered_findings`, add to `reported_findings`, and set `status: "complete"`

**Resume logic (after compact):**
- Read findings file, check `session_id` matches current invocation
- Skip agents already in `agents_completed`
- Run only missing agents
- Continue from where filtering left off

**Session-scoped design rationale:**
- No stale data across different `/p` runs (fresh scan every time)
- Session-only `reported_findings` prevents noise within current invocation
- Simpler than git diff hash tracking (works with auto-commit hooks)
- Multi-terminal safe: different terminals get different session_ids

### Step 0: Eligibility Pre-Check

Before running any analysis, check if the target is eligible for review:

```
Check the following IN ORDER:

1. **Trivial target check:**
   - Is the target < 10 lines (only comments/imports)?
   - If yes → SKIP (too small for adversarial review)

2. **Partial review check:**
   - Does .claude/findings/p2-{terminal_id}-{target_hash}.json exist with status "in_progress"?
   - If yes → RESUME (continue from where agent left off)

3. **Eligible:**
   - If target is non-trivial AND no partial findings exist → ELIGIBLE (proceed to Step 1)

Report: "ELIGIBLE" (proceed), "RESUME" (partial findings), or "SKIP" with reason.
```

**Skip outcomes:**
- Trivial target (< 10 lines) → Report: "Target too small for adversarial review"

**Resume outcome:**
- Partial findings exist → Report: "RESUME - {N} of 10 agents completed, resuming remaining"

**Eligible outcome:**
- Non-trivial target → Report: "ELIGIBLE - Full adversarial review"

**Rationale for removing delta check:**
- Auto-commit hooks make git diff unreliable (changes committed immediately)
- Session-level deduplication in Step 2 prevents repetitive reporting
- Solo-dev + AI workforce: scanning is fast and thorough
- Better to find everything than miss something due to stale delta detection

Only proceed to Step 1 if the agent returns "ELIGIBLE" or "RESUME".

### Step 1.5: Synergy Detection (Multi-File Refactoring)

After adversarial review completes, run `/refactor --dry-run` on the same target to detect **cross-file synergies** that per-finding fixes would miss:

```

```

This adds findings that adversarial review alone doesn't catch:
- **extract** — common code across files that should be a shared module
- **merge** — similar interfaces that can combine
- **consolidate** — scattered patterns (e.g., config access in 5 files)
- **standardize** — inconsistent error handling, naming, or patterns
- **restructure** — circular imports, coupling issues

**Merge these synergy findings into the adversarial findings list** before prioritizing. Synergies map to priorities:
- Restructure (circular deps) → P0
- Standardize (inconsistent error handling) → P1
- Extract / Consolidate / Merge → P2

**Skip this step if** the target is a single file (synergies require 2+ files).

**Layer 0: Context Classification** (Production vs Exploratory)
- Classify target as **PRODUCTION** or **EXPLORATORY** before filtering

**Production indicators** (full standards apply):

- Used/imported by other production code

- **PRODUCTION code**: All findings apply (security, quality, testing, compliance)
- **EXPLORATORY code**: Only security + basic logic findings apply

  - KEEP: Path traversal, unsafe file ops, crashes, data loss

**Layer 1: Session-Level Deduplication** (replaces delta filter)
- Track findings reported in this session to avoid repetitive reporting
- Deduplication key: `finding_id = f"{file}:{line}:{issue_type}"`
- If finding_id was already reported in this session, skip it
- Store seen finding_ids in memory for the current `/p` invocation
- Rationale: Prevents noise from repeated scans without missing new issues
- Note: This is session-scoped (not persisted), so new invocations will re-report all findings

**Layer 2: Architectural Pillar Filter + Constitutional Filtering**
- Reject suggestions violating core architectural decisions
- Apply SoloDevConstitutionalFilter to reject enterprise-bloat:
  - "Add monitoring/observability" → continuous tracking (prohibited)
  - "Design for scalability" → enterprise pattern
  - "Implement caching layer" → over-engineering for solo dev
  - "Lock ordering/acquisition order" → enterprise bloat

**Layer 3: Test Quality Validation**

**Layer 4.5: Practicality Filter** (Manual - Director + AI Workforce Context)

Before presenting findings to the director, apply practical judgment to filter out findings that don't fit the solo-dev + AI workforce context.

**Filtering criteria:**

```python
def filter_findings_for_director(findings):
    """Apply practical judgment to adversarial findings."""
    approved = []
    filtered = []

    for finding in findings:
        # Rule 1: Performance micro-optimizations
        # Filter: <500ms savings when current performance <1000ms
        if finding.get("type") == "PERF" and finding.get("savings_ms", 0) < 500:
            if finding.get("current_perf_ms", 0) < 1000:
                filtered.append({
                    **finding,
                    "status": "FILTERED",
                    "reason": (
                        f"Current perf {finding.get('current_perf_ms')}ms is adequate. "
                        f"Optimizing for {finding.get('savings_ms')}ms savings is premature. "
                        "Reconsider only if performance becomes a demonstrated bottleneck."
                    )
                })
                continue

        # Rule 2: Complexity > benefit
        # Filter: HIGH/MEDIUM complexity for <50% improvement
        if finding.get("complexity") in ["HIGH", "MEDIUM"]:
            improvement_pct = finding.get("improvement_pct", 0)
            if improvement_pct < 50:
                filtered.append({
                    **finding,
                    "status": "FILTERED",
                    "reason": (
                        f"Complexity {finding.get('complexity')} too high for "
                        f"{improvement_pct}% improvement. "
                        "Not worth the engineering time."
                    )
                })
                continue

        # Rule 3: AI implementation speed adjustment
        # When findings estimate human development time, apply 10-100x AI multiplier
        if finding.get("estimated_hours"):
            # AI does this 10-100x faster
            ai_minutes = finding["estimated_hours"] * 0.6  # midpoint: 36x faster

            # Still not worth if >30 minutes for <50% improvement
            if ai_minutes > 30 and finding.get("improvement_pct", 0) < 50:
                filtered.append({
                    **finding,
                    "status": "FILTERED",
                    "reason": (
                        f"AI estimate {ai_minutes:.0f}min too high for "
                        f"{finding.get('improvement_pct')}% improvement. "
                        "Time better spent elsewhere."
                    )
                })
                continue

        approved.append(finding)

    return approved, filtered
```

**When to filter**:
- Apply **before** showing results to user
- Log filtered findings so they can be reviewed on request
- Always explain why something was filtered (transparent)

**What gets through**:
- ✅ Security issues (data leaks, injection vectors)
- ✅ Actual bugs (logic errors, crashes)
- ✅ Clear performance problems (>500ms, measured)
- ✅ High-value improvements (>50% gain, LOW complexity)

**What gets filtered**:
- ❌ Premature optimization (<500ms savings, adequate current perf)
- ❌ Over-engineering (HIGH complexity for <50% gain)
- ❌ Micro-optimizations (not worth the time)

**Director model context**: Solo human + AI workforce means:
- AI implementation is 10-100x faster than human estimates
- Current performance "good enough" bar is higher (no enterprise SLAs)
- Your time is valuable - don't waste on premature optimization

## Analysis Depth Modes

P2 supports three depth modes (from `/analyze`). Default is **standard**.

| Mode | Adversarial Agents | PR-Review Agents | Synergy | Duplicates | Use When |
|------|-------------------|------------------|---------|------------|----------|
| quick | 4 agents (security, quality, testing, performance) | 1 agent (code-reviewer only) | Skip | Skip | Fast iteration, single-file changes |
| standard | 7 agents (full adversarial) | 3 agents (code-reviewer, pr-test-analyzer, silent-failure-hunter) | Yes | Yes | Normal development (default) |
| deep | 7 agents + council perspectives | 3 agents + repeat adversarial batch | Yes + architectural review | Yes + AST similarity | Complex architecture, high-risk changes |

**Quick mode:** Runs only 4 core adversarial agents + code-reviewer. Skips pr-test-analyzer, silent-failure-hunter, synergy detection, and duplicate detection. Useful for fast feedback during active development.

**Standard mode:** Runs all 7 adversarial agents + all 3 pr-review-toolkit agents. Includes synergy detection and duplicate detection. This is the default for normal development.

**Deep mode:** Runs all 10 agents (7 adversarial + 3 pr-review-toolkit), plus adds:
- Architectural perspective analysis (from `/analyze --mode council`)
- AST-based similarity detection (catches near-duplicates beyond hash matching)
- Cross-module dependency analysis
- Repeat adversarial batch for coverage verification

**Mode selection:**
```
/p --phase=2 <target>                # Standard (default)
/p --phase=2 <target> --quick        # Quick mode
/p --phase=2 <target> --deep         # Deep mode
```

**When /p invokes P2:** `/p` passes `--quick` when using `--quick` flag. Otherwise standard.

## Usage

```
/p --phase=2 <target>           # Review a file or directory (standard mode)
/p --phase=2 src/module.py      # Single file
/p --phase=2 src/               # Directory
/p --phase=2                    # Infer from context
/p --phase=2 <target> --quick   # Quick mode (4 agents, no synergy/duplicates)
/p --phase=2 <target> --deep    # Deep mode (7 agents + council + AST similarity)
```

## What This Does NOT Do

- Does not write initial tests (that's `/p1`)
- Does not run the full validation pipeline (that's `/p3`)
- Does not generate portfolio artifacts (that's `/p4`)
- Does not skip MEDIUM/LOW findings that pass the 5-layer filter — those get fixed too
