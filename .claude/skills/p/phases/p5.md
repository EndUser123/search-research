# Phase 5: Certify

> **Core Question: Is this ready for production?**

Systematic quality assurance to certify features after Phase 4 (Publish) and before production deployment, preventing regressions, security issues, and performance degradation from reaching production.

## Purpose

A strict quality gate that certifies features after `/p4` completion and before production release. This is the **final production certification checkpoint** that validates:

- Feature completeness and stability
- Security and compliance requirements
- Performance under load
- End-to-end user journey validation
- Production readiness criteria

## Semantic Ownership in P5

P5 owns residual semantic risk certification:
- verify P2/P3 semantic findings are resolved or explicitly waived
- fail certification when unresolved blocking semantic risks remain
- include semantic risk disposition in `qa_report.md`

P5 does not duplicate discovery scans from P2; it certifies closure.

## Decomposition Ownership (qa)

P5 fully owns former `/qa` feature-certification workflow:
- session-scoped target detection
- triage routing (`FAST|STANDARD|CAREFUL`)
- 4-phase certification flow (SANITY, E2E, CHAOS, REPORT)
- certification evidence packaging in `qa_report.md`

Operational assets:
- flow: `P:/.claude/skills/p/flows/certify.md`
- templates: `P:/.claude/skills/p/resources/`

Standalone `/qa` is deprecated; use `/p --phase=5`.

## Decomposition Ownership (value/value-maximization)

P5 owns certification-stage value completeness checks:
- classify excluded certification items by value level (`HIGH|MEDIUM|LOW`)
- require disclosure of `HIGH` exclusions and `MEDIUM` exclusions when 3+
- include exclusions and rationale in `qa_report.md` before final verdict

## AID Integration (Certification Evidence)

P5 runs `aid_deep_file_analysis` on every `/p5` invocation to generate structured file-by-file certification evidence.

Usage in P5:
- fold high-signal outputs into certification risk summary
- use as evidence for coverage/risk blind spots before final verdict
- do not reassign discovery ownership from `/p2` or validation ownership from `/p3`

## 🎯 Context-Aware Target Detection (Session Scope)

**CRITICAL: P5 analyzes ONLY what was done in this terminal session.**

Git status is PROHIBITED for scope detection - it accumulates stale changes from multiple sessions.

### Session Scope Rules

**ONLY analyze:**
- Files explicitly discussed/edited in this conversation
- Features implemented in this session
- Test results from this session

**EXCLUDE from analysis:**
- `.claude/sessions/` - session metadata (auto-generated)
- `__csf/` - separate project context
- Unrelated projects not discussed in this chat
- Stale git changes from previous sessions

### Target Detection Priority (Session-Based)

| Priority | Detection Method | Example |
|----------|------------------|---------|
| **1** | Conversation history | What was discussed/implemented |
| **2** | Recent Read/Edit tools | Files touched in this session |
| **3** | Working directory | `P:/projects/yt-fts` → target=`yt-fts` |
| **4** | User provided | `/p --phase=5 explicit_target` |

**Inference Logic:**
```python
# Pseudo-code for session-based detection
if not provided_target:
    if conversation_mentions_project:
        target = extract_from_conversation()
    elif recent_edits_in_session:
        target = extract_module_from_path(recent_edits[0])
    elif cwd.startswith("P:/projects/"):
        target = cwd.split("/")[-1]
    else:
        target = "."  # Current directory only
```

### Why Session Scope?

Git accumulates changes from:
- Previous terminal sessions
- Other concurrent work
- Unrelated branches
- Stale edits

**Example:**
```
git status shows: __csf/src/research/engine.py (modified)
BUT: Conversation never touched research → STALE, IGNORE
```

**What to analyze instead:**
- What files did we Read/Edit in THIS conversation?
- What did the user say they worked on?
- What tests did we run and saw results for?

### Phase 1: SANITY (Smoke Test & Security)

**Objective:** Fail fast on broken or insecure builds.

#### Test Strategy Selection

**Run pytest directly:**

```bash
# Verify pytest is available
python -m pytest --version

# Run tests with coverage
python -m pytest tests/ -v --tb=short --cov=. --cov-report=term-missing

# Security audit with bandit (if available)
python -m bandit -r src/ -f screen -ll
```

#### Option B: No test infrastructure

1. **Static analysis:**
    ```bash
    python -m ruff check src/     # Linting
    python -m mypy src/           # Type checking (if configured)
    ```

2. **Manual code review** - Check for:
   - Import errors
   - Undefined variables
   - Syntax issues
   - Security vulnerabilities (SQL injection, command injection, etc.)

**Exit Criteria:** Tests pass OR manual review finds no critical issues.

### Phase 2: E2E (Browser Automation)

**Objective:** Verify critical user paths.

**Note:** Uses `notebooklm`'s browser factory for robust automation.

1. **Select Scenario:**
   - Use E2E scenario template to define steps:
     ```
     ## Scenario: [Name]
     - **Target URL:** [e.g., http://localhost:3000]
     - **Entry Point:** [e.g., Homepage]

     ### Steps:
     1. **[Step 1]**: [Action] -> [Expected Result]
     2. **[Step 2]**: [Action] -> [Expected Result]
     3. **[Step 3]**: [Action] -> [Verify Success State]

     ### Verification Checklist:
     - [ ] Primary CTA is visible
     - [ ] Data persists after refresh
     - [ ] No console errors
     ```

2. **Execute Path:**
   > "Using the browser tool, navigate to [Local URL]. Perform [Core Action]. Verify [Success State]."

**Exit Criteria:** User story verified with visual evidence.

### Phase 3: CHAOS (Fuzz & Stress)

**Objective:** Find hidden crashes.

1. **Property-Based Fuzzing:**
    ```bash
    python -m pytest tests/ --hypothesis-seed=0 -v
    ```
2. **API Schema Fuzzing (if schemathesis available):**
    ```bash
    schemathesis run http://localhost:8000/docs --hypothesis-seed=0
    ```
3. **Concurrency Stress (if locust available):**
    ```bash
    locust -f locustfile.py --headless -u 10 -r 5 -t 30s
    ```

**Exit Criteria:** No unhandled exceptions or 5xx errors.

   - **FAIL:** Blocked. Return to `/p1` (Build) or `/p3` (Validate).

## Failure Modes

| Failure    | Symptom              | Recovery                            |
| :--------- | :------------------- | :---------------------------------- |
| Smoke fail | Test assertion error | Return to `/p1` (fix regression)    |
| UI fail    | Playwright timeout   | Debug with `E2E_HEADLESS=false`     |
| 500 error  | Server crash in logs | `/rca` the log trace                |
| Flaky test | Intermittent fail    | Re-run with `pytest --lf`           |
| Low tokens | Context exhausted    | Switch to FAST or quick test        |
