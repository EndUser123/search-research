# Session Namespace Isolation

## Overview

Session Namespace Isolation prevents file lock conflicts when multiple Claude Code sessions run concurrently. Each session uses its own lock subdirectory, eliminating the "file locked by another session" errors that occur when parallel operations compete for the same lock files.

## Problem

Previously, the file lock manager stored all locks in a flat directory structure:

```
.claude/.locks/
├── SKILL.md.lock
├── analyze.py.lock
└── file.py.lock
```

When two sessions tried to edit `SKILL.md` simultaneously:
1. Session A acquires `SKILL.md.lock`
2. Session B tries to acquire `SKILL.md.lock`
3. Session B gets "Locked by session_A (7s remaining)" error
4. Session B must wait or retry

This caused unnecessary blocking and delays in parallel workflows.

## Solution

Each session now uses its own lock subdirectory:

```
.claude/.locks/
├── session_ppid_12345/
│   ├── SKILL.md.lock
│   └── file.py.lock
└── session_ppid_67890/
    ├── SKILL.md.lock      ← Different file! No conflict!
    └── file.py.lock
```

Now both sessions can edit `SKILL.md` concurrently without lock conflicts.

## Architecture

### Session Identification

Session IDs are generated by `_get_session_id()` in `file_lock_manager.py`:

1. **Environment Variable**: `CLAUDE_SESSION_ID` (if set by Claude Code)
2. **Parent PID**: `ppid_<pid>` using psutil (most reliable)
3. **Current PID**: `pid_<pid>` (fallback)

### Lock Path Resolution

The `_get_lock_path()` function now resolves paths to session-specific locations:

```python
def _get_lock_path(file_path: str) -> Path:
    normalized = file_path.replace("\\", "/").replace(":", "_").replace("/", "_")
    session_dir = _get_session_lock_dir()
    return session_dir / f"{normalized}.lock"
```

Example:
- Input: `P:\.claude\skills\analyze\SKILL.md`
- Output: `P:\.claude\.locks\session_ppid_12345\___claude_skills_analyze_SKILL.md.lock`

### Session Directory Management

```python
def _get_session_lock_dir() -> Path:
    """Get the session-specific lock directory."""
    session_id = _get_session_id()
    session_dir = LOCK_DIR / f"session_{session_id}"
    SESSION_LOCK_DIR = session_dir  # Cache for performance
    return session_dir
```

The session directory is created on-demand when the first lock is acquired.

## API

### New Functions

#### `cleanup_session_locks(session_id: str | None = None) -> int`

Remove all locks for a specific session.

**Parameters:**
- `session_id`: Session ID to clean up. If `None`, uses current session.

**Returns:**
- Count of locks removed.

**Example:**
```python
# Clean up current session's locks
removed = cleanup_session_locks()

# Clean up specific session's locks
removed = cleanup_session_locks("ppid_12345")
```

### Modified Functions

#### `_get_lock_path(file_path: str) -> Path`

Now returns a path in the session-specific subdirectory.

#### `cleanup_stale_locks() -> int`

Enhanced to:
- Clean locks in all session directories
- Remove empty session directories
- Still handle legacy (flat) locks for backward compatibility

## Usage

### Basic Lock Operations

```python
from file_lock_manager import acquire_lock, release_lock

# Acquire lock (uses current session automatically)
success, message = acquire_lock("path/to/file.py")
if not success:
    print(f"Could not acquire lock: {message}")

# Release lock
release_lock("path/to/file.py")
```

### Multi-Session Scenarios

```python
import os

# Simulate two concurrent sessions
os.environ["CLAUDE_SESSION_ID"] = "session_A"
success_a, _ = acquire_lock("shared_file.py")

os.environ["CLAUDE_SESSION_ID"] = "session_B"
success_b, _ = acquire_lock("shared_file.py")

# Both succeed! No conflict.
assert success_a and success_b
```

### Session Cleanup

```python
# Clean up all locks for current session
from file_lock_manager import cleanup_session_locks
removed = cleanup_session_locks()
print(f"Removed {removed} locks")
```

## Design Decisions

### Why Session Subdirectories?

**Alternatives considered:**
1. Lock file naming with session prefix (`sessionA_file.lock`)
2. Central lock coordinator process
3. Database-backed lock management

**Chosen approach (subdirectories):**
- Simple and filesystem-native
- No external dependencies
- Easy cleanup (remove directory to remove all locks)
- Works with existing lock semantics

### Why Parent PID for Session ID?

Parent PID provides:
- **Consistency**: All hooks in same CC session share parent PID
- **Automatic cleanup**: When CC process exits, PID becomes invalid
- **Collision resistance**: PIDs are unique per running process
