# Hook Optimization Recommendations — Adversarial Critique

## Intent Summary

Five hook optimization recommendations were surfaced from NotebookLM research: lazy regex initialization, a 200ms hard timeout budget, matcher filters in settings.json, SQLite WAL for handoff state, and QueueHandler for hook I/O. This critique evaluates each for soundness, feasibility, and multi-terminal safety.

---

**QA-002 Verification Criteria:**
- ≥80% = Healthy — Low risk, minor improvements possible
- 50-79% = Warning — Significant issues in 2+ domains, address HIGH items first

The recommendations are directionally correct. Multi-terminal data corruption risks in concurrent JSONL writes are the most urgent unaddressed issue.

## 1. Logical Gaps & Inconsistencies

1.1. [CRITICAL] **SQLite WAL is already implemented — but JSONL state was missed** (source: adversarial-security, evidence_store.py:64-68)

WAL mode is implemented in `evidence_store.py` for the evidence spool. But `skill_execution_gate.jsonl` uses raw JSONL with no WAL. Concurrent terminal writes to this log file are unprotected. The recommendation to "use SQLite WAL" is partially satisfied but the actual gap (unprotected JSONL state logging) was not identified.

**Concrete fix**: Migrate `skill_execution_gate.jsonl` to SQLite WAL, or replace JSONL append with atomic rename pattern.

1.2. [CRITICAL] **SIGALRM timeout is non-functional on Windows** (source: Phase 2 meta-critique)

`signal.SIGALRM` and `signal.alarm()` do not exist on Windows. The hook framework runs on Windows 11. Any recommendation using `signal.alarm()` for timeout enforcement will silently do nothing. The proposed fix at `hook_base.py:119` cannot work as specified.

**Concrete fix**: Use `threading.Timer` with callback interrupt, or implement a cooperative polling model within the hook framework. Do NOT use signal-based timeout.

1.3. [HIGH] **FileLock exception handling allows lock-free writes on non-timeout exceptions** (source: adversarial-security, evidence_store.py:360)

When `FileLock` raises an exception other than `TimeoutError` (OSError, PermissionError), the code falls through to a temp file write without holding the lock (lines 360-373). This is a multi-terminal data corruption risk.

**Concrete fix**: At `evidence_store.py:360`, replace `except Exception:` with `except TimeoutError:` only. The fallback should only be reached when `FILE_LOCK_AVAILABLE` is False (lock never attempted), not when lock was attempted but failed for other reasons.

1.4. [HIGH] **Regex laziness was partially addressed in recent commits** (source: Phase 2 verification)

CRIT-001 (Remove FileLock timeout fallback), CRIT-004 (TOCTOU in evidence freshness), and SEC-001/SEC-002 from earlier GTO rounds suggest these issues were already known and partially fixed. The current state of evidence_store.py:349-372 shows partial remediation (TimeoutError path does not fall through), but the `except Exception: pass` on line 360 still allows non-timeout failures to proceed to lock-free fallback.

**Concrete fix**: Restrict the fallback to only execute when `FILE_LOCK_AVAILABLE == False`, not when FileLock threw an exception.

1.5. [MEDIUM] **Phase 1 found 605 regex compilations but did not verify which are actually in hot paths** (source: Phase 2 meta-critique)

The count of 605 `re.compile()` calls across 121 files is real. But the recommendation assumes all compiled patterns are on the startup hot path. Patterns compiled in lazily-imported modules or in hooks that rarely run are not on the critical startup path.

**Concrete fix**: Distinguish startup-cost regex (compiled at module import) from runtime-cost regex (compiled lazily on first use). Prioritize the startup-cost group only.

## 2. Hidden Assumptions & Fragile Dependencies

2.1. [MEDIUM] **QueueHandler assumes hook I/O is the bottleneck — it is not** (source: Phase 2 meta-critique)

QueueHandler in Python's logging module is designed for bursty producers writing to slow consumers. Hook execution is serialized (one hook runs to completion), so there is no producer burst problem. The bottleneck is CPU/pattern matching in hook logic, not I/O queuing.

**Assumption being made**: I/O is the hook bottleneck. This is fragile — it would add architectural complexity for a non-existent problem.

2.2. [MEDIUM] **200ms timeout assumes hooks are the user-visible bottleneck** (source: Phase 2 meta-critique)

The 200ms budget was cited from NotebookLM research as a common pattern. But no measurement was done to establish whether hooks are actually the user-visible bottleneck in this environment. Without measurement, the timeout could fire on legitimate long-running hooks (e.g., transcript parsing) that are not the UX problem.

**Assumption being made**: Hook latency is the UX bottleneck. If it isn't, the 200ms cap is an arbitrary constraint that would fire incorrectly.

2.3. [LOW] **Matcher pre-filter assumes hook loading is the bottleneck, not hook execution** (source: Phase 2 meta-critique)

If hook execution (the actual pattern matching, file I/O) is slow, pre-filtering saves only the import cost. But if hooks are imported once per session and then cached, the import savings are amortized across the session.

## 3. Missing Obvious Actions / Best Practices

3.1. [HIGH] **Fix the FileLock exception handling before implementing any of the other recommendations** (source: Phase 2 meta-critique, CRIT-001 from task ledger)

SEC-001 is a data corruption bug in concurrent multi-terminal scenarios. It should be fixed first — it is a pre-existing bug, not a new optimization. The task ledger shows CRIT-001 was previously addressed but the fix is incomplete.

**Concrete fix**: At `evidence_store.py:360`, change `except Exception:` to `except TimeoutError:`. Verify that the fallback (lines 364-373) only runs when `FILE_LOCK_AVAILABLE == False`.

3.2. [HIGH] **Verify actual hook startup latency before implementing lazy regex** (source: Phase 2 meta-critique)

Lazy regex is correct in principle. But the 3-second startup estimate assumes all 605 regex compilations are on the critical path. Hook modules are imported once per session; the actual startup impact may be <500ms. Implementing lazy regex adds code complexity for uncertain savings.

**Concrete fix**: Measure actual import time with `python -X importtime` before committing to the refactor.

3.3. [MEDIUM] **TOCTOU in transcript_path read was identified but no fix was proposed** (source: adversarial-performance, StopHook_skill_execution_gate.py:300)

The transcript file can be deleted between when the path is read and when the file is opened. A try/except around the file read was identified but not included in the recommendations.

**Concrete fix**: Wrap transcript file read in try/except FileNotFoundError in StopHook_skill_execution_gate.py.

## 4. Risks and Edge Cases

4.1. [MEDIUM] **Lazy regex changes module-level API to function-call API** (source: Phase 2 meta-critique)

Existing code references `_FIX_PATTERNS` as a module-level list. Changing to `@cached_property` or a getter function breaks every caller. This is a breaking API change requiring migration of all call sites.

**Edge case**: Backward compatibility requires maintaining the module-level list while also providing lazy initialization — doubling the code.

4.2. [MEDIUM] **Hard timeout creates a new failure mode: premature hook termination** (source: Phase 2 meta-critique)

If a 200ms timeout fires during a legitimate long-running hook (e.g., SQLite query, transcript parsing), the hook terminates mid-execution. Any state the hook was updating could be left in an inconsistent state. This is a new failure mode, not a fix.

**Edge case**: Hook that acquires a lock, times out, releases lock — other terminals proceed with stale assumption about this terminal's state.

4.3. [LOW] **SQLite WAL migration requires data migration from existing JSONL** (source: Phase 2 meta-critique)

If JSONL state is migrated to SQLite, existing data must be migrated. If migration is not done, historical state is lost. Migration during a live session could cause consistency issues.

## 6. Open Questions / Unknowns

6.1. [LOW] **What is the actual hook startup latency?** (source: Phase 2 meta-critique)

The 3s estimate is based on 605 regex compilations × 5ms each. Without measurement, this is an estimate. Actual startup cost may be significantly lower due to Python's regex compilation cache.

6.2. [LOW] **Are hooks actually the user-visible bottleneck?** (source: Phase 2 meta-critique)

No latency profiling was cited for the claim that "200ms timeout is needed." If the bottleneck is elsewhere (LLM inference, network), the timeout fixes the wrong problem.

6.3. [LOW] **How many of the 605 regex patterns are on the startup hot path?** (source: Phase 2 meta-critique)

Modules imported lazily at session start don't contribute to startup latency. The actual number of eagerly-compiled startup patterns may be much smaller than 605.
