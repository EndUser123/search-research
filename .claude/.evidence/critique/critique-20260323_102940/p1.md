## Brief Intent Summary
This ADR+Plan proposes to fix LLM debugging reasoning failures (premature closure, causality drift, self-interference loops) by: (1) deriving RCA-turn detection from existing skill_state metadata in Stop_router.py, (2) adding a new stateless RCA contract gate with 8 structural fields, (3) demoting prose-police hooks for RCA turns while keeping objective guards hard, (4) updating debugRCA.md workflow, (5) deleting the adversarial-rca stub skill. The core insight: replace prose-pattern-matching hooks with mechanically-verifiable structural enforcement.

## Logical Gaps & Inconsistencies
1. **Dead code in activation logic**: The skill_state check at ADR:27 and Plan:168 includes `"adversarial-rca"` but TASK-005 (lines 196-198, 228) mandates deleting adversarial-rca entirely. If the skill is deleted, it can never activate — the condition `skill_state.get("skill") in ("debugrca", "adversarial-rca")` becomes permanently false for the second value. Either adversarial-rca must be KEPT (contradicting the decision), or the activation check must be updated to only match `"debugrca"`. (Plan:168, ADR:27)

2. **ADR and Plan are concatenated without merge**: Lines 1-143 are the ADR; lines 145-367 are the Plan. They contain overlapping but not fully consistent information. The ADR section (line 30) says "delete adversarial-rca skill entirely" but the Plan (line 198) qualifies it with "First, add aliases: [/rca] to debugRCA.md... the alias must be transferred before deletion." These are not reconciled — which is the actual constraint?

3. **8-field schema is asserted but never defined**: ADR:92 claims the RCA contract validates an "8-field response schema" but no document defines what those 8 fields are, their names, or validation logic. The prose describes categories (Symptom, Evidence, Executed Path, etc.) but the exact field boundary between "Root Cause" and "Fix" vs "Verification" is ambiguous — a Root Cause could also be a Fix in some cases.

4. **Verification has circular dependency**: TASK-003 (lines 314-315) creates tests for "RCA turn activation from skill_state" — but those tests require Stop_router.py to already expose skill_state-derived fields, which is exactly what TASK-001 (lines 308-309) is supposed to implement. Tests cannot verify the modification until the modification exists, but the tests are the specified verification for TASK-001.

5. **Hook path claim is repeated inconsistently**: Line 89 and line 100 both state hooks are in the root `P:/.claude/hooks/` "not in the stop/ subdirectory" — but line 51 references "the stop/ subdirectory only contains a subset." This is a precision issue: either stop/ is a subset of the root, or the claim is that ALL Stop hooks are in root. Need actual file listing to verify.

## Hidden Assumptions & Fragile Dependencies
1. **skill_state reliably exposes `skill` field**: The entire activation model depends on `skill_state.get("skill")` being populated by the router. If skill_state schema changes or the field is named differently (e.g., `skill_name`, `active_skill`), the derivation silently fails and no RCA hooks fire. No schema reference cited for skill_state.

2. **adversarial-rca /rca alias is the ONLY /rca routing**: The plan assumes `/rca` maps to adversarial-rca and must be transferred to debugRCA before deletion. But the plan itself notes (line 112) that `/rca` "is handled by orchestrator's skill_router.py which routes to __csf.src.features.rca.rca." This suggests /rca may already route to debugRCA regardless of adversarial-rca's existence. If so, deleting adversarial-rca does NOT break /rca, and the "alias transfer" rationale is unnecessary.

3. **MEMORY.md anti-patterns are "stable"**: The plan appends reasoning rules as "stable anti-patterns" (line 29, line 113) but provides no criteria for what makes an anti-pattern "stable" vs temporary. Rules that are later found to be wrong become technical debt with no removal mechanism specified.

4. **Hook demotion is additive safety, not required for correctness**: The plan treats hook demotions (Phase 3) as part of the solution but doesn't establish what breaks if demotions are incomplete. If step_header_verifier is NOT skipped for RCA turns, does the overall solution still work?

5. **DebugRCA.md update is a single task but has cascading effect**: TASK-004 is scoped as "update debugRCA.md" but the file is the primary human-facing interface for the RCA workflow. Changes to its required output format must match StopHook_rca_contract.py's validation exactly — but there's no verification step ensuring that alignment.

## Missing Obvious Actions / Best Practices
1. **No pre-implementation verification of skill_state schema**: Before committing to skill_state derivation, verify the actual schema of skill_state in Stop_router.py — what fields exist, their types, whether `skill` (or equivalent) is populated for debugRCA turns.

2. **No rollback test for TASK-001**: The rollback section (lines 115-120) restores hook enforcement modes but does not test that restoration actually works. If the rollback is imperfect, the system could be left in a broken state.

3. **No verification that Stop_negative_existence_guard.py actually covers RCA turns**: The ADR claims this hook "already handles" negative-existence for RCA turns (line 28, line 74) but provides no evidence the hook fires during RCA turns. It may be conditioned on something else entirely.

4. **No mention of how debugRCA skill frontmatter looks**: To add `aliases: [/rca]` to debugRCA.md, one must first read debugRCA.md's existing frontmatter. No task for this prerequisite read exists.

5. **No gto/assertion verification step for the ADR itself**: The Constitution requires self-verifying implementations with binary assertions. The ADR proposes a new hook and workflow changes but contains no gto-style assertion verification plan.

## Risks and Edge Cases
1. **skill_state derivation silently fails if field naming is inconsistent**: If the router uses `skill_name` instead of `skill`, or if skill_state is None for certain turn types, rca_turn永远是False. No error, no warning — just completely silent failure of the entire RCA enforcement system.

2. **RCA contract field boundary ambiguity causes compliance disputes**: "Root Cause" and "Fix" fields could overlap (fixing a symptom IS the root cause resolution). If an LLM structures its RCA with Fix embedded in Root Cause, the gate could block a correct analysis on technicality.

3. **adversarial-rca deletion with alias transfer timing risk**: If adversarial-rca is deleted BEFORE the /rca alias is confirmed working on debugRCA, users lose /rca access. The plan's "transfer alias first" sequence is correct but not enforced by any tool-level dependency.

4. **Hook demotion creates two code paths with no migration strategy**: Non-RCA turns use full prose-police enforcement; RCA turns use advisory enforcement. If a turn transitions from RCA to non-RCA mid-session (unlikely but possible), the hook policy switches with no explicit trigger.

5. **Regression fixture uses dead code that may be removed**: The plan (line 215) uses `_read_slash_command_intent_state()` as a regression test case — but this function could be cleaned up in normal maintenance, breaking the test without the test knowing why.

## Concrete Recommendations
1. **Remove `"adversarial-rca"` from skill_state check** (Plan:168) — since adversarial-rca is being deleted, its inclusion in the activation condition is dead code. Change to `skill_state.get("skill") == "debugrca"` or verify if debugRCA skill_name is something else.

2. **Define the 8-field schema explicitly** — Create an enumerated list: (1) Symptom, (2) Evidence, (3) Executed Path, (4) Alternative Hypothesis, (5) Falsifier, (6) Root Cause, (7) Fix, (8) Verification. For each field, specify: required vs optional, what constitutes valid content, what triggers a block.

3. **Add skill_state schema verification as prerequisite task** — Before TASK-001, run a Read on Stop_router.py to confirm skill_state field names and types. This is a 5-minute verification that prevents a fundamental architectural mismatch.

4. **Verify /rca routing BEFORE deleting adversarial-rca** — Confirm current /rca behavior. Only delete adversarial-rca after confirming /rca still functions.

5. **Add debugRCA.md frontmatter read as prerequisite to TASK-004** — Must see current frontmatter before adding aliases field.

6. **Clarify Stop_hook directory structure** — Run `ls P:/.claude/hooks/` and `ls P:/.claude/hooks/stop/` to confirm which hooks live where, then update lines 89-100 to reflect reality.

7. **Add rollback verification task** — After rollback (lines 115-120), explicitly verify hook enforcement modes are restored to original state. Currently rollback is described but not verified.

## Open Questions / Unknowns
1. **What is the actual skill_name for debugRCA in skill_state?** — The plan assumes `"debugrca"` but if the skill uses a different name (e.g., `"debug_rca"`, `"rca"`), activation never fires. No source cited for the exact skill_name string.

2. **Does Stop_negative_existence_guard.py actually fire during RCA turns?** — The claim (ADR:28, Plan:187-188) that it "already handles" RCA turns is asserted but not verified. Need to read the guard's activation condition.

3. **What are the "6 patch fixes" from Sonar that were rejected?** — The ADR references Sonar (lines 14, 42, 62) but the actual fix content is in an external file (`C:\Users\brsth\Downloads\proposal sonar.md`). Without reading that file, we cannot assess whether Sonar was fairly rejected.

4. **Does the 85% confidence rating account for the activation logic bug?** — The confidence (ADR:141, Plan:233) is Tier 2, citing "architectural analysis + dead-code verification." The adversarial-rca activation contradiction is an architectural inconsistency that should lower confidence.

5. **How does the RCA contract gate interface with the existing hook ledger?** — The ADR mentions "turn-scoped metadata" (line 262) but doesn't explain the data flow: does the contract read from the ledger, write to it, or both?

6. **What happens when a non-RCA turn misidentifies itself as RCA?** — If skill_state is corrupted or manually set, could a non-RCA turn receive RCA-level hook demotions, bypassing important prose-police guards?
