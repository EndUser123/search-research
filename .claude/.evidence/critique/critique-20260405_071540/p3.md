The core question: can a PreToolUse layer work within Claude Code's actual hook schema constraints, or is Stop-only the architecturally correct final design?

## Logical Gaps & Inconsistencies

1.1. [BLOCKER] PreToolUse comparative claim guarding is structurally impossible. The PreToolUse schema provides `{tool_name, tool_input, session_id, terminal_id}` — no `current_context` (planned response) and no `tool_history` (accumulated reads). Comparative claim guarding requires comparing "what I am about to say" against "what I have read." This operation is impossible in PreToolUse regardless of implementation approach. (source: adversarial-logic, LOGIC-001)

1.2. [BLOCKER] State file handoff approach is fundamentally broken. PreToolUse fires BEFORE Read completes — the causal chain is backwards. When PreToolUse fires for a Read tool, the state file is empty because Read hasn't executed yet. By the time Read completes and state could be written, the LLM is already drafting, and PreToolUse has stopped firing. (source: adversarial-logic, LOGIC-002)

1.3. [HIGH] False positive risk in Stop hook detection logic. The hook can trigger on long narrative content containing "/" characters, not just file paths. A session recap ~1000 characters with path-like segments triggered a block. The `_is_plausible_path` length check (150 chars) was added reactively but the fundamental detection quality has not been verified against real comparative claim patterns. (source: this session's false positive block)

1.4. [MEDIUM] Severity calibration inconsistency between specialists. adversarial-logic rated LOGIC-001/LOGIC-002 as BLOCKER while adversarial-critic rated ARCH-001 as HIGH. Both reach the same conclusion but use different severity labels — BLOCKER is more appropriate for a structurally impossible feature. (source: p2 calibration analysis)

## Hidden Assumptions & Fragile Dependencies

2.1. [MEDIUM] Plan assumes transcript_path provides reliable cross-turn state. The work mentions "timing issues" with JSONL transcript reading but doesn't verify what Stop actually receives vs what the schema claims. The reliability of transcript_path as an evidence source is assumed, not validated. (source: adversarial-logic, p2 analysis)

2.2. [LOW] Token waste on blocked responses is framed as a significant disadvantage. For high-stakes claims that could cause harm if unchallenged, the reactive model with blocking is acceptable trade-off.

## Missing Obvious Actions / Best Practices

3.1. [HIGH] Add explicit "Irreducible Constraints" section to architecture plans. Identify hard limits early, reducing analysis time on unsolvable approaches. The plan spent significant space analyzing PreToolUse approaches that are fundamentally unsolvable. (source: adversarial-critic, BIAS-001)

3.2. [MEDIUM] Consider PostToolUse state accumulator as alternative approach. Neither specialist fully analyzed PostToolUse-based state accumulation: a PostToolUse hook on Read operations could write what was read to a state file, which Stop could then read for comparative analysis. This is viable (fires after Read completes) but was only mentioned as BLIND-001 with low confidence. (source: adversarial-critic, BLIND-001)

3.3. [LOW] Add detection quality verification. The Stop hook's detection precision vs recall has not been tested against real comparative claim patterns. A test corpus of actual comparative claims (both valid and invalid) would ground the analysis in empirical evidence.

## Risks and Edge Cases

4.1. [MEDIUM] Stop-only fires AFTER response generation (reactive). User sees wrong response before block fires, wastes token generation on content that gets blocked. This is acceptable given the structural impossibility of PreToolUse, but the user experience trade-off should be explicitly acknowledged. (source: adversarial-logic, LOGIC-004)

4.2. [LOW] PostToolUse state accumulator has reliability risks. If the PostToolUse hook fails or the state file becomes corrupted, the Stop hook would have incomplete reading context. Any PostToolUse-based enhancement would need its own failure handling.

## Concrete Recommendations

5.1. [HIGH] Close PreToolUse investigation as not viable. Document that PreToolUse is not viable due to hard schema constraints — no implementation required. The PreToolUse efficiency layer should not be built. (source: adversarial-logic, adversarial-critic consensus)

5.2. [MEDIUM] Test Stop hook detection quality. Create a test corpus of real comparative claim responses (both valid and invalid) and verify precision/recall. The false positive that triggered this session suggests detection quality may need improvement. (source: this session's experience)

5.3. [LOW] Consider PostToolUse_read_state_accumulator.py as future optional enhancement. Not required for the core use case, but could improve Stop hook's per-turn reading context if needed. (source: adversarial-critic, BLIND-001)

5.4. [LOW] Add confidence threshold to minimize token waste. Consider blocking only high-severity comparative claim failures, allowing low-severity cases through with advisory warnings. (source: adversarial-critic, CAL-001)
