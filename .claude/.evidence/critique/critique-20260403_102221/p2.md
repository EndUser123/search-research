# Phase 2 Meta-Critique — /critique self-review

## Cross-Agent Contradictions

1. **COMP-001 vs RISK-006 design intent** — adversarial-compliance says the RuntimeError for pre-fix sessions should be removed and the stale entry should silently fall through to new session creation. However, the original RISK-006 fix was specifically designed to raise RuntimeError to satisfy the pre-mortem's kill criterion: "If Phase 2 glob finds 0 specialist files → fail with explicit error." COMP-001's proposed fix (silent fall-through) would make the pre-fix session silently create a new session with no way to distinguish it from a normal new session — the user's old work is quietly orphaned without warning. The RuntimeError is the correct behavior; the gap is that it prevents ALL session creation for that terminal_id, not just the problematic session.

2. **COMP-002 (stale `last_used` on recovery) vs COMP-001 fix** — COMP-002 identifies that `last_used` is never refreshed on recovery. The COMP-001 proposed fix (pop stale entry + fall through) would create a brand-new session with a fresh `last_used`, which sidesteps the issue. But COMP-002's actual fix (call `_save_registry()` before returning recovered instance) is the right answer for sessions that ARE legitimately resumed. These are complementary fixes for different scenarios, not contradictions.

## Severity Calibration Issues

1. **COMP-004 (Windows path traversal)** — rated MEDIUM but actual exploitability is near-zero. `Path.resolve()` always returns an absolute path with the OS-native separator. `str(resolved_root) + str(Path("/"))` produces `P:\...\.evidence\critique/` on Windows — this is a valid path prefix. A path traversal would need to escape above `P:\` entirely, which `resolve()` prevents. The check is correct on Windows; the only actual risk is if `staging_root` itself is a symlink pointing outside the tree (not the case — it's a constant `Path` literal). Calibration: LOW.

2. **COMP-005 (Windows shell quoting for WORK_INPUT)** — rated MEDIUM but the triggering condition (WORK_INPUT containing spaces or special characters) is rare in practice. The work input is typically a skill name like `/critique` or a file path — neither typically contains spaces. Calibration: LOW.

## Missed Blind Spots

1. **Stale entry corrupts find-or-create oracle without COMP-001 fix** — COMP-001 identifies that RuntimeError blocks ALL session creation, but does not name the specific mechanism: when `sessions.json` has a stale entry (terminal_id points to a deleted/moved session_dir), the next `find_or_create_session()` call hits the RuntimeError and aborts. The entire skill becomes unusable for that terminal. The fix is not just "pop stale entry" — it must be done in the recovery path BEFORE the RuntimeError check, so stale entries are silently cleaned up and normal creation proceeds. Location: `lib/critique_io.py:213` — the RuntimeError is the right sentinel but sits in the wrong place relative to stale-entry cleanup.

2. **No Phase 1 completion gate in SKILL.md** — COMP-003 correctly identifies the Phase 2 zero-specialist gap, but the root cause is earlier: SKILL.md Step 4 says "Wait for all specialist agents to complete before continuing" but never defines what "completed" means in terms of output files. The guard should be at Phase 1 exit, not Phase 2 entry. No specialist flagged this boundary-layer gap.

3. **Interrupted session between p1_findings.md and specialist JSONs** — The recovery validation checks `work.md` and `p1_findings.md` existence but no specialist noted the scenario where: Phase 1 writes `p1_findings.md`, some or all specialist JSONs in `specialists/` were also written, then compaction occurs. On resume, `find_or_create_session()` recovers the session as valid (work.md + p1_findings.md present), but the specialists/ glob in Phase 2 could return a partial set. This is a data-integrity gap — the session appears valid but is actually incomplete. The kill criterion requires "all specialist files" not just "some".

4. **Concurrent terminal_id collision in test** — TEST-001 notes missing Phase 2/3 filename tests, but the adversarial-critic's own concurrent test (`test_critique_io_concurrent.py`) revealed that `_get_terminal_id()` in spawned worker processes resolves to the parent's terminal ID via skill_guard, not the worker's synthetic ID. This is a terminal isolation gap in the test itself — it proves the test infrastructure cannot simulate two concurrent terminals without patching at the module level. No specialist flagged this test infrastructure limitation.

## Precision Failures

1. **COMP-006 (redundant `!=` in path safety check)** — Flagged as a finding, but the `!=` serves as a short-circuit guard: if `resolved_dir == resolved_root`, `relative_to()` would return `.` (not raise), so we explicitly want False in that case. The expression is correct as written, just slightly confusing. Not a real bug.

2. **QUAL-002 (lexical sort in get_recent_sessions)** — The sort uses `sorted(STAGING_ROOT.iterdir(), reverse=True)` on directory names that start with `critique-YYYYMMDD_HHMMSS`. Lexical reverse sort IS chronological reverse sort because the timestamp portion is the entire suffix and SortASCII order equals chronological order for fixed-format timestamps. Not a real bug; low-priority clarity improvement only.

3. **LOGIC-001 (RuntimeError lacks actionable guidance)** — True but minor. The error message says "cannot be resumed" which implies starting over. SKILL.md Step 7 already says sessions persist until manually removed. A documentation note would help but this is not a blocking gap.

## Improvements to the Phase 1 Findings

1. **COMP-001 needs nuance**: The RuntimeError should NOT be removed — it is the correct fail-fast signal for pre-fix sessions. The real fix is to move the stale-entry cleanup earlier in the recovery logic, BEFORE the RuntimeError check, so that genuinely stale entries (pointing to non-existent or incompatible session dirs) are silently cleaned up rather than throwing. Only truly pre-fix sessions that exist but lack `specialists/` should raise.

2. **COMP-002 and COMP-001 interact**: The correct fix for COMP-002 (refresh `last_used` on every recovery) is actually simpler than stated — just call `_save_registry()` before returning at line 224. This is a one-line fix that directly resolves the staleness risk.

3. **Phase 1 completion criteria should be named**: The gap behind COMP-003 (zero-specialist silent failure) stems from unnamed Phase 1 completion criteria. SKILL.md should define: "Phase 1 is complete when at least one specialist JSON exists in `specialists/` AND `p1_findings.md` exists."
