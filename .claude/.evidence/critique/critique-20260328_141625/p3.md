## Intent Summary

The ADR proposes a three-phase architecture fix for the intelligence-stream pipeline's fragmentation problem: three isolated deduplication stores (`.ingested_ids`, `batch_status.sqlite`, `transcript_cache.sqlite`) with no unified view, and a pipeline disconnect where `csf-ingest --analyze` calls `csf-analyze` sequentially as a subprocess rather than through `batch_status`-controlled parallel processing. The decision is Option C (immediate pipeline composition) + Option A (full source registry later), with a three-tier enumeration strategy (RSS → YouTube Data API with `publishedAfter` cursor → yt-dlp fallback) for channel monitoring.

## 1. Logical Gaps & Inconsistencies

### 1.1 [CRITICAL] Phase 1 transcript cache reuse is unimplementable as described
**Source:** adversarial-compliance §1 [HIGH], adversarial-critic META-018

The ADR states at line 198: *"check transcript_cache via list_cached_transcripts(video_id)"*. The actual API at `cache.py:283` is:

```python
def list_cached_transcripts(lang: str | None = None) -> list[TranscriptCache]:
```

This function takes only `lang`, not `video_id`. There is no `has_cached_transcript(video_id)` function. The `analyze_video()` function at `csf-analyze:481` has no cache integration whatsoever — it calls `get_youtube_transcript()` directly every time.

**Impact:** Phase 1 item 3 cannot be implemented as written. Three things must be added: (a) `has_cached_transcript(video_id) -> bool` in `cache.py`, (b) `analyze_video_with_transcript(transcript)` variant, (c) integration in `analyze_videos_parallel()` to check cache first. None of these exist.

**Citation:** `cache.py:283`, `csf-analyze:481`

---

### 1.2 [HIGH] Gap resolution algorithm — unbounded quota consumption, not infinite loop
**Source:** adversarial-critic META-004 [CRITICAL], confirmed by meta-critique Phase 2 verification

The gap resolution loop (ADR lines 139-147) has no quota monitoring. The adversarial-critic called this "infinite loop potential" — but YouTube has a hard ceiling of ~5M videos per channel. The actual risk is **unbounded quota consumption**: the algorithm keeps fetching until overlap is found, and if API results are erroneous or the channel has unusual upload patterns, quota exhausts silently with no user notification.

**Impact:** Silent failure. User sees zero new videos for a channel with no indication that quota was exceeded.

**Citation:** ADR:129-148

---

### 1.3 [HIGH] Option C correctness claim is inconsistent with Phase 1 scope
**Source:** adversarial-critic META-013, META-011

Decision driver says "Correctness: Never redownload..." (ADR:32) and favors Option A for this reason. But the Decision (ADR:83) picks Option C, which the ADR itself acknowledges is "Incomplete (no channel-level enumeration)" (ADR:77). Phase 1 adds a `source` column and changes the subprocess call — it does not unify the three stores. Correctness is promised in the driver but deferred to Phase 3.

**Impact:** User adopts this ADR expecting correctness guarantees that Phase 1 does not deliver.

**Citation:** ADR:32, 77, 83, 85-89

---

### 1.4 [HIGH] `mark_complete(video_id, source=...)` does not exist
**Source:** adversarial-compliance §1 [HIGH]

The ADR describes at line 194: *"New public API: mark_complete(video_id, source=...), get_source(video_id)"*. The actual function at `batch_status.py:137`:

```python
def mark_complete(video_id: str, db_path: Path | None = None) -> None:
```

Takes `video_id` and `db_path` only. No `source` parameter. No `get_source()` function exists.

**Impact:** This is a new API to be created (not a modification), but the ADR presents it as if it were a modification to an existing function.

**Citation:** `batch_status.py:137`

---

### 1.5 [HIGH] Gap detection TOCTOU race — two terminals can queue duplicate video_ids
**Source:** adversarial-critic META-002

The gap detection algorithm (ADR:129-148) performs `result_ids ∩ batch_status_videos` check, then a write, with no locking. Two terminals running `csf-source check` simultaneously on the same channel can both detect the same gap and queue the same video_ids.

**Impact:** Duplicate processing for overlapping video_ids. Wastes API quota and Gemini calls.

**Citation:** ADR:35, 129-148

## 2. Hidden Assumptions & Fragile Dependencies

### 2.1 [MEDIUM] 7-day gap detection threshold has no empirical justification
**Source:** adversarial-critic META-001, adversarial-compliance §3

The gap detection trigger (ADR:114-119) uses `> 7 days ago` with no documented rationale. Why 7 and not 5, 10, or 14? The threshold determines when API gap resolution (which costs quota) is triggered.

**Fragile dependency:** If channel upload frequency differs from the assumption, this threshold causes either false positives (unnecessary API calls) or false negatives (missed gaps).

**Citation:** ADR:114-122

---

### 2.2 [MEDIUM] `channel_metadata` table schema never formally defined

The ADR references `channel_metadata(channel_url, last_checked, last_full_enumeration, video_count_estimate)` at line 244 but no `CREATE TABLE` statement appears anywhere in the Implementation Changes section.

**Fragile dependency:** The Phase 2 implementation will define this schema ad-hoc, risking inconsistency with what the ADR assumes.

**Citation:** ADR:244

**Source:** adversarial-critic META-003

ADR line 235 claims *"atomic write only on full success"* for `.ingested_ids`. No implementation citation provided. Plain `open(path, 'a')` append is not atomic on crash.

## 3. Missing Obvious Actions / Best Practices

### 3.1 [HIGH] Phase 1 scope must be revised — two and only two paths
**Source:** adversarial-compliance synthesis

The Phase 1 implementation has three items. Item 3 (transcript cache pre-check) requires APIs that don't exist and behavior that isn't in the code. **Two paths:**

**Path A — Narrow Phase 1:** Only items 1 (add `source` column) and 2 (ingest calls `analyze_videos_parallel()`). Defer transcript cache reuse to Phase 1b with proper API design. This is the minimal immediate fix.

**Path B — Expanded Phase 1:** Add items to Phase 1: (a) `has_cached_transcript(video_id)` to `cache.py`, (b) `analyze_video_with_transcript()` variant, (c) modify `analyze_videos_parallel()` to check cache first. Phase 1 becomes non-minimal but complete.

Either path must be chosen explicitly.

---

### 3.2 [HIGH] Gap resolution algorithm needs explicit iteration bound
**Source:** adversarial-critic META-005

The algorithm refetches using the oldest result's `publishedAt` as the new cursor. For a channel with irregular upload patterns (e.g., 10 videos from 6 months ago, then nothing for months, then recent uploads), the cursor can move in unexpected ways. Add max 20 iterations (1000 videos = reasonable channel ceiling) and a `publishedBefore` upper bound.

**Citation:** ADR:139-147

---

### 3.3 [MEDIUM] `csf-source` CLI interface must be fully specified before Phase 2
**Source:** adversarial-critic META-007

The ADR lists command names (`add`, `list`, `check`, `sync`) but not behavior: no `--dry-run`, `--limit`, output format, exit codes, or error handling. This is a specification before implementation requirement.

**Citation:** ADR:202-208

---

### 3.4 [MEDIUM] Add API quota tracking with warning threshold
**Source:** adversarial-critic META-004 (refined from CRITICAL to HIGH)

Before Phase 2 ships: add per-request quota cost tracking. Warn user when quota remaining < 20%. Document what happens on quota exhaustion (log + surface to user, not silent).

**Citation:** ADR:34

## 4. Risks and Edge Cases

### 4.1 [MEDIUM] Phase 1 `source` column migration — existing rows get NULL
**Source:** adversarial-compliance §4

`ALTER TABLE analysis_status ADD COLUMN source TEXT` means all existing rows have NULL source. The ADR doesn't specify whether this is acceptable or whether existing rows should be backfilled (how?).

**Risk:** Source queries return NULL for all historical videos until backfilled.

**Citation:** ADR:190-194

---

### 4.2 [MEDIUM] Concurrent `csf-source check` on same channel — write contention on `channel_metadata.last_checked`
**Source:** adversarial-compliance §5

If two terminals run `csf-source check` on the same channel simultaneously, both write `last_checked = now()`. No WAL-mode discussion for the new table.

**Citation:** ADR:244

---

### 4.3 [MEDIUM] Option C correctness deferred — Phase 3 may never happen
**Source:** adversarial-critic META-011

Phase 3 is *"evaluate whether to unify stores"*. Phase 3 is deferred indefinitely. The correctness problem the ADR identifies will persist until Phase 3 is executed. If Phase 3 is never executed, the federated three-store model remains the permanent state.

**Citation:** ADR:89

---

### 4.4 [MEDIUM] Tier 3 triggered by "fewer videos than expected" not by API failure
**Source:** adversarial-critic META-014

API-first policy (ADR:33) but Tier 3 is triggered when *"API returns fewer videos than expected"* (ADR:107). If a channel has 500 videos and API returns 450 due to API visibility limits, Tier 3 kicks in — penalizing API for its inherent limitations rather than for actual failures.

**Citation:** ADR:33, 107-109

---

### 4.5 [MEDIUM] `--force` behavior on partial video files not defined
**Source:** adversarial-critic META-015

ADR line 36 claims idempotent restart via `--force`. But the video file state on interrupt (partial download) is not described: overwrite? append? delete? No mention.

**Citation:** ADR:36, 235

## 6. Open Questions / Unknowns

### 6.1 [LOW] What happens when `publishedAfter` cursor is newer than all channel videos?
**Source:** adversarial-critic META-005 (edge case)

If `newest_downloaded_video.publishedAt` is actually the most recent video in the channel (channel went inactive), `playlistItems.list(publishedAfter=cursor)` returns all channel videos with no overlap, cursor moves to oldest fetched... and we're fetching the entire history. Does this loop until we've fetched everything? Until max-iterations? No specialist analyzed this.

---

### 6.2 [LOW] Transcript cache staleness — YouTube transcript immutability assumption
**Source:** adversarial-critic META-018 (precision refinement)

YouTube transcripts are generally immutable post-upload. Are there documented cases of transcript edits on published videos? If transcripts are immutable, `cached_at` freshness tracking is unnecessary complexity. If not, freshness validation is needed.

---

### 6.3 [LOW] Test matrix completeness — missing concurrent check test
**Source:** meta-critique Phase 2

No test for two terminals simultaneously running `csf-source check` on the same channel. This is the TOCTOU race scenario from H-5.
