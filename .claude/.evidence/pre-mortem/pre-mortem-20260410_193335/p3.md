# Pre-Mortem: git/sync.py Destructive Git Guard Fix

## Intent Summary

The `/git` skill uses `subprocess.run()` internally to execute git commands, bypassing the PreToolUse hook pipeline entirely. This fix adds a skill-level `_check_destructive_git()` guard that intercepts CRITICAL-level destructive git operations before they reach the subprocess layer, closing the gap where PreToolUse hooks cannot see skill-internal subprocess calls.

## Logical Gaps & Inconsistencies

1.1. [CRITICAL] **Severity filter gap — only CRITICAL blocked, HIGH operations pass through**

`sync.py:181` checks `danger["severity"] == "CRITICAL"` but `git clean -fd` and `git stash drop/clear` are classified `severity="HIGH"` in `git_guard_config.py`. The `_check_destructive_git()` function detects them correctly but enforcement at line 181 ignores them.

- **Evidence:** `sync.py:181` — `if danger and danger["severity"] == "CRITICAL":`
- **Impact:** `git clean -fd` (delete untracked files + directories) bypasses the skill-level guard entirely. PreToolUse handles direct user commands but cannot see skill subprocess calls. The skill guard was added as defense-in-depth but has a gap — HIGH ops go through.
- **Verification:** `git_guard_config.py:33-44` defines clean with `severity="HIGH"` and stash with `severity="HIGH"`.

1.2. [HIGH] **Fallback data structure mismatch — unreachable but broken by design**

`sync.py:32-36` defines fallback as dict with `{"danger_flags": ("--hard",), "severity": "CRITICAL"}` but lines 136-137 access `op.danger_flags` as dataclass attribute. If the import ever fails, the fallback activates and immediately crashes with `AttributeError: 'dict' object has no attribute 'danger_flags'`.

- **Evidence:** `sync.py:136-137` — `danger_flags = op.danger_flags or ()` (attribute access on expected DangerOp dataclass)
- **Impact:** The fallback is dead code that would silently crash if triggered. Since the import succeeds reliably, this is not a runtime issue but is a design smell.
- **Note:** Tests at `test_destructive_git_guard.py` exist and pass — confirming the import path works.

## Hidden Assumptions & Fragile Dependencies

2.1. [MEDIUM] **Hook adds operations not in shared config — inconsistent protection levels**

`PreToolUse_destructive_git_guard.py` adds `pull` and `rebase` at MEDIUM severity locally. These are NOT in the shared `DESTRUCTIVE_GIT_OPS`. The skill only references the shared config, so hook-specific additions are not blocked by the skill guard.

- **Evidence:** `PreToolUse_destructive_git_guard.py:64-84` — local DESTRUCTIVE_OPS dict with pull/rebase
- **Impact:** If a user invokes `git pull` or `git rebase` directly, the hook blocks it (MEDIUM). But if the skill's `run()` function called these internally, the skill guard would not block them (since they're not in shared config). This is acceptable because pull/rebase are not truly destructive in the same sense as reset --hard — but the inconsistency exists.
- **Status:** Informational — not a bug but documented as design choice.

2.2. [MEDIUM] **`_BlockedResult.check_returncode()` raises on blocked result**

`_BlockedResult.check_returncode()` at `sync.py:168-170` raises `subprocess.CalledProcessError` when `returncode != 0`. Since `_BlockedResult` always sets `returncode = 1` (failure), any caller that invokes `.check_returncode()` on a blocked result will get an exception.

- **Evidence:** `sync.py:162-166` — `_BlockedResult.returncode = 1`, `sync.py:168-170` — `check_returncode` raises if `returncode != 0`
- **Impact:** If a caller does `result = run(cmd); result.check_returncode()`, a blocked command triggers an exception. The normal use pattern in `sync.py` doesn't call `.check_returncode()` directly on the result, so this doesn't trigger in practice.
- **Blind spot caught by Phase 2 meta-critique** — not caught by specialists.

2.3. [MEDIUM] **Same architectural gap exists in other skills**

The fix is narrowly scoped to `sync.py`. If other skills use `subprocess.run()` internally with git commands, they have the same gap — PreToolUse cannot see their subprocess calls. The fix establishes a pattern but doesn't generalize it.

- **Evidence:** `sync.py` is the only skill with this guard currently.
- **Impact:** Future skills with similar patterns would need similar guards.

## Risks and Edge Cases

4.1. [MEDIUM] **`git rev-list --count` assumes remote/branch exists**

`get_repo_status()` at `sync.py:366` calls `git rev-list --count origin/{branch}..HEAD` without checking if the remote or branch still exists. Non-zero returncode is treated as zero commits ahead.

- **Evidence:** `sync.py:366-376`
- **Impact:** Local commits exist but reported as "up-to-date" if remote branch was deleted. Silent incorrect status.

4.2. [LOW] **MAIN_ROOT path not validated before use**

`MAIN_ROOT = Path("P:/")` at `sync.py:60` is not checked to exist before `rglob('.git')`. If the drive is unmounted, all repos are silently missed.

- **Evidence:** `sync.py:60`
- **Impact:** Silent failure — no error raised, script proceeds assuming no repos.

4.3. [LOW] **Bare `except ImportError:` swallows failures**

Line 30 catches all ImportError silently. A more specific exception or logging would help diagnose import path issues.

## Concrete Recommendations

5.1. [HIGH] **Change severity check at `sync.py:181`**

```python
# From:
if danger and danger["severity"] == "CRITICAL":
# To:
if danger and danger["severity"] in ("CRITICAL", "HIGH"):
```

This is the primary surgical fix. Blocks both CRITICAL and HIGH destructive operations.

5.2. [MEDIUM] **Add HIGH severity `run()` blocking test**

Add `test_run_blocks_clean` and `test_run_blocks_stash_drop` to `test_destructive_git_guard.py` to verify that `run()` blocks HIGH severity operations after the fix.

5.3. [MEDIUM] **Remove the broken fallback at `sync.py:32-36`**

Since the import works reliably, the fallback is dead code. Remove it and replace with an assertion that fails fast if the config structure ever changes:

```python
from __lib.git_guard_config import DESTRUCTIVE_GIT_OPS
assert hasattr(DESTRUCTIVE_GIT_OPS["reset"], "danger_flags"), "git_guard_config structure changed"
```

5.4. [LOW] **Add existence check for MAIN_ROOT**

```python
if not MAIN_ROOT.exists():
    print("ERROR: P:/ drive not accessible", file=sys.stderr)
    sys.exit(1)
```

5.5. [LOW] **Fix `get_repo_status()` return value on git rev-list failure**

Return `(has_remote, -1)` when `ahead_result.returncode != 0` to indicate unknown status.
