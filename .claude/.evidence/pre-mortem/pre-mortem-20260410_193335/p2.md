## Missed Blind Spots

1. **The hook itself cannot see skill subprocess calls** — None of the specialists explicitly called out the architectural gap this fix was meant to address: the PreToolUse hook is bypassed by definition for skill-internal `subprocess.run()`. The fix adds a skill-level guard, but what about OTHER skills that also use subprocess internally? This fix is narrowly scoped to sync.py — if another skill has the same pattern, it has the same gap.

2. **`_BlockedResult` interface mismatch**: The specialists found the severity gap and the fallback issue, but missed that `_BlockedResult.check_returncode()` raises `subprocess.CalledProcessError` if `returncode != 0`. Callers of `run()` that call `.check_returncode()` will get an exception — but `run()` returning `_BlockedResult` for a blocked command means `returncode == 1` (failure), and `check_returncode()` on a blocked result would raise. This is a subtle but real issue.

3. **Worktree operations not covered by guard**: `git worktree add` is listed as CREATIVE_OPS in the hook (with `-b` flag as danger flag), but the skill's `sync.py` has `worktree_add()` and `worktree_remove()` functions that call `run(["git", "worktree", "add", ...])`. The skill guard doesn't cover worktree operations at all.

## Improvements to the Phase 1 Findings

1. **Add architectural context**: The Phase 1 findings should explicitly note that this fix closes a specific gap (skill-internal subprocess calls bypass PreToolUse) and that the same gap may exist in other skills. This frames why the severity gap is critical — because PreToolUse can't see these calls at all.

2. **Distinguish "defense-in-depth" from "gap"**: The HIGH severity ops (clean, stash) ARE blocked by the PreToolUse hook when invoked directly. The skill-level guard is an additional layer. The Phase 1 framing treats this as if nothing is blocking HIGH ops — but the hook does block them for direct user commands. The skill guard is defense-in-depth. The issue is that the skill bypasses the hook AND the skill guard doesn't fully compensate.

3. **Recommend the minimal fix first**: Change severity check from `== "CRITICAL"` to `in ("CRITICAL", "HIGH")`. This is the surgical fix. Changing severity classifications in shared config affects the PreToolUse hook and is broader scope. Recommend the skill-level fix first.
