The work adds a content-match fallback (`_claim_matches_tool_output`) to the stop hook's `_should_block_claim` function to resolve false positives when a claim's text appears in tool output but the target file path wasn't in the claim's targets list. A SILENT verdict (no path-matched evidence) now triggers a secondary check: if the claim's text or key terms appear in any tool event output from the current turn, the claim passes instead of being blocked.

## Logical Gaps & Inconsistencies

### 1.1 [MEDIUM] Cross-target verification bypass (source: adversarial-compliance, engine.py:631-643)

The fallback matches claim text against ANY tool event output without checking whether the event's command/output relates to the claim's targets. A claim "X was blocked by hook Y" could be verified by output about an unrelated tool that happened to contain the words "blocked" and "hook" — even if hook Y was never involved. The `claim.targets` field is never consulted in the fallback.

**Impact:** False positives possible when claim text is generic enough to appear in unrelated tool output.

**Fix:** Before accepting a content match, verify at least one of the claim's targets appears in the event's command/output context.

### 1.2 [MEDIUM] Stopword set is incomplete (source: adversarial-logic, engine.py:621-627)

Common function words not in the stopword set: 'if', 'else', 'when', 'then', 'also', 'any', 'all', 'both', 'none', 'every', 'each'. A claim containing these words could produce false subset matches against unrelated output containing the same terms.

**Impact:** Minor for typical claims, but could cause spurious matches for claims with many common function words.

**Fix:** Extend stopword set with additional common function words, or require a higher match threshold for claims with many short terms.

### 1.3 [LOW] Empty claim text returns True (source: adversarial-logic, engine.py:617)

If `claim.text` is empty string, `claim_text = ''` and `'' in output` returns True for any non-empty output. This is extremely unlikely in practice (claims with empty text would have empty `key_terms` and the subset match would also fail), but the guard is trivial to add.

**Fix:** Add `if not claim.text.strip(): return False` at the top of `_claim_matches_tool_output`.

## Risks and Edge Cases

### 4.1 [MEDIUM] SILENT verdict conflates two distinct causes

`verdict.status == SILENT` can mean:
- **Cause A:** No tool events were used at all → should block confident claims
- **Cause B:** Tool events were used but no target path matched → fallback is appropriate

The current code treats both causes identically. Cause A should block; Cause B should try the fallback. If loaded_events is empty, the condition `loaded_events` short-circuits (empty list is falsy) and the fallback is skipped — correctly handling Case A. But this is implicit. The distinction would be clearer if made explicit with a named flag or comment.

### 4.2 [LOW] Subset match threshold not proportional to claim length

A 3-word claim requires all 3 terms (100% match). A 20-word claim also requires only 3 terms (15% match). This asymmetry could allow short generic claims with 3 common non-stopword terms to match unrelated output.

**Fix:** Consider a proportional threshold: `ceil(len(key_terms) * 0.5)` or at minimum require at least 50% of key terms to match.

## Concrete Recommendations

### 5.1 [MEDIUM] Add target pre-check before content match fallback

In `_should_block_claim`, in the SILENT branch, add a check before calling `_claim_matches_tool_output`: scan `loaded_events` to see if any claim target appears in any event's command or output. If not, don't call the fallback — it's not a target-mismatch case.

```python
# Before calling _claim_matches_tool_output:
target_mentioned = any(
    any(target.lower() in str(e.get("command", "")).lower() or target.lower() in str(e.get("output", "")).lower()
        for target in claim.targets)
    for e in loaded_events
)
if not target_mentioned:
    return True  # No target mentioned anywhere → block
```
