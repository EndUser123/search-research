## Logical Gaps & Inconsistencies

### 1.1 [HIGH] Step 3 and Step 4 have circular dependency on directory existence (source: adversarial-quality, adversarial-compliance, p1_initial_review.md:69 vs 71-82)

Step 3 idempotency check reads `{session_dir}/specialists/dispatch_manifest.json` but Step 4 is what creates the `specialists/` directory if absent. If session_dir doesn't exist and setup() wasn't called, Step 3 fails with FileNotFoundError before the defensive mkdir in Step 4 can run. This is a correctness issue — new sessions with uninitialized directories cause early failure.

**Impact:** New pre-mortem sessions on an uninitialized session_dir would fail before any dispatch occurs.

**Fix:** Swap ordering: Step 4 (mkdir) must precede Step 3 (manifest read).

### 1.2 [HIGH] adversarial-qa in specialist table but SKILL.md defines adversarial-rca (source: adversarial-quality, adversarial-compliance, p1_initial_review.md:56)

Line 56 lists `adversarial-qa` as the 7th specialist for failure/RCA dispatch, but the SKILL.md subagent registry defines `adversarial-rca`, not `adversarial-qa`. Dispatching based on this file for RCA-type reviews would try to dispatch a non-existent agent.

**Impact:** RCA-type pre-mortem reviews would fail at dispatch time.

**Fix:** Change `adversarial-qa` to `adversarial-rca` in line 56.

## Hidden Assumptions & Fragile Dependencies

### 2.1 [MEDIUM] Template variable substitution is external and undocumented (source: adversarial-compliance, p1_initial_review.md:9)

The document uses {WORK_FILE}, {session_dir}, {specialist} throughout but provides no in-file substitution mechanism. The document assumes the calling orchestrator (SKILL.md workflow) will pre-substitute these before presenting the file. A developer reading this file as a standalone procedure would not understand it requires variable substitution. The template variables appear at lines 9, 62, 64, 69, 77, 94, 95, 101, 116, 124-127, 172, 174, 246-248.

**Impact:** Developer misunderstanding this as an executable procedure rather than an orchestrator prompt template.

**Fix:** Add a header note: "NOTE: This is an orchestrator prompt template. Variables {WORK_FILE}, {session_dir}, {specialist} must be substituted by the calling workflow before use."

### 2.2 [MEDIUM] Phase 1 Completion Gate cannot enforce itself within this file (source: adversarial-compliance, p1_initial_review.md:241)

Lines 241-255 state "MANDATORY before proceeding to Phase 2" and define failure modes referencing Phase 2, but the gating mechanism is entirely external — enforced by the SKILL.md orchestrator. This file alone cannot prevent a Phase 2 from running if the gate fails. The note is advisory prose with no self-enforcing code.

**Impact:** A triage agent following only this file literally would have no mechanism to actually gate Phase 2.

**Fix:** Add explicit note: "Phase sequencing is enforced by /pre-mortem SKILL.md orchestrator, not this file."

## Missing Obvious Actions / Best Practices

### 3.1 [MEDIUM] Idempotency check logic is split across Step 3 and Step 5c (source: adversarial-compliance, p1_initial_review.md:66 vs 136)

Step 3 (lines 60-68) describes checking for valid JSON and promises complete logic, but the actual JSON validity checking (try/except block) is implemented in Step 5c (lines 136-160). A reader implementing Step 3 literally would not include the validation and would make skip decisions based on file existence alone.

**Impact:** Incomplete implementation of the idempotency check if Step 5c is not also followed.

**Fix:** Add reference in Step 3 to Step 5c, or inline the validation logic in Step 3.

### 3.2 [MEDIUM] No post-dispatch verification for per-specialist completion markers (source: adversarial-critic, p1_initial_review.md:130-134)

The dispatch pattern instructs agents to write completion markers but only verifies them after ALL specialists return (Step 5c / Phase 1 Completion Gate). There is no incremental verification step that detects a partial failure — where an agent writes its JSON but crashes before writing its completion marker — before the consolidation phase.

**Impact:** Low in practice — the Phase 1 Completion Gate catches missing JSONs on resume. But the failure mode (no completion marker) is not distinguished from "specialist not yet dispatched."

**Fix:** Add a per-specialist verification step after each specialist returns, not just after all return.

### 3.3 [LOW] No test corpus validates procedure logic against edge cases (source: adversarial-quality, p1_initial_review.md:29-36)

The procedure describes complex logic (idempotent dispatch, manifest pre-population, conditional skip, completion gate) but has no test scenarios validating behavior against: new session, interrupted mid-dispatch, partial results, complete results.

**Impact:** Flaws in procedure logic are only discovered at runtime.

**Fix:** Create `tests/test_p1_initial_review_procedure.py` with scenarios: fresh session, interrupted dispatch, partial specialists complete, all complete.

## Risks and Edge Cases

### 4.1 [MEDIUM] Step 4 defensive mkdir has tautological condition (source: adversarial-compliance, p1_initial_review.md:73-74)

Line 73-74 says "setup() already creates specialists/ when the session is initialized" but then Step 4 still does a defensive mkdir. The note acknowledges the mkdir is needed "if this step is absent" but doesn't verify that setup() was actually called. The mkdir is safe to call unconditionally (exist_ok=True), but the conditional makes the logic confusing.

**Impact:** Confusion about preconditions; no functional risk since mkdir with exist_ok=True is idempotent.

**Fix:** Remove the conditional around the mkdir — call `mkdir(exist_ok=True)` unconditionally.
