## Missed Blind Spots

1. **Carryover-only render path never tested** — No specialist asked: what happens when `render_actions([])` is called with `carryover=[...]` but zero current-session actions? The do-all footer shows `0 items` (empty actions + carryover items). The footer rendering logic at line 126-129 uses `total = len(actions) + len(carryover)` but the domain sections are skipped when `actions` is empty — carryover gets its own section. This is correct behavior but untested.

2. **Subletter overflow affects carryover items** — LOGIC-001 correctly identified the 26-item overflow in domain groups, but carryover items are numbered starting at `1a` within the carryover section, not within a domain group. The carryover numbering loop at line 117 also uses `chr(ord('a') + idx - 1)` — same overflow applies there.

3. **`render_machine_format` dead code** — `render_machine_format` never iterates `carryover` (TEST-003 correctly flagged this), but no specialist noted the `render_actions` function at line 77 does `carryover = carryover or []` which is correct, while `render_machine_format` at line 200 does the same but then ignores it. The machine format branch was clearly copy-pasted from the text format.

4. **No specialist reviewed `_resolve_options`** — `_resolve_options` at line 166 has `return DEFAULT_OPTIONS` as a dead fallback that can never be reached (all paths above return first). Not a bug, but no specialist caught the dead code.

5. **Domain sort key `-len(actions)` tiebreaker is inverted logic** — `_domain_sort_key` uses `-len(actions)` so domains with *more* items sort first. But domain_num is assigned sequentially (1, 2, 3...) as domains are encountered in sorted order, not by item count. The `-len(actions)` only affects tiebreaking when two domains have the same explicit_order AND same item count (alphabetical tiebreak). This is a very narrow edge case but the logic is confusingly named.

## Precision Failures

1. **TEST-002 dedupe hash collision is theoretically valid but practically unrealistic** — Two action descriptions that share 50 identical prefix characters but diverge after is rare in RNS output. The dedupe key includes `domain|action` prefix which already distinguishes most items. The 50-char description truncation is a defense-in-depth measure, not the primary dedupe mechanism. Rating this HIGH overstates the risk.

2. **LOGIC-003 + LOGIC-004 are the same issue split in two** — Both stem from the `priority_part.replace('high', 'high')` no-op. LOGIC-003 says "it's a no-op" and LOGIC-004 says "priority_part isn't stripped" — but priority_part IS stripped at line 92. These should have been merged into one MEDIUM finding.

3. **TEST-001 (Unicode truncation) scope is renderer, not chain** — The truncation bug is in `render_action_line` and only triggers when `max_description_chars` is set AND the description contains emoji/non-ASCII. All existing tests use ASCII only. This is a genuine issue but the severity (HIGH) seems high for a visual-only bug with a rare trigger condition.

4. **TEST-005 "silently ignores" is factually wrong** — The finding says `format_rns_output` "silently ignores" unknown kwargs. In reality it raises `TypeError` from `RenderOptions(**kwargs)`. That's a crash, not silent ignore. The real issue is poor error message quality, not silent behavior.
