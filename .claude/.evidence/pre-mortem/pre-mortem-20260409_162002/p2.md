## Cross-Agent Contradictions

### 1. No direct contradictions — but divergent framing of same root cause
SEC-001 (SECURITY), LOGIC-001 (LOGIC), and IO-001 (IO) all identify the identical gap: `_skill_guard_path` is created but `.exists()` is never called before the path is inserted into `sys.path`. None contradict each other — they approach the same flaw from different domain lenses.

However, they disagree on severity for what is structurally the same finding:
- **SEC-001: CRITICAL** — frames as arbitrary code execution risk if directory is compromised
- **LOGIC-001: HIGH** — frames as silent fail-open bypass
- **IO-001: HIGH** — frames as path object created but not validated

**Assessment:** The CRITICAL vs HIGH split is not a contradiction but a **calibration issue**. SEC-001's CRITICAL rating requires an attacker to already have write access to `P:/packages/skill-guard/`. For a solo-developer local machine, this is a constrained scenario. LOGIC-001's HIGH (silent bypass → enforcement gap) more accurately reflects the realistic failure mode.

## Severity Calibration Issues

### 1. SEC-001 (CRITICAL) overstates actual risk
**Finding:** `PreToolUse_skill_pattern_gate.py:61` — unvalidated path insertion enables arbitrary code execution if directory is compromised.

**Calibration problem:** The CRITICAL rating assumes P:/packages/skill-guard/ is an attacker-controlled location. For this to be true on a solo-developer machine: attacker already has write access to the filesystem, at which point they have already won. The pre-mortem's own LOGIC-001 correctly identifies the realistic failure mode — the hook fails open silently and enforcement is bypassed.

**Suggested recalibration:** HIGH for the silent bypass pathway (more plausible), CRITICAL only if evidence shows P:/packages/skill-guard/ has weak ACLs.

### 2. LOGIC-001 and IO-001 duplicate each other without cross-citation
Both flag the missing `.exists()` check at the same location (lines 61-66) as HIGH. IO-VALIDATION calls it "IO-001", LOGIC calls it "LOGIC-001". This is not wrong — different specialists can flag the same issue independently — but p1_findings.md should explicitly note they are the same root cause to avoid diluting the finding count.

### 3. SEC-003 (MEDIUM) vs LOGIC-003 (LOW) — inconsistent severity for path separator variance
Both flag the Windows path separator problem ('P:/' vs 'P:\\'). SEC-003 rates it MEDIUM, LOGIC-003 rates it LOW. Neither explains the discrepancy. The actual impact (duplicate sys.path entries) is LOW — MEDIUM overstates it.

## Missed Blind Spots

### 1. QUAL-004 (HIGH) was NOT caught by security, logic, or io-validation specialists
Only adversarial-quality flagged the **second phantom import at line 516**: `from skill_guard.breadcrumb.tracker import _load_workflow_steps` inside `handle_pre_tool_use` with no sys.path guard.

This is a genuine **recall failure**. The security, logic, and io-validation specialists focused on the module-level import (lines 61-66) and never examined the function-body imports. QUAL-004's finding is structurally independent — it would still exist even if SEC-001's fix were applied perfectly.

**Why it matters:** The fix at lines 60-66 only addresses the module-level phantom import. Line 516's import is a separate failure point with no sys.path guard. Workflow step enforcement (Layer 0) can still fail silently via line 516.

### 2. No specialist examined the interaction between module-level sys.path setup and function-level imports
The hook has two execution contexts:
- **Import time:** lines 60-66 run when Python imports the hook file
- **Execution time:** line 516 runs inside `handle_pre_tool_use` when the hook is called

If `handle_pre_tool_use` is invoked in a subprocess (which it is — PreToolUse hooks run as subprocesses), the module-level sys.path setup at import time doesn't persist. Specialists assumed module-level sys.path setup covers all call paths — none examined the subprocess execution model.

### 3. No specialist examined the top-level fail-open handler interaction
The p1 findings note that ImportError propagates to a "top-level fail-open handler at line 762". But none of the specialists examined:
- What actually happens at line 762 when ImportError reaches it
- Whether the fail-open behavior is the correct design choice for this hook
- Whether SEC-001/LOGIC-001's "existence check + resolve()" fix would prevent the fail-open from triggering at all

This is a **second-order effect gap** — specialists analyzed the immediate code but not the broader exception-handling architecture.

### 4. No specialist examined the test file's coverage of the line 516 import
The test file (`test_skill_pattern_gate_coverage.py`) tests the module-level import (lines 60-66) but no test exercises the line 516 import path. This is a test coverage gap, and none of the 4 specialists flagged it.

## Precision Failures

### 1. SEC-001 recommendation is architectural, not a local patch
SEC-001 recommends "ownership validation" and "canonical path verification" before sys.path insertion. This is the right long-term answer but is not a minimal fix for the CRIT-LOGIC-001 patch context. The recommendation reads like it belongs in a security hardening spec, not a pre-mortem of a single-file hook patch.

**Why it matters:** Pre-mortem findings are meant to be actionable. A recommendation to "add canonicalization + ownership validation" on a hook that was failing to import a package is over-engineering for the immediate fix scope.

### 2. QUAL-002 and QUAL-001 are the same finding expressed differently
QUAL-002: "hardcoded absolute path instead of __file__-derived path"
QUAL-001: "sys.path pattern inconsistent with other hook files"

Both recommend changing line 61 from hardcoded `'P:/packages/skill-guard/src'` to a `__file__`-derived path. QUAL-001 calls it an inconsistency problem; QUAL-002 calls it a fragility problem. These should have been merged into a single finding.

### 3. LOGIC-002's recommendation is overly complex
LOGIC-002 recommends adding local exception handling around the skill_guard.skill_auto_discovery import at line 66. But this import is already inside a try/except at the module level (the overall hook has a top-level exception handler). Adding nested exception handling would complicate the code without addressing the root cause (the path doesn't exist → fix the path).

## Improvements to Phase 1 Findings

### 1. Cross-specialist deduplication
SEC-001, LOGIC-001, IO-001 should have been flagged as "same root cause, three domain perspectives" in p1_findings.md. This would have reduced 3 findings to 1, focusing attention on QUAL-004 which was the only genuinely new issue.

### 2. Execution model analysis missing
Phase 1 should have explicitly analyzed: "PreToolUse hooks run as subprocess via `subprocess.run([sys.executable, hook_path])`". This changes the threat model for SEC-001 (arbitrary code execution requires compromising a directory in a subprocess, not the parent process) and explains why line 516's import is a separate failure point.

### 3. The "CRIT-LOGIC-001" label should not influence severity inflation
The pre-mortem was explicitly of the "CRIT-LOGIC-001 fix". This framing may have caused specialists to inflate severity to justify "this was a critical logic bug". The findings should be rated on actual impact, not on the prestige of the bug they are reviewing.

### 4. Missing adversarial-testing specialist
For a fix that touches sys.path manipulation and import logic, `adversarial-testing` would have been the right specialist to catch: "does any test exercise the line 516 import path?" None of the 4 dispatched specialists are focused on test coverage analysis.
