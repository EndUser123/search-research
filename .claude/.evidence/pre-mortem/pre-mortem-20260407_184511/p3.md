## Hidden Assumptions & Fragile Dependencies

### CRITICAL: systemContext is Not a Framework Feature (Blind Spot #1)
**Assumption:** The fix uses "systemContext" as a dict key that the Claude Code framework recognizes and handles specially (internal-only context hidden from users).

**Reality:** UserPromptSubmit.py (lines 307-317) only recognizes "replacePrompt" and "additionalContext" keys. The "systemContext" key falls through to the else branch and is treated identically to additionalContext — meaning content is **NOT hidden from users**.

**Evidence:**
```python
# UserPromptSubmit.py lines 307-317
if isinstance(res.context, dict) and "replacePrompt" in res.context:
    replacement_prompt = res.context["replacePrompt"]
    # ...
elif isinstance(res.context, dict) and "additionalContext" in res.context:
    injections.append(res.context["additionalContext"])
else:
    injections.append(res.context)  # systemContext falls through here
```

**Impact:** The fix likely does not achieve its stated purpose. The enumeration content remains visible to users.

**Source:** P:/.claude/hooks/UserPromptSubmit.py:307-317 (Tier 1 evidence)

### MEDIUM: Breaking Change Without Consumer Verification
**Assumption:** Changing HookResult.context from str to dict is safe because the HookResult API supports both types.

**Reality:** While the HookResult contract technically supports both str and dict, the specific "systemContext" key is not recognized by consumer code. Unknown consumers may crash with AttributeError when attempting to call .format() or .replace() on a dict.

**Evidence:** LOGIC-001 (MEDIUM), TEST-006 (MEDIUM) — both specialists identified this as a breaking change risk.

**Impact:** Potential runtime errors in downstream consumers that expect string context.

### LOW: Token Count Estimation Unverified
**Assumption:** LOGIC-002 claims "~20% underestimation due to JSON overhead" but no specialist verified this with actual measurement.

**Reality:** JSON overhead for `{"systemContext": "..."}` is minimal (~35 chars fixed overhead), making the 20% figure questionable.

**Impact:** Low severity (token counts are estimates anyway), but demonstrates unverified claim propagation.

## Risks and Edge Cases

### CRITICAL: Fix May Not Achieve Stated Purpose
**Risk:** Users continue seeing "SKILL EVALUATION REQUIRED" enumeration despite the fix.

**Evidence:** UserPromptSubmit.py does not distinguish systemContext from additionalContext (QUAL-003, QUAL-004, Blind Spot #1).

**Likelihood:** HIGH — framework doesn't support systemContext as a special key.

**Mitigation:** Either add systemContext handling to UserPromptSubmit.py OR use the existing additionalContext contract and accept that content is user-visible.

### HIGH: Unknown Consumers May Crash (LOGIC-001)
**Risk:** Downstream consumers expecting string context may fail with AttributeError when receiving dict.

**Example:** Consumer code calling `context.format()` or `context.replace()` on a dict will crash.

**Likelihood:** MEDIUM — unknown number of consumers, unknown robustness.

**Mitigation:** Add isinstance checks in consumers OR revert to string context OR add regression tests.

### MEDIUM: Framework Does Not Distinguish System vs User Context
**Risk:** The Claude Code framework may not have a concept of "system-only" context that is hidden from users.

**Evidence:** Only "replacePrompt" and "additionalContext" keys are recognized (Blind Spot #1).

**Likelihood:** HIGH — based on code inspection of UserPromptSubmit.py.

**Mitigation:** Verify framework documentation OR implement systemContext handling in UserPromptSubmit.py OR accept that all context is user-visible.

### LOW: Token Count Underestimation (LOGIC-002)
**Risk:** Token budget calculations may be slightly inaccurate due to JSON overhead.

**Likelihood:** LOW — token counts are estimates anyway, and fixed overhead is minimal (~35 chars).

**Mitigation:** None required (low impact).
