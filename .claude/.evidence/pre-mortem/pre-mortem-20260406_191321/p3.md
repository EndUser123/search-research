## Intent Summary

On-error stale bytecode cleanup retry logic in `hook_importer.py`: When `load_hook()` fails with `ImportError` or `SyntaxError`, the implementation clears stale `.pyc`/`.pyo` bytecode files and retries the import once before failing. This resolves hook import failures in multi-terminal environments where cached bytecode can become stale.

## Logical Gaps & Inconsistencies

1.1. [HIGH] Silent retry failure masking: The bare `except Exception:` at line 233 swallows any exception raised during retry without logging or preserving it. The original exception from line 209 is always what gets reported — if retry fails for a *different* reason than the initial failure, that reason is never exposed. This makes debugging retry failures difficult since the logged error always describes the original failure. (source: adversarial-logic, hook_importer.py:233)

1.2. [MEDIUM] Control flow reliance on fall-through: The retry logic depends on implicit fall-through from the inner except block (line 233) to the _log_anomaly call (line 238). This is fragile — a future maintainer could "improve" the bare except by adding `raise` or removing the fall-through, not realizing it would break the retry-also-fails path. (source: adversarial-logic, hook_importer.py:233-238)

## Hidden Assumptions & Fragile Dependencies

2.1. [MEDIUM] Retry always improves state: Assumes that clearing .pyc/.pyo files will fix the import error. This is true for stale bytecode but not for structural import errors (missing dependencies, syntax errors in source). If the initial ImportError is caused by a missing dependency that exists in source but not bytecode, retrying after bytecode cleanup won't help — but the retry will fail again, silently masking that the cleanup was pointless. (source: adversarial-logic)

2.2. [LOW] TOCTOU in _clear_hook_bytecode: `pycache_dir.exists()` check at line 167 followed by iteration. If another process deletes `__pycache__` between check and loop, `FileNotFoundError` could be raised and caught by the outer except, preventing retry. Low risk since multi-process hook loading is uncommon. (source: adversarial-io-validation, hook_importer.py:167-171)

2.3. [LOW] No thread safety on _cache: `load_hook()` writes to `self._cache` without locking. Concurrent calls from multiple threads could cause cache corruption. However, Claude Code's hook runner executes hooks sequentially in the same process, so this is unlikely in practice. (source: adversarial-testing, hook_importer.py:188)

## Missing Obvious Actions / Best Practices

3.1. [HIGH] test_retry_on_import_error_after_bytecode_cleanup doesn't test retry: The test verifies cleanup is NOT called on successful first load, but never triggers the retry path. The retry mechanism has never been exercised by the test suite — a broken retry would pass all tests. (source: adversarial-testing, test_hook_bytecode_cleanup.py:100)

## Risks and Edge Cases

4.1. [MEDIUM] Wrong error reported when retry fails differently: If initial failure is ImportError (missing dependency in .pyc) and retry fails with SyntaxError (source has syntax error), the logged error will describe the retry's SyntaxError while the actual root cause was the .pyc's missing dependency. User sees "syntax error in hook" when the real issue is "missing dependency that was added to source but not .pyc". (source: adversarial-logic)

4.2. [LOW] Retry with no __pycache__: If the hook has never been imported before (no .pyc exists), `_clear_hook_bytecode()` does nothing and retry will fail the same way. This is correct behavior but worth noting. (source: adversarial-io-validation)

## Concrete Recommendations

5.1. [MEDIUM] Log the retry exception before swallowing it: Add `retry_error = None` before the retry block, capture `retry_error = e` in the inner except, and log it alongside the original error in `_log_anomaly`. This preserves information about why retry failed without changing the exception that's raised. (source: adversarial-logic, hook_importer.py:233)

5.2. [MEDIUM] Add explicit retry failure path comment: Add a comment at line 233 noting the fall-through behavior is intentional and explaining why. Prevents future "improvements" that break the retry-also-fails path.

5.3. [MEDIUM] Split test_load_hook_catches_syntax_error_and_retries into two tests: (1) verify Python ignores stale bytecode naturally, (2) force ImportError via mock and verify retry succeeds. (source: adversarial-testing, test_hook_bytecode_cleanup.py:126)

5.4. [LOW] Consider logging when _clear_hook_bytecode succeeds: Currently silent on success. For debugging, it's useful to know whether cleanup ran. Add a debug-level log entry.

## Open Questions / Unknowns

6.1. [LOW] Is multi-process concurrent hook loading a real scenario? The hooks directory is typically single-process. If yes, TOCTOU in _clear_hook_bytecode becomes more than LOW. (source: adversarial-io-validation)

6.2. [LOW] Should the retry ever succeed if initial failure wasn't bytecode-related? Currently we clear bytecode on any ImportError/SyntaxError, even if caused by source itself. Should we validate that a .pyc actually existed before retrying? (source: adversarial-logic)
