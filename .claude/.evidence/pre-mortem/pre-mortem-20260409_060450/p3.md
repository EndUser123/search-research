## Intent Summary

`log-hook.py` provides a cross-platform Python port of `log-hook.sh`, appending hook events and transcript diffs to a user's `claude-log.jsonl`. It uses a mkdir-based atomic lock with a retry-on-locked wrapper for file reads and writes, and runs as a pre-commit or post-commit hook in Claude Code.

## Health Score: 35%

The work has a coherent design but is critically compromised by two interacting defects: a dead retry in `get_lock()` that makes the locking mechanism unreliable, and error masking in `_retry_on_locked()` that obscures actual failures. The 10-second lock timeout, silent lock-acquisition failure path, asymmetric retry coverage (transcript vs. log writes), and missing test coverage compound the risk. This is not production-ready without fixes.

## Logical Gaps & Inconsistencies

1.1. [CRITICAL] **Dead retry in `get_lock()` — lock acquisition is unreliable.** `Path.mkdir(exist_ok=True)` does not raise `FileExistsError` when the directory already exists; it silently succeeds. The `except FileExistsError:` block (log-hook.py:26) never triggers on collision, so the 50-iteration retry loop (lines 21-27) is unreachable dead code once the lock directory exists. A process that calls `get_lock()` when another process already holds the lock will return immediately with a valid `lock_path`, giving both processes a false sense of synchronization. This is the central design flaw. Source: adversarial-io-validation (IO-001), verified against log-hook.py:19-28.

1.2. [CRITICAL] **Error masking in `_retry_on_locked()` — actual errors are lost.** After all retry attempts exhaust, the function raises `last_err`, which holds the `PermissionError` from the immediately preceding attempt — not the error that actually caused failure on the final attempt. Any `OSError` that is not a `PermissionError` on the final attempt is silently dropped; `last_err` retains the value from the previous attempt's `except` block. This makes diagnosis impossible. Source: adversarial-logic (LOGIC-002), verified against log-hook.py:31-45.

1.3. [HIGH] **`max_attempts=0` raises `None` (TypeError).** If `_retry_on_locked()` is called with `max_attempts=0`, the loop body never executes, `last_err` remains `None`, and `raise last_err` raises `TypeError: raising None`. The function should validate `max_attempts >= 1` and raise `ValueError` for invalid values rather than producing a confusing `TypeError`. Source: adversarial-logic (LOGIC-001), verified against log-hook.py:31-45.

1.4. [HIGH] **Lock acquisition failure silently continues without degraded-state tracking.** `main()` continues all file operations (lines 77-175) even when `get_lock()` returns `None` (lines 69-75). No flag, metric, or path guard records that synchronization is unavailable. Subsequent writes proceed unsynchronized, creating a race window. Source: adversarial-quality (QUAL-004), verified against log-hook.py:69-76 and 77-183.

1.5. [HIGH] **`get_lock()` returns `lock_dir` rather than a unique lock file — race condition between processes.** `get_lock()` returns the lock directory path itself, not a file within it. Two processes that both call `get_lock()` for the same `lock_dir` will both succeed (because `exist_ok=True` makes `mkdir` silently succeed on collision). Each gets the same `lock_path` and both believe they hold the lock. No further coordination distinguishes the holder. Source: adversarial-io-validation (IO-001), verified against log-hook.py:19-28.

## Hidden Assumptions & Fragile Dependencies

2.1. [HIGH] **`TMPDIR` assumed valid and writable — no pre-condition check.** Line 65 uses `os.environ.get("TMPDIR", ...)` without validating that the resulting path is a writable directory. If `TMPDIR` points to an invalid or full path, `get_lock()` will retry 50 times (up to 10 seconds) before returning `None`, wasting resources before the silent failure path. Source: adversarial-io-validation (IO-004), verified against log-hook.py:65.

2.2. [HIGH] **`transcript_path` not validated for Windows reserved names or path traversal.** Line 87 constructs `Path(transcript_path_str)` directly from stdin. A malicious or malformed `transcript_path` value could cause writes to unintended locations (path traversal) or fail silently on Windows reserved names (`CON`, `PRN`, `AUX`, etc.). Source: adversarial-io-validation (IO-005), verified against log-hook.py:86-87.

2.3. [MEDIUM] **`release_lock()` assumes `rmdir` failure is safe to ignore.** Lines 48-54 silently swallow all `OSError` from `lock_path.rmdir()`. This includes scenarios where the lock directory is non-empty (e.g., stale temp files accidentally placed inside it). The silent swallow leaves stale locks on disk, causing future `get_lock()` calls to behave as if a lock is held. Source: adversarial-io-validation (IO-003), verified against log-hook.py:48-54.

2.4. [MEDIUM] **`PermissionError` assumed to cover all WinError 32 cases.** `_retry_on_locked()` only catches `PermissionError`. On some Python builds or configurations, Windows file lock errors may manifest as `OSError` with `winerror=32` rather than `PermissionError`, bypassing the retry entirely. Neither specialist found evidence that this is guaranteed to never happen. Source: adversarial-logic (LOGIC-003) and adversarial-quality (QUAL-003).

## Missing Obvious Actions / Best Practices

3.1. [HIGH] **Retry applied to `transcript_copy` operations but NOT to `log_jsonl` writes — asymmetric failure mode.** Four `log_jsonl` write sites (lines 101-102, 140-141, 159-160, 174-175) use raw `open(...).write()` without `_retry_on_locked()`. If another process holds the file handle, these writes fail immediately with `PermissionError`. The `transcript_copy` writes (line 165) use `_retry_on_locked()`, creating an asymmetry: transcript diffing retries, hook logging does not. Source: adversarial-quality (QUAL-002) and adversarial-io-validation (IO-002), verified against log-hook.py:101-102, 140-141, 159-160, 165, 174-175.

3.2. [HIGH] **No attempt count or structured result from `_retry_on_locked()` — silent failure.** `_retry_on_locked()` raises a bare `PermissionError` after all retries with no indication of how many attempts were made. A caller cannot distinguish an immediate failure from a 5-retry failure that exhausted all attempts. This obscures both transient lock contention and chronic lock contention patterns. Source: adversarial-quality (QUAL-001), verified against log-hook.py:31-45.

3.3. [HIGH] **`release_lock()` failures logged to stderr — not observable from caller.** Even though `release_lock()` swallows `OSError`, it does not emit any diagnostic. The `main()` function has no visibility into whether lock release succeeded. A stale lock is invisible until the next invocation fails to acquire it. Source: adversarial-io-validation (IO-003), verified against log-hook.py:48-54.

3.4. [MEDIUM] **Lock failure does not disable retry for subsequent operations.** When `get_lock()` returns `None` (line 71), `main()` continues and `log_jsonl` writes proceed without any retry protection. Combined with 3.1, the compound failure mode is: lock broken (IO-001) → no synchronization → `log_jsonl` writes have no retry (IO-002) → concurrent writes can corrupt JSONL structure. No specialist connected these two findings into a failure chain. Source: p2.md Cross-Agent Contradictions analysis.

## Risks and Edge Cases

4.1. [HIGH] **Concurrent writes to `log_jsonl` can corrupt JSONL structure.** When two Claude Code instances both proceed past `get_lock()` (which is broken per 1.1), they write to `log_jsonl` simultaneously. On Windows, append mode (`"a"`) does not guarantee atomic write separation at the OS level. Bytes from concurrent writes can be interleaved, producing a malformed JSONL file where lines are corrupted mid-record. This is the actual failure mode if two instances run simultaneously. Source: p2.md Missed Blind Spots #1.

4.2. [MEDIUM] **10-second timeout on invalid `TMPDIR` wastes resources without giving context.** `get_lock()` retries 50 times at 0.2s intervals = up to 10 seconds of blocking per call. If `TMPDIR` is invalid, this retry delay provides no useful purpose — the code should validate the path before entering the retry loop, not wait for all retries to fail. Source: p2.md Missed Blind Spots #2.

4.3. [MEDIUM] **`OSError` with WinError 32 may bypass retry on some Python builds.** `_retry_on_locked()` only catches `PermissionError`. If Windows file lock errors manifest as `OSError` with a different error code on certain Python builds or locales, these would bypass the retry loop entirely, causing immediate failure where retry would succeed. Source: adversarial-logic (LOGIC-003) and adversarial-quality (QUAL-003).

4.4. [LOW] **`write_text` kwargs fragility is theoretical, not current risk.** Line 165 passes `encoding="utf-8"` to `transcript_copy.write_text()`. This is standard and not currently at risk. The concern about method signature changes is valid for long-term maintenance but is not a present reliability issue. Source: adversarial-io-validation (IO-006).

4.5. [LOW] **Stub test provides zero functional coverage.** The test file has zero coverage for retry behavior, lock acquisition, error masking, or concurrent write handling — the core reliability properties of this hook. Source: adversarial-quality (QUAL-005).

## Concrete Recommendations

5.1. [CRITICAL] **Replace `get_lock()` dead retry with a proper atomic lock.** Options: (a) Remove `exist_ok=True`, let `FileExistsError` propagate naturally and retry on that, (b) use `Path.mkdir()` without `exist_ok=True` and catch `FileExistsError` specifically to trigger retry, or (c) use a dedicated lock file with `os.link()` (atomic on POSIX and Windows Vista+) instead of directory-based locking. The current `exist_ok=True` approach makes `mkdir` silently succeed on collision, defeating the retry mechanism. Source: adversarial-io-validation (IO-001), log-hook.py:19-28.

5.2. [CRITICAL] **Fix `_retry_on_locked()` error masking.** On the final attempt, re-raise the actual exception from that attempt, not `last_err` which holds the exception from the *previous* attempt. If the final attempt raises an `OSError` that is not `PermissionError`, that error must not be silently dropped. Consider a `LockRetryExhausted` exception that wraps `attempts, last_error` for structured diagnostics. Source: adversarial-logic (LOGIC-002), log-hook.py:31-45.

5.3. [HIGH] **Apply retry to ALL `log_jsonl` writes consistently.** Create an `_append_log()` helper that wraps file writes with `_retry_on_locked(open(...).write)` or use the retry wrapper consistently at all four write sites (lines 101, 140, 159, 175). Do not allow hook event logging to be less reliable than transcript diffing. Source: adversarial-quality (QUAL-002) and adversarial-io-validation (IO-002), log-hook.py:101-102, 140-141, 159-160, 174-175.

5.4. [HIGH] **Validate `TMPDIR` before use in `get_lock()`.** Before entering the retry loop, verify `tmp_dir.is_dir()` and that it is writable. Fail fast with a clear error rather than spending 10 seconds retrying on an invalid path. Source: adversarial-io-validation (IO-004), log-hook.py:65.

5.5. [HIGH] **Track lock acquisition failure state and propagate to callers.** Store whether `get_lock()` succeeded in a module-level or return-value flag. Use this to either (a) skip or warn on subsequent operations when lock is unavailable, or (b) document in the log output that synchronization was not achieved. Source: adversarial-quality (QUAL-004), log-hook.py:69-76.

5.6. [HIGH] **Validate `transcript_path` for Windows reserved names and path traversal.** Apply `os.path.check_for_reserved_names()` or equivalent validation before using `transcript_path`. Reject paths that would write outside the intended log directory. Source: adversarial-io-validation (IO-005), log-hook.py:86-87.

5.7. [MEDIUM] **Log `release_lock()` failures rather than silently ignoring.** At minimum, emit a warning to stderr. Ideally, surface the failure in a way that is visible in log output, so stale lock accumulation is detectable. Source: adversarial-io-validation (IO-003), log-hook.py:48-54.

5.8. [MEDIUM] **Validate `max_attempts >= 1` in `_retry_on_locked()` and raise `ValueError` for invalid values.** Source: adversarial-logic (LOGIC-001), log-hook.py:31.

5.9. [MEDIUM] **Add functional tests for retry behavior.** Test: retry succeeds after transient lock, retry exhausts and raises after max_attempts, `max_attempts=0` raises `ValueError`, error masking does not lose non-PermissionError exceptions. Source: adversarial-quality (QUAL-005), log-hook.py:31-45.

5.10. [LOW] **Fix test module import syntax.** Rename the test module from any hyphenated name to a valid Python identifier (e.g., `test_log_hook.py`). Source: adversarial-quality (QUAL-005).

## Open Questions / Unknowns

6.1. [LOW] **Was `log_jsonl` retry intentionally omitted?** The asymmetric retry coverage (transcript operations have retry, log operations do not) may reflect a deliberate scoping decision that was not documented. If intentional, the rationale should be captured. If not intentional, it should be fixed. Source: adversarial-io-validation (IO-002).

6.2. [LOW] **What Python version targets?** Python 3.10+ on Windows maps WinError 32 consistently to `PermissionError`, but this mapping may not be guaranteed on all builds. Source: adversarial-logic (LOGIC-003) and adversarial-quality (QUAL-003).

6.3. [LOW] **Why does `get_lock()` return the lock directory itself rather than a file within it?** Returning `lock_dir` directly means any caller that has the lock path can call `lock_dir.exists()` and believe they have a lock. A more robust design would return a file path that requires exclusive creation (via `os.link` or similar) to establish uniqueness. Source: adversarial-io-validation (IO-001).
