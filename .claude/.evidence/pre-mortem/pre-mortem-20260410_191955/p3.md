# Pre-Mortem: Skill-guard Breadcrumb Tracker

## Intent Summary

The breadcrumb tracker is a v2.0 workflow step verification system for Claude Code skills. It records skill execution steps via `set_breadcrumb()`, persists state to a hybrid SQLite + JSON file backend, and provides tiered enforcement (MINIMAL / STANDARD / STRICT) to verify skill completion. The system is designed for terminal-scoped isolation and multi-terminal safety.

## 1. Logical Gaps & Inconsistencies

1.1. **[BLOCKER]** `tool_count` is initialized to 0 but never incremented — MINIMAL and STANDARD enforcement always fail (adversarial-logic, tracker.py:350, enforcement.py:198) — `tool_count` is set to 0 in the trail dict and at `sqlite_backend.py:95`, and only `.get("tool_count", 0)` reads it back at tracker.py:623. No increment operation exists anywhere in the codebase. `_verify_minimal` checks `tool_count < 2` which always evaluates True. Only STRICT enforcement works.

1.2. **[HIGH]** `initialize_breadcrumb_trail` returns early when `workflow_steps` is empty — no trail created, `set_breadcrumb` subsequent calls also return early with `force=False` (adversarial-logic, tracker.py:316-321) — When `_load_workflow_steps` returns `[]`, `initialize_breadcrumb_trail` returns without creating any state. Later `set_breadcrumb` calls invoke `get_state` which returns None (no trail), then `initialize_breadcrumb_trail` with `force=False` also returns early. Skills without `workflow_steps` in frontmatter silently opt out of all tracking.

1.3. **[HIGH]** `_load_from_log` only reconstructs `completed_steps` from log entries — `steps` dict, `current_step`, `tool_count`, and evidence are all lost on cache invalidation (adversarial-testing, cache.py:162) — `BreadcrumbStateCache._load_from_log` only handles `step_complete` events to append to `completed_steps`. No handling of `trail_initialized` event to reconstruct workflow_steps and steps dict structure. After cache invalidation, verification runs with incomplete state.

1.4. **[MEDIUM]** `_load_from_log` reverses log entries expecting oldest first, but `replay()` returns newest first (adversarial-testing, cache.py:158) — `entries = list(reversed(log.replay()))` puts the newest entry at `entries[0]`, which is then used as the base state. The `trail_initialized` event (oldest) ends up at the end after reversal, not processed as initialization.

1.5. **[MEDIUM]** Regex fallback in `_regex_workflow_steps_fallback` only captures step ID before colon — dict-format workflow_steps like `{id: analyze, description: Analyze}` not parsed correctly (adversarial-logic, tracker.py:258) — Pattern `r"^[ \t]+- ([^:\n]+)(?::?\s*(.*))?$"` captures the step ID but the YAML dict on the same line is not matched by the regex. Only string-format steps `- analyze` work via regex.

## 2. Hidden Assumptions & Fragile Dependencies

2.1. **[HIGH]** P: drive is always available — no validation or fallback when drive is unavailable (adversarial-io-validation, tracker.py:54, database.py:39) — `STATE_DIR = Path("P:/.claude/state")` and `DEFAULT_DB_PATH` are hardcoded. If P: is a mapped network drive and VPN disconnects, all breadcrumb operations raise `OSError`. No graceful degradation, no in-memory fallback, no temp directory fallback.

2.2. **[HIGH]** Cannot distinguish "no workflow_steps declared" from YAML parse error from regex parse error — all return empty list (adversarial-io-validation, tracker.py:183-226) — When `_load_workflow_steps` returns `[]`, callers cannot determine whether: (a) skill has no workflow_steps, (b) YAML parsing failed, (c) regex fallback also failed. This masks data loss silently.

2.3. **[HIGH]** Evidence stored in `steps[step]['evidence']` is never validated by any enforcement level (adversarial-testing, enforcement.py:139-180) — `verify_breadcrumb_trail()` checks step completion counts and keyword matching via `_verify_standard`, but no enforcement level validates that evidence is well-formed, non-empty, or contains required fields. A skill can claim completion with empty evidence and pass all checks.

2.4. **[MEDIUM]** Database errors return None without distinguishing corruption from other failures (adversarial-io-validation, database.py:138) — `get_connection()` catches all exceptions (OSError, sqlite3.Error) and returns None. A corrupted `diagnostics.db` silently degrades to file-based mode with no indication. No error type discrimination.

2.5. **[MEDIUM]** SQLite and file storage can diverge on partial failures — no reconciliation (adversarial-testing, tracker.py:453-466) — `update_trail` catches Exception from `sqlite_backend.update_trail` and falls back to file-based operations without verifying whether SQLite actually persisted. If both succeed with different data, subsequent reads from one backend return stale data.

2.6. **[MEDIUM]** `_db_initialized` global has no threading lock — race condition in multi-threaded hook execution (adversarial-quality, tracker.py:67) — `_ensure_database_initialized()` checks `_db_initialized` without locking. In concurrent hook execution, two threads could both see `_db_initialized = False` and attempt schema initialization simultaneously, or one thread could set `_db_initialized = True` while another is mid-initialization.

## 3. Missing Obvious Actions / Best Practices

3.1. **[HIGH]** Increment `tool_count` in `set_breadcrumb()` — the only caller is PostToolUse_breadcrumb_tracker.py, which should track every tool use (adversarial-logic) — `set_breadcrumb` should increment `trail['tool_count']` and call `persist()` on every invocation. Alternatively, expose `increment_tool_count()` callable by the PostToolUse hook after each tool. Currently `tool_count` is dead storage.

3.2. **[HIGH]** Add env var override for `STATE_DIR` (like `DB_PATH` uses `CLAUDE_STATE_DIR`) — `STATE_DIR = Path(os.environ.get("CLAUDE_STATE_DIR", "P:/")) / ".claude/state"` would provide portability (adversarial-io-validation, tracker.py:54)

3.3. **[HIGH]** When `workflow_steps` is empty, create a minimal trail with default step `invoke_skill` so duration and tool_count still track (adversarial-logic, tracker.py:320-321) — Skills without `workflow_steps` should still participate in MINIMAL enforcement. A default `invoke_skill` step allows tool_count tracking even without declared workflow steps.

3.4. **[HIGH]** Add evidence validation to `_verify_strict` — check that `evidence` field is a non-empty dict (adversarial-testing, enforcement.py:139-180) — In `_verify_strict`, add: `if 'evidence' not in steps[step] or not steps[step]['evidence']: missing_steps.append(step)`. This closes the enforcement gap where evidence is optional but should be required for STRICT.

3.5. **[MEDIUM]** Merge duplicate `except Exception: pass` findings — IO-006 and QUAL-001 both flag bare except in `_append_ledger_event` (adversarial-io-validation, adversarial-quality, tracker.py:115) — Consolidate into one finding with a single recommendation: add `logging.debug()` in the exception handler rather than silent pass.

3.6. **[MEDIUM]** Use word-boundary regex matching for verification keywords in `_verify_standard` (adversarial-quality, enforcement.py:232-235) — `re.search(r'\b' + kw + r'\b', step.lower())` instead of substring matching. "preverified" and "testimony" would no longer false-match.

3.7. **[MEDIUM]** Add file locking during `_rotate_log` or make rotation idempotent (adversarial-io-validation, log.py:176-195) — Concurrent terminals can cause rotation to fail silently. Use `fcntl.flock` on Linux or a cross-platform lock pattern. At minimum, log when rotation fails so silent growth is observable.

## 4. Risks and Edge Cases

4.1. **[HIGH]** TOCTOU race in `get_breadcrumb_trail` — cache returns at line 109, file re-read at line 576 for terminal_id verification. No lock held between (adversarial-testing, tracker.py:572-586) — Stale cache could be returned even when file was modified by another terminal. Consider file locking or atomic compare-and-swap when cache and file diverge.

4.2. **[MEDIUM]** `initialize_breadcrumb_trail` early return gives no indication whether skill has no steps or error loading them (adversarial-io-validation, tracker.py:316-321) — No log entry, no breadcrumb file created. If YAML parse fails on a skill that SHOULD have workflow_steps, the user gets no feedback. Add `logger.info` when no workflow_steps found.

4.3. **[MEDIUM]** `run_id` not included in `_get_cache_key` — force=True re-initialization of a skill corrupts cached state from prior invocation (adversarial-testing, cache.py:91) — With same skill and terminal but different run_id, cache key collides. Either invalidate cache on force=True initialization, or include run_id in the cache key.

4.4. **[MEDIUM]** `_append_ledger_event` bare except swallows ALL exceptions including import errors and hook_ledger bugs (adversarial-io-validation, tracker.py:100-116) — Audit trail gaps are completely invisible. Add DEBUG-level logging at minimum so operators can enable verbose mode to observe ledger failures.

4.5. **[LOW]** Rotated log archives (`*_{timestamp}.jsonl`) are never cleaned up — disk space grows unbounded (adversarial-testing, log.py:186) — `cleanup_old_log_dirs()` only removes old directories, not rotated log files. Add logic to glob and remove rotated archives older than cutoff.

4.6. **[LOW]** `_windows_safe_unlink` silently proceeds on failure — orphaned breadcrumb files accumulate (adversarial-io-validation, tracker.py:501-525) — Return success/failure status from `_windows_safe_unlink`. Log when cleanup fails after all retries so operators are notified.

5.5. **[MEDIUM]** Add threading.Lock around `_db_initialized` check (tracker.py:67) — `_db_init_lock = threading.Lock()` protecting the check-and-set in `_ensure_database_initialized`

5.6. **[MEDIUM]** Add word-boundary regex for verification keywords in `_verify_standard` (enforcement.py:232-235) — `re.search(r'\b' + kw + r'\b', step.lower())`

5.7. **[MEDIUM]** Add debug logging when `_append_ledger_event` catches exceptions (tracker.py:115) — `logger.debug(f"Failed to write ledger event {event_type}: {e}")` instead of silent pass
