# Phase 2: Cross-Agent Meta-Critique

## Cross-Agent Contradictions

1. **Substring vs word-boundary keyword matching** — adversarial-logic (LOGIC-004, LOW) flags regex pattern only captures step ID before colon but doesn't catch dict-format items. adversarial-quality (QUAL-006, LOW) separately flags substring matching for "preverified"/"testimony" false positives. These are related precision issues in the same regex code but rated LOW by both — no specialist called out that the regex is doing double duty (both step extraction AND keyword matching) and both functions have problems.

2. **Early return interpretation** — adversarial-logic (LOGIC-002, HIGH) says `initialize_breadcrumb_trail` returns early on empty workflow_steps silently. adversarial-io-validation (IO-005, MEDIUM) also flags this as silent early return but rates it MEDIUM. No contradiction in rating but IO validation didn't escalate to HIGH despite same evidence.

3. **tool_count BLOCKER vs evidence validation gap** — adversarial-logic identified LOGIC-001 as BLOCKER (tool_count never incremented). adversarial-testing identified TEST-009 as HIGH (evidence stored but never validated). These are parallel completeness failures in the enforcement layer — one blocks MINIMAL/STANDARD from working, the other allows fraudulent completion claims. Both HIGH+ severity but no cross-specialist note that these are the two enforcement half-turns that are broken.

## Severity Calibration Issues

1. **IO-001 (BLOCKER) vs IO-003 (HIGH)** — Hardcoded P: path with no fallback (IO-001, BLOCKER) is severity BLOCKER because it causes total failure. Database corruption causing silent fallback (IO-003, HIGH) also causes total failure but rated HIGH. Both disable the system; IO-003's impact is arguably equal to IO-001. No justification for the severity gap.

2. **TEST-001 (HIGH) vs LOGIC-003 (MEDIUM)** — Both concern _load_from_log assuming first entry has `completed_steps`. adversarial-testing flagged this as HIGH because the state reconstruction is incomplete (missing steps dict, evidence, tool_count). adversarial-logic flagged it as MEDIUM because it causes KeyError only on malformed logs. Same root cause, 2-severity gap. TEST-001's framing (incomplete reconstruction) is more accurate.

3. **IO-006 (MEDIUM) vs QUAL-001 (MEDIUM)** — Both flag bare `except Exception: pass` in `_append_ledger_event`. adversarial-io-validation calls it "silent failure" at MEDIUM. adversarial-quality calls it "no logging, no warning" also at MEDIUM. No disagreement, but this is the same bug cited twice — should be merged.

4. **QUAL-005 (MEDIUM) vs QUAL-006 (LOW)** — QUAL-005 flags dot in skill names being rejected (overly broad path validation). QUAL-006 flags substring matching false positives. Both are regex precision issues in enforcement. QUAL-005 is MEDIUM because it blocks valid skill names; QUAL-006 is LOW because false positive risk is theoretical. Calibration is defensible but both land in the same code area (enforcement.py + tracker.py path validation).

## Missed Blind Spots

1. **No specialist reviewed the PostToolUse_breadcrumb_tracker.py hook itself** — The session target was the breadcrumb tracker system, which includes both the tracker.py module AND the PostToolUse hook that calls `set_breadcrumb`. The hook is the sole caller of `set_breadcrumb` and the only thing that could increment `tool_count`. No specialist examined whether the hook correctly passes all required fields, whether it handles tool failures, or whether it has its own silent failure modes. This is the missing consumer-contract review for the breadcrumb system.

2. **No specialist examined the SKILL.md frontmatter parsing contract** — `_load_workflow_steps` parses YAML frontmatter from SKILL.md. If the frontmatter has complex nested structures (e.g., steps with `parameters:` sub-keys), the YAML parse fails and falls back to regex. No specialist addressed: what is the actual schema contract for workflow_steps? What fields are required vs optional? What happens when a step has only an `id` (string shorthand) vs full dict with `description`, `kind`, `optional`?

3. **No specialist examined the cache key collision across terminals** — `_get_cache_key` uses `skill_name:terminal_id` but terminal_id format differs between Windows (`console_abc`) and Linux shells (`env_xyz`). The tracker.py uses `detect_terminal_id()` from skill_guard.utils but no specialist verified whether this function returns consistent formats across different shell environments. This could cause cross-terminal state bleed.

4. **No specialist examined the cleanup_on_session_end path** — `tracker.py` mentions `cleanup_on_session_end` and `cleanup_on_precompact` for stale trail cleanup. No specialist verified: does SessionEnd actually trigger cleanup? Is PreCompact cleanup actually registered? If the cleanup is missing from the hook dispatch chain, orphaned breadcrumb files accumulate indefinitely.

5. **STRICT enforcement only level that works** — The BLOCKER (tool_count never incremented) means MINIMAL and STANDARD enforcement are completely broken. Only STRICT works. But no specialist called out that 2 of 3 enforcement levels are non-functional — this is a systemic availability failure, not just a local bug.

## Precision Failures

1. **IO-004 TOCTOU in _rotate_log rated MEDIUM** — The rotation failure scenario (two terminals, both check size, both append, one renames, other rename fails silently) could result in log growing unbounded with no indication. If this happens, the audit trail becomes unreliable. MEDIUM may be too low for "silent log growth unbounded."

2. **QUAL-010 threading lock on _db_initialized rated MEDIUM** — In Claude Code's hook system, multiple hooks can run concurrently. `_db_initialized` race condition could cause duplicate schema initialization attempts or, worse, leave `_db_initialized = True` when initialization actually failed on one thread while another thread skips initialization. This is an correctness issue, not just a performance issue. Should be HIGH or BLOCKER.

3. **TEST-003 SQLite/file divergence rated MEDIUM** — If SQLite succeeds but file write fails, subsequent reads from file (via fallback path) return stale data. The trail says step was completed but file-based state says it wasn't. This creates split-brain state that could cause verification to fail incorrectly or pass incorrectly. Should be HIGH.

## Improvements to Phase 1 Findings

1. **Merge duplicate `except Exception: pass` findings** — IO-006 (adversarial-io-validation) and QUAL-001 (adversarial-quality) both flag the same bare except in `_append_ledger_event`. Consolidate into one finding with appropriate severity (MEDIUM, not two separate entries).

2. **Elevate enforcement half-turn failures** — LOGIC-001 (tool_count) and TEST-009 (evidence validation) should be explicitly cross-referenced. The pre-mortem should note: MINIMAL and STANDARD enforcement are completely non-functional (tool_count = 0 always fails checks); STRICT enforcement has no evidence validation. These are two sides of the same broken enforcement coin.

3. **Add missing consumer-contract review** — Phase 1 should have included `adversarial-compliance` to examine: (a) PostToolUse hook as consumer of set_breadcrumb API, (b) SKILL.md frontmatter as producer of workflow_steps contract, (c) enforcement.py as consumer of breadcrumb trail state. Without this review, the system has no verified producer-consumer contract.

4. **Distinguish parse failure from absence for workflow_steps** — IO-002 correctly identifies the problem (no way to distinguish"no steps" vs "parse error") but doesn't offer a concrete solution: return a named tuple `WorkflowStepsResult(steps=[], parse_error=None)` where `parse_error` contains the exception message when both YAML and regex fail. This would make the failure observable.
