## Cross-Agent Contradictions

1. **StopIteration severity mismatch** — adversarial-state-machine rated the StopIteration escape as [HIGH] (batch_scheduler.py:188-201) and explicitly called it "dangerous because no exception propagates to alert the caller." But adversarial-performance, despite identifying the jitter-sleep as a blocking issue inside the same generator loop, did not flag the StopIteration issue at all. These are related — the generator is blocked AND can terminate silently — yet only one specialist flagged the termination risk. This is a recall failure (state-machine caught it but performance missed the interaction).

2. **Yield_next consumer safety** — adversarial-state-machine flagged yield_next() as "not safe for multi-worker consumption" as [MEDIUM] (batch_scheduler.py:174-220), but adversarial-performance described the exact same pattern as the canonical behavior (8 workers pulling via next()) without flagging it as a risk. The state-machine finding notes "StopIteration propagates out, terminating the generator mid-iteration" — but batch.py's actual usage (single consumer pulling, workers as fire-and-forget) means this is NOT actually a problem in practice. The finding is technically correct but operationally misleading for this specific usage.

3. **consecutive_429s field** — adversarial-state-machine called it a [LOW] "dead field." adversarial-security did not mention it at all. No specialist evaluated whether the field should be removed or used. The state-machine specialist correctly identified it as unused but did not escalate to a recommendation.

## Severity Calibration Issues

1. **Cross-terminal sync silent failure** — adversarial-security rated it [LOW] (transcript.py:222-225). But adversarial-performance flagged the same pattern (BatchScheduler() instantiated per 429) as [MEDIUM] because of checkpoint overhead. The security finding notes "could cause cascading failures under high 429 rates" but rates it LOW while performance rates the same instantiation overhead as MEDIUM. The security risk (silent divergence between in-memory and SQLite cooldown state) seems more serious than a performance concern — calibration inconsistency.

2. **Connection-per-call in hot paths** — adversarial-performance rated it [HIGH] (multiple connections per yield). adversarial-state-machine rated the same pattern as [LOW] for _is_in_cooldown and [LOW] for _archive_status. Performance cites exact per-call overhead; state-machine correctly notes that with jitter sleep (2-10s between yields), the overhead is "negligible." Both are correct within their framing — performance from a throughput standpoint, state-machine from an correctness standpoint. The HIGH/MEDIUM vs LOW calibration reflects different lenses, not a true disagreement.

3. **Stale attempting recovery** — adversarial-state-machine rated as [HIGH] (no runtime recovery). adversarial-testing also flagged the missing boundary condition test as [MEDIUM]. These are consistent — the risk is high even if the test coverage gap is medium.

## Missed Blind Spots

1. **The batch.py total_estimate is stale at start** — batch.py:224 initializes `total_estimate = sum(len(scheduler._get_pending_videos(ch)) for ch in scheduler._channels)` from the scheduler's initial state. But `yield_next()` removes exhausted channels from active_channels. The progress callback uses `total_estimate - completed` as pending count. As channels are exhausted, `total_estimate` becomes increasingly inaccurate — it overstates pending videos throughout the run. No specialist caught this.

2. **The scheduler is a singleton in transcript.py** — transcript.py calls `BatchScheduler()` inside `_record_source_429` and `_record_source_success` on every 429/success. This creates a NEW BatchScheduler instance (with its own `__init__` that calls `_recover_stale_attempting()`) every single time a transcript method fails. With multiple videos processing in ThreadPoolExecutor, this means many concurrent `BatchScheduler()` instantiations all contending on the same WAL DB. None of the security, performance, or state-machine specialists identified this as a cascading failure risk — only the performance specialist flagged the checkpoint overhead but didn't connect it to the "every failure creates a new instance" pattern.

3. **yield_next is a method, not a function — self._channels is captured at init time** — batch_scheduler.py:27-32 initializes `self._channels` once at `__init__`. But `yield_next()` calls `_get_pending_channels()` again only when iterators are rebuilt (line 194). The `active_channels` list in the loop comes from the init-time `self._channels` plus iterator rebuild. If new channels are added to the database after the scheduler is created (e.g., a new sync run adds videos while the scheduler is still running), they won't be picked up. This is a stale-queue risk — none of the specialists caught it because they didn't examine the init-time snapshot capture.

4. **Missing "all methods failed" path in archive** — transcript.py:888 returns `_none_result(last_error)` after all methods fail, but never calls `BatchScheduler().archive_finalize(video_id, 'failed')` in that path. The plan specified "On all-methods-failed: `BatchScheduler().archive_finalize(video_id, 'failed')`" (plan TASK-002), but this was NOT implemented — the final fallback returns without archiving. The video remains "attempting" if it was marked attempting before failing all methods. This is a gap between plan and implementation that no specialist caught (because they reviewed implementation, not the plan).

5. **The analyze_videos_round_robin total_estimate counting is biased** — `scheduler._get_pending_videos(ch)` is a snapshot at init time. Videos that complete before their channel's videos are all fetched are already marked complete (by `mark_complete()` in batch.py), so `get_pending_videos` still returns them because it reads from the DB, not from in-memory state. But the scheduler's `yield_next()` will skip already-archived videos. So `total_estimate` overcounts — it includes videos that will be immediately skipped. No specialist identified this discrepancy.

## Precision Failures

1. **[MEDIUM] Jitter inside generator blocks workers** (adversarial-performance) — The finding says "workers cannot fill the pipe faster" because sleep is inside the generator. But in batch.py's usage, workers don't pull from the generator — they are SUBMITTED tasks. The generator yields to the main thread, which then submits tasks to the executor. Workers don't call `next(yield_next())`. The sleep does serialize the producer, but "workers are serialized" overstates the impact — the bottleneck is the producer thread, not the workers. The real issue is the jitter is in the wrong place (should be per-worker), but the framing is imprecise.

2. **[LOW] WAL PRAGMAs set per-connection** (adversarial-security) — The finding warns that future code could add queries without PRAGMAs. This is speculative about future code changes, not a finding about the current implementation. The concern is valid but the severity ([LOW] appropriate) doesn't match the framing, which implies there's an active risk rather than a hypothetical future risk.

3. **[MEDIUM] yield_next generator termination on mid-pass channel exhaustion** (adversarial-state-machine) — The finding says "callers consuming yield_next() would silently stop receiving videos." In the actual batch.py usage, the main thread iterates yield_next() and submits tasks — when yield_next exhausts, the loop exits naturally and the function returns. There is no "silent stop" — the caller gets StopIteration and exits cleanly. The finding describes a theoretical misuse, not the actual usage. Precision failure.

## Improvements to the Phase 1 Findings

1. **The StopIteration finding needs operational context** — It should distinguish between the theoretical risk (multi-caller consumption) and the actual usage (single consumer, clean termination). The finding is technically accurate but operationally misleading as written.

2. **Performance should separate connection overhead from correctness** — The HIGH rating for connection-per-call conflates a performance concern (overhead) with a correctness concern (could it fail under load?). The jitter sleep between yields makes connection overhead negligible in practice. The HIGH rating for "severe connection churn" should be downgraded to MEDIUM given the actual workload characteristics.

3. **Cross-terminal test gap should be HIGH, not MEDIUM** — The adversarial-testing finding correctly notes no cross-terminal cooldown test exists. But adversarial-state-machine rated the cross-terminal cooldown as a hard requirement from the ADR. The absence of this test should be [HIGH] because it means the core ADR value proposition (cross-terminal cooldown sharing) has zero verification.

4. **Missing "all methods failed" archive write** — This should be added to the consolidated findings — it's a plan-implementation gap that no specialist caught because they reviewed implementation only, not the plan spec against the implementation.
