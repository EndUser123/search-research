## Intent Summary

Implement a round-robin batch scheduler for the intelligence-stream batch pipeline that adds 429 resilience by interleaving videos across multiple channels, using a persistent download archive to skip already-attempted videos on restart, and sharing per-channel cooldown state across all terminals via SQLite WAL.

## Logical Gaps & Inconsistencies

1.1. [HIGH] **StopIteration escape in yield_next for-loop** — If `StopIteration` is raised anywhere in the `for channel in list(active_channels)` body other than the explicit `next(self._iterators[channel])` call, it silently exits the `for` loop without propagating. The outer `while` loop then continues with potentially depleted `active_channels`, causing the generator to yield nothing for the rest of that pass. The fix: wrap the entire for-loop body in `try/except StopIteration` to catch all StopIteration sources, not just the iterator step. (source: adversarial-state-machine, batch_scheduler.py:188-201)

1.2. [HIGH] **Jitter blocks the producer, not workers** — `time.sleep(random.uniform(_JITTER_MIN, _JITTER_MAX))` sits inside `yield_next()` at line 215, between yields. Because `yield_next` is a generator, the sleep blocks the producer thread that is generating values. Workers calling `next(scheduler.yield_next())` cannot fill the pipe faster than one yield per sleep cycle. In batch.py's usage (producer thread yields, submits to executor), this means the producer thread is the bottleneck, not the workers. The jitter should be moved to per-worker waits in `batch.py`, not inside the generator. (source: adversarial-performance, batch_scheduler.py:215)

1.3. [HIGH] **Plan-implementation gap: all-methods-failed never archives** — `transcript.py:889` returns `_none_result(last_error)` after all methods fail, but never calls `BatchScheduler().archive_finalize(video_id, 'failed')`. The plan (TASK-002) explicitly required this call. Without it, the video stays "attempting" on restart and will be re-processed, potentially repeatedly hitting 429s indefinitely. (source: meta-critique, transcript.py:888-889)

1.4. [MEDIUM] **No runtime stale attempting recovery** — `_recover_stale_attempting()` runs only at `__init__` (batch_scheduler.py:58-67). If a worker picks up a video, crashes mid-processing, and never calls `archive_finalize`, the video stays `attempting` indefinitely. The 30-minute threshold is a startup-only gate. A periodic recovery call in `yield_next()` or a periodic timer would close this gap. (source: adversarial-state-machine, batch_scheduler.py:58-67)

1.5. [MEDIUM] **yield_next is not safe for multi-worker consumption** — StopIteration propagates out of the inner `for` loop, terminating the generator mid-iteration. In batch.py's current single-producer pattern this is clean, but if the API is reused by a multi-consumer caller, it would silently stop receiving videos. Not a problem today, but a fragile design. (source: adversarial-state-machine, batch_scheduler.py:174-220)

1.6. [MEDIUM] **total_estimate is inaccurate throughout the run** — `batch.py:224` computes `total_estimate = sum(len(scheduler._get_pending_videos(ch)) for ch in scheduler._channels)` from the init-time snapshot. As videos complete and channels exhaust, this overcounts remaining work because completed videos are still in the DB query results. The progress callback (`pending = total_estimate - completed`) will show more pending than actually exist. (source: meta-critique, batch.py:224)

1.7. [LOW] **Active channels not re-evaluated between outer-while passes** — `yield_next()` filters `active_channels` at the top of the loop (line 185) but if a channel enters cooldown between passes, stale channels may consume iterations in the next call before being skipped. Not a correctness issue for the current usage but indicates stale iterator management. (source: adversarial-performance, batch_scheduler.py:185)

## Hidden Assumptions & Fragile Dependencies

2.1. [MEDIUM] **Cross-terminal sync is best-effort with silent failures** — `_record_source_429` and `_record_source_success` in `transcript.py` use `try/except pass` around `BatchScheduler()` calls. If SQLite fails repeatedly (disk full, lock timeout), the in-memory circuit breaker and shared SQLite cooldown diverge without any alerting. The ADR promised cross-terminal protection, but silent failure means that protection can degrade without operator awareness. (source: adversarial-security, transcript.py:222-225, 236-239)

2.2. [MEDIUM] **BatchScheduler() instantiated on every 429/success** — transcript.py creates a new `BatchScheduler()` instance on every 429 and every success. Each instantiation runs `_recover_stale_attempting()` (an UPDATE + PRAGMA wal_checkpoint). Under high concurrency (ThreadPoolExecutor with 8 workers), many concurrent failures/successes all trigger this, creating checkpoint contention on the shared WAL DB. A module-level singleton would avoid this. (source: adversarial-security, transcript.py:219-225, 236-239)

2.3. [MEDIUM] **Jitter serializes producer regardless of worker count** — The design assumes 8 workers pull from the generator concurrently, but the jitter is placed in the producer. This means the producer is always the bottleneck regardless of worker parallelism. No specialist quantified this interaction until the meta-critique. (source: adversarial-performance, batch_scheduler.py:215)

2.4. [LOW] **consecutive_429s is written but never read** — The field is persisted to `channel_cooldown` but no code reads it. The cooldown state machine has no escalating behavior based on consecutive failure count. The field is harmless but dead — indicates a planned feature not implemented. (source: adversarial-state-machine, batch_scheduler.py:120-138)

2.5. [LOW] **WAL PRAGMAs set per-connection, not enforced globally** — Every query path sets `journal_mode=WAL` and `busy_timeout=5000`, but there's no enforcement mechanism preventing a future code path from running a query without these settings. A connection factory pattern would make this safe by default. (source: adversarial-security, batch_scheduler.py:39-56)

## Missing Obvious Actions / Best Practices

3.1. [HIGH] **No cross-terminal cooldown test** — The test suite has no test where one `BatchScheduler` instance writes a cooldown and a second instance (new connection, simulating a different terminal) respects it. This is the core ADR value proposition (cross-terminal cooldown sharing) and it has zero automated verification. (source: adversarial-testing, tests/test_batch_scheduler.py)

3.2. [MEDIUM] **Round-robin order not verified** — `test_round_robin_interleaving` only checks channel counts (each channel appears 3 times) but does not assert the interleaving sequence. A non-interleaved result (A1,A2,A3,B1,B2,B3,C1,C2,C3) also passes the current assertions. The order A1,B1,C1,A2,B2,C2,A3,B3,C3 should be explicitly asserted. (source: adversarial-testing, tests/test_batch_scheduler.py:99-121)

3.3. [MEDIUM] **No concurrent yield_next race test** — The EXCLUSIVE transaction in `_record_attempting` was added specifically to prevent two terminals yielding the same video simultaneously. No test exercises this scenario. (source: adversarial-testing, tests/test_batch_scheduler.py)

3.4. [MEDIUM] **record_success reset not tested** — No test verifies that `consecutive_429s` resets to 0 after `record_success()` is called. (source: adversarial-testing, tests/test_batch_scheduler.py:301-319)

3.5. [MEDIUM] **Stale boundary at exactly 1800s not tested** — `test_stale_attempting_recovery` uses `_STALE_ATTEMPTING_SECONDS - 10` (29:50), not the exact threshold or just-over. The boundary at exactly 1800 seconds should be tested separately. (source: adversarial-testing, tests/test_batch_scheduler.py:234-261)

3.6. [MEDIUM] **Double archive_finalize not tested** — No test verifies idempotency when `archive_finalize` is called twice on the same video, or that `INSERT OR REPLACE` correctly updates an existing `attempting` row to `failed`. (source: adversarial-testing, tests/test_batch_scheduler.py:339-354)

3.7. [LOW] **test_empty_channel_handling doesn't test empty channels** — The test seeds two videos and verifies they are yielded, but never tests what happens when `active_channels = []` (all channels exhausted). (source: adversarial-testing, tests/test_batch_scheduler.py:285-299)

## Risks and Edge Cases

4.1. [MEDIUM] **Worker completion creates EXCLUSIVE-lock stampede** — Each of 8 workers calls `archive_finalize()` immediately on completion, firing 8 concurrent BEGIN EXCLUSIVE transactions against the WAL DB. With `busy_timeout=5000`, these queue safely, but under heavy load the queue could grow. Batching writes (buffer N completions, flush after a short timeout) would reduce contention. (source: adversarial-performance, batch.py:265,269)

4.2. [MEDIUM] **yield_next() yields from init-time channel snapshot** — `self._channels` is captured at `__init__` (batch_scheduler.py:27-32). If new channels are added to the database while the scheduler is running, they won't be picked up until the scheduler is restarted. This is acceptable for the current usage (all channels known at start) but a latent fragility if the API is reused. (source: meta-critique, batch_scheduler.py:27-32)

4.3. [MEDIUM] **yield_this_pass spin risk under high archive-hit rate** — If a channel returns only already-archived videos, `yielded_this_pass` stays empty and the loop spins until a non-archived video is found. With high completion rates, this could cause repeated full-pass scans. Not a correctness issue but adds latency. (source: adversarial-performance, batch_scheduler.py:218-220)

4.4. [LOW] **Silent failure on repeated cross-terminal sync failures** — `try/except pass` in `_record_source_429` and `_record_source_success` means repeated SQLite failures go unobserved. If the WAL becomes persistently locked, the cross-terminal protection degrades silently. A log warning would make this observable. (source: adversarial-security, transcript.py:222-225, 236-239)

## Concrete Recommendations

5.1. [MEDIUM] **Move jitter out of yield_next into batch.py per-worker waits** — Move `time.sleep(random.uniform(_JITTER_MIN, _JITTER_MAX))` from `batch_scheduler.py:215` to a per-worker random delay in `batch.py` between when a worker finishes and when it picks up the next job. This decouples the producer rate from the jitter interval. (source: adversarial-performance, batch_scheduler.py:215)

5.2. [MEDIUM] **Wrap yield_next for-loop body in comprehensive StopIteration handler** — Add a `try/except StopIteration` around the entire `for channel in list(active_channels)` body (not just the `next()` call) so that any StopIteration source is caught and handled gracefully, with exhausted channels removed from `active_channels` rather than silently exiting the loop. (source: adversarial-state-machine, batch_scheduler.py:188-201)

5.3. [MEDIUM] **Add archive_finalize('failed') in transcript.py all-methods-failed path** — Before `return _none_result(last_error)` at `transcript.py:889`, add `BatchScheduler().archive_finalize(video_id, 'failed')` with the same best-effort exception handling used for success/429 writes. This closes the plan-implementation gap. (source: meta-critique, transcript.py:888-889)

5.4. [MEDIUM] **Add module-level BatchScheduler singleton for cross-terminal writes** — Replace `BatchScheduler()` instantiation in `_record_source_429` and `_record_source_success` with a shared singleton to avoid repeated `_recover_stale_attempting()` + `wal_checkpoint` overhead on every failure. (source: adversarial-security, transcript.py:219-239)

5.5. [MEDIUM] **Add cross-terminal cooldown test** — Add a test that creates a cooldown in one `BatchScheduler` instance and verifies a second instance (fresh connection) respects it. This is the primary missing test for the ADR's core value proposition. (source: adversarial-testing, tests/test_batch_scheduler.py)

5.6. [MEDIUM] **Add record_success counter reset test** — Add a test that calls `record_429` 3 times then `record_success` and verifies `consecutive_429s = 0` in the DB. (source: adversarial-testing, tests/test_batch_scheduler.py:301-319)

5.7. [MEDIUM] **Fix total_estimate to count remaining at runtime** — Replace the init-time snapshot count with a query that reflects actual remaining pending work, or compute it as `len([v for v in yielded_videos if not archived])` tracked at runtime. (source: meta-critique, batch.py:224)

5.8. [LOW] **Log cross-terminal sync failures as warnings** — Replace `try/except pass` in `_record_source_429` and `_record_source_success` with `try/except Exception as e: logging.warning(f"[transcript] Cross-terminal sync failed: {e}")` so silent degradation is observable. (source: adversarial-security, transcript.py:222-225, 236-239)

5.9. [LOW] **Assert round-robin order in test** — Change `test_round_robin_interleaving` to explicitly assert the sequence order: `[A1,B1,C1,A2,B2,C2,A3,B3,C3]`. (source: adversarial-testing, tests/test_batch_scheduler.py:99-121)

5.10. [LOW] **Remove dead consecutive_429s field or use it** — Either implement escalating cooldown based on `consecutive_429s` count (e.g., longer cooldown for repeat offenders) or remove the field from the schema to avoid confusion. (source: adversarial-state-machine, batch_scheduler.py:120-138)

## Open Questions / Unknowns

6.1. [LOW] Is WAL busy_timeout=5000 sufficient under sustained 8-worker completion load? Not measured. Under extreme load, the exclusive lock queue could grow beyond 5 seconds. Monitoring this in production would confirm whether the timeout needs to increase. (source: adversarial-performance)

6.2. [LOW] The jitter is 2-10s by default but the test assertion uses a +0.5s fudge factor making it nearly meaningless for detecting actual jitter vs a constant. The test is too weak to distinguish random.uniform from JITTER_MAX. (source: adversarial-testing, tests/test_batch_scheduler.py:263-283)

6.3. [LOW] If a channel has 0 pending videos but is in cooldown, it won't be in `_get_pending_channels()` so won't be yielded. The cooldown will persist until it expires but is functionally irrelevant since no work exists. This is acceptable behavior but worth noting. (source: adversarial-state-machine)
