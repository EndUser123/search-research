## Intent Summary

GTO v3 session chain analysis memoization caches expensive LLM-powered cross-session analysis results to `~/.claude/.evidence/gto-sessions/{session_id}.json`, keyed by session file mtime and chain composition. On cache hit, the analysis is served without an LLM call. On cache miss, the full critique loop runs and the result is persisted.

## Health Score: 35% — Warning

The implementation has correct core logic but 5 HIGH-severity correctness issues (cache corruption on interrupt, path traversal, stale data return for origin session, missing test coverage), plus significant performance degradation from O(n) sequential filesystem operations.

## Logical Gaps & Inconsistencies

1.1. [HIGH] Origin session mtime not validated after cache load — `session_memoizer.py:213`: After loading the origin session's cache and verifying its `chain_signature`, the code never re-validates the origin session's own transcript mtime. Only non-origin sessions are checked in the loop at lines 220–235. If the origin session's transcript file changes after caching, `get_cached_chain_result` returns stale cached analysis. This is the highest-impact correctness bug.

1.2. [HIGH] Missing transcript_path skips mtime validation silently — `session_memoizer.py:227`: The loop checks `if transcript_path:` and `continue`s when absent, bypassing mtime validation entirely. A session entry with no `transcript_path` can produce a cache hit even if its underlying transcript was modified. Session is added to missed list only if it has no cache or mismatched chain_signature — not for mtime staleness.

1.3. [HIGH] Non-atomic cache write can corrupt on interrupt — `session_memoizer.py:128`: `open(cache_path, "w")` truncates the file immediately before `json.dump()` completes. A process kill or crash between truncate and write leaves a corrupted JSON file. On next load, `json.JSONDecodeError` is caught and the cache is silently discarded, losing the cached entry permanently.

1.4. [HIGH] Path traversal via unsanitized session_id — `session_memoizer.py:58`: `_get_session_cache_path()` uses session_id directly in the file path with no sanitization. A malicious session_id containing `../` can escape the cache directory. While session_id derives from Claude Code internals (UUIDs), the code should be defense-in-depth. Fix: validate resolved path is within cache directory.

1.5. [HIGH] TOCTOU between exists() and open() — `session_memoizer.py:86`: `cache_path.exists()` is checked before `open()`. On a concurrent or network filesystem, the file could be deleted between check and open. The `except OSError` catches the resulting `FileNotFoundError`, but the `exists()` check is redundant and creates a misleading appearance of safety.

1.6. [MEDIUM] TOCTOU between mtime capture and cache write — `session_memoizer.py:259`: `mtime = _get_session_mtime(transcript_path)` is captured before calling `_save_session_cache()`. The transcript file could change between capture and write, causing the cached entry to have a mismatched mtime. Not caught until next cache check.

1.7. [MEDIUM] chain_depth not validated on cache retrieval — `session_memoizer.py:172`: The cached `chain_depth` is not checked against `len(entries)` on retrieval. While `chain_signature` provides stronger validation, `chain_depth` serves as an independent consistency check.

## Hidden Assumptions & Fragile Dependencies

2.1. [HIGH] No unit tests for session_memoizer module — Zero test coverage for a correctness-critical cache layer. Cache invalidation logic (mtime checks, chain_signature validation, path traversal blocking) is entirely untested.

2.2. [HIGH] No integration tests for orchestrator cache integration — `gto_orchestrator.py:1007–1080`: The integration point in `_run_session_chain_analysis` has no tests verifying cache hit returns cached result, cache miss runs analysis, or write failures are handled gracefully.

2.3. [MEDIUM] Cache write has no exception handling in orchestrator — `gto_orchestrator.py:1063`: `memoizer.cache_session_result()` is called without `try/except`. Disk full or permission errors propagate and fail the entire analysis even though the LLM call succeeded.

2.4. [MEDIUM] Cache immortalizes bad analysis — No TTL or expiry. If the LLM produces a confabulated or contextually wrong analysis for a session, that error persists in the cache indefinitely. Only mtime changes or manual `clear_cache()` can invalidate it.

2.5. [LOW] Unvalidated result dict schema — `session_memoizer.py:100`: The cached `result` dict is stored and returned without validating required fields exist. Malformed cache data could cause `KeyError` or return incomplete results to consumers.

## Risks and Edge Cases

4.1. [MEDIUM] `Path.home()` can raise RuntimeError — `session_memoizer.py:51`: If HOME/USERPROFILE is not set, `_get_sessions_cache_dir()` throws at module load, breaking the entire GTO orchestrator. Windows and CI environments can have unusual HOME configurations.

4.2. [LOW] Redundant cache load wastes one file read — `session_memoizer.py:205`: Origin session is loaded at line 205, then again at line 220 inside the loop. Saves nothing on the first call.

4.3. [LOW] Redundant mkdir on every write — `session_memoizer.py:118`: `cache_path.parent.mkdir(parents=True, exist_ok=True)` runs on every save even though `_get_sessions_cache_dir()` already ensures the directory exists.

4.4. [LOW] Empty chain_signature ambiguous — `session_memoizer.py:192`: Returns `(None, [])` for both "empty chain" and "cache not found", obscuring which case occurred.

4.5. [LOW] Cache miss double-counting — `session_memoizer.py:238`: A session that fails multiple checks is appended to `missed_sessions` multiple times before deduplication at return. The `_cache_misses` counter reflects the pre-dedupe count.

## Concrete Recommendations

5.1. [HIGH] Add path containment validation in `_get_session_cache_path()` — `session_memoizer.py:58`: Use `Path.resolve()` and verify `resolved_path.is_relative_to(cache_dir)` before returning.

5.2. [HIGH] Fix non-atomic write using `os.replace()` pattern — `session_memoizer.py:128`: Write to `cache_path.with_suffix('.tmp')`, then `os.replace(tmp, cache_path)`.

5.3. [HIGH] Remove `exists()` check before open — `session_memoizer.py:86`: Let `open()` raise `FileNotFoundError` naturally; the existing `except OSError` handles it.

5.4. [HIGH] Fix origin session mtime validation gap — `session_memoizer.py:213`: After verifying chain_signature, add mtime check for origin session using the same pattern as non-origin sessions.

5.5. [HIGH] Fix missing transcript_path handling — `session_memoizer.py:227`: Change `if transcript_path:` to `if not transcript_path: missed_sessions.append(sid); continue`.

5.6. [MEDIUM] Add TTL-based cache expiry — Add `expires_at` field, reject cache entries older than e.g. 7 days as a safety net against immortalized errors.

5.7. [MEDIUM] Hash chain_signature to prevent session relationship leakage — `session_memoizer.py:74`: Store `hashlib.sha256(chain_signature.encode()).hexdigest()` instead of raw session IDs.

5.8. [MEDIUM] Add fallback for `Path.home()` failure — `session_memoizer.py:51`: Catch `RuntimeError` and fall back to `/tmp/.claude/.evidence/gto-sessions/` with a warning log.

5.9. [MEDIUM] Use `cache_path.unlink(missing_ok=True)` in `clear_cache()` — `session_memoizer.py:280`: Remove the redundant `exists()` check.

## Open Questions / Unknowns

6.1. [LOW] What is the maximum expected chain depth? The code handles arbitrary depth but no upper bound is enforced. Should there be a `MAX_CHAIN_DEPTH` constant? (source: meta-critique)

6.2. [LOW] Should the cache be invalidated if any session in the chain is modified (not just the origin)? Currently only mtime changes on individual session files trigger invalidation. Should adding a new session to the chain invalidate caches for all prior sessions? (source: meta-critique)

6.3. [LOW] Should cache entries include a content hash of the session transcript (not just mtime)? mtime can change without content changing (e.g., touch), causing unnecessary cache misses. (source: adversarial-io-validation)
