## Logical Gaps & Inconsistencies

1.1. [MEDIUM] **metadata=None crash in _diversify_results** (claude_history_backend.py:300)

`result.get("metadata", {})` returns `None` when the key exists with value `None` — Python's `dict.get()` returns the default only when the key is absent, not when the key's value is `None`. Calling `.get("session_id", "unknown")` on `None` raises `AttributeError: 'NoneType' object has no attribute 'get'`.

**Verification:** Confirmed at line 300 — the pattern `result.get("metadata", {}).get("session_id", "unknown")` is vulnerable to `metadata=None`.

**Fix:** `(result.get("metadata") or {}).get("session_id", "unknown")`

## Hidden Assumptions & Fragile Dependencies

2.1. [MEDIUM] **max_per_session=0 bypasses diversification entirely** (claude_history_backend.py:316)

When `max_per_session=0`, the round-robin loop runs `range(0)` = empty, adding zero results. The fallback then adds ALL remaining results sorted only by score. The diversification contract is silently violated — callers expecting session-limited results get score-only ordering.

**Verification:** Confirmed — `max_rounds = max_per_session` at line 316; with `max_per_session=0`, the loop at lines 317-325 never executes.

**Fix:** Early guard at function start: `if max_per_session <= 0: return sorted(results, key=lambda x: x.get("score", 0), reverse=True)[:limit]`

2.2. [MEDIUM] **LEFT JOIN + project filter silently drops orphaned messages** (claude_history_backend.py:244)

In `_like_search()`, when a `project` filter is specified, the query appends `AND s.project_id = ?`. The `LEFT JOIN sessions s` returns `NULL` for `s.project_id` when no session matches `m.session_id`. `NULL = ?` is always false, so messages from unmatched sessions are silently excluded from project-filtered results.

**Verification:** Confirmed at line 244 — `sql += " AND s.project_id = ?"` follows a `LEFT JOIN sessions s ON s.session_key = m.session_id`.

**Fix:** Change to `INNER JOIN` when project filter is used, or add `OR s.project_id IS NULL` clause to include orphaned messages.

2.3. [LOW] **_fts5_search returns None vs _like_search returns [] — inconsistent return types** (claude_history_backend.py:131)

`_fts5_search` returns `list[SearchResult] | None` (None triggers fallback), while `_like_search` returns `list[SearchResult]` (empty list = no results). The caller already handles this correctly, but the inconsistency complicates maintenance and future changes.

**Fix:** Standardize `_fts5_search` to raise on SQLite errors instead of returning None.

## Risks and Edge Cases

4.2. [LOW] **max_per_session=2 could starve high-similarity sessions** when user wants relevance-first ordering rather than diverse coverage. The default of 2 is hardcoded and not configurable at the search() API level.

## Concrete Recommendations

5.1. [MEDIUM] Fix metadata access at line 300: change `result.get("metadata", {}).get("session_id", "unknown")` to `(result.get("metadata") or {}).get("session_id", "unknown")` — converts falsy metadata (None, {}) to safe empty dict.

5.2. [MEDIUM] Add max_per_session=0 guard at line 294: add `if max_per_session <= 0: sorted_results = sorted(results, key=lambda x: x.get("score", 0), reverse=True); return sorted_results[:limit]` before session grouping.

5.3. [MEDIUM] Fix LEFT JOIN NULL handling at line 244: change `LEFT JOIN sessions s` to `JOIN sessions s` when project filter is used. Alternatively: `AND (s.project_id = ? OR s.project_id IS NULL)`.

5.4. [LOW] Escape LIKE wildcards in _like_search: `re.escape(query)` on the input before building LIKE patterns to prevent `_` and `%` in search terms from acting as wildcards.

5.5. [LOW] Add test cases for malformed metadata: `test_diversify_results_metadata_none`, `test_diversify_results_missing_session_id`.

5.6. [LOW] Consider making max_per_session configurable via search() kwargs, with documented tradeoffs between diversity-first and relevance-first modes.
