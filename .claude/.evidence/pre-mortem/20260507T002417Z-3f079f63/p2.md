## Cross-Agent Contradictions

1. **notebook_id scoping assumption** — adversarial-logic (LOGIC-003) treats nlm_source_id as potentially notebook-scoped and flags it as a correctness bug. adversarial-security, adversarial-quality, and adversarial-testing all missed this entirely. No specialist confirmed whether nlm_source_id is notebook-scoped or globally unique. The finding stands but is unverified.

2. **Severity for the profile bypass** — adversarial-security, adversarial-logic, and adversarial-quality all correctly identify this as CRITICAL/BLOCKER/HIGH. But adversarial-testing rated it HIGH rather than CRITICAL. The bypass is a guaranteed PERMISSION_DENIED failure when NOTEBOOKLM_PROFILE is set — that warrants CRITICAL given the definition in Phase 1 rubric.

3. **parse_nlm_output severity** — adversarial-logic (LOGIC-004) rates it MEDIUM. adversarial-testing (TEST-004) rates it MEDIUM. adversarial-quality doesn't mention it. It's not over/under-stated but is under-weighted — a NULL source_id in the DB is a data integrity issue, arguably HIGH for correctness.

## Severity Calibration Issues

1. **Profile bypass**: adversarial-security=CRITICAL, adversarial-logic=BLOCKER, adversarial-quality=HIGH, adversarial-testing=HIGH. The range spans CRITICAL/BLOCKER vs HIGH. Given that every `export_composite()` call WILL fail with PERMISSION_DENIED under noninteractive mode (guaranteed failure, not probability), this is clearly CRITICAL — consistent with security and logic specialists, inconsistent with quality and testing.

2. **Test gap**: All four specialists agree it's HIGH. Calibration is consistent.

3. **bare except**: Only adversarial-quality flagged it. Nobody else mentioned error handling in their domain. This is a precision gap in the other specialists — they focused exclusively on the profile bypass and didn't inspect error handling despite it being in scope.

4. **notebook_id validation**: Only adversarial-quality flagged it as MEDIUM. Others missed it. Consistent rating where found, but recall failure.

## Missed Blind Spots

1. **Isolation between export_composite calls** — None of the four specialists examined whether concurrent `export_composite()` calls on the same composite could race. The module docstring references FM-010 (InterProcessLock) at a higher level, but `export_composite()` itself has no per-composite locking. If two processes call `export_composite()` simultaneously for the same composite_id with different content, the idempotency check race could produce inconsistent DB state. This is a concurrency blind spot.

2. **nlm_source_id lifecycle** — No specialist examined what happens when a source is deleted from NotebookLM. The idempotency check would return a stale nlm_source_id that no longer exists in NotebookLM. Downstream consumers querying by source_id would find nothing.

3. **_cleanup_tmp silent failure** — `_cleanup_tmp` is called in multiple exception handlers but swallows all errors silently with bare except pass. If cleanup itself fails (e.g., permission denied), it is invisible.

4. **tmp_path in content hash** — `_make_composite` generates `content_hash` from sorted video_ids only (line 170). It does NOT include the tmp_path or any other state. But `content_hash` is stored in the DB and used for idempotency. If the same set of videos is exported to different tmp_path locations (e.g., different machines with different `P:` drive configurations), the content_hash remains identical but the file content is stored at different paths. This could cause "already exported" to be skipped even though the export path is non-portable.

## Precision Failures

1. **adversarial-quality QUAL-001 code_fix references non-existent function** — The recommended `nlm_auth_guard.get_nlm_executable()` doesn't exist in nlm_auth_guard.py (only `build_nlm_command()`). The fix should use `build_nlm_command()` instead, or just use `run_nlm()` directly which handles binary resolution internally. The code_fix is not actionable as written.

2. **adversarial-security SEC-NLM-002 code_fix patch path is wrong** — The recommended fix patches `'csf.nlm_auth_guard.run_nlm'` in a context where the module already imports run_nlm at module level (line 229). The correct patch path depends on whether `nlm_auth_guard` is imported at the module level of nlm_exporter.py or only used inline. The recommendation doesn't account for this.

3. **adversarial-testing TEST-003 code_fix patch path is wrong** — Same issue. The patch path `'csf.nlm_exporter.nlm_auth_guard.run_nlm'` assumes nlm_auth_guard is imported at module level in nlm_exporter.py, which it currently is NOT (it's imported inside the try block). After the fix is applied, nlm_auth_guard will be imported at module level, making the patch path valid. The recommendation is only correct after the primary fix is applied.
