## Section 3: Blind Spots

### BLIND-001. [HIGH] SKILL.md dispatch uses non-existent Agent subagent types — no specialist caught the root cause

All three active specialists (compliance, quality, logic) confirmed the symptom: "subagents don't exist" or "not implemented." **None identified why they don't exist:** The SKILL.md references `Agent(subagent_type="gto-logic")`, `Agent(subagent_type="gto-quality")`, `Agent(subagent_type="gto-code-critic")`. The registered subagent types in `P:/.claude/agents/` are `adversarial-*` variants, not `gto-*` variants. The gap is not that subagents were never created — it is that SKILL.md uses the wrong naming convention entirely. The fix is not "create these three subagents" but "use existing adversarial-* types or register new gto-* subagents."

This is a **multi-turn reasoning chain blind spot**: each specialist independently identified "subagent X doesn't exist" without asking "what naming convention do registered subagents actually use?"

### BLIND-002. [HIGH] No specialist examined the polling loop's AGENT_PIDS dependency

SKILL.md step 4 (lines 148-165) relies on `${AGENT_PIDS[@]}` for exit code verification. adversarial-logic's open question #3 flags uncertainty about whether `Agent` tool dispatch populates `AGENT_PIDS` via `PIDS=($!)`. **None of the specialists actually verified this.** The polling loop's correctness (LOGIC-002: exit without wait) is assessed in isolation without checking whether the PIDs array it depends on is even populated. If `AGENT_PIDS` is empty, the exit code verification in step 4 does nothing at all.

### BLIND-003. [MEDIUM] No specialist examined the `enable_subagents=True` code path

gto_orchestrator.py `_run_subagents()` (line 453) returns empty dict when `enable_subagents=False`. When `enable_subagents=True` (the path SKILL.md describes), what happens? The method calls `find_gaps()` from GapFinderSubagent — **not the Agent-dispatched correctness subagents**. No specialist traced through `enable_subagents=True` to see if it actually routes to the described Agent dispatch workflow. The work.md claims a rewrite happened, but the actual code path still uses GapFinderSubagent. This should have been the **first finding** — the work description does not match what the code does in either flag state.

### BLIND-004. [MEDIUM] merge_agent_results.py field mismatch — no specialist traced to Gap dataclass consumer

adversarial-quality (QUAL-004) correctly identified that `REQUIRED_FIELDS = {'id', 'severity', 'location', 'title'}` doesn't match Gap dataclass fields (`gap_id`, `severity`, `file_path`, `line_number`, `message`). However, no specialist asked: **what consumes the Gap dataclass, and does the mismatch matter at runtime?** If GTO's output pipeline actually serializes Gap objects via `to_dict()`, the field mismatch would cause silent data loss in the final JSON artifact — but only if merge_agent_results.py is ever called. Since it's orphaned (QUAL-002), the mismatch has no runtime effect, only documentation effect. The severity of QUAL-004 should be contextualized by the orphaned status, which no specialist did.
