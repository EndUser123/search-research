# Phase 3: Synthesized Refined Critique — yt-is batch optimization

## Intent Summary
Wired `_fetch_via_notebooklm_batch` into the transcript chain via a thin `_fetch_via_notebooklm` wrapper. The batch function creates one notebook, adds up to 300 YouTube sources at once with `--wait`, then extracts raw transcript content per source using `nlm source content`. Real integration test confirmed 2.2x speedup (42s batch vs 91s sequential for 3 videos). The optimization is real and working but has correctness and test gaps that surface under adversarial analysis.

## Logical Gaps & Inconsistencies

1.1. [HIGH] Dead except clause — catches wrong exception type (transcript.py:1195)
- Source: adversarial-logic (LOGIC-001), confirmed by code inspection
- `except json.JSONDecodeError` only catches JSON parse failures. After `json.loads()` succeeds (line 1172), subsequent `sources_data.get("sources", [])` (line 1177) raises `AttributeError` if `sources_data` is a list (which the code handles at line 1174-1175). The except block never catches this. Malformed API responses silently proceed with empty `vid_to_source`, causing all videos to fail with "source not found in notebook" — a misleading error masking the real parse failure.
- Fix: Replace `except json.JSONDecodeError` with `except (json.JSONDecodeError, AttributeError, TypeError)`

1.2. [MEDIUM] Video ID regex applied to titles (transcript.py:1187)
- Source: adversarial-logic (LOGIC-002)
- The same URL regex `[?&]v=([a-zA-Z0-9_-]{11})` is applied to source titles at line 1187, which may contain plain-text references to other videos or arbitrary strings that match the 11-char pattern. Fake video IDs extracted from titles cause correct sources to be silently mismatched, resulting in wrong transcripts mapped to wrong video IDs.
- Fix: Remove title-extraction fallback, or require `youtube.com/watch` context in title

## Hidden Assumptions & Fragile Dependencies

2.1. [HIGH] `lang` parameter is silently ignored — a cross-specialist theme confirmed by code
- Source: adversarial-testing (TEST-NLM-002) + inference from code
- `_fetch_via_notebooklm(video_id, lang)` accepts `lang` at line 1224 but never passes it to `_fetch_via_notebooklm_batch([video_id])` at line 1241. The batch function has no lang parameter. Docstring at line 1235-1236 acknowledges it: "lang: BCP-47 language code (currently unused)." This is a silent no-op — callers passing language preferences have no effect.
- Fix: Either wire `lang` through the batch chain or remove the parameter entirely. Adding it later as a breaking change is worse.

2.2. [MEDIUM] `vid_to_source` fallback to positional ordering is fragile (transcript.py:1192-1194)
- Source: adversarial-testing (TEST-NLM-005)
- When URL extraction fails for a source, the code falls back to `batch_ids[idx]` assuming sources appear in the same order as input video IDs. This assumption holds only if the NotebookLM API returns sources in insertion order — no contract guarantees this. Wrong transcripts silently mapped to wrong video IDs.
- The fallback triggers when `_extract_video_id_from_url(src_title)` returns None — which happens for any source whose title doesn't contain a YouTube URL pattern.

2.3. [MEDIUM] No test for `YTIS_NLM_MAX_SOURCES_PER_NOTEBOOK` env var cap (transcript.py:1131-1137)
- Source: adversarial-testing (TEST-NLM-003)
- The cap of 300 is enforced at line 1137 via slicing. No test verifies truncation behavior or env var override. If the env var name is mistyped (note: the code has a typo in the env var name — `NOTEBOOK` vs `NOTEBOOK`), it would silently use the default and not honor user configuration.

2.4. [MEDIUM] `_ensure_nlm_auth` failure path is untested and produces ambiguous errors (transcript.py:1128-1129)
- Source: adversarial-testing (TEST-NLM-007)
- When `_ensure_nlm_auth()` returns False, the batch function returns `"nlm auth failed"` for all videos. The caller chain has no special handling for auth failures vs other failure modes. Production auth failures would produce identical error signatures to notebook creation failures, making debugging difficult.

## Missing Obvious Actions / Best Practices

3.1. [HIGH] `_fetch_via_notebooklm_batch` has zero dedicated unit tests
- Source: adversarial-testing (TEST-NLM-001)
- The function is only tested indirectly via mock patches on `_fetch_via_notebooklm` in the fallback chain. Internal error paths (auth failure, notebook create failure, source add failure, source list failure, JSON parse failure, content < 20 chars, empty video_ids) are completely untested. Any regression in batch-specific logic will not be caught.
- Fix: Add unit tests with subprocess mocks covering each error path

3.2. [HIGH] No test for concurrent content fetch behavior
- Source: adversarial-performance (PERF-001) cross-referenced with testing
- The sequential content fetch loop (lines 1199-1212) is a performance bottleneck at scale. No test validates concurrent behavior. If ThreadPoolExecutor is added later, there is no test to confirm parallel execution or catch regressions in concurrency logic.

3.3. [MEDIUM] No test for content length threshold (20 chars) boundary
- Source: adversarial-testing (TEST-NLM-004)
- Line 1209 discards transcripts ≤ 20 chars silently. No test verifies behavior at exactly 19, 20, 21 characters. If the threshold changes, no test catches it.
- Fix: Add parameterized test for boundary values

3.4. [MEDIUM] No test for `_parse_notebook_id` returning None
- Source: adversarial-testing (TEST-NLM-008)
- If the notebook create output format changes, `_parse_notebook_id` returns None and all videos fail with "parse notebook ID failed." No test exercises this path (line 1148-1150).

## Risks and Edge Cases

4.1. [HIGH] Sequential subprocess calls in content fetch loop — verified bottleneck at scale
- Source: adversarial-performance (PERF-001), confirmed by code inspection
- Lines 1199-1212 call `subprocess.run(["nlm", "source", "content", source_id])` sequentially per video, each blocking up to 60s. For 300 videos at 2s average: 600s of sequential blocking I/O. The 2.2x speedup was measured at N=3 where notebook creation overhead dominates. At scale, this loop becomes the bottleneck. The fix is to parallelize with `ThreadPoolExecutor(max_workers=15)`.
- Note: Severity HIGH is justified by the scale regression (the optimization that works at N=3 provides no benefit at N=300 due to this loop).

4.2. [MEDIUM] ThreadPoolExecutor with max_workers=1 provides no throughput parallelism
- Source: adversarial-performance (PERF-002)
- Lines 370, 416, 895 each use `ThreadPoolExecutor(max_workers=1)` — this is timeout-asynchronous wrapping only, not throughput parallelism. The finding is correctly rated MEDIUM because it is a missed optimization rather than a correctness bug. However, if the intent was throughput parallelism, these locations should be flagged for review.

4.3. [LOW] JSON parse failure silently swallowed — redundant with LOGIC-001
- Source: adversarial-testing (TEST-NLM-006)
- `except json.JSONDecodeError: pass` at line 1195 with no error propagation. This is the same root cause as LOGIC-001 (wrong exception type). The two findings are different perspectives on the same bug. The consolidation should merge them.

## Concrete Recommendations

5.1. [HIGH] Fix exception handling in `_fetch_via_notebooklm_batch` (transcript.py:1195)
- Specific change: Replace `except json.JSONDecodeError` with `except (json.JSONDecodeError, AttributeError, TypeError)` and add error propagation so malformed API responses fail clearly instead of silently proceeding with empty mapping.

5.2. [HIGH] Add unit tests for `_fetch_via_notebooklm_batch`
- Specific change: Add dedicated unit tests with subprocess mocks covering each error path: auth failure, notebook create failure, source add failure, source list failure, JSON parse failure, content < 20 chars, empty video_ids list, and truncation at 300-video cap.

5.3. [MEDIUM] Wire or remove the `lang` parameter (transcript.py:1224)
- Specific change: Either pass `lang` through to `_fetch_via_notebooklm_batch` and document how it affects behavior, or remove the parameter from the function signature. Silent no-op parameters are worse than absent parameters — they create false expectations.

5.4. [MEDIUM] Parallelize content fetch loop with ThreadPoolExecutor (transcript.py:1199-1212)
- Specific change: Replace sequential loop with `ThreadPoolExecutor(max_workers=15)` to reduce 300×2s = 600s sequential blocking to ~40-60s parallel. Keep workers modest to avoid NotebookLM rate limits.

5.5. [MEDIUM] Remove title-extraction fallback or add YouTube context requirement (transcript.py:1187)
- Specific change: Remove `vid = _extract_video_id_from_url(src_title)` or add a check that the title actually contains `youtube.com/watch` before applying the regex. Titles can legitimately contain strings that match the video ID pattern without being URLs.

5.6. [LOW] Add boundary test for 20-char content threshold (transcript.py:1209)
- Specific change: Add parameterized test verifying 19-char content is rejected, 20-char is accepted, 21-char is accepted. Document the threshold in a constant.

## Open Questions / Unknowns

6.1. [LOW] Does NotebookLM guarantee source ordering in `nlm source list --json` output?
- Source: adversarial-testing (TEST-NLM-005) inference
- The positional fallback at lines 1192-1194 assumes sources are returned in insertion order. No NotebookLM documentation confirms this ordering guarantee. If order is not guaranteed, the fallback maps wrong transcripts to wrong videos.

6.2. [LOW] Does NotebookLM `nlm source content` respect language preferences?
- Source: adversarial-testing (TEST-NLM-002) inference
- The `lang` parameter is passed unused. It is unclear whether NotebookLM's source content extraction has any language filtering capability. If it does, the batch function should expose it; if it doesn't, the parameter should be removed.

6.3. [LOW] What is the actual rate limit for `nlm source content` calls?
- Source: adversarial-performance (PERF-001) inference
- PERF-001 recommends max_workers=15 to avoid rate limits. This number is not validated. If NotebookLM rate limits are lower, the parallelization gain is smaller than estimated.
