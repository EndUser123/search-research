## Missed Blind Spots

1. **No specialist examined the entity extraction flow as the actual failure path** — All specialists focused on the rstrip bug and the fix. But the *reason* the runtime-construct fallback at lines 296-304 existed was to handle cases where entities ARE extracted but entity-based verification fails. The adversarial-quality (QUAL-002) flagged the substring matching at line 296 as LOW, but didn't trace through what happens when the entity IS extracted (which it always is via `no\s+(\S+)`). In the failing test case: entities = {'subprocess'}, entity-based loop checks 'subprocess' in file path 'config.json' → False, returns False. The runtime fallback at lines 296 is inside `if not entities:` so it never runs. The substring matching at line 296 is therefore unreachable dead code for this claim type — a specialist should have verified reachability.

2. **No specialist examined the `_should_exempt_claim` function as a parallel path** — `_claim_was_verified_this_turn` (the new function) and `_should_exempt_claim` (the original function) both handle claim exemption. adversarial-logic only examined the new function. If these two functions have different logic for the same claim, the guard could behave inconsistently depending on which path is taken. No specialist verified whether `_should_exempt_claim` would also exempt or block "There's no subprocess" — this is a cross-function interaction blind spot.

3. **adversarial-testing did not verify the full exemption flow end-to-end** — TEST-001 focused on test coverage gaps, but no specialist traced the actual execution path: `_guard_exists` → `_check_claims` → `_claim_was_verified_this_turn` → returns True/False → `_should_exempt_claim`. The TEST-001 finding about singular subprocess without verification assumes the new function is the only path, but `_should_exempt_claim` at line 420 uses Grep-only word-boundary logic — different semantics. If the claim flows through `_should_exempt_claim` instead of `_claim_was_verified_this_turn`, the rstrip fix is irrelevant.

## Precision Failures

1. **QUAL-001's "plural entity extraction mismatch" framing is imprecise** — The finding says "no normalization between claim and tool evidence" causing rstrip corruption. But the actual bug was: `"subprocess".rstrip("s")` produces `"subproce"`, which is a pure string manipulation error, not an entity-normalization design flaw. The fix (word-boundary regex without stripping) is correct but the finding's framing suggests a deeper normalization problem that doesn't exist. The real lesson is: don't use string manipulation to normalize when a regex word boundary achieves the same result correctly.

2. **IO-002 (empty tool_events + empty evidence_store → blocking) is not a finding** — This is correctly identified as "fail-safe correct behavior" but listed as a MEDIUM finding anyway. A finding that recommends *no action* ("consider adding a comment") and acknowledges the behavior is correct should not be MEDIUM severity. This is informational, not a gap.

3. **TEST-004 (comment misleading about rstrip as fallback) duplicates QUAL-001** — Both adversarial-quality and adversarial-testing flagged the same comment as misleading, with the same root cause analysis. This is a recall failure — the Phase 1 consolidation didn't deduplicate findings across specialists.
