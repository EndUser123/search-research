## Cross-Agent Contradictions
1. No direct contradictions — all specialists agree the TOCTOU path guard is broken. Security and IO-validation both flag it as HIGH, logic catches the mode validation gap as BLOCKER. No specialist says something is safe while another says it's risky.

## Severity Calibration Issues
1. adversarial-logic rated LOGIC-001 (compare mode 400 error) as BLOCKER while adversarial-compliance rated COMP-001 (port mismatch) as HIGH — both make the service completely non-functional. Either is a complete dispatch failure. Should both be BLOCKER or at minimum CRITICAL.
2. adversarial-security rated SEC-002 (model JSON → tool actions, prompt injection) as HIGH while adversarial-io-validation did not independently flag the same mechanism — the code agent loop JSON execution was only covered by security. IO-validation focused on Bifrost response validation but missed the model output → action execution path.
3. adversarial-compliance rated COMP-001 (port mismatch) as HIGH while it is actually a complete dispatch blocker. Severity should be BLOCKER/CRITICAL per consistency with LOGIC-001.

## Missed Blind Spots
1. No specialist flagged that REQUEST_TIMEOUT_MS env var parsing happens at import time and is never re-read — if the service is long-running and env vars change, the stale value persists with no reload mechanism.
2. No specialist noted that BF_CODE_MAX_TURNS is not validated to be positive — a value of 0 would cause the code agent loop to exit immediately without processing.
3. The /bf/compare endpoint has no authentication or rate limiting — an attacker who can reach the service can trigger unlimited parallel model calls, potentially running up costs.
4. No specialist flagged that the compare graph uses SYNTHESIS_MODEL for the synthesis pass but there's no guard preventing SYNTHESIS_MODEL from being one of the models being compared — self-synthesis could produce biased results.
5. The LangGraph graph is rebuilt on every /bf/compare request (build_graph called in handler). For large model lists this is wasteful — no caching or reuse.

## Precision Failures
1. adversarial-compliance COMP-004 (enforcement: advisory is inert) is LOW severity — correctly sized. The field is cosmetic, not a security or functional issue.
2. adversarial-io-validation IO-007 (log_event TypeError from non-serializable extra) is LOW — the try/except in tool_read_file etc. would catch it, but log_event itself has no inner try/except. Impact is unclear since extra is constructed from controlled fields (strings, ints, bools). Mild.
3. adversarial-security SEC-005 (mkdir arbitrary directories) is LOW — mkdir is within allowed root. The real risk is from SEC-001+SEC-002, not the mkdir alone.

## Improvements to the Phase 1 Findings
1. The BLOCKER classification from LOGIC-001 should propagate to COMP-001 and be re-labeled CRITICAL or BLOCKER — they are the same root cause (service not configured correctly for the dispatch contract).
2. SEC-002 (model JSON as tool actions) deserves cross-reference to LOGIC-001 — the mode validation gap means compare is inaccessible, but code mode IS accessible via /bf/code and has the injection risk. The pre-mortem should have flagged code mode as the injection attack surface.
3. IO-001 (BF_ALLOWED_ROOT not validated) and SEC-001 (TOCTOU) are the same finding at different layers. A joint HIGH finding rather than two separate HIGHs would be more accurate.
4. Missing: the startup validation gap (BF_ALLOWED_ROOT, REQUEST_TIMEOUT_MS=0, BF_CODE_MAX_TURNS=0) should be consolidated into a "startup configuration hardening" recommendation.
