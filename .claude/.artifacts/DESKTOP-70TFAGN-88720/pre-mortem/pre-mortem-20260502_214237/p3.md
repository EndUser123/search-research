# Phase 3: Synthesized Refined Critique

## Intent Summary
Fix the `sync_single_repo()` commit loop in `sync.py` to correctly detect and commit worktree changes, replacing a broken `has_changes` check with `_has_uncommitted_worktree_changes(repo)`. The commit loop stages changes, checks for remaining worktree dirt, commits if dirty, and retries until clean or iteration limit is reached.

The commit loop is structurally sound but has one correctness issue (LOGIC-001), one medium-severity error handling gap (QUAL-001), and zero test coverage. The highest-priority items are: (1) the max_iterations guard placement, and (2) adding test coverage.

## Logical Gaps & Inconsistencies

1.1. [HIGH] (source: adversarial-logic, sync.py:883-885) — max_iterations guard fires AFTER the commit block. When max_iterations reaches 0 during a commit iteration, the loop: (a) decrements counter to 0 at line 855, (b) stages at line 857, (c) detects dirty at line 863, (d) commits successfully (did_commit=True at line 879), (e) checks max_iterations <= 0 and breaks. Result: did_commit=True is returned, implying the sync completed, but the loop actually exhausted iterations. The guard placement means the commit executes on the same iteration that triggers the limit violation.

## Hidden Assumptions & Fragile Dependencies

2.1. [MEDIUM] (source: adversarial-quality, sync.py:912-913) — `_has_uncommitted_worktree_changes` returns False on git status failure, treating it as "no uncommitted changes." If git status fails due to corruption, permissions, or concurrent lock, the commit loop exits prematurely, leaving the repo dirty but reporting success. No way for the caller to distinguish "clean" from "git error."

2.2. [LOW] (source: adversarial-quality, sync.py:853) — max_iterations=20 is arbitrary with no documented derivation. In a high-churn multi-terminal environment, 20 iterations might not be sufficient, but no comment explains the limit's origin.

2.3. [LOW] (source: adversarial-io-validation, sync.py:847-848) — lock_file.unlink() has a TOCTOU window between exists() check and unlink(). A concurrent git process can recreate the lock between check and delete.

## Missing Obvious Actions / Best Practices

3.1. [HIGH] (source: adversarial-testing, test_sync.py) — Zero behavioral tests. The only test asserts `sync is not None`. The commit loop (lines 852-896), `_has_uncommitted_worktree_changes` (lines 899-930), and the auto-push logic (lines 887-893) are all untested. Any regression in these paths goes undetected.

3.2. [HIGH] (source: adversarial-testing, sync.py:857-858) — git add -A result is checked only for index.lock errors. If the command fails for any other reason (detached HEAD, .git not writable, out of disk space), execution falls through to `_has_uncommitted_worktree_changes` without indication that staging failed. The loop may attempt to commit on an incomplete or stale staging state.

## Risks and Edge Cases

4.1. [MEDIUM] (source: adversarial-io-validation, sync.py:872-875) — index.lock retry for git commit uses bare `continue` that restarts the entire loop (re-runs git add -A + git status). If the retry also hits index.lock, the failure is not re-checked on subsequent iterations — it falls through to the generic error handler at line 876. This can cause up to 20 iterations of repeated lock contention before giving up.

4.2. [MEDIUM] (source: adversarial-testing, sync.py:883-884) — Error message "Max iterations reached (0)" is misleading. After 20 decrements, max_iterations equals 0, but the original limit was 20. A developer debugging this message sees "(0)" and may think the limit was 0, not 20.

4.3. [LOW] (source: adversarial-io-validation, sync.py:858-861) — Second git add failure (after retry) is not validated. If it also fails, execution proceeds to `_has_uncommitted_worktree_changes` on a worktree that may not be fully staged.

## Concrete Recommendations

5.1. [HIGH] (source: adversarial-logic, sync.py:854-855) — Move the max_iterations check to the TOP of the loop, before staging:
```python
while True:
    if max_iterations <= 0:
        print(f"  X Max iterations reached, leaving dirty state")
        break
    max_iterations -= 1
```
This prevents committing on the iteration that exhausts the limit. The did_commit flag will correctly reflect whether a commit was actually made.

5.2. [HIGH] (source: adversarial-testing, test_sync.py) — Add behavioral tests for the commit loop and `_has_uncommitted_worktree_changes`. At minimum: verify the function ignores staged changes, handles index.lock retry, handles "nothing to commit" break, and handles max_iterations exit.

5.3. [HIGH] (source: adversarial-testing, sync.py:857-858) — Add non-zero returncode check for git add -A beyond index.lock:
```python
add_result = run("git add -A", cwd=worktree, silent=True)
if add_result.returncode != 0 and "index.lock" in add_result.stderr:
    time.sleep(0.5)
    add_result = run("git add -A", cwd=worktree, silent=True)
if add_result.returncode != 0:
    print(f"  X git add failed ({add_result.stderr.strip()[:100]}), leaving dirty state")
    break
```

5.4. [MEDIUM] (source: adversarial-quality, sync.py:912-913) — Return error indicator from `_has_uncommitted_worktree_changes` or add VERBOSE logging on git status failure. At minimum, don't silently treat git errors as "clean repo."

5.5. [MEDIUM] (source: adversarial-testing, sync.py:883-884) — Store original max_iterations value before the loop for clearer error messages: `print(f"  X Max iterations reached ({original_max})")`

5.6. [LOW] (source: adversarial-quality, sync.py:860,874) — Remove inline `import time` statements. Module-level `import time` at line 22 already covers all uses.

5.7. [LOW] (source: adversarial-quality, sync.py:853) — Add comment explaining max_iterations=20 derivation.
