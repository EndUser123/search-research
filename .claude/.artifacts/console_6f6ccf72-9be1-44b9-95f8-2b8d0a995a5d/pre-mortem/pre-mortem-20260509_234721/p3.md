# Pre-Mortem Final Critique — Stop_lazy_workaround_gate.py proximity detector fix

## Intent Summary

The work replaces a brittle regex pattern `(duplicates?|redundant|extra|double).*(is\s+)?(fine|acceptable|expected|normal|ok)` with a proximity-based keyword matcher `_check_duplicate_acceptance_proximity()` that only triggers when problem words and acceptance words are within 8 tokens of each other. It also extends ROOT_CAUSE_PHRASES bypass to handle investigation verb patterns. The goal is to eliminate false positives on documentation mentions like "ignoring duplication" while maintaining blocking on pure acceptance phrases like "duplicate is fine".

## Health Score: 70% (Warning)

The fix is functionally sound — 19 tests pass and the core detection logic works. However, one correctness bug (off-by-one in forward window) and three quality issues (duplicated bypass logic, inline import, unexamined state machine) reduce the score below the Healthy threshold.

## Logical Gaps & Inconsistencies

1.1. [HIGH] Off-by-one error in forward window (adversarial-logic, Stop_lazy_workaround_gate.py:73)

`end = min(i + _PROXIMITY_TOKENS + 1, len(tokens))` creates a 9-token window (indices i+1 through i+8 inclusive) when PROXIMITY_TOKENS=8. The backward window at line 81 correctly uses `start = max(0, i - _PROXIMITY_TOKENS)` without +1, making the two windows asymmetric. Text with exactly 8 tokens between a problem word and an acceptance word (e.g., "duplicate [tok1][tok2][tok3][tok4][tok5][tok6][tok7][tok8] fine") would be detected backward but NOT forward. This directly contradicts the stated contract of PROXIMITY_TOKENS=8 and the docstring promise of "within this many tokens of each other".

**Fix:** Change line 73 to `end = min(i + _PROXIMITY_TOKENS, len(tokens))`.

1.2. [MEDIUM] Off-by-one creates asymmetric detection behavior (adversarial-logic)

Acceptance words AFTER a problem word require 9 tokens of separation to trigger, while acceptance words BEFORE trigger at only 8 tokens. This is not a risk — it is a present functional gap. The same 8-token gap detected backward from "fine" to "duplicate" would NOT be detected forward from "duplicate" to "fine". This is a correctness issue, not a potential risk, and should be treated as HIGH.

## Hidden Assumptions & Fragile Dependencies

2.1. [MEDIUM] ROOT_CAUSE_PHRASES bypass duplicated at two locations (adversarial-quality, Stop_lazy_workaround_gate.py:170-171 and :203-204)

The same bypass check `if any(re.search(phrase, clean_lower) for phrase in ROOT_CAUSE_PHRASES):` appears at line 170-171 (after regex match) and line 203 (after proximity match). If the bypass logic needs to change in the future, both locations must be updated together. Currently both are correct, but the duplication is a maintenance risk.

**Fix:** Extract into a helper: `def _has_investigation_intent(text: str) -> bool: return any(re.search(p, text) for p in ROOT_CAUSE_PHRASES)`

2.2. [LOW] No test for the 8-token boundary condition

All 19 existing tests pass, but none explicitly test the boundary: a sentence with exactly 8 tokens between "duplicate" and "fine" should trigger in both directions. The off-by-one fix would go undetected in regression without a targeted boundary test.

2.3. [LOW] _strip_quoted_blocks state machine has implicit transitions (adversarial-quality, Stop_lazy_workaround_gate.py:115-144)

The skip/continue logic across multiple conditions is difficult to trace. Specifically, the interaction between `<system-reminder>` toggling and Stop-hook feedback pattern matching was not verified against all artifact pattern variants. LOW priority because tests exist, but the state machine is not obviously correct.

## Missing Obvious Actions / Best Practices

3.1. [MEDIUM] Extract bypass logic into helper function (adversarial-quality)

Both detection paths (regex at 170-171, proximity at 203-204) use identical `ROOT_CAUSE_PHRASES` bypass checks. Extracting to `_has_investigation_intent(clean_lower)` eliminates duplication and makes the bypass behavior changeable in one place.

3.2. [LOW] Move `import string` to module level (adversarial-quality, Stop_lazy_workaround_gate.py:66)

The `import string` statement inside `_check_duplicate_acceptance_proximity` executes on every call. Move to module level alongside `import re` and `import json` to avoid repeated import overhead and improve clarity.

3.3. [LOW] Add rationale comment for _PROXIMITY_TOKENS = 8 (adversarial-quality, Stop_lazy_workaround_gate.py:52)

The comment "Must be within this many tokens of each other" only restates the code. A rationale comment explaining why 8 tokens was chosen (enough context for "X is fine" detection, avoiding false positives from distant acceptance words) would prevent future maintainers from changing the value without understanding the design intent.

3.4. [LOW] Cache str.maketrans translation table at module level (adversarial-io-validation, Stop_lazy_workaround_gate.py:67)

`str.maketrans("", "", string.punctuation.replace("'", ""))` is created fresh on every call to `_check_duplicate_acceptance_proximity`. Cache at module level: `_PUNCTUATION_TABLE = str.maketrans("", "", string.punctuation.replace("'", ""))`.

## Risks and Edge Cases

4.1. [MEDIUM] Block message provides no diagnostic detail (adversarial-quality, Stop_lazy_workaround_gate.py:206-218)

When the proximity detector blocks a response, the message says "ignoring duplication" without specifying which problem word or acceptance word triggered it. For a blocking hook, this makes it difficult to understand why a legitimate response was blocked and to improve detection patterns. Not critical for end-users, but meaningful for hook development and debugging.

**Fix:** Extend `_check_duplicate_acceptance_proximity` to return `tuple[bool, list[str]]` — the matched words — and include them in the block message.

4.2. [LOW] stdin.read() blocks without input (adversarial-io-validation, Stop_lazy_workaround_gate.py:232)

Standard for hook pipes but worth noting: if the script is invoked without stdin data and without arguments, it blocks indefinitely. Acceptable for hooks but not a correctness issue.
