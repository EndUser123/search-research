## Severity Calibration Issues

1. **COMP-001 [HIGH] vs QUAL-006 [MEDIUM] — severity inversion** — COMP-001 (transcripts.sqlite schema undocumented) is rated HIGH while QUAL-006 (ingest dispatch has no atomicity or resume mechanism; crash mid-dispatch leaves partial state that re-dispatches on retry) is rated MEDIUM. The dispatch atomicity failure (QUAL-006) is a systemic hazard: a crash mid-dispatch leaves the manifest in a partial state with no recovery mechanism, causing duplicate wiki pages and duplicate yt-is calls on retry. COMP-001 is a documentation gap — the schema is referenced but not documented. Documentation gaps can be verified and fixed; a crash-prone dispatch with no idempotency key is an architectural defect. The severity rating for QUAL-006 should be at least HIGH, not MEDIUM. The calibration across specialists is inconsistent.

2. **QUAL-004 [LOW] vs QUAL-006 [MEDIUM] — same severity despite asymmetric impact** — Both are rated LOW/MEDIUM despite QUAL-004 (Gemini CLI subprocess crash with no manifest update) being recoverable by re-run, while QUAL-006 (partial dispatch state causing duplicate processing) creates data corruption risk. The severity gap is unjustified.

3. **COMP-003 [LOW] vs COMP-001 [HIGH] — architectural vs contractual gap treated differently** — COMP-003 (Option A decision not recorded) is [LOW] while COMP-001 (schema condition not documented) is [HIGH]. The Option A decision is equally architectural — both are documentation gaps that affect future maintainers. The severity differential is not justified by any stated criterion in either finding.

## Missed Blind Spots

1. **yt-is pipeline failure modes are not specified anywhere** — work.md states "Gemini CLI failover when transcripts.sqlite shows no_transcript for all methods exhausted." The yt-is pipeline has three stages (yt-dlp → Selenium → Gemini CLI). No Phase 1 specialist identified that the SKILL.md does not document which methods are tried in order, what "exhausted" means for each method, or what failure_reason values can appear in transcripts.sqlite beyond `no_transcript`. COMP-001 identifies the schema gap but does not ask what other failure_reason values exist or whether the SKILL.md correctly enumerates all trigger conditions.

2. **No specialist examined the QMD update command's error handling** — SKILL.md line 147 shows `qmd update wiki --lang en 2>$null; if ($LASTEXITCODE -ne 0) { qmd update wiki }`. The stderr redirect to null and automatic retry on non-zero exit are never evaluated for correctness or completeness. What happens if the second call also fails? What error state is propagated to the user? No Phase 1 specialist addressed this.

3. **No specialist examined the slug generation logic** — SKILL.md line 101: "Slug = lowercase alphanumeric + hyphens from filename." What happens with filenames containing unicode, multiple spaces, or other special characters? The slug generation HEREDOC is not tested (per QUAL-001), but no specialist flagged that slug generation edge cases could produce invalid filenames or collisions.

4. **The dispatch manifest schema has no stated contract** — SKILL.md describes the manifest as tracking `path`, `size`, `hash`, `status`, `tier` per entry. But there is no stated schema for what fields are required vs optional, what valid values `status` can take, or what happens if a field is missing. This is distinct from COMP-001 (transcripts.sqlite schema gap) — the manifest is the dispatch state machine, and its schema is equally undocumented.

## Precision Failures

1. **COMP-002 conflates two separate issues** — EVIDENCE_GAP appears in body text (lines 131-136) AND is absent from frontmatter schema (lines 109-125). The finding treats this as a single issue, but the root causes differ: (a) the frontmatter schema simply doesn't include `evidence_gaps` field, which is a straightforward schema addition; (b) the body text annotation format is underspecified — "flag any EVIDENCE_GAP" does not define the annotation syntax (is it `- EVIDENCE_GAP: <text>` or `[EVIDENCE_GAP]` or some other format?). COMP-002 does not distinguish between the schema omission and the body annotation ambiguity.

2. **QUAL-005 (YouTube URL validation) is imprecise** — The finding says "simple substring checks (youtube.com/watch) do not validate video ID presence" but does not examine what the actual validation logic is. The SKILL.md lines 151-152 show pattern matching against 5 URL variants (youtube.com/@, youtube.com/channel/, youtube.com/c/, youtu.be/, youtube.com/watch). The finding does not identify whether the substring check applies to all 5 patterns or only some. It also does not identify that youtu.be links (line 152) use a different URL structure than youtube.com/watch and would require different ID extraction logic. The finding is generic — "substring matching is fragile" — without identifying which of the 5 patterns are actually validated and which are not.

3. **QUAL-002 (hardcoded paths) is imprecise** — The finding identifies three hardcoded paths but does not distinguish between them: VAULT_DIR (line 35) is a runtime configuration constant used by the manifest script; DEFAULT_SRC (line 38) is a fallback default that only applies when no argument is passed; MANIFEST path (line 37) is a temp file path. The severity and remediation differ: VAULT_DIR is user-specific data path (should be env-var), DEFAULT_SRC is an ergonomic default (arguably acceptable), MANIFEST is a temp path (should use `tempfile` module). Treating all three as equivalent reduces the finding's actionability.

## Improvements to the Phase 1 Findings

1. **Resolve the HEREDOC script question before consolidation** — Open Question 6.5 should be answered by actually reading the two HEREDOC scripts and comparing them line-by-line. The consolidated findings should not recommend extracting both scripts as duplicates until the similarity question is resolved. If they are identical, one is a pure duplicate that should be eliminated; if they differ, each needs its own test coverage and the differences should be documented.

Separating these prevents conflating a user data path with a temp file path.
