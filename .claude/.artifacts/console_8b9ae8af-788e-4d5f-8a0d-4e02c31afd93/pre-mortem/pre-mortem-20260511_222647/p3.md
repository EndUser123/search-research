## Intent Summary
wiki SKILL.md v1.3.0 adds YouTube URL auto-detection and a yt-is pipeline (yt-dlp → Selenium → Gemini CLI failover) to the existing Obsidian wiki + QMD search skill. The skill aims to automate knowledge ingestion from YouTube videos and local files, with tiered size handling, hash-based deduplication, and semantic auto-linking.

## Health Score: 48%

The skill is functionally ambitious but has critical architectural gaps: the core failure contract (transcripts.sqlite schema) is undocumented, the dispatch state machine has no atomicity guarantees, and the QMD error handling silently swallows failures. These are not polish issues — they are structural defects that cause data corruption on crash and silent failures on routine errors.

## Logical Gaps & Inconsistencies

1.1. [CRITICAL] (COMP-001, confirmed by SKILL.md:220) — transcripts.sqlite schema is referenced by the failover contract (`failure_reason: no_transcript`) but never documented. The table name, column names, and semantics of `failure_reason` values are absent. A yt-is pipeline schema change (e.g., renaming the column, using a different table) would silently break the failover trigger with no validation error. Maintainers cannot verify the manifest correctly records failure states.

1.2. [HIGH] (QUAL-006) — Ingest dispatch has no atomicity or resume mechanism. A crash mid-dispatch leaves the manifest in partial state (some `pending`, some `done`, some `failed`). On retry, all `pending` entries are re-dispatched, causing duplicate wiki pages and duplicate yt-is calls. This is a systemic architectural defect, not a documentation gap — severity should be HIGH per p2 meta-critique, not MEDIUM. No idempotency key exists to prevent re-processing.

1.3. [MEDIUM] (COMP-002, refined per p2) — EVIDENCE_GAP annotations exist in body text (SKILL.md:134-136) but are not a frontmatter field. Two separate root causes: (a) `evidence_gaps` field is simply absent from the frontmatter schema (SKILL.md:109-125 — straightforward schema addition); (b) the body annotation syntax is underspecified — "flag any EVIDENCE_GAP" does not define whether it is `- EVIDENCE_GAP: <text>`, `[EVIDENCE_GAP]`, or another format. These have different remediation paths and should be separate findings.

1.4. [MEDIUM] (p2: QMD update error handling) — SKILL.md:147 shows `qmd update wiki --lang en 2>$null; if ($LASTEXITCODE -ne 0) { qmd update wiki }`. Stderr redirect to null suppresses all error output. The automatic retry has no limit. If the second call also fails, the error is silently swallowed — no status is written, no user notification, no indication that the wiki index is stale. This is a silent failure mode with no recovery path.

1.5. [MEDIUM] (p2: yt-is pipeline failure modes not specified) — SKILL.md:220 fires the Gemini CLI failover "when transcripts.sqlite shows `failure_reason: no_transcript` for all methods exhausted." What methods are tried in order (yt-dlp → Selenium → Gemini CLI)? What does "exhausted" mean for each stage? What other `failure_reason` values can appear in transcripts.sqlite? None of this is documented. COMP-001 identifies the schema gap but does not ask what other failure_reason values exist or whether the SKILL.md correctly enumerates all trigger conditions.

1.6. [LOW] (COMP-003) — "One wiki page per video" Option A decision is implemented in SKILL.md but not recorded as an architectural choice. Future maintainers may inadvertently refactor to multi-video pages without knowing this was a deliberate 2026-05-11 decision.

1.7. [LOW] (QUAL-005, refined per p2) — YouTube URL validation uses substring checks against 5 patterns (youtube.com/@, youtube.com/channel/, youtube.com/c/, youtu.be/, youtube.com/watch). The finding "substring matching is fragile" is generic — it does not distinguish which of the 5 patterns are validated and which are not. The youtu.be links use a different URL structure than youtube.com/watch and would require different ID extraction logic. The finding does not identify whether video ID presence is validated for any of the 5 patterns.

1.8. [LOW] (p2: HEREDOC script question resolved) — I compared the two HEREDOC scripts at SKILL.md:32-78 and SKILL.md:176-216 line-by-line. The second HEREDOC reads source from stdin (`sys.stdin.read().strip()`) instead of `sys.argv`, but the core logic — manifest generation with safe/large_warn/large_skip tiers, SHA256 dedup, LOG_FILE check — is functionally identical. They are duplicates. The second HEREDOC is justified by the stdin-based source injection mechanism but should be extracted to `scripts/wiki_manifest.py` to eliminate drift risk.

## Hidden Assumptions & Fragile Dependencies

2.1. [HIGH] (QUAL-006 scope) — The ingest dispatch assumes that re-dispatching `pending` entries after a crash is safe. It is not — duplicates result. This assumption is structural and affects the entire dispatch model.

2.2. [MEDIUM] (cognitive_load advisory notation, SKILL.md:121) — Frontmatter declares `cognitive_load: <1-5>` with advisory angle-bracket notation. No enforcement exists — YAML parsing silently accepts values outside 1-5. Subagents could emit `cognitive_load: 6` with no validation error. The assumption that the advisory notation implies enforcement is false.

2.3. [MEDIUM] (p2: dispatch manifest schema has no stated contract) — SKILL.md describes the manifest as tracking `path`, `size`, `hash`, `status`, `tier` per entry, but there is no stated schema: required vs optional fields, valid `status` values, what happens on missing fields. This is distinct from COMP-001 (transcripts.sqlite schema gap) — the manifest is the dispatch state machine and its contract is equally undocumented.

2.4. [LOW] (QUAL-002, refined per p2) — Three hardcoded paths with different severity: VAULT_DIR (SKILL.md:35) is a runtime configuration constant used by the manifest script — should use env-var; DEFAULT_SRC (SKILL.md:38) is a fallback default only used when no argument is passed — arguable ergonomic default with lower remediation priority; MANIFEST (SKILL.md:37) is a temp file path — should use `tempfile` module. The finding should distinguish these to avoid conflating a user data path with a temp file path.

2.5. [LOW] (QUAL-005, scope clarification) — YouTube URL validation assumes any URL containing one of 5 substrings is structurally valid. Malformed URLs (e.g., `youtube.com/watch?v=` with empty video ID, or `youtube.com/watch?v=DEADBEEF` where video does not exist) pass this check and fail downstream in the yt-is pipeline. The error surface is downstream rather than at the skill entry point.

2.6. [LOW] (p2: slug generation edge cases) — SKILL.md:101: "Slug = lowercase alphanumeric + hyphens from filename." Filenames containing unicode, multiple spaces, or special characters are not tested. What happens with `My File (1).md`? The slug HEREDOC (SKILL.md:101) has no test coverage per QUAL-001, and no specialist flagged slug generation edge cases as a potential invalid-filename or collision source.

2.7. [LOW] (p2: transcripts.sqlite schema change silently breaks failover) — If yt-is pipeline changes its schema (renames `failure_reason` column, uses a different table name), the SKILL.md failover trigger at SKILL.md:220 would silently stop working with no validation error. Both specialists confirmed this gap.

## Risks and Edge Cases

4.1. [HIGH] (QUAL-006, elevated per p2) — Crash mid-dispatch causes partial manifest state with no recovery mechanism. Re-dispatch of `pending` entries on retry creates duplicate wiki pages and duplicate yt-is calls. Data corruption risk is systemic and architectural, not a documentation issue.

4.2. [MEDIUM] (QUAL-004) — Gemini CLI subprocess call has no error handling and no timeout. A network failure, timeout, or non-zero exit code from `gemini -p` (SKILL.md:158) crashes the subagent without any manifest update. The failure is invisible to the orchestrator until the subagent completes with an error. The error is recoverable by re-run but not by retry-without-duplicate.

4.3. [LOW] (QUAL-005, downstream failure surface) — A YouTube URL that passes substring validation but is malformed (empty video ID, non-existent video) reaches the yt-is pipeline, which fails at that level. The error surface is downstream — yt-is returns an error that the SKILL.md ingest dispatch must handle.

4.4. [LOW] (p2: transcripts.sqlite schema change silent break) — If yt-is pipeline changes its schema (renames `failure_reason` column, uses a different table name), the SKILL.md failover trigger would silently stop working with no validation error.

4.5. [LOW] (p2: slug generation invalid filenames or collisions) — Unicode filenames, multiple spaces, or special characters may produce invalid filesystem names or collisions. No edge case testing exists. The risk is unquantified.

4.6. [LOW] (p2: QMD update silent failure on second attempt) — If the second `qmd update wiki` call (SKILL.md:147) also fails, the error is silently swallowed. The wiki index becomes stale with no user notification, no manifest entry, and no recovery path.
