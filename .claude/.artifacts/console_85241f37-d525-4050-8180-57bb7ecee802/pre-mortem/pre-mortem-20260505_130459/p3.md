## Logical Gaps & Inconsistencies

### 1.1 [HIGH] Default model mismatch across layers — bf_agent.py:1032 vs SKILL.md:132

`run_simple()` hardcodes `model: str = "DSv4-flash"` at line 1032, but SKILL.md §Invocation specifies the non-compare default is `"M27"`. The `DEFAULT_MODELS` env fallback at line 33-36 also lists `M27` first. A user calling `run_simple()` without an explicit model gets DSv4-flash; a user reading SKILL.md expects M27. **Verified at bf_agent.py:1032.**

### 1.2 [HIGH] Port split — bifrost_call uses 8081, catalog/probe use 8080 — bf_agent.py:31 vs 198

`bifrost_call()` (line 524) uses `BIFROST_BASE_URL` which defaults to `http://localhost:8081`. `list_catalog_models()` (line 214) and `probe_model()` (line 267) use `BIFROST_HTTP_PORT` which defaults to `8080`. These are the same Bifrost daemon (confirmed by the daemon running on one port, not two), but the code sends existing model calls to 8081 and new discovery/probe calls to 8080. If Bifrost serves both from port 8080, all existing `bifrost_call` invocations route to the wrong port. **Verified at bf_agent.py:31, 198, 214, 267, 524.**

### 1.3 [HIGH] add_route() CEL expression f-string injection — bf_agent.py:389

`cel_expr = f'model == "{model}"'` embeds `model` directly without escaping. A model name containing `"` or `\` produces a malformed CEL string. The SELECT at line 397 uses parameterized query, but the value is already the interpolated f-string result — so a payload like `model="\" OR 1=1--"` bypasses the duplicate-check and stores a broken CEL expression in `routing_rules`. The duplicate-check only prevents exact duplicates; it does not prevent CEL injection that produces a different string. **Verified at bf_agent.py:389, 397.**

### 1.4 [MEDIUM] add_route() idempotency is misleading — bf_agent.py:399-401

SKILL.md calls add_route() "idempotent". If a disabled rule with the same CEL exists, calling `add_route(enabled=True)` returns `{ok: False}` rather than reactivating it. User must manually delete then recreate the rule. This breaks the idempotency UX promise. **Verified at bf_agent.py:399-401.**

### 1.5 [MEDIUM] max_turns no validation in run_code() — bf_agent.py:1144

`run_code()` passes `max_turns` directly to `run_code_agent()`. If caller passes `0`, Python's `range(0)` produces an empty sequence — zero turns execute. If caller passes a negative, `range(-1)` also produces empty. The function silently produces no tool calls. `BF_CODE_MAX_TURNS` is validated at module level but an explicit caller value bypasses it. **Line 1144 confirmed.**

## Hidden Assumptions & Fragile Dependencies

### 2.1 [HIGH] VALID_MODELS removal leaves no defensive model validation — bf_agent.py:58

P1 removed `VALID_MODELS = set()` as the hardcoded set. Bifrost now validates at runtime — but if Bifrost is unreachable, missconfigured, or returns an unexpected error format, malformed model names pass straight to the HTTP endpoint with no early validation. **Verified at bf_agent.py:58.**

### 2.2 [MEDIUM] SEC-001 auth token not actually in log — bf_agent.py:108-127 (adjusted)

The log_event() payload includes `model` and `provider` fields but NOT the `Authorization` header or `BIFROST_VK` value itself. The Bearer token is in HTTP headers during the request; it is not serialized into the JSON log payload. The finding should be restated: model/provider names logged alongside HTTP calls *could* hint at what model was used, but the actual API key is not in stdout logs unless it appears in a model name or the model/provider fields are captured by a log aggregator that also captures HTTP headers. **Code verified at bf_agent.py:108-127 — auth header not in payload.**

### 2.3 [MEDIUM] SKILL.md import path — unresolved

SKILL.md workflow_steps execute `from bf_agent import run_simple`. Whether `P:/tools/mcp/` is on `sys.path` in the subprocess execution context is unknown. The test suite (`P:/tests/test_bf_agent.py`) explicitly adds `P:/tools/mcp` to `sys.path` before importing — but SKILL.md does not. If SKILL.md runs as a subprocess without path injection, the import fails with `ModuleNotFoundError`. **Open question — not verified.**

### 2.4 [LOW] P:/ hardcoded as installation root in SKILL.md:16

PowerShell path `P:/.claude/provider-configs/cc-bifrost.ps1` is absolute. If the installation root changes, all management commands break. **SKILL.md:16 verified.**

## Missing Obvious Actions / Best Practices

### 3.1 [MEDIUM] DB path duplicated in 4 locations — bf_agent.py:313, 388, 454, 488

Each of probe_routes(), add_route(), delete_route(), and list_routes() independently evaluates `os.getenv("BIFROST_DB", r"C:\Users\brsth\AppData\Roaming\bifrost\config.db")`. If the DB location changes, all 4 must be updated atomically. Should be one module-level constant `BIFROST_DB`. **Verified at each listed line.**

### 3.2 [LOW] tool_read_file() duplicate read_text() — bf_agent.py:660-661

Line 660: `p.read_text(encoding="utf-8", errors="ignore")` — result discarded. Line 661: `content = p.read_text(encoding="utf-8", errors="ignore")` — actual read. The comment says "re-resolve before I/O" which suggests `_resolve_allowed_path` may be doing filesystem work, not just string manipulation. If `_resolve_allowed_path` resolves symlinks or validates path segments, calling it twice is wasteful. If it's purely a string operation, the first call is dead code. No agent confirmed what `_resolve_allowed_path` actually does. **Verified at bf_agent.py:660-661.**

### 3.3 [LOW] delete_route() silently returns on exception — bf_agent.py:476-477

Unlike add_route() which logs on failure, delete_route() returns `{"ok": False, "error": ...}` on exception without calling `log_event()`. Makes debugging harder. **Verified at bf_agent.py:476-477.**

### 3.4 [LOW] delete_route() no transaction wrapper — bf_agent.py:468-469

Two separate `c.execute()` DELETE calls without explicit transaction. If second DELETE fails, orphaned `routing_targets` remain. **Verified at bf_agent.py:468-469.**

## Risks and Edge Cases

### 4.1 [HIGH] CR-LF injection in tool_write_file() — bf_agent.py:706-711

`tool_write_file()` passes raw model output to `write_text()` with no sanitization. CRLF sequences in model-generated content could enable HTTP response splitting if the file is later served by a web server (CWE-93). Null bytes could truncate files on some systems. **Verified at bf_agent.py:706-711.**

### 4.2 [MEDIUM] No daemon pre-flight check before probe_routes() — SKILL.md workflow_steps

If Bifrost daemon is not running, `probe_routes()` fails with a generic connection error, not an actionable message. User gets no guidance to run `/bf start` first. **SKILL.md:17-18 verified.**

### 4.3 [LOW] SEC-003 local auth — bf_agent.py:267 (downgraded from p1)

No local auth token on Bifrost HTTP. In a single-user solo-dev context this is an accepted constraint. Rate as LOW for the stated use case; HIGH if multi-user environment. **Code verified at bf_agent.py:267.**

## Open Questions / Unknowns

### 6.1 [MEDIUM] SKILL.md import path — bf_agent.py not on subprocess sys.path?

SKILL.md executes `from bf_agent import run_simple` with no sys.path manipulation. Whether `P:/tools/mcp/` is pre-injected in the Claude Code skill execution context is unknown. **Need to verify:** does `/bf brainstorm M27 test` work in a fresh session, or does it crash with `ModuleNotFoundError`? If it works, the skill execution environment must be adding `P:/tools/mcp` to path somehow. If it fails, SKILL.md needs `sys.path.insert(0, "P:/tools/mcp")` before the import.

### 6.2 [MEDIUM] Does Bifrost serve both endpoints on port 8080, or is 8081 a separate messages endpoint?

The code assumes both ports work for Bifrost routing — but this was never confirmed. If port 8081 is the actual messages endpoint and port 8080 is catalog-only, then catalog/probe calls going to 8080 is correct and `bifrost_call` going to 8081 is also correct. If Bifrost runs on one port, the port mismatch in 1.2 is a bug.

### 6.3 [LOW] `_resolve_allowed_path` in tool_read_file() — what does line 660 actually do?

If `_resolve_allowed_path` does pure string path normalization, line 660 is dead code and line 661 repeats the work. If `_resolve_allowed_path` does filesystem I/O (stat, symlink resolution), line 660 discards the result and immediately re-does the same I/O. Either way, the pattern is suspicious.

### 6.4 [LOW] DB path hardcodes Windows username `brsth` — intentional or bug?

The default fallback `C:\Users\brsth\AppData\Roaming\bifrost\config.db` assumes a specific user. On a multi-machine setup or if the Windows username differs, this default is wrong. Should use `%APPDATA%` or `Path(os.getenv("APPDATA")) / "bifrost" / "config.db"` instead.
