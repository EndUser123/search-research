## Cross-Agent Contradictions

1. **bf_agent.py existence — adversarial-io-validation vs p1_findings.md** — adversarial-io-validation claims IO-001 and IO-002 are BLOCKERs: the module does not exist anywhere on the system. p1_findings.md explicitly marks both as "[BLOCKER — INCORRECT]" and states the file exists at `P:/tools/mcp/bf_agent.py` and is verified importable by the test suite. These are direct opposites. The io-validation agent searched `skills/bf/` instead of the actual module path `P:/tools/mcp/`. This is not a calibration difference — one agent asserts the file does not exist and the other asserts it does exist with equal confidence.

2. **SEC-002 injection mechanism — adversarial-security vs adversarial-compliance** — adversarial-security (SEC-002) states the SELECT uses a parameterized query. adversarial-compliance (COMP-001 finding) confirms the SELECT but describes the vulnerability as "malicious model containing `"` or `\` could break the CEL expression". The p1_findings.md correctly surfaces this as "SQL injection is constrained (parameterized query for INSERT) but CEL expression integrity is compromised" — yet the raw security finding claims parameterized query is protection, which it is not when the f-string interpolation has already produced a malformed value before the parameter is bound.

## Severity Calibration Issues

1. **COMP-005 transaction wrapping — adversarial-compliance rates LOW, but the consequence warrants MEDIUM** — The finding states "two separate DELETE statements" with risk of "orphaned routing_targets" on failure. This is a data integrity issue, not just a code tidiness issue. adversarial-compliance assigned LOW based on "user_visible: false", but orphaned target records accumulating silently over time is a medium-term correctness issue that could cause phantom routing behavior. The LOW rating is likely anchored on low probability, not on impact magnitude.

2. **SEC-003 local auth — adversarial-security rates HIGH, no specialist challenge** — No agent pushed back on this rating, but it conflates two separate issues: (a) no local auth token on the HTTP endpoint, and (b) any local process can call it. In a single-user solo-dev context, this is not HIGH severity — it is an accepted environment constraint, similar to how localhost HTTP services operate. The HIGH rating is correct for multi-user contexts but is not justified for the stated use case. No agent called this out.

3. **VALID_MODELS removal — adversarial-critic rates HIGH but it's a blind spot, not a consensus finding** — adversarial-critic lists this as a "HIGH consensus" item in its summary table (line 22), but the meta_findings section calls it a "blind_spot" with severity HIGH. The p1_findings.md correctly categorizes it under "Hidden Assumptions" as 2.1 [HIGH], but the adversarial-critic's own summary table mislabels it as consensus. This is an internal inconsistency within the same agent's output.

## Missed Blind Spots

1. **SKILL.md import path resolution — not examined by any specialist** — No agent examined whether `from bf_agent import run_simple` in SKILL.md would actually resolve at runtime. The p1_findings.md mentions "adversarial-io-validation agent's concern about the import path in SKILL.md may still be valid if SKILL.md executes as a subprocess rather than with P:/tools/mcp pre-injected" as open question 6.2. This is a legitimate blind spot: the import statement assumes `bf_agent` is on the Python path, but no agent verified that SKILL.md's execution context has `P:/tools/mcp/` in `sys.path`. The false-positive IO-001/IO-002 consumed all the adversarial-io-validation bandwidth, leaving the actual import mechanism unexamined.

2. **test suite path doesn't validate runtime behavior** — The p1_findings.md uses the test suite (`P:/tests/test_bf_agent.py`) as proof that `bf_agent.py` is "verified importable". But the test suite may run with a different `sys.path` than SKILL.md when executed as a subprocess. This is not the same as runtime SKILL.md behavior. No agent flagged this distinction.

3. **probe_routes() behavior when Bifrost returns empty routing_rules** — All findings assume the happy path or well-defined failures. What happens when `probe_routes()` returns zero routes — is that an error state or a valid empty state? No agent examined the caller's handling of this edge case.

## Precision Failures

1. **SEC-001 — "writes model/provider fields to stdout without redaction" is imprecise** — The finding says the Bearer token is included in log_event() JSON output. But the code evidence shows `model` and `provider` fields — not the `Authorization` header or `BIFROST_VK` itself. The finding conflates "fields that could hint at what key was used" with "the key itself is in the log". The actual auth token (BIFROST_VK) is sent as a Bearer header in HTTP calls and is not directly in the log payload — but if `model` or `provider` values contain the key itself (e.g., if a model name contains the literal API key string), it would leak. The finding should say "model/provider fields logged alongside auth context could expose the key if model names contain auth data", not "Bearer token included in log_event output".

2. **SEC-002 — "SELECT uses parameterized query" is misleading framing** — The finding says "parameterized query for INSERT" implies safety. But the SELECT checks the already-interpolated f-string result. The actual vulnerability: `f'model == "{model}"'` is interpolated before the parameterized SELECT runs, so the attacker can shape the SQL string itself. Calling this "SQL injection" is correct but the mechanism description ("parameterized query protects against injection") is wrong and could mislead an implementer into thinking no fix is needed because parameterized queries are already used.

3. **QUAL-003 double-read — "wasteful on every file read" is imprecise** — The evidence shows `p.read_text()` on line 660 (result discarded) then `p.read_text()` on line 661 (actual read). The adversarial-quality finding calls this "wasteful I/O". But the code comment says "re-resolve before I/O" — suggesting line 660 may be a path re-resolution step, not an actual read. If `_resolve_allowed_path` involves filesystem calls (not just string manipulation), discarding its result while calling it again could be a no-op pattern or an actual bug. No agent verified what `_resolve_allowed_path` actually does, so the "wasteful" characterization is assumption rather than confirmed fact.

4. **COMP-002 port mismatch — "two different HTTP services" is unverified** — The finding asserts that port 8081 and 8080 are "two different HTTP services". This is a hypothesis — it could also mean one Bifrost daemon listens on both ports, or the same service exposes different endpoints on each port. The open question 6.1 acknowledges this. Without verification, saying "these are two different services" is speculative and could cause unnecessary architecture changes.

5. **COMP-003 "behavior is actually correct by coincidence" — self-contradicting** — The finding says the fallback logic "works correctly by coincidence" then recommends simplifying it because it "duplicates logic". If the behavior is correct and the code is clear, the recommendation has no grounds. The finding should either confirm the behavior is correct (and drop the recommendation) or identify a concrete bug (and explain why it matters).

## Improvements to the Phase 1 Findings

1. **Remove IO-001 and IO-002 from consolidated findings entirely** — p1_findings.md already marks these as "[BLOCKER — INCORRECT]" with explanation. The consolidated findings section should not list them as having any remaining validity. Currently section 4's "Risks and Edge Cases" does not mention IO findings at all, which is correct, but the open questions section (6.2) still treats the import-path question as potentially valid. It would be cleaner to resolve 6.2 with a concrete answer: does SKILL.md's execution context have P:/tools/mcp in sys.path, yes or no?

2. **SEC-002 should be rewritten to accurately describe the injection mechanism** — Replace "parameterized query for INSERT" framing with: "The CEL expression is constructed via f-string interpolation before any SQL parameter binding occurs. A model name containing `"` or `\` produces a malformed CEL string that bypasses the duplicate-check SELECT, allowing injection of arbitrary CEL content into the routing_rules table." This correctly identifies the attack surface without the misleading parameterized-query caveat.

3. **SEC-003 should separate severity by use case** — Rate it HIGH for multi-user environments and LOW for single-user solo-dev context. The finding's own recommendation "(b) document as single-user-only assumption" confirms the LOW severity path is available. The current HIGH rating without context could drive unnecessary feature development for a tool that is explicitly single-user.

4. **COMP-004 idempotency finding needs a concrete example** — Currently it describes the problem abstractly. A single line showing exactly what the user would see ("error: Rule already exists with id 7") and what they expected ("route re-enabled") would make the issue unambiguous and prevent "works as designed" pushback during implementation review.

5. **All findings should cite the actual line number from the reviewed file, not just from the p1_findings.md synthesis** — Multiple findings cite lines that appear in the specialist JSON but are described as from `P:/tools/mcp/bf_agent.py` without specifying whether the line numbers are from the current state of that file. If bf_agent.py has been modified since the specialists reviewed it, line number citations become unreliable.

6. **The adversarial-critic meta_findings should include its own verification methodology** — It says "VERIFIED: line 108-127 includes model/provider fields without redaction" but doesn't explain how that verification was performed (read the file? ran the code? checked the log output?). A reviewer cannot distinguish between confirmed findings and assumed findings without knowing the verification method.
