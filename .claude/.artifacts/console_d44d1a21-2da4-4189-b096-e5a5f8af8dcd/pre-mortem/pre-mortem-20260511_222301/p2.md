## Cross-Agent Contradictions

1. **Block message channel contradiction** — `adversarial-logic` (LOGIC-002) flags exit 2 + stderr as "legacy" that "may not properly block" on modern Claude Code. `adversarial-compliance` (COMP-002) flags the opposite: that `_log_gate_event` is dead code (never called). Neither verified against actual PROTOCOL.md or hook_runner behavior. Both specialists assume without evidence that the current behavior is wrong.

2. **Terminal ID severity divergence** — `adversarial-compliance` rates the terminal ID mismatch as HIGH (COMP-001), stating it "defeats enforcement entirely." `adversarial-io-validation` rates the same phenomenon as LOW (IO-003), calling it a "maintenance hazard, not runtime failure (values currently match)." These are irreconcilable characterizations of the same issue.

## Severity Calibration Issues

1. **matched_pattern redaction (SEC-002 vs COMP-001 framing)** — `adversarial-security` rates missing redaction on `matched_pattern` as HIGH severity. `adversarial-compliance` does not mention it at all (focuses on telemetry/registration gaps). If it is HIGH for security, it should be HIGH across all specialists — not absent from one analysis.

2. **IO-005 fail-open vs exit 0 interpretation** — `adversarial-io-validation` rates empty stdin fail-open as MEDIUM ("violates fail-secure principle"). `adversarial-logic` rates the same behavior (via LOGIC-002 exit code path) without mentioning stdin handling. No cross-specialist calibration on what "allow on error" means for security gates.

3. **Truncation-before-redaction severity** — `adversarial-security` (MEDIUM) flags the truncation-before-redaction sequence. `adversarial-io-validation` does not mention it at all. Should appear in both analyses if it is genuinely a MEDIUM risk.

## Missed Blind Spots

1. **No specialist examined task_tracker_hook.py state clearing** — `adversarial-testing` (TEST-008) notes three modules have separate `_clear_delegation_state()` functions but none verified whether `task_tracker_hook.py` actually wires into the same state path. The prospector writes to `.artifacts/{terminal_id}/hook_state/`, but does `task_tracker_hook.py` read from the same location?

2. **Claude Code hook runner contract not verified** — All specialists assume the stdout JSON vs stderr+exit2 question is unresolved. No specialist actually read `PROTOCOL.md` or `hook_runner.py` to verify what the current runner expects. This is the highest-impact unknown and no specialist addressed it.

3. **Atomic write pattern not verified for race conditions** — `_write_delegation_state` uses `tempfile + os.replace()` for atomicity. No specialist verified what happens if two terminals race on the same state file path (e.g., both with `unknown` terminal ID). The atomic write protects against corruption but not against one terminal's state being overwritten by another.

4. **No specialist examined the `_get_terminal_id()` vs `_detect_terminal_id()` call chain** — COMP-001 (terminal ID mismatch) was identified but no specialist traced where each function is called, what values they receive, and under what conditions they would diverge. The fix is obvious; the root cause mechanism is not.

5. **PostToolUse hook registration not verified** — `task_tracker_hook.py` clears state after Task/Agent invocation, but no specialist verified whether the PostToolUse hook is actually registered and firing. If the PostToolUse hook doesn't run, state is never cleared until TTL expires.

## Precision Failures

1. **TEST-001 "no end-to-end integration test"** — `adversarial-testing` flags this as HIGH but the description conflates "uses synthetic stdin" with "no integration test." Using synthetic stdin is a valid test isolation technique. The real issue is whether the synthetic test exercises the correct state path (COMP-001). TEST-001 conflates two separate concerns.

2. **LOGIC-005 bypass flag naming** — Flagged as LOW but the description ("Users may interpret inline as allowing inline code") is speculative. The flag `--allow-inline` appears in both code and tests — no evidence that users have actually been confused by this name. This is a design opinion, not a verified failure mode.

3. **IO-003 "unknown" fallback is shared isolation key** — Labeled LOW but could be MEDIUM. The actual risk depends on whether Claude Code ever runs in environments without `WT_SESSION`. If it does (CI, Docker), multiple concurrent sessions would share one state directory. No specialist estimated the probability of this scenario.

4. **SEC-003 temp file persistence** — Labeled LOW but no evidence that `os.replace()` actually fails in practice on Windows. The atomic write pattern is designed to avoid this. Flagging it as a finding without evidence of actual occurrence is speculative.

## Improvements to the Phase 1 Findings

1. **Read the actual PROTOCOL.md** before claiming exit 2 + stderr is legacy or broken. Verify what the current hook_runner.py actually does with hook output.

2. **Trace the terminal ID call chain** — Where does `_get_terminal_id_from_context()` get its value from? What sets `context.data["terminal_id"]`? The mismatch mechanism is the key to fixing COMP-001.

3. **Verify PostToolUse registration** — Before fixing `_log_gate_event()` (COMP-002), verify `task_tracker_hook.py` is actually registered and clearing state. If not, the gate stays blocked until TTL expires even after Task/Agent runs.

4. **Distinguish "may fail" from "fails in practice"** — Several findings (IO-003, IO-005, SEC-003) describe theoretical failure modes without evidence they occur. Mark these as "[MEDIUM/LOW] - theoretical" if unverified, not as confident findings.

5. **Calibrate terminal ID severity** — Either COMP-001 is HIGH (enforcement fails when IDs diverge) or IO-003 is LOW (values currently match). Pick one severity based on evidence, not assumptions.
