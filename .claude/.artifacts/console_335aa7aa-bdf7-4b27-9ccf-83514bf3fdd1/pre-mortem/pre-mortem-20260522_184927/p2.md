## Cross-Agent Contradictions
1. **Credential severity inconsistency**: `adversarial-security` rated both SEC-001 and SEC-002 as CRITICAL (hardcoded BIFROST_API_KEY and ANTHROPIC_AUTH_TOKEN), but `adversarial-logic` rated the same issues as HIGH in LOGIC-002. The evidence is identical (line 46 and 50 in cc-bifrost.ps1), the impact is equivalent, yet security rates them CRITICAL while logic rates them HIGH — no calibration justification in either report. This is a calibration failure.

2. **$proc scope finding — duplicate severity**: `adversarial-logic` (LOGIC-001) and `adversarial-compliance` (MEDIUM finding) both flag the Show-BifrostDashboard undefined $proc issue. Logic rates it "blocker", compliance rates it MEDIUM. Again no calibration justification for the discrepancy. This is the same finding entered twice at different severity levels.

3. **Sync-BifrostConfig empty rules severity split**: `adversarial-logic` (LOGIC-003, HIGH) says sync writes empty config.json when rules are empty and reports success, but notes the guard at lines 202-205 partially addresses it. `adversarial-compliance` does not flag this at all. `adversarial-io-validation` (IO-005) flags the write path without APPDATA validation but doesn't mention the empty-rules silent success case. Three specialists look at the same function and only one calls out the silent success on empty rules.

## Severity Calibration Issues
1. **Hardcoded credentials should be unanimous CRITICAL**: All four specialists found the hardcoded secrets at lines 46 and 50. Only `adversarial-security` rated them CRITICAL; `adversarial-logic` rated them HIGH. In a routing proxy that carries live API keys and auth tokens, hardcoded credentials at rest are CRITICAL regardless of lens. No specialist provided justification for the downgrade.

2. **Silent env fallback — split between security and io-validation**: `adversarial-security` (SEC-003, HIGH) flags the .env loading without path allowlist. `adversarial-io-validation` (IO-001, blocker) flags the same issue but as a blocker — required env vars used without validation after .env load. Both describe the same root cause but with different severity and framing. IO-001's "blocker" framing (env vars used without validation) is more accurate than SEC-003's path allowlist framing — the real issue is that the hardcoded fallback values silently substitute for missing credentials, not the load path itself.

3. **Temp file cleanup — inconsistency**: `adversarial-security` did not flag temp file cleanup at all (no mention of lines 475-478 or 493-496), while `adversarial-io-validation` flagged it as HIGH (IO-002, IO-003). Security's SEC-005 flags the error log path but misses the Python temp file leak which is more operationally relevant since those temp files contain routing information.

## Missed Blind Spots
1. **Sync-BifrostConfig schema validation absent**: No specialist flagged that the clean_rules array is written directly to `governance.routing_rules` with no schema validation. If the DB returns rules in an unexpected format (null targets, wrong types), the write succeeds and Bifrost reads a malformed config on next reload. The config structure (`$schema`, `version`, `providers`, `governance.routing_rules`) is assumed to be the only valid shape.

2. **PowerShell job output drainage reliability**: `adversarial-logic` (LOGIC-004) identified the race condition in Get-BifrostProcess's Output.Count filter but rated it MEDIUM. No other specialist addressed it. The scenario (job accumulates output between filter and drain, then is returned with unread output) could cause the function to return a job that appears to have no output but actually has buffered content — potentially affecting subsequent operations that depend on job state.

3. **routes_probe.py and bifrost_db.py not reviewed by all specialists**: The compliance specialist reviewed both helper scripts and found the priority ordering bug, but the logic and security specialists only reviewed cc-bifrost.ps1. The I/O validation specialist did review both helpers and found the hardcoded Windows path issue. This means the helpers only got partial coverage — no specialist systematically reviewed all three files for all lens categories.

4. **Binary version fallback chain is unverified**: The fallback from v1.5.2 → v1.5.0-prerelease8 → 7 → 6 is never verified to actually work. If the binary at the checked path is corrupted or wrong architecture, Start-BifrostDaemon reports "Running" but the HTTP server never starts. No specialist called this out as a validation gap — only io-validation (IO-008) mentioned it partially, and only as a MEDIUM.

## Non-Static Validation Coverage
1. **--sync write path has no live verification**: The most important non-static gap — Sync-BifrostConfig writes config.json but never verifies the write succeeded or that Bifrost can read it back. All findings are static (file exists, code path分析). A live run of `cc-bf --sync` followed by reading config.json back and confirming it contains the expected rules would verify this. No specialist recommended this as a required probe.

2. **PID detection reliability not proven**: The 'bifrost' substring match in Get-BifrostProcess is identified as fragile but never tested. Could a process named 'bifrost-wrapper' trigger a false positive? Could a stale PID survive across session restart? These require a live test to verify, not static analysis alone.

3. **Restart bootstrap 70s timeout not tested**: Restart-BifrostDaemon waits 70s for the HTTP endpoint. If the binary starts but the HTTP server takes longer (machine under load, network latency), the function returns with warning but no error exit code. The actual behavior under load is unknown — static analysis only.

## Missing Lens Fail Condition
1. **Testing lens not applied**: No test suite found for cc-bifrost.ps1, routes_probe.py, or bifrost_db.py. The testing specialist was not dispatched. For a routing proxy that manages live API credentials and daemon lifecycle, test coverage gaps are significant — even a basic smoke test that verifies --sync writes valid JSON and --status correctly reports daemon state would catch several of the identified issues.

2. **Observability/tracing lens not applied**: When Bifrost fails or misbehaves, there is no structured diagnostic path. The error log goes to a shared TEMP location, the status probe uses hardcoded routing keys, and the --routes output requires manual interpretation. No specialist identified the absence of structured failure telemetry.

3. **Performance lens not applied**: The 70-second restart bootstrap wait is hardcoded. routes_probe.py has LATENCY_TTL of 90 days but no justification. The retry policy in routes_probe.py only retries on Timeout and 500 Server Error — 404 and 400 are terminal, which could cause unnecessary probe failures on transient routing issues.

## Precision Failures
1. **SEC-006 (binary fallback PATH hijack) is inflated**: adversarial-security rates the binary fallback chain as LOW with "PATH can be controlled by attacker." This assumes the attacker already controls PATH, which would be a terminal compromise of the whole system. The real issue is that no integrity check exists before executing the binary — but this is only actionable if the binary path is known and controllable by an attacker with the same access level as the Bifrost user.

2. **SEC-007 (routing table not validated at load time) is vague**: "corrupted or tampered routing database can produce malformed CEL expressions that crash routing" — no explanation of what a "malformed CEL expression" looks like in practice or what crash means. The finding doesn't say whether Bifrost itself validates CEL syntax before accepting rules. It might already catch this and the finding is moot. Without knowing Bifrost's own validation, this finding is speculative.

3. **IO-004 PID detection — "kill wrong process" framing is imprecise**: The finding says the loose 'bifrost' substring match "can kill an unrelated process." But it also says "ProcessName -like 'bifrost'" — which is a wildcard match, not a contains match. In PowerShell, `-like 'bifrost'` means the full name must match the pattern, not that 'bifrost' appears anywhere in the name. The actual risk is that a process literally named "bifrost-something" is killed, not that any process with 'bifrost' in its command line is caught.

## Improvements to the Phase 1 Findings
1. **Unify credential severity to CRITICAL across all specialists** — hardcoded live API keys in a routing proxy are CRITICAL regardless of which lens found them. Phase 1 should have caught the duplication and calibrated it.

2. **Add testing lens** — for a daemon management script with credential handling, static analysis is insufficient. At minimum, a smoke test verifying --sync produces valid output and --status correctly detects daemon state should exist.

3. **Consolidate duplicate $proc findings** — LOGIC-001 (blocker) and compliance's MEDIUM finding are the same issue. Phase 1 consolidation should have merged them and assigned a single severity.

4. **Add model field validation to clean_sync** — compliance found that provider is validated but model is not. This should have been caught in the design review of the clean_sync logic itself — the function was added in #376 but model validation was not part of the spec.

5. **Confirm whether Bifrost validates CEL expressions on load** — SEC-007 is unverifiable without understanding Bifrost's own validation. A probe that checks whether Bifrost rejects malformed CEL expressions would confirm or deny the finding.

6. **Document why restart timeout is 70 seconds** — the 70s value in Restart-BifrostDaemon has no justification. Is this empirically measured or an arbitrary guess? If empirically measured, document why. If arbitrary, this is a candidate for the LATENCY_TTL-style fix (make configurable).
