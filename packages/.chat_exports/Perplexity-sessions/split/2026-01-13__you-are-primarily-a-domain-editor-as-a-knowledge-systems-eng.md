## Assistant

Progressive disclosure for AI agents in Claude Code and MCP is about turning tools and knowledge into files that the model discovers and loads only when needed, instead of preloading huge tool schemas into context.[1]

## Core pattern: tools as files, discovered on demand

- MCP schemas and large tool catalogs should not be loaded directly as tools into the LLM; this wastes tokens and many tools are never called.[1]
- Cloudflare found it is better to have the model write TypeScript that calls MCP servers as a TypeScript API inside an isolated sandbox, instead of emitting JSON tool calls.[1]
- Anthropic’s tool search tool only exposes the tools required for the current task, dropping context usage from about 77k tokens to 8.7k (≈85% reduction) while increasing MCP eval accuracy (e.g., Opus 4 from 49% to 74%, Opus 4.5 from 79.5% to 88.1%).[1]
- Cursor independently reported a similar dynamic-context approach, cutting total agent tokens by about 46.9%.[1]
- Cloudflare’s code-mode architecture achieved a reported 98.7% reduction in token usage by moving to code-executed tools in sandboxes rather than static tool context.[1]

## File system + bash as the universal substrate

- Industry trend: instead of equipping agents with explicit knowledge of every protocol (e.g., Postgres specifics), give them a file system plus bash and let them search, read, and write files and scripts.[1]
- Agents can use shell capabilities (grep, glob, directory traversal) to locate relevant files and only load those into context when needed.[1]
- Sandboxes from Anthropic, Vercel, Cloudflare, Daytona, Lovable, etc., provide ephemeral file systems where agents spin up mini-apps, read/write files, then tear them down. This is emerging as a core paradigm for agentic development by 2026.[1]
- In Anthropic’s consumer-facing web app, many operations already work by writing to a file system and generating scripts (e.g., spreadsheet operations).[1]
- The effective stack becomes: MCP + file system + code execution, with tools represented as files and invoked by code rather than direct tool schemas.[1]

## Skills and progressive disclosure in Claude Code

- In Claude Code, **skills** are the main vehicle for progressive disclosure:  
  - A skills directory contains multiple skill files (e.g., `web_research`, `code_review`).[1]
  - Each skill file has small front matter (≈10–100 tokens) that is always in static context and describes when/why to invoke the skill.[1]
  - The bulk of the skill (scripts, markdown, supporting files) is only read when the agent decides to use that skill.[1]
- Skills can reference other files and scripts, enabling chained progressive disclosure:  
  - The agent loads the first file, follows references to subskills or auxiliary markdown/scripts, and only then reads additional content.[1]
  - Skills can live in flat directories or hierarchical structures with subskills, and the agent traverses “lineage” to find the specific referenced file it needs.[1]
- Memory and knowledge are treated as simple files:  
  - Markdown like `claw.md`, other `.md` docs, scripts, and skill files act as memory; there is no embeddings or complex retrieval.[1]
  - The design principle is “if it’s simple for humans (read/edit/search in files), it’s simple for agents.”[1]

## MCP tool search and experimental CLI in Claude Code

- Anthropic’s advanced tool use bundles three key pieces:  
  - Tool search tool: discovers relevant tools on demand, not preloaded.[1]
  - Programmatic tool calling: tools are invoked in a code execution environment (similar to Cloudflare’s sandbox TS approach).[1]
  - Memory tool: operates on simple file-based markdown memory.[1]
- Claude can automatically clear old tool results as context limits are approached, progressively removing less relevant tool outputs instead of keeping everything.[1]
- An experimental MCP CLI flag in Claude Code enables tool search at the MCP level:  
  - Instead of putting all MCP server schemas into context, the flag allows Claude Code to search and discover MCP tools on demand.[1]
  - This is a work in progress; behavior and flags may change, and performance may not yet match having MCPs directly in context, but it already cuts tens of thousands of tokens per request down to near zero (aside from a small system-prompt overhead).[1]
- With dynamic discovery, systems no longer need to cap at 5–20 MCP servers to avoid context bloat; they can feasibly expose thousands or even hundreds of thousands of skills or MCP endpoints organized in directories and subdirectories.[1]

## Context management, scaling, and ambitions

- Loading all tools and schemas into a 100k-token context degrades model quality compared with leaner contexts (e.g., ~10k), by crowding out “room” for actual task content.[1]
- Progressive disclosure shifts from “load everything up front” to “discover on demand, load only what is needed, and drop older, less relevant tool outputs as limits approach.”[1]
- Token savings translate directly into:  
  - Faster applications.  
  - Cheaper runs.  
  - More capacity for real work (task content, intermediate reasoning).[1]
- With file-based memory, dynamic tool search, and progressive skill loading, agents can:  
  - Run for multiple hours.  
  - Use dozens, hundreds, or thousands of tool integrations.  
  - Execute complex workflows without heavy external orchestration logic, as long as they can search for tools/skills/files effectively.[1]
- Systems gain both “memory” (persistent files) and “working memory” (current context + helper scripts), and can even update skills over time, writing new scripts and refining skill files.[1]

## Operational patterns and setups

### Multi-entity flows

- **MCP servers + TypeScript + sandbox**  
  - The model writes TypeScript which calls MCP servers exposed as a TypeScript API in an isolated sandbox.[1]
  - MCP schemas are not fed as tool definitions; instead, the sandbox code handles discovery and invocation.[1]
- **Claude Code + skills + file system + bash**  
  - Claude Code sees only skill front matter in static context.[1]
  - When a skill suits the current task (e.g., web research or code review), Claude reads the corresponding skill file, then follows references to scripts/markdown in that skill folder.[1]
  - Bash is used to navigate directories, search files (grep/glob), and execute scripts; Claude then loads only relevant file slices into context.[1]
- **Tool search + programmatic tool calling + memory**  
  - Tool search identifies which MCP or other tools are relevant given the current state.[1]
  - Programmatic tool calling executes those tools in a code environment, not by direct JSON tool invocation.[1]
  - Tool outputs and long-lived knowledge are persisted as simple markdown memory files, which are later found by file search rather than embedding search.[1]

### Automation patterns

- **Dynamic tool discovery at inference time**  
  - Tool schemas and MCP capability descriptions are not pre-loaded; an internal tool search routine picks which tools to surface as needed.[1]
- **Automatic context pruning**  
  - As the conversation approaches context limits, Claude clears older tool results that have become less relevant, reducing risk of context overflow while preserving current task information.[1]
- **On-demand skill loading and chaining**  
  - Only skill front matter is always-on; actual skill content is pulled in lazily when the agent decides to use that skill.[1]
  - Within a skill, references to subskills and supporting docs are followed only when specific details become necessary.[1]
- **Sandbox lifecycle**  
  - Sandboxes with ephemeral file systems are created to run code, read/write files, and then shut down after the task or phase completes.[1]

### Guardrail artifacts

- **Skill front matter as guardrail/config**  
  - Each skill file’s front matter acts as a micro-guardrail: it encodes when the skill should be used, what it does, and how it should behave.[1]
  - Only the front matter is guaranteed to be in context at decision time, shaping when the agent is allowed to expand into deeper skill content.[1]
- **File-based memory docs**  
  - Markdown files like `claw.md`, skills, and other `.md` documents serve as persistent “policy plus knowledge” artifacts.[1]
  - Their enforcement is emergent: the agent must intentionally search, open, and read them via file system + bash, so they act as explicit references the agent chooses when needed.[1]
- **Sandbox boundaries**  
  - Running tools via TypeScript in isolated sandboxes constrains side effects: the tool API is mediated by the sandbox rather than directly by the model.[1]
  - This architecture implicitly separates “decide what to call” (model) from “execute safely” (sandboxed environment).[1]

## Practical recommendations

- Treat **tools as files**: expose MCPs and other capabilities via code APIs and file-based interfaces, and let the model write code (TypeScript, bash, scripts) to discover and call them.[1]
- Move to **progressive disclosure**: keep only small skill/tool descriptors (front matter) in static context; load actual tool schemas, docs, and scripts from the file system only when needed.[1]
- Use a **skills directory** in Claude Code with:  
  - One file per skill (web research, code review, etc.) with concise front matter and references to supporting docs/scripts.  
  - A hierarchy of subskills so the agent can traverse from high-level skills to increasingly specific files.[1]
- Prefer **file-based memory** over complex embeddings for your core agent workspace: store persistent knowledge in markdown and scripts that the agent can grep, glob, and edit directly.[1]
- Enable and iterate on **MCP tool search** (or equivalent dynamic discovery) so you can scale from a handful of MCP servers to thousands of skills/MCP endpoints without context collapse.[1]
- Architect around **file system + bash + sandbox**:  
  - Give agents read/write/search over an ephemeral file system.  
  - Let them write helper scripts and update skills.  
  - Execute tools via sandboxed code rather than raw JSON tool calls.[1]
- Rely on **automatic context pruning** where available, and design your workflows assuming that older tool outputs may be cleared; persist anything important into memory files instead of relying on long conversations.[1]
