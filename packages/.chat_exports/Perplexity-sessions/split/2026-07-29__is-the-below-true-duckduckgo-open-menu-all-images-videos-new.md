Not fully. The core idea is **partly true**, but several claims in that DuckDuckGo-generated answer are mixed together in a misleading way. ACP is primarily a protocol between an ACP client and an ACP-compatible coding agent, not a generic “all chat apps can directly talk to each other” mechanism, and Chrome by itself is not the thing that makes ACP work.[1][2]

## What is true

ACP does standardize communication between code editors or clients and coding agents, and it is meant for local or remote scenarios.  The public ACP registry shows many agents already registered, including entries such as `claude-acp`, `codex-acp`, `grok-build`, `opencode`, and `pi-acp`, so the ecosystem is real and broader than just Claude Code.[3][4][2][1]

It is also true that a browser-based ACP client exists. ACP UI explicitly says it runs on desktop, mobile, and the web, and that the web build can connect to remote ACP agents over WebSocket.[5][1]

## What is false or overstated

The statement “you can use ACP with Claude Code and Chrome” is too vague to be reliable. A plain Chrome tab cannot run local stdio agents or access the host filesystem the way a desktop ACP client can; ACP UI’s own docs say the web build omits local stdio agents and host filesystem access because those require a local subprocess and are not available in a browser tab.[1]

The answer also blurs **Claude in Chrome** with ACP. Claude in Chrome is a specific Anthropic browser integration, while ACP is a separate protocol/ecosystem; even if both involve agents and browsers, they are not the same mechanism. The ACP UI docs describe browser support in terms of remote WebSocket-connected ACP agents, not direct browser-native control of local CLI agents.[2][1]

## Practical interpretation

If your goal is “ChatGPT, Claude, or Perplexity in a Chrome tab should directly talk to Codex CLI, Claude Code CLI, Auggie CLI, or OpenCode on my Windows 11 desktop,” the browser-only part is the blocker. In practice, you need a local or remote ACP bridge that exposes those CLIs over WebSocket, because the browser cannot spawn or manage those local agent processes on its own.[1]

ACP UI documents exactly this pattern: desktop clients can run local stdio agents, while mobile and web clients must connect to remote agents over WebSocket, and it recommends `@rebornix/stdio-to-ws` to expose a local stdio agent over the network.  That means the right architecture is not “Chrome alone,” but “Chrome UI + ACP bridge + local CLI agents.”[1]

## Suggested setup

For your Windows 11 use case, my suggestion is:

- Use a real ACP front end first, preferably ACP UI desktop or VS Code ACP, because those are designed to speak ACP cleanly.[6][5]
- Run each CLI behind an ACP-capable adapter or bridge. ACP UI already ships example configs for Claude Code, Codex CLI, Gemini CLI, Auggie CLI, and OpenCode.[1]
- If you need browser access, expose the local agents through WebSocket with `@rebornix/stdio-to-ws`, then connect from Chrome to that endpoint.[1]
- Treat consumer chat websites separately. I do not see evidence in the sources that ChatGPT web, Claude web, or Perplexity web natively act as arbitrary ACP clients to your local machine. Based on the sources here, you should assume **no native direct ACP support** from those web apps unless a vendor explicitly documents it.[2][1]

## Add Chrome or browser access later

ACP UI’s web build works at [acp-ui.github.io](https://acp-ui.github.io/) and connects only to remote ACP agents over WebSocket. It explicitly omits local stdio agents and host filesystem access in the browser.[2]

So for Chrome access, do this:

### Step 1: start a WebSocket bridge

ACP UI recommends `@rebornix/stdio-to-ws`. The README gives this exact command pattern:[2]

```powershell
npx @rebornix/stdio-to-ws "npx @zed-industries/codex-acp@latest" --port 3000 --persist --grace-period -1
```

You can swap the wrapped command. For example, Claude Code bridge:

```powershell
npx @rebornix/stdio-to-ws "npx @agentclientprotocol/claude-agent-acp@latest" --port 3001 --persist --grace-period -1
```

OpenCode bridge:

```powershell
npx @rebornix/stdio-to-ws "npx opencode-ai@latest acp" --port 3002 --persist --grace-period -1
```

Those exact wrapped commands are adapted from ACP UI’s documented agent commands plus its documented `stdio-to-ws` pattern.[2]

### Step 2: allow Windows Firewall

ACP UI provides the one-time elevated PowerShell firewall rule pattern:[2]

```powershell
New-NetFirewallRule -DisplayName "stdio-to-ws-3000" -Direction Inbound -LocalPort 3000 -Protocol TCP -Action Allow -Profile Private
New-NetFirewallRule -DisplayName "stdio-to-ws-3001" -Direction Inbound -LocalPort 3001 -Protocol TCP -Action Allow -Profile Private
New-NetFirewallRule -DisplayName "stdio-to-ws-3002" -Direction Inbound -LocalPort 3002 -Protocol TCP -Action Allow -Profile Private
```

### Step 3: connect from Chrome on same machine

Important constraint: if you use the hosted HTTPS ACP UI web app, the browser can only open `wss://`, not plain `ws://`, because of mixed-content rules. ACP UI states this explicitly.[2]

You therefore have **two** choices:

- **Choice A, easiest for localhost/LAN testing:** run the ACP UI web bundle locally over HTTP, then connect to `ws://localhost:3000/`. ACP UI documents `npm run preview:web` for this.[2]
- **Choice B, easiest for hosted browser access:** expose the port through Microsoft Dev Tunnels and use a `wss://...` URL. ACP UI documents this flow too.[2]

### Choice A: local browser UI

```powershell
cd C:\ai\acp\repos
git clone https://github.com/formulahendry/acp-ui.git
cd .\acp-ui
npm install
npm run preview:web
```

Open:

```text
http://localhost:4173/
```

Then in the ACP UI web page:
1. Open **Settings**.
2. Add a new WebSocket agent.
3. URL: `ws://localhost:3000/`
4. Save.
5. Select the agent.
6. Start a new session.

ACP UI documents that `preview:web` serves the production bundle locally and that the local non-HTTPS path can use `ws://`.[2]

### Choice B: Dev Tunnels for `wss://`

ACP UI documents this exact pattern:[5][2]

Terminal 1:
```powershell
npx @rebornix/stdio-to-ws "npx @zed-industries/codex-acp@latest" --port 3000 --persist --grace-period -1
```

Terminal 2:
```powershell
devtunnel host -p 3000
```

That prints a URL like:

```text
https://<id>-3000.<region>.devtunnels.ms
```

Replace `https` with `wss` when you enter it into ACP UI web:

```text
wss://<id>-3000.<region>.devtunnels.ms/
```

ACP UI explicitly says to do that conversion.[5][2]
