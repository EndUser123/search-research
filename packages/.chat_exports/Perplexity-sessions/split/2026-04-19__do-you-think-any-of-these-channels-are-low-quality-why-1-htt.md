def code_like_score(text: str) -> float:

def has_resource_links(description: str) -> bool:

```python
def channel_structural_metrics(infos: list[dict]):
    now = datetime.utcnow()
    n = len(infos)
    if n == 0:
        return {}

    transcripts = [has_transcript(i) for i in infos]
    transcript_rate = sum(transcripts) / n

    durations = [i.get("duration") or 0 for i in infos]

    # If you have transcripts text, compute word counts & code score
```

### Minimal Python structure
```python

    "https://www.youtube.com/@channel1",

        "skip_download": True,
```

## yt-dlp rate limits
The main knobs yt‑dlp exposes for rate-limit avoidance are request sleeps, randomized pre-download sleeps, retry backoff, rate caps, and controlling concurrent fragments. The most relevant options are:[4][2]

- `--sleep-requests SECONDS`: sleep between extraction requests.[2]
- `--sleep-interval SECONDS` with `--max-sleep-interval SECONDS`: randomized sleep before each download.[5][2]
- `--retry-sleep TYPE:EXPR`: backoff schedule for HTTP, fragment, extractor, or file retries.[2]
- `--limit-rate RATE`: cap bandwidth per connection.[6][7]
- `--concurrent-fragments N`: reduce this if you are also rate-limiting, because the limit applies per connection, not globally.[7]

A practical **metadata-only** batch profile is:

```bash
yt-dlp \
  --skip-download \
  --sleep-requests 2 \
  --sleep-interval 3 \
  --max-sleep-interval 8 \
  --retry-sleep http:exp=1:20 \
  --retry-sleep extractor:exp=1:10 \
  URL
```

For heavier jobs with subtitles/comments, be more conservative:

```bash
yt-dlp \
  --skip-download \
  --write-subs \
  --write-auto-subs \
  --sleep-requests 3 \
  --sleep-subtitles 2 \
  --sleep-interval 5 \
  --max-sleep-interval 12 \
  --retry-sleep http:exp=2:30 \
  --retry-sleep extractor:exp=2:15 \
  URL
```

## Batch strategy
For 10 channels, the safest design is **sequential channels, small per-channel bursts, checkpointing, and resumability** rather than high concurrency. Concretely:[8][2]

- Process 1 channel at a time.
- Limit to the most recent 10–20 videos first.
- Save raw results after each video, not only at the end.
- On HTTP failures, retry with exponential backoff via `--retry-sleep`.[2]
- If you use `--limit-rate`, also reduce `--concurrent-fragments`, since rate is applied per fragment connection.[7]
- Prefer metadata-first runs, then only fetch subtitles/comments for shortlisted videos.

That last point matters: most rate-limit pain comes from trying to do full extraction on everything at once, when your knowledge-mining pipeline only needs deep extraction for a smaller subset.

## Advanced yt-dlp flags for concurrent fragment downloads

yt-dlp supports `-N, --concurrent-fragments N` for DASH/HLS/native fragment downloads and documents that this changes how many fragments are downloaded concurrently. This improves throughput, but it also multiplies pressure on the remote service if you set it too high. The safest default for metadata-focused or subtitle-focused pipelines is still `1`, because you are not optimizing bulk media throughput.[1][4]

Useful flags:
- `-N, --concurrent-fragments N` — concurrent fragment downloads for DASH/HLS/native media.[1]
- `--limit-rate RATE` — cap per-connection rate.[1]
- `--throttled-rate RATE` — re-extract if bandwidth drops below a threshold.[1]
- `--fragment-retries RETRIES` — retry failed fragments.[1]
- `--retry-sleep fragment:EXPR` — fragment-specific backoff.[4][1]
- `--skip-unavailable-fragments` — continue when a fragment is unavailable, default for supported protocols.[1]
- `--hls-use-mpegts` — reduce corruption risk for interrupted HLS downloads, especially relevant for actual media downloads.[1]

### Rules of thumb
- For **metadata + subtitles only**: keep `--concurrent-fragments 1`.
- For **actual media downloads** on stable sources: try `-N 2` or `-N 4`, but combine it with `--limit-rate`, retries, and jitter.[1]
- If you hit throttling or bans, lower concurrency before adding more complexity.

## Scaling from 10 channels to 100 with proxy rotation

### What yt-dlp supports
yt-dlp documents `--proxy URL` for HTTP/HTTPS/SOCKS proxies and `--source-address IP` to bind the client-side IP address, plus request sleeps and retries for rate-limit resilience. There is no built-in “rotate through a proxy list” feature in yt-dlp; third-party guidance recommends either a rotating proxy gateway or a wrapper script that cycles through a list of proxies.[3][1][2]

### Practical scaling pattern
1. **Keep phases separate**: inventory pass, metadata pass, subtitles pass, comments pass.
2. **Use sequential channels with modest parallelism only at the job-queue level**, not inside a single yt-dlp process.
3. **Rotate proxy per channel or per video**, depending on failure rate and proxy cost.[3]
4. **Persist after each video** so failures never wipe a whole batch.
5. **Promote only shortlisted videos to deeper extraction** to reduce load.
6. **Use random jitter** between requests and between jobs.
7. **Measure failure and 429 rates per proxy** so you can quarantine bad exits.

### Suggested proxy files
`channels.txt`
```text
https://www.youtube.com/@channel1
https://www.youtube.com/@channel2
```

`proxies.txt`
```text
http://user:pass@proxy1:8080
socks5://user:pass@proxy2:1080
http://user:pass@proxy3:8080
```

### Operational note
For 100 channels, a rotating proxy provider with sticky sessions is usually simpler than self-managing dozens of raw proxies, because yt-dlp can point at one gateway while the provider rotates exits upstream. A wrapper is still useful even with a rotating provider so you can handle retries, checkpointing, and per-job fallbacks.[1][3]

## Advanced yt-dlp flags relevant to scaling
- `--proxy URL` — send traffic through a proxy.[2][1]
- `--source-address IP` — bind to a specific local IP.[1][2]
- `--socket-timeout SECONDS` — fail faster on dead exits.[2][1]
- `--sleep-requests SECONDS` — pause between extraction requests.[2]
- `--sleep-interval` / `--max-sleep-interval` — randomized sleep before each download.[2]
- `--retry-sleep TYPE:EXPR` — exponential backoff for HTTP, extractor, or fragment failures.[2]
- `-N, --concurrent-fragments N` — only for fragment downloads; useful for media throughput, but usually keep at `1` for metadata-focused quality analysis.[1]

## How to rotate proxies automatically in a yt-dlp script

yt-dlp supports `--proxy` and `--source-address`, but not native proxy rotation; automatic rotation must be handled in your wrapper script or by a proxy provider with a rotating gateway. The practical patterns are:[4][3]
