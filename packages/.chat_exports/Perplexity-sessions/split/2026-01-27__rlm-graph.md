## Assistant

RLM + Graph (often called “RLM‑Graph” or “RLM‑on‑KG”) is basically Recursive Language Models applied on top of a graph/knowledge‑graph instead of just a flat text buffer or file system.[1][2][3][4]

## Core idea

- A **Recursive Language Model** treats the long context as an external “environment” it can inspect and modify via tools (Python REPL, file APIs, etc.), rather than stuffing everything into one massive prompt.[2][1]
- RLM + Graph swaps that environment from “files/chunks only” to a **graph**: nodes (entities, chunks, concepts) and edges (relations, references), which the model explores and updates recursively.[3][4]

## How it works (high level)

- Documents are chunked, embedded, and turned into nodes and edges (entity nodes, chunk nodes, relationship edges) stored in a graph DB plus an in‑memory vector store.[4][3]
- On a query, the agent:
  - Uses vector search to get semantically relevant chunks.[3][4]
  - Uses graph traversal to follow relations (entities, co‑mentions, citations, KG links) and pull structurally related context, not just keyword/semantic matches.[4][3]
  - Recursively issues further searches or traversals, maintaining a **working memory** of discovered facts, node IDs, and partial summaries to avoid redundant exploration.[3][4]
- A Python‑like REPL (or similar tool layer) orchestrates this: the LM writes “code” that calls search/traversal functions, inspects results, stores them in variables, and iterates until it has enough evidence to answer.[1][2][4][3]

## Why combine RLM with graphs?

- **Infinite-ish context with structure**: RLM lets you span effectively unbounded information; the graph gives a **map** so exploration is targeted, not random chunk‑hopping.[2][4][3]
- **Better retrieval than plain RAG**: pure vector RAG struggles with compositional queries and multi‑hop reasoning; graph edges and typed nodes encode explicit relationships that can be traversed.[4][3]
- **Explainability and grounding**: because answers are built from graph nodes and edges, you can trace which nodes were used, show paths, and audit the reasoning.[3][4]

## Relation to GraphRAG and classic RAG

- Classic RAG: vector store over chunks; retrieve top‑k; answer.[5][4][3]
- GraphRAG: build a graph over documents (communities, entities), then use graph queries and summaries at query time.[4][3]
- RLM + Graph:
  - Uses an RLM control loop (recursive tool‑calling LM) where the environment is a **graph** (or RDF KG) plus vectors.[2][3][4]
  - Emphasizes iterative graph navigation and working memory, not just one‑shot community retrieval.[2][3][4]

## Implementation sketch (for someone like you)

Very roughly, an RLM‑Graph system looks like:

- Storage:
  - Graph DB (Neo4j, Memgraph, RDF store, etc.) for entities, chunks, and relations.[3][4]
  - Vector store for chunk embeddings (FAISS, Qdrant, pgvector, etc.).[4][3]
- Tools exposed to the LM:
  - `search_vectors(query_embedding, k)`  
  - `graph_neighbors(node_id, relation_type, depth)`  
  - `get_chunk(node_id)` / `get_entity(node_id)`  
  - `add_node`, `add_edge`, `update_summary`, etc.  
- Control:
  - An RLM harness that lets the LM iteratively write “code” in a Python REPL or similar, call the above tools, maintain a working memory structure, and decide when to stop and answer.[1][2][3][4]
