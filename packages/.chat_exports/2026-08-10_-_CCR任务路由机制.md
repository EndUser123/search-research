## We can combine routing with capability enforcement

Grok's native subagents have explicit `capability_mode` values:

- 
`read-only`

- 
`read-write`

- 
`execute`

- 
`all`

and built-in `explore`/`plan` agents cannot edit files, whereas `general-purpose` gets the full toolset. [[image]GitHub](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-pager/docs/user-guide/16-subagents.md?utm_source=chatgpt.com)

That means classification doesn't merely have to determine **which model**.

It can determine:

```
WORK CLASS
    │
    ├── cognitive capability
    │      mechanical / implementation / reasoning
    │
    └── operational capability
           read / write / execute
```

For example:

```
investigation/debugging
        ↓
reasoning-capable worker
        +
read-only/execute capability
        ↓
cannot modify code prematurely
```

versus:

```
approved implementation
        ↓
coding-capable worker
        +
read-write/execute
```

That gives us a powerful way to enforce the **investigate → decide → implement** boundary rather than merely telling the LLM about it.

### Claude permissions add another enforcement layer

Grok directly reads Claude Code `allow`, `ask`, and `deny` permission rules. More importantly, Grok's authorization order is:

```
PreToolUse hook
      ↓
permission rules
      ↓
remembered grants
      ↓
built-in approvals
```

A `PreToolUse` denial happens **before** the permission system, and `deny` permission rules beat `ask` and `allow`. [[image]GitHub](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-pager/docs/user-guide/22-permissions-and-safety.md?utm_source=chatgpt.com)

So we could have:

```
              Grok reasoning
                    │
                    ▼
             proposed delegation
                    │
                    ▼
           ROUTING GUARD HOOK
                    │
             is route valid?
                    │
                    ▼
              PERMISSIONS
                    │
          is action authorized?
                    │
                    ▼
              CAPABILITY MODE
                    │
         does worker even possess
            required tools?
                    │
                    ▼
                 execute
```

Those are three independent controls rather than one giant hook.

## This suggests a better architecture than we had 10 minutes ago

I wouldn't make the routing hook responsible for everything.

I'd use **four layers**.

**1. Grok — semantic authority**

Grok decomposes the task and proposes:

```
class: investigation
effort: high
worker: reasoner
capability: read-only
```

**2. Routing guard — cognitive floor**

The hook only checks for obviously unsafe under-routing:

```
investigation → mechanical worker
architecture → implementation worker
unknown root cause → mechanical worker
```

Reject and return the reason to Grok.

**3. Agent capability — action boundary**

Use Grok's native capability modes to make certain mistakes impossible:

```
reasoning/investigation
    → read-only or execute

implementation
    → read-write/all

mechanical
    → narrowly scoped capability
```

**4. Permission policy — dangerous-operation boundary**

Use `.grok/config.toml` or Claude-compatible `.claude/settings.json` rules for things that should be blocked regardless of classification.

For example:

```
rm -rf
git push --force
credential files
production operations
etc.
```

This is better separation of concerns.

### Claude compatibility gives us another strategic advantage: reuse

There is already a lot of Claude Code work around routing, hooks, skills and agents.

Because Grok intentionally consumes Claude's configuration structures, we potentially don't need to **port the conceptual pattern and rewrite everything**.

For a candidate Claude routing project we can ask:

```
Can Grok consume this directly?
        │
        ├── yes → reuse
        │
        ├── mostly → thin adapter
        │
        └── no → port mechanism
```

That materially changes how I'd approach the repo research we discussed earlier.

For instance, the existing Claude-model-router-hook pattern becomes considerably more interesting if its `PreToolUse` machinery and settings schema can be made Grok-compatible with only a thin adaptation.

### But compatibility isn't magical

There are two important boundaries.

First, **Claude session compatibility is currently staged/inert**. The configuration exists, but Grok's docs explicitly say no foreign-session scanner consumes it yet. [[image]GitHub](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-pager/docs/user-guide/05-configuration.md?utm_source=chatgpt.com) So we should not design anything that depends on Claude session semantics being faithfully reproduced.

Second, compatibility doesn't mean every Claude behavior is identical. We need to distinguish:

```
configuration-compatible
        ≠
payload-compatible
        ≠
behavior-compatible
```

That is especially important for hooks.

A Claude hook may load successfully but still receive a different-enough tool name, payload structure, agent identifier, or lifecycle behavior that our classifier doesn't work correctly.

## One capability I would exploit heavily

Grok's headless interface gives us very strong control over delegated workers:

`--tools`, `--disallowed-tools`, `--agents`, `--max-turns`, `--effort`, permission modes and sandbox profiles can constrain individual executions. It can even prohibit all subagent spawning or specific agent types. [[image]GitHub](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-pager/docs/user-guide/14-headless-mode.md?utm_source=chatgpt.com)

So eventually:

```
                 ROUTING DECISION
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
   MECHANICAL      IMPLEMENTATION   REASONING
        │              │              │
 low-cost model    coding model    strong reasoner
        │              │              │
 narrow tools      write+test       read+execute
        │              │              │
 low effort        medium effort     high/xhigh
        │              │              │
 short turns       bounded turns     larger budget
```

**Classification can control model + reasoning effort + tools + permissions + sandbox + turn budget**, not merely model selection.

That is substantially more valuable than a Claude-Code-Router-style "Haiku versus Sonnet versus Opus" switch.

### What I would do next

Before designing anything, I would do a targeted source-level comparison of:

1. 
Grok native hooks,

2. 
Grok Claude-compatible hook parsing and payload translation,

3. 
`claude-model-router-hook`,

4. 
Grok subagent selection/capability modes,

5. 
Grok headless model/effort/tool controls.

The key question isn't anymore **"Can Grok support our classifier?"** It clearly has most of the primitives.

The better question is:

> 
**How much of an existing Claude routing implementation can we reuse through Grok's compatibility layer, while letting native Grok capabilities handle enforcement that Claude routing projects had to build themselves?**

I suspect the resulting implementation could be **considerably smaller than what we've been envisioning**—possibly a thin routing guard plus policy/configuration rather than a new routing subsystem.

## #4 · assistant

Yes. After checking the current implementations more carefully, I would **revise part of my previous answer**.

**Grok's Claude compatibility mode does not magically give Grok Claude's larger hook system.** It is primarily an **import/translation compatibility layer over Grok's own hook runtime**.

My confidence in that conclusion is **~95%** because the current Grok Build hook documentation states the behavior explicitly, and it matches the current configuration docs. [[image]GitHub+1](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-pager/docs/user-guide/10-hooks.md)

## What actually happens

Grok scans:

```
~/.claude/settings.json
.claude/settings.json
.claude/settings.local.json
```

when `[compat.claude].hooks = true`. [[image]GitHub+1](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-pager/docs/user-guide/10-hooks.md)

But then the configuration enters **Grok's hook engine**:

```
Claude settings.json
        ↓
Grok compatibility loader
        ↓
translate what Grok understands
        ↓
GROK HOOK MODEL
        ↓
Grok lifecycle events
```

It does **not** become:

```
Claude settings
       ↓
full Claude hook runtime
       ↓
all Claude lifecycle capabilities
```

The smoking-gun sentence in the Grok documentation is that **unrecognized hook event names are skipped so shared Claude/Cursor settings files can still load**. [[image]github.com](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-pager/docs/user-guide/10-hooks.md)

So compatibility means approximately:

> 
"Run the compatible subset without making you rewrite all your Claude configuration."

Not:

> 
"Emulate Claude Code."

Only `PreToolUse`, `Stop`, and `SubagentStop` provide blocking control. [[image]github.com](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-pager/docs/user-guide/10-hooks.md)

Claude Code currently exposes considerably more, including:

```
TeammateIdle

InstructionsLoaded
ConfigChange
CwdChanged
DirectoryAdded

```

Claude's official current hook reference lists those lifecycle points explicitly. [[image]Claude](https://code.claude.com/docs/en/hooks)

So if a Claude configuration contains:

```
"TaskCompleted": [...]
```

Grok does **not** synthesize a `TaskCompleted` lifecycle event.

It simply doesn't have that event to fire.

## Where Grok does translate

There is some meaningful adaptation.

For example Claude tool matchers are translated:

```
Claude             Grok

Bash          →    run_terminal_command
Read          →    read_file
Edit/Write    →    search_replace
Grep          →    grep
Glob/ListDir  →    list_dir
WebSearch     →    web_search
Task          →    spawn_subagent
```

Grok also retains the original alias so a Claude-style matcher such as `Bash` can still match the Grok tool. [[image]GitHub](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-pager/docs/user-guide/10-hooks.md)

That's good compatibility engineering.

Likewise, `SubagentEnd` is accepted as an alias for Grok's `SubagentStop`. [[image]github.com](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-pager/docs/user-guide/10-hooks.md)

So there are three cases:

| Claude feature | Grok behavior |
| --- | --- |
| Same concept exists | Run it |
| Same concept, different naming | Translate/map |
| Grok has no equivalent lifecycle event | Skip it |

That third category is the important one.

# Claude also has hook *types* Grok doesn't currently expose

This is another distinction I previously underweighted.

Current Grok's documented handler types are:

```
command
http
```

[[image]GitHub](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-pager/docs/user-guide/10-hooks.md)

Claude currently has five:

```
command
http
mcp_tool
prompt
agent
```

[[image]Claude](https://code.claude.com/docs/en/hooks)

Claude's `prompt` hook can itself invoke an LLM to make a semantic decision. Its `agent` hook can launch an agent with tools to investigate before returning its decision. [[image]Claude+1](https://code.claude.com/docs/en/hooks)

That's directly relevant to **our classifier idea**.

Claude can natively express something like:

```
PreToolUse(Task)
       ↓
agent hook
       ↓
inspect delegated work
       ↓
reason about classification
       ↓
allow / reject
```

Grok currently doesn't give us that same first-class `type:"agent"` hook mechanism.

We can reproduce the behavior with a **command or HTTP hook that invokes another process/model**, but that's our implementation—not compatibility magically supplying Claude's feature.

# Async hooks are another difference

Claude has:

```
{
  "type": "command",
  "async": true
}
```

which lets the hook run in the background and later inject results back into the conversation. [[image]Claude](https://code.claude.com/docs/en/hooks)

Grok's documented handler schema does not currently expose that Claude async-hook mechanism. Grok does have its own background-task machinery, but that's a different facility; I would **not assume a Claude async hook imported from `settings.json` retains Claude semantics** without a live test. [[image]GitHub](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-pager/docs/user-guide/10-hooks.md)

That's exactly the kind of compatibility edge where "configuration loads" can be mistaken for "behavior is equivalent."

# There are even payload differences on hooks that *are* supported

Grok explicitly documents several.

Claude uses snake_case in places where Grok's raw hook wire format uses camelCase:

```
Claude                  Grok

stop_hook_active   →    stopHookActive
hook_event_name    →    hookEventName
tool_response      →    toolResult
```

Grok also has different `permissionMode` values and slightly different Stop semantics. [[image]GitHub](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-pager/docs/user-guide/10-hooks.md)

So an old Claude hook can satisfy:

```
✓ event exists
✓ matcher loads
✓ executable runs
```

and still fail because:

```
✗ script reads wrong payload field
```

That's especially relevant to the system you've been building, because we've repeatedly found that **payload identity and actual live-path semantics matter much more than a nominal compatibility claim**.

# What this means for our routing solution

This actually makes me **more confident in Grok's suitability**, but for a narrower reason.

We don't need most of Claude's additional hook surface for the routing guard we're discussing.

The critical path is:

```
              GROK
                │
        decides delegation
                ↓
       spawn_subagent
                │
                ↓
     ┌────────────────────┐
     │ PreToolUse         │
     │ routing guard      │
     └─────────┬──────────┘
               │
          allow / deny
               ↓
            WORKER
               │
               ↓
     ┌────────────────────┐
     │ SubagentStop       │
     │ evidence gate      │
     └─────────┬──────────┘
               ↓
             GROK
               │
               ↓
     ┌────────────────────┐
     │ Stop               │
     │ completion gate    │
     └────────────────────┘
```

**All three enforcement points exist natively in Grok and are blocking.** [[image]GitHub+1](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-pager/docs/user-guide/10-hooks.md)

That's the important finding.

We don't need:

- 
`TaskCompleted`

- 
`PostToolBatch`

- 
`TeammateIdle`

- 
`WorktreeCreate`

- 
`ConfigChange`

- 
etc.

to implement the core cognitive-routing control.

## Where Claude's extra functionality *would* improve our design

There are two Claude features I'd genuinely like to have.

### 1. `agent` hook

This would let an independent verifier examine ambiguous routing decisions without us constructing a subprocess orchestration layer ourselves. Claude describes agent hooks as spawning a tool-capable subagent to investigate the condition before producing a structured decision. [[image]Claude](https://code.claude.com/docs/en/hooks)

For us:

```
Grok says:
"mechanical"

         ↓

routing guard:
obviously safe?
   │
   ├─ yes → allow
   │
   ├─ no → deny
   │
   └─ ambiguous
          ↓
     independent
       reasoner
```

In Grok, we'd have to implement that final branch ourselves.

But I don't think we need it initially.

### 2. `TaskCreated` / `TaskCompleted`

Those would give very clean task-level instrumentation and lifecycle state.

Instead, in Grok we'd likely derive much of it from:

```
PreToolUse(spawn_subagent)
SubagentStart
SubagentStop
PostToolUse(spawn_subagent)
```

That's sufficient, but less semantically rich.

# One concern is more important than missing features

Grok hooks **fail open**.

Its documentation says hook timeout, crash, malformed output, etc. do not block execution; only an explicit deny from a successfully executed hook blocks `PreToolUse`. [[image]GitHub+1](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-pager/docs/user-guide/10-hooks.md)

Therefore:

```
bad classification
      ↓
guard detects it
      ↓
DENY
```

works.

But:

```
bad classification
      ↓
guard crashes
      ↓
execution continues
```

also happens.

For **cost/quality routing**, I think that's acceptable.

For **security/safety/integrity enforcement**, I wouldn't treat the Grok hook as the sole authority.

That's an important design boundary.
