## 2. Page Format

Every concept page uses this structure:

### Frontmatter (required + optional fields)

```yaml
---
# Required
title: "<descriptive title>"
created: <YYYY-MM-DD>
source: session-<YYYY-MM-DD> | <original_filename> | <URL>
tags: [<relevant lowercase tags>]
summary: >
  <2-3 sentence summary of the big idea — the single most important takeaway>

# Recommended (advisory, not lint-enforced)
agent: grok | claude-code           # cross-agent provenance
host: grok | claude | both          # which host wrote/tested this (2026-07-18 convention)
cognitive_load: <1-5>               # mental effort to apply (see §3 below)
verification: local-only | inferred-only | multi-source-verified

# Optional (context-dependent)
evidence_gaps:                      # list of what evidence is missing
  - "<description of gap>"
source_url: <URL if web source>     # enables --source-drift checks
source_hash: <SHA256 of source>     # enables --source-drift checks
relations:                          # typed relationships
  - target: wiki/concepts/<page>
    type: supports | contradicts | refines | supersedes | related
    reciprocal: <type if target references back>
---

## Summary
<2-3 sentence "big idea">

## Key Findings
<List of specific findings, quotes, or claims. Annotate with:>
- EVIDENCE_GAP: <what evidence is missing or unverified>
- Assumption: <what is assumed but not proven>

## Related
<Hand-authored wikilinks to related pages: [[page-slug]]>
<Typed wikilinks: [[Page]]@supports | @contradicts | @refines | @supersedes | @related>

## Auto-related
<Auto-generated by wiki_after_write.py — do not edit manually>

## Sources
<Source files, URLs, tool calls, or "session-YYYY-MM-DD">
```

### `## Auto-related` vs `## Related` convention

- `## Auto-related` — **auto-managed** by `wiki_after_write.py`. Re-run regenerates. Never hand-edit.
- `## Related` — **hand-authored** by the page writer. Never touched by automation.
- Both coexist on the same page. The separation lets automation and human curation coexist.

## 3. Frontmatter Field Definitions

### `cognitive_load: <1-5>`

Self-rated **mental effort to correctly apply the page**, not complexity of the
underlying topic. Distribution in current corpus (55 of 784 pages have it set):

| Value | Pattern | Effort |
|---|---|---|
| `1` | Single-fact rule, often wikified AGENTS.md subsection. Load and apply reflexively | Minimal reading (n=3 in corpus) |
| `1-3` | Same rule with edge cases. Quick scope check before applying | Mixed (range form, 8 pages) |
| `2` | Single concept with caveats (ADRs, scoped conventions, diagnostic mechanics) | Read carefully; apply with caveats (20 pages) |
| `3` | Investigation / debugging recap with evidence_gaps. Read, probe, judge before acting | Multi-step (17 pages) |
| `4` | Architecture / wide-impact (multi-system ADRs, cross-provider benchmarks) | Deep reading; sustained reasoning (7 pages) |
| `5` | Reserved; unused in current corpus | n/a |

Pick the lowest value that honestly describes the effort. Default `2` if unsure.

### `verification: local-only | inferred-only | multi-source-verified` `[self-discipline]`

- `local-only` — verified via direct probe, file inspection, or live test in the cited session
- `inferred-only` — inferred from web research, documentation, or analogous cases; **NOT** locally reproduced
- `multi-source-verified` — confirmed via two or more independent sources (e.g., local probe + upstream changelog)

Default when evidence is mixed: `inferred-only`.

**This field is advisory** — `wiki_health_check.py` does not currently require it
(`REQUIRED_FRONTMATTER = ('title',)` only). Promote to required only after the
convention has stabilized across multiple sessions of usage.

### `agent: grok | claude-code`

Every page includes `agent: <host>` in frontmatter. Pages written by Claude Code
have `agent: claude-code` or no `agent` field (older pages pre-dating the convention).
This lets future sessions trace which agent discovered each finding without reading the body.

### `host: grok | claude | both`

For pages that document host-specific behavior (e.g., Grok Build vs Claude Code
hook mechanics), tag the `host:` field. Missing field = pre-convention (treat as host-agnostic).

## 4. Quality Gate `[self-discipline]`

Before writing a page, verify the content passes ALL of these. There are two wiki-worthy content types — **findings** (something we learned about the world) and **decisions** (a choice made with rationale). Both belong in the wiki; the gate differs.

### 4a. Findings — something learned about how the system/library/world behaves

- **Is it non-obvious?** (Would a future agent/human not already know this?)
- **Is it verified?** (Did we confirm it with a tool call, live probe, doc fetch, or code read? Unverified → flag with EVIDENCE_GAP or skip.)
- **Are CLI commands, file paths, and numeric counts verified?** (Every CLI command, file path, and count written into a page must be confirmed by a tool call this session — not recalled from memory. Run the command; check the path exists; recount if needed.)
- **Is it durable?** (Will this still be true/relevant in 3 months?)
- **Is it distinct?** (Not already covered by an existing wiki page?)
- **Is the host tagged?** (If the finding describes behavior specific to one platform, `host:` must be set. A Claude Code bug written by a Grok agent still needs `host: claude`.)
- **Are generalizations scoped?** (Every generalization in Key Findings — "X affects Y, Z, W" — must cite per-claim evidence or carry an inline `EVIDENCE_GAP: generalized from <specific observation>`. Don't present inferred patterns at the same confidence level as verified observations.)

### 4b. Decisions — a design/architectural choice made with rationale

Decisions are wiki-worthy when they meet ALL of:

- **Is it architectural?** (Does it shape the system's structure — skill design, pattern choice, schema, convention? A routine tactical choice like "used list not tuple" is NOT a decision; it's implementation detail.)
- **Has a selection criterion?** (Names the axis optimized — cost, reversibility, evidence-fit, reliability. Without a criterion, the choice is arbitrary and not durable.)
- **Has a rationale?** (States WHY the chosen option wins on that criterion. Future sessions will re-litigate decisions without rationale.)
- **Has a steelman?** (Names the rejected viable alternative and why it was reasonable. A decision with no steelman is suspect — it means alternatives weren't considered.)
- **Has a falsifier?** (States what observation would make this decision wrong or obsolete — when to re-litigate.)
- **Is it durable?** (Will this decision still be relevant in 3+ months?)
- **Is it distinct?** (Not already covered by an existing decision page? If it refines an existing decision, add a `relations: type: refines` entry instead of a new page.)

Decision pages use the same frontmatter and template as findings, but their body should include: **Decision context** (the problem), **the principle/decision** (what was chosen), **selection criterion + rationale**, **steelman of the rejected alternative**, **falsifier**.

### 4c. Failure mode this division prevents

The 2026-07-25 session produced 3 decision pages (multi-producer-cross-model-synthesis, inline-conditional-over-dispatch-for-skill-design, synchronous-review-direct-write-pattern) that were initially treated as findings. They were actually decisions — choices with alternatives and criteria. Without the decision gate, decision pages were held to the findings standard ("is it verified?") instead of the decision standard ("does it have a steelman + falsifier?"). Decision quality discipline was missing. The §4b gate makes it explicit.

If any check fails (for the relevant content type), skip or flag with EVIDENCE_GAP. Never write a page that fails the non-obvious/distinct (findings) or architectural/durable (decisions) checks.

## 5. Link Density `[self-discipline]`

> **Enforcement tier:** `[self-discipline]` — `wiki_health_check.py` does not check link count. `[lint-enforced]` rules have a script gate; `[self-discipline]` rules rely on agent behavior.

Every new concept page should link to **≥3 other concept pages** via `[[wikilinks]]`
in `## Related` or `## Auto-related`. The 3-link empirical sweet spot is from
the Zettelkasten / Obsidian link-density tradition: 2 tends to be too few
(likely redundant), 5+ tends to be cognitive overload at write time.

**Advisory only** — `wiki_health_check.py` does not currently enforce it.
Baseline coverage is only ~18% of the corpus (143/784 pages meet ≥3).
Promote to lint-enforced only after one session of usage data shows what
natural authoring behavior is.

## 6. Log Protocol

Append to `P:/.data/wiki/log.md` for each page written or updated:

```
## [YYYY-MM-DD] ingest | <title>
Source: session-<YYYY-MM-DD>
Agent: grok | claude-code
Notes: <optional context>
Page: wiki/concepts/<slug>.md
```

For updates:
```
## [YYYY-MM-DD] update | <title>
Source: session-<YYYY-MM-DD>
Agent: grok | claude-code
Notes: <what changed and why>
Page: wiki/concepts/<slug>.md
```

**Field notes:**
- `Source:` records the session date (provenance). The original ADR / doc / URL
  path is recorded in the wiki page's `source:` frontmatter field instead, so the
  log stays compact.
- `Agent:` records which host wrote the entry (`grok` or `claude-code`).
- `Notes:` is a single line; longer context belongs in the page body.
- SHA256 is not part of the canonical log format (was used in some earlier
  entries; provenance now flows through the page `source:` field).

Newest entries go at the TOP. Append-only; never edit or delete historical entries.
Use `wiki_log_append.py` (see §9) for atomic prepending with idempotency — it
handles the `# Vault Log` sentinel, the `.tmp` + `os.replace` atomic write pattern,
and skips if the same page+type entry already appears in the first 200 log lines.

## 7. Typed Wikilinks

For explicit relationships, use typed wikilink syntax:

- `[[Page]]@supports` — Page provides supporting evidence
- `[[Page]]@contradicts` — Page contradicts this one
- `[[Page]]@refines` — Page refines or clarifies this one
- `[[Page]]@supersedes` — Page supersedes this one
- `[[Page]]@related` — general relationship

When using typed wikilinks, also record in frontmatter under `relations:`.

## 8. Speculative Linking Policy

When ingesting, if content references pages that don't exist yet, create
`[[wikilinks]]` to those pages anyway — they become "red links." This is
**intentional**: future ingest of those pages will resolve the links
automatically. **Never suppress a link because the target doesn't exist yet.**

Do NOT suppress a broken red-link just because the target doesn't exist.
Speculative links are seeds for future pages.

## 10. Operations

> **All operational procedures live here — both hosts use the same scripts
> via absolute paths.** Each host's SKILL.md contains only host-specific
> invocation notes (e.g., `/main --fix` automation on Claude-side).

### Ingest

**Session-ingest** (default when `/wiki` is invoked with no args):
1. Scan conversation for durable findings (non-obvious fixes, benchmarks, decisions, rejected alternatives).
2. Deduplicate: grep `P:/.data/wiki/concepts/` for slugs/titles/content overlap. Read top 2-3 candidates to confirm real overlap. **When checking for existing pages on the same topic, verify `host:`** — a same-topic page for a different host is NOT a duplicate (e.g., Grok `/export` filename behavior ≠ Claude Code `/export` mkdir failure).
3. If nothing unique survives → report "nothing new to ingest" and stop.
4. If multiple distinct findings survive → write one page per finding. Do not aggregate.
5. Write each page using §2 page format. **If the finding is host-specific** (observed on one platform, not necessarily others), **set `host:` in frontmatter**. This prevents conflation when the same command name exists on multiple hosts (e.g., `/export` exists in both Grok Build and Claude Code with different implementations and different failure modes).
6. Run auto-link: `python .../wiki_after_write.py <page-path>`. Best-effort; no-op if QMD returns nothing.
   Then run contradiction scan: `python .../wiki_contradiction_scan.py <page-path>`. Same best-effort contract — falls back to tag-overlap grep if QMD returns nothing, and is a clean no-op when no opposing-polarity claims are detected. v1 scope is tag-overlap + simple negation-keyword matching only (supersession and version-drift patterns deferred to v2). Injects `[[slug]]@contradicts` lines into the existing `## Auto-related` section with a `<!-- contradiction-scan: detected YYYY-MM-DD -->` marker; never touches the hand-authored `## Related` section.
   **Single-call alternative:** `python .../wiki_ingest.py --post-write <page-path> --notes "<1-line>"` runs all post-write steps in order — verify → `qmd update` → auto-link → contradiction-scan → log-append. Steps run in strict order; failures are reported in JSON status but do not abort the chain. Prefer this driver for bulk ingest; use the individual scripts for ad-hoc operations.
7. Append to `log.md` (§6 format).
8. Run QMD update if available: `qmd update` to refresh the semantic index.
9. Report: pages written (title → path) and pages skipped.

**Bulk file ingest** (when ingesting from Downloads, transcripts, or other directories):
1. Pre-phase: run manifest script (`wiki_manifest.py`) to SHA256-hash all files and dedup against `log.md`. Output: manifest JSON with `{path, hash, size, status, tier}`.
2. Ingest phase: dispatch one subagent per `status: pending` manifest entry. Each subagent reads its file, verifies hash, writes a wiki page, appends to log, updates manifest status.
   - **Tier classification**: safe (`<200KB`) → direct ingest; large-warn (`200KB-500KB`) → ingest with warning; large-skip (`>500KB`) → skip unless `--force`.
   - **Idempotency**: SHA256 dedup via `log.md` check. Files already logged → `status: skipped`. On retry, pending entries re-dispatch.
3. Post-phase: run QMD update wrapper.

**URL handling**:

**YouTube URLs** (`youtube.com/@`, `/channel/`, `/c/`, `youtu.be/`, `/watch`):
1. **Channel already tracked** (`csf-source list`): run `python bin/csf-source fetch --source <url>` → check `transcripts.sqlite` → on failure, invoke Gemini CLI: `gemini -m gemini-2.5-flash -p "Summarize: <url>"`. Write to `P:/.data/yt-is/transcripts/`.
2. **Channel NOT tracked**: `python bin/csf-source add <url>` → then fetch.
3. **Single video URL**: extract ID → `csf-transcripts <video_id> --transcript` → if not cached: `csf-transcript-fetch` or Gemini CLI.
4. **After transcripts**: run manifest script targeting `P:/.data/yt-is/`.
5. **Failover**: fires when `transcripts.sqlite` shows `failure_reason: no_transcript`.

**Non-YouTube web URLs**: invoke `/crawl <url> --max-pages 5 --collection wiki`.

**Auto-linking detail**: After writing ANY page, run `wiki_after_write.py <page-path>`.

conceptual neighbors get no auto-links — keep a hand-authored `## Related` section
as fallback. Re-run anytime to regenerate from current QMD state. Never touches
hand-authored `## Related`.

### Query

**Step 1 — Scope routing (DEFAULT TO SESSION).**

Classify the query BEFORE searching. The session is the freshest source.

- **Session scope** (default — answer from chat, NO search): vague, conceptual, or references current session work ("the proposal", "what did we decide", "what's important", "recap", "what's unique", "what's the state of"). → Synthesize from conversation context. Cite session evidence by turn/topic.
- **External scope** (search the vault): names a specific tool, library, concept, or prior decision NOT in the current session, OR explicitly asks for persistent knowledge ("what does the wiki say", "search for", "look up", "prior art", "previous note on"). → Run Step 2.
- **Ambiguous → prefer session scope.** Give a one-line answer and note "I can search the wiki if you want more."

**Step 2 — Search (external scope only):**

1. **QMD semantic search** (primary): `qmd search --collection wiki "<question>"` → read top 3-5 results.
2. **Grep fallback** (for exact terms, file paths, error strings): `grep "<exact term>" P:/.data/wiki/concepts/`.
3. **Synthesize**: cite page paths. If nothing relevant, say so — don't fabricate.

**Auto-save high-value results**: if the synthesized answer reveals a new non-trivial insight (connection not already in the vault, resolved ambiguity, decision-relevant synthesis), save directly as a new concept page. Write frontmatter, run auto-link, append to log. Only ask the user if the synthesis is uncertain or incomplete.

### Lint

Two-layer health check: deterministic graph+staleness via script, then LLM judgment.

**Phase 1 — Deterministic (script, no LLM):**
```bash
python P:/packages/.claude-marketplace/plugins/cc-skills-utils/skills/main/scripts/wiki_health_check.py [--json]
```
Emits: broken wikilinks, orphan pages, duplicate slugs, missing frontmatter, stale page count (mtime > 90d).

**Phase 2 — Judgment (LLM, on top of Phase 1):**
For each issue the script could NOT safely auto-fix:
- **Broken red-links**: keep if intentional seed, fix only if clear fuzzy-match target exists at ≥0.9 confidence.
- **Orphan clusters**: keep | merge into related page | leave as seed.
- **Stale claims**: flag assertions referencing deprecated/renamed tools or APIs.
- **Contradictions**: if two pages share a typed `@contradicts` link, note the conflict.

Per policy (§8): **never suppress a broken red-link just because the target doesn't exist** — speculative links are intentional seeds.

**`--fix` mode:** script applies ONLY safe deterministic repairs (unique fuzzy-match broken links at ≥0.9 confidence, single candidate). Never deletes orphans or red-links.
```bash
python .../wiki_health_check.py --fix [--dry-run]
```

**Automation (Claude-side only):** Phase 1 of `/wiki lint` is included in the `/main` health check on every invocation; `/main --fix` applies the safe-subset through a needs-based gate (re-runs only when vault mtime fingerprint changed since last fix; sentinel at `P:/.claude/.artifacts/_main/wiki_autofix_fingerprint.txt`).

**External reference scanning** (consolidation safety net): `--fix` also scans
`P:/docs/handoffs/` and `P:/docs/` for broken path references to deleted wiki
pages. When a wiki page is consolidated/deleted/merged, handoffs referencing it
by path become stale. `--fix` repairs what it can (unique fuzzy match at ≥0.9)
and flags the rest as "manual review needed." **Run `--fix` after every
consolidation pass** (manual merge, `/dream`, or Phase 2 deletions).

### Update

Refresh stale wiki pages by detecting topics that need updating.

**Phase 1 — Discovery** (4 signals):
1. **Stale pages** (deterministic): `wiki_health_check.py --stale --max-age 90 --limit 20 --json`. Lists pages by mtime age (oldest first).
2. **Source drift** (opt-in, for pages with `source_url`): `wiki_health_check.py --source-drift --json`. Fetches upstream URL, hashes it, flags drift vs stored `source_hash`. Reports: `changed`, `missing_hash`, `fetch_failed:<Error>`.
3. **QMD search frequency**: overlay on stale + drift lists to prioritize actively-searched topics.
4. **Git-commit delta**: intersect changed files since `<sha>` with `Sources:` frontmatter on each page. Catches doc-code drift that age and source-drift signals miss.

**Phase 2 — Staleness scoring**: rank candidates by days since update + source-drift signal (strongest — upstream actually moved) + search frequency.

**Phase 3 — Offer to user**: present top candidates ranked by score. Interactive selection (`[U] update [S] skip [D] dismiss`).

**Phase 4 — Refresh pipeline**: for each selected item: fetch current source → compute SHA256 → compare against log → if changed: rewrite page, inject new wikilinks, update log entry, run QMD update → if unchanged: report "already current".

### Index

Rebuild `index.md` catalog from current wiki state.

### Init

Seed project `CLAUDE.md` with a Wiki Index pointer so agents know the wiki exists and how to query it. Idempotent: re-running updates the fenced block, never duplicates.

## 12. Evidence-First Principles

- **E1 — Evidence before claims.** Before claiming code is absent, unchanged, or non-existent — search the codebase and verify with tools first. Claims of absence are valid only after confirmed Read/Grep/git failures.
- **E4 — Investigate before asking.** Do NOT answer without reading relevant source files first. Do not ask the user for information you can obtain via Read, Grep, Bash, git, or MCP tools.
- **E5 — Anti-lazy escape hatch.** Prohibited: "I assume" / "I think" / "probably" without tool verification. Claiming something doesn't exist without confirmed tool failure.

## 13. Key Principles

1. **One page per finding** — never aggregate unrelated findings.
2. **Dedup before write** — grep the vault first, read candidates to confirm.
3. **Evidence over confidence** — cite the tool call, probe, or doc that verified the claim.
4. **Shared vault** — `P:/.data/wiki/` is the single source of truth for all agents.
5. **Speculative links are fine** — `[[nonexistent-page]]` seeds future pages.
6. **Never fabricate** — if the vault doesn't have it, say so.
7. **Use the scripts** — auto-link, health check, QMD search already exist. Call them.
8. **Cross-agent provenance** — tag `agent:` so future sessions know the source.
9. **Proactive** — suggest saving when a hard-won finding surfaces mid-conversation.
10. **Meta-work ≤ value-work** — schema edits, MOC creation, skill refactoring, and governance changes should not exceed the effort of actual knowledge capture they support. If you've spent more time organising the wiki than writing findings, stop organising and start writing. The wiki's value is its content, not its governance.
11. **Decision-time facts must be findable at the keyword a search would actually use** — if a fact would change a planning decision (a capacity limit, an API constraint, a tier-specific behavior, a cap, a default), it gets its own page — even if it's a one-paragraph fact, and even if it's already mentioned inside a longer page. Discoverability beats density: a future session grepping "notebooklm source limit" will not read a 4-page gotchas doc end-to-end, and QMD indexes by chunk — if the fact is buried in chunk 4 of a different doc, the keyword query won't surface it reliably. "Covered elsewhere in the vault" is the same as "doesn't exist" for keyword search. **The keyword test:** before merging a thin fact into an existing page, ask "what 2–4 word query would a future session actually type when they need this fact?" If that query doesn't return the page containing the fact in the top 3 results, the fact needs its own page. Reference failure (2026-07-25): the NotebookLM "paid account = 300 sources" correction was initially buried inside a longer operational-gotchas page; a future session searching for the source limit would have missed it. Extracted to its own page: `wiki/concepts/notebooklm-source-limits-free-vs-paid.md`.
