# I/O safety review lens

## The pattern that standard lenses miss

Standard `/review` lenses (correctness, maintainability, security,
architecture) naturally focus on **logic** — does the code do the right
thing? They rarely ask: **what happens if the filesystem operation
half-completes?**

The canonical data-loss pattern:

```python
os.remove(target)        # ← original gone
shutil.copy2(src, dest)  # ← if this fails, data is LOST
```

This is correct on the happy path. It is catastrophic on failure:
disk full, file locked, network drop, permission denied, antivirus
quarantine. The exception handler logs an error, but the file is gone.

## Why 4 reviews missed it

Reviews #1-3 on Keep-Smaller-Copy focused on the UI layer (spinner,
buttons, reactive state, placeholder). The data-path code
(`_do_process`) was read as part of "does copy work?" — and it does
work, on the happy path. Nobody asked "what if the copy fails?" because
the lens didn't include failure-mode analysis of I/O operations.

Review #4 was explicitly "full codebase trace including data paths" —
and found it in 30 seconds once it looked at the delete-before-copy
sequence.

## The fix: "I/O failure mode" lens

Add this to `/review` Step 2 lens inference:

| Signal | Add lens |
|--------|----------|
| Code does `os.remove` / `os.unlink` / `shutil.rmtree` followed by copy/write/move | **io-safety** |
| Code writes to a file without temp+replace pattern | **io-safety** |
| Code modifies shared state (dict, list) from a worker thread without snapshot | **io-safety** |
| Session touched copy/move/delete/rename of real files | **io-safety** |

## What the io-safety lens checks

1. **Delete-before-copy:** any `remove`/`unlink` that runs before a
   `copy`/`write`/`move` without a temp-file safety net.
2. **Non-atomic writes:** `open(path, 'w')` without temp+replace —
   crash mid-write leaves corrupt file.
3. **Partial-overwrite:** `shutil.copy2` overwriting an existing file
   in-place — partial copy on failure leaves truncated file.
4. **Worker-thread mutation:** shared `_candidates` list or `selected_rows`
   set mutated from UI thread while a worker iterates it.

## The correct pattern (atomic file replacement)

```python
# Atomic copy: never lose the original
tmp = dest + ".tmp"
shutil.copy2(src, tmp)        # copy to temp
assert os.path.getsize(tmp) == expected_size  # verify
os.replace(tmp, dest)         # atomic rename (same volume)
if dest != old_file:
    os.remove(old_file)       # remove old ONLY after success
```

`os.replace` is atomic on both POSIX and Windows (same volume). If the
copy fails, the temp file is orphaned but the original is intact.
