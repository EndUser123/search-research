# Grok Build hook exit code 1: stderr output as failure signal

## The symptom

All three global SessionStart hooks report exit code 1 when Grok Build
fires them on new session start:

```
X global/SessionStart:session_start[0].hooks[0] (1242ms)  exit code 1
X global/active-surface: session_start[0].hooks[0] (441ms) exit code 1
X global/active-surface: session_start[1].hooks[0] (415ms) exit code 1
```

But the hooks work correctly:
- They exit 0 when run manually (`python scripts/hook.py`)
- They exit 0 with stdin piped (matching Grok's invocation pattern)
- They exit 0 from the correct working directory
- The exec logs confirm they fire and write data on real SessionStart events
- The reported timing (1242ms) is higher than manual runs (<50ms) — unexplained

## The likely cause (MEDIUM confidence)

**Grok Build's hook runner treats stderr output as a failure signal.**
The hooks print status messages to stderr (per `10-hooks.md:205` which
says "stdout is ignored" for SessionStart). The hook runner sees stderr
output and reports exit code 1, even though the script exits 0.

**Precedent:** claude-mem issue #1181 (Feb 2026) documents the identical
symptom in Claude Code:
> "Claude Code's UI displays 'SessionStart:startup hook error' on every
> session start, even though the hooks complete successfully. The hooks
> work correctly — the system reminders confirm 'success' — but the UI
> labels them as errors because it interprets any stderr output as an
> error indicator."

Grok Build inherits the compat layer from Claude Code; the hook runner
behavior likely transfers.

## What's NOT the cause

- **Not a script bug:** hooks exit 0 when run manually under identical
  conditions
- **Not a path issue:** relative paths resolve correctly from the hooks
  directory
- **Not a timeout:** 1242ms < 5000ms configured timeout
- **Not a functional failure:** data is written to exec logs and status
  files on every firing

## The fix (pending verification)

If the stderr theory is confirmed by the diagnostic instrumentation:

1. **Remove `print(..., file=sys.stderr)` from the PASS path** of all
   three hooks. PASS should be silent (file-only). This also resolves
   the R3 review nit (silent-on-PASS, matching the `active-surface`
   convention).
2. **Keep stderr for FAIL/SKIP paths only** — these are actual error or
   warning conditions where stderr is appropriate.
3. **Apply to all three hooks:** `qmd_patches_session_start.py`,
   `active_surface_snapshot.py`, `drift_surface_session_start.py`

## Diagnostic instrumentation

Commit `5145e2c` added diagnostic logging to `qmd_patches_session_start.py`.
On the next new session, it captures to `~/.grok/qmd-patches.diagnostic.log`:
- Python executable path and version
- Working directory
- Environment variables (Grok/Claude)
- stdio state (isatty, stdin data)
- Elapsed time
- Result (PASS/FAIL/SKIP)

This will produce a measurement comparing the invocation environment under
Grok Build vs manual execution.

## What this means for hook design on Grok Build

Until confirmed and fixed, hook authors on Grok Build should:
- **Avoid stderr for non-error output** — use file-based status reporting instead
- **Write status to a `.last.txt` file** (durable, readable by cold-start LLMs)
- **Write history to an `.exec.log` file** (append-only, proves the hook fired)
- **Reserve stderr for actual errors only** — conditions that need human attention
