# Plan skill completeness: what makes LLM plans safe to execute

## The U-shaped cost curve

Total cost of an LLM coding task is U-shaped against specification completeness:

- **Too little spec:** zero upfront cost, but correction loops, rework, and
  human re-engagement compound downstream. Each correction carries token
  cost plus human time.
- **Too much spec:** high upfront human effort, but automated verification
  (tests, oracles) replaces repeated human review.
- **Sweet spot:** structured acceptance criteria or BDD-style scenarios.
  The spec is complete enough to constrain the agent but not so heavy it
  over-constrains valid solutions.

Source: O'Reilly (Eisele, 2026-07) — "Minimal specification looks cheap
only before downstream rework enters the chart."

## Six mandatory completeness checks

Before a plan ships to the operator for approval:

1. **Data-flow completeness** — trace every output artifact from source →
   transformation → output. If any step is missing, add a task packet.
2. **Latency/performance spec** — any hot-path code (hooks, per-turn
   processing) must specify complexity class and scan window.
3. **Under-specified definitions** — fuzzy predicates ("related",
   "similar", "nearby") must have concrete operational definitions.
4. **Cost-proxy accuracy** — formulas that model cost must account for
   caching/discount factors, not naive multiplication.
5. **Exception safety** — new pipeline stages must verify the existing
   wrapper catches errors.
6. **Internal consistency** — no two task packets contradict each other
   (e.g., one says "warn only" and another says "block").

Source: checks 1-5 derived from session 019f8507 AAR efficiency plan review.
Check 6 derived from O'Reilly (Eisele, 2026-07): "specs can be internally
inconsistent: two requirements that contradict each other."

## Multi-agent shift

On a multi-agent host (5+ concurrent sessions sharing one repo):

- The handoff contract IS the product. Every agent boundary needs:
  schema, invariants, allowed ambiguity, validation checks, failure
  behavior.
- "Loose conversational handoff" is insufficient. Typed contracts
  (structured frontmatter + mandatory fields) prevent interpretive drift.
- The breakeven point shifts right: more specification pays off faster
  because drift compounds across handoffs.

Source: O'Reilly (Eisele, 2026-07).

## Adversarial spec review is mandatory

"Attack this spec. Find contradictions, ambiguous terms, hidden
dependencies, untestable claims, missing failure modes, and places where
an implementation could pass the written criteria while still violating
the intent."

This maps to the `/tp` review step. The plan skill should name `/tp`
explicitly as the adversarial reviewer, not leave it to the operator to
remember.

Source: O'Reilly (Eisele, 2026-07).

## Plan review ≠ code review

Plan review catches design-level errors (missing data flow, contradictory
requirements, under-specified definitions). Code review catches
implementation-level errors (bugs, security, style). Both are needed at
different stages. A plan that passes all completeness checks can still
produce buggy code; code review is not optional just because the plan
was good.

Source: Reddit r/AgentsOfAI (LOW quality but valid point);
corroborated by O'Reilly's framing of spec validation as a distinct
cost category.
