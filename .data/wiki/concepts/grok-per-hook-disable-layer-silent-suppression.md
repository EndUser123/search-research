## Summary

A single disabled hook entry in `~/.grok/disabled-hooks` silently suppresses dispatch
while leaving the plugin showing as `(enabled)` in `grok inspect`. This produces the
confusing state where discovery appears correct but enforcement doesn't fire.

## Key Findings

- **File location:** `~/.grok/disabled-hooks`
- **Format:** JSON-encoded list of strings, each a JSON-pointer-ish path:
  `plugin/<plugin-name>/hooks:<event_name>[N].hooks[N]`
  Example: `plugin/exec-gate/hooks:pre_tool_use[0].hooks[0]`
- **Mechanism:** pressing `Space` in the `/hooks` tab toggles a hook's enabled state
  and adds/removes the corresponding entry in this file (source: local
  `~/.grok/docs/user-guide/10-hooks.md` L335-341).
- **Visibility in `grok inspect`:** the plugin shows as `(user, enabled) hooks`. The
  per-hook disable is NOT visible in the standard inspect output unless you already
  know to look for it. The Hooks section shows the matcher but not a `[disabled]` tag
  for plugin hooks (unlike project hooks, which DO show `[disabled]`).
- **Undocumented:** official docs at `docs.x.ai/build/features/hooks` do not mention
  `disabled-hooks` or the persistence of Space-toggle decisions. The file format is
  also undocumented.
- **Persists across version bumps:** entries key by plugin path, not version. Disabling
  exec-gate at v0.1.0 persists when the plugin is rebuilt at v0.1.0+ (un-versioned).
- **No version-staleness signal:** there is no warning when a disabled hook's parent
  plugin has been updated since the disable decision.

## Diagnostic (when hooks don't dispatch)

If `grok inspect` shows a plugin as enabled with hooks, but the hooks don't fire:

1. **Check `~/.grok/disabled-hooks` first** — grep for the plugin name. Any entry
   suppresses dispatch silently.
2. **Check the TUI scrollback annotations** — disabled hooks produce no annotation
   (unlike errored hooks, which show the failure).
3. **Check `grok inspect --json`** — the JSON output may include a per-hook disabled
   flag that the human-readable output suppresses (unverified).

## Re-enabling

Two paths:

1. **`/hooks` tab** (documented): navigate to each disabled hook, press `Space` to
   re-enable. Tedious if multiple hooks are disabled.
2. **Edit `~/.grok/disabled-hooks` directly** (undocumented but mechanically obvious):
   remove the entries for the hooks you want to re-enable. The file is plain JSON;
   no schema validation observed. Save and reload hooks (`/hooks` → `r`).

## Incident (this session)

exec-gate plugin was built (21/21 tests pass, auto-discovered, `(user, enabled)`)
but its hooks did not dispatch. Diagnosis drifted through several wrong hypotheses:
- `${GROK_PLUGIN_ROOT}` expansion failure (wrong — the env var is always injected)
- Hook command syntax (wrong — the command was well-formed)
- Plugin-level disable (wrong — plugin showed enabled)

The actual cause: a prior session (2026-07-20) had pressed Space on all 4 exec-gate
hooks in the `/hooks` tab, disabling them. The disabled-hooks file persisted this
across session restarts and plugin rebuilds. Discovered via
`P:/.data/wiki/concepts/grok-build-disabled-hooks-per-hook-layer.md` during a `/www`
research pass — the wiki page from 2 days earlier had already documented the mechanism.
