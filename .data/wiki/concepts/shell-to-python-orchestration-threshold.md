# Shell-to-Python orchestration threshold: when to extract pipeline logic

## Decision context

The `/check` Step 0.9 grew organically from 5 lines of PowerShell (running
ruff + pyright) to 100+ lines running 9 tools with JSON parsing, conditional
execution, and merged output. The PowerShell block had:

- 7 SyntaxError incidents from quoting issues (f-string interpolation in
  inline Python, `@pyFiles` splatting, backtick line continuations)
- 0 tests (untestable — PowerShell embedded in a markdown code block)
- Non-portable (Windows-specific cmdlets)
- LLM translation overhead (agents translated PowerShell to Python anyway)

## The rule (Class C escalation tier 4)

From `~/.grok/AGENTS.md`:

> **Class C escalation tier 4 (orchestration threshold):** when shell
> orchestration logic exceeds ~10 lines, or involves parsing JSON output
> from multiple tools (`ConvertFrom-Json` + `ForEach-Object` +
> `ConvertTo-Json` chains), extract it to a Python script in `__lib/`.
> Shell is for commands; Python is for orchestration.

## The escalation ladder (complete)

| Tier | Trigger | Action | Example |
|------|---------|--------|---------|
| 1 | Inline shell payload | Run inline | `git diff --name-only` |
| 2 | Quoting fails once | One corrected retry | Fix the quote |
| 3 | Repeated/nested quoting failure | Temp `.ps1` or process invocation | `git commit -F P:/tmp/msg.txt` |
| **4** | **Orchestration >10 lines or multi-tool JSON parsing** | **Extract to Python in `__lib/`** | `run_deterministic_checks.py` |

## Why Python, not TypeScript

- The fleet is Python-native (skills, hooks, scripts, tests)
- `subprocess.run` + `shutil.which` provides clean tool-availability checks
- Python is testable via pytest (shell is not)
- Python JSON parsing is robust (`json.loads` vs PowerShell `ConvertFrom-Json` edge cases)
- Python scripts can be imported and unit-tested in isolation

## What changed in /check

Before (100+ lines of PowerShell):
```powershell
$scopeFiles = @()
if ($packet -and $packet.scope_files) { ... }
$ruff = ruff check --select E,F --output-format=json @pyFiles 2>$null
$ruffExit = $LASTEXITCODE
$pyright = pyright --outputjson @pyFiles 2>$null | ConvertFrom-Json
# ... 80 more lines ...
```

After (1 line):
```bash
python "P:/.grok/skills/check/__lib/run_deterministic_checks.py" \
    --py-files <files> --run-dir <dir> --scope-files <all> \
    --output <packet.json>
```

The Python script handles:
- `shutil.which()` for tool availability (no more `2>$null` hacks)
- Timeout handling per tool
- JSON parsing with fallbacks
- Conditional execution (pip-audit needs requirements.txt, diff-cover needs coverage.xml)
- Merged output in one packet

## Anti-patterns this rule prevents

| Anti-pattern | Example | What happens |
|--------------|---------|-------------|
| Growing PowerShell inline | Each layer added 5-10 lines | Eventually hits quoting wall |
| JSON pipeline in shell | `ConvertFrom-Json \| ForEach-Object \| ConvertTo-Json` | Fragile, untestable |
| Error suppression | `2>$null` on every tool call | Hides real failures |
| LLM translation tax | Agent translates PowerShell to Python before executing | Wastes tokens, introduces errors |

## Falsifier

This rule is wrong if:
- The Python scripts themselves become unmaintainable (the extraction didn't help)
- Python `subprocess.run` adds significant latency vs direct PowerShell (measured: negligible, <100ms overhead)
- The extraction scatters logic across files that should be co-located (mitigated by `__lib/` convention)
