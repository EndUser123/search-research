# Scheduled tasks: date-triggered content maintenance

## Decision context

Wiki content goes stale. Benchmark scores shift daily on BenchLM. Pool
contracts reference models that get updated or deprecated. Free promotions
expire. Without a tracking mechanism, these changes are discovered only when
something breaks — and by then, the stale data has already been used for
decisions.

The operator proposed: a simple list in the wiki. If a date passes, the task
fires. This concept documents the design.

## Design

### Storage

`P:/.data/wiki/scheduled-tasks.md` — a plain markdown table. No database,
no external service, no cron daemon. The wiki IS the store.

### Schema

```markdown
| Task | Due Date | Frequency | Action | Last Done | Status |
|------|----------|-----------|--------|-----------|--------|
```

- **Task:** short description
- **Due Date:** ISO date (YYYY-MM-DD) when the task should next run
- **Frequency:** one-time | weekly | monthly | quarterly
- **Action:** what to do (can be a command, a URL to fetch, a file to re-run)
- **Last Done:** ISO date of last execution (empty = never)
- **Status:** pending | done | skipped

### Checking mechanism

Any session lifecycle skill (`/todo`, `/maintain`, `/close`) or SessionStart
hook reads the table, finds rows where `Due Date <= today` and `Status = pending`,
and surfaces them to the operator. The operator decides: run now or defer.

This is NOT auto-execution. The operator approves each task. Auto-execution
of simple tasks (like fetching a URL) is a future enhancement.

### Expandability

- **Auto-execution:** future enhancement where tasks tagged `auto:yes` with
  simple actions (fetch URL, run command) execute without operator approval
- **Skill integration:** `/maintain` reads the table during its DIAGNOSE phase
- **Staleness scoring:** tasks overdue by >2x their frequency get flagged as
  STALE (e.g., a monthly task overdue by 2 months)
- **New task types:** any wiki content that has a freshness requirement gets
  a row — model pricing, model availability, benchmark scores, pool contracts,
  API documentation, security advisories

## Falsifier

This system is dead weight if:
- Nobody checks the table (skills don't surface it)
- Tasks are always deferred (no accountability)
- The table grows without pruning (noise drowns signal)
- Due dates are set too conservatively (everything is always "not due yet")

If any pattern appears within 3 months, retire or iterate.
