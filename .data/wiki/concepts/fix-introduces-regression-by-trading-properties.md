# Fix-introduces-regression by trading properties

## The pattern

A fix that resolves defect A introduces defect B by optimizing one property
while silently breaking another. The fix is **correct for what it targets**
but **wrong for what it trades away**. The trade is invisible at fix time
because the traded property was an implicit guarantee, not a stated
requirement.

## Observed instances

| Fix | Targeted property | Traded-away property | Discovered by |
|-----|-------------------|---------------------|---------------|
| C4: O_CREAT\|O_EXCL publish | Collision safety (2^-80) | Torn-read atomicity (40% partial reads) | /review specialist empirical test |
| F1: Publish-before-claim | Crash recovery (no orphan claims) | On-disk `claimed` field accuracy | /review specialist code inspection |
| S2: Separate JSON vs IO errors | Transient-error data preservation | API compatibility (3-tuple return) | /review specialist signature check |

## Why it happens

1. **Implicit guarantees are invisible.** The atomicity guarantee of
   `os.replace` was in the docstring but not in the test suite's acceptance
   criteria. The fix author optimized for the explicit requirement
   (collision safety) without checking what implicit property the old code
   provided.

2. **Fixes optimize locally.** Each fix addresses one defect. Nobody
   asks "what property does the current code provide that this fix
   might remove?" because the current code's properties aren't enumerated.

3. **Tests verify the fix, not the trade.** Test 19 (barrier race) verified
   that the claim mechanism works. It did not verify that publish remains
   atomic. The traded property had no test.

## Structural prevention

Three layers, in order of strength:

### Layer 1: Property inventory (strongest)
Before changing any load-bearing function, enumerate what properties the
current code provides. Ask: "does this fix preserve all of these?"

### Layer 2: Mid-implementation checkpoint (H4.5 in /go)
Between implement and verify, ask: "Did the fix change a documented
property without updating the docstring?" This is the gate that catches
documentation drift, which is the symptom of a property trade.

### Layer 3: Docstring-code agreement lens (/review --focus docstrings)
During review, mechanically verify that every property claim in a docstring
("atomic," "permanent," "before publishing") matches the actual code. A
docstring lie is evidence of a property trade that wasn't documented.

## How to recognize it

When reviewing a fix, ask:

> **What property does the OLD code provide that the NEW code might not?**

If you can name one, the fix may be trading it away. Verify whether the
trade is intentional and acceptable. If unintentional, the fix introduces
a regression.

## Relationship to other patterns

- [[narrative-as-signal]]: the fix author constructs a narrative for why
  the fix is correct without checking the traded property.
- [[invariants-beat-environment-comfort]]: the traded property is often
  an invariant the old code happened to satisfy, not one it was designed
  to guarantee.
- [[self-correction-reflection-loop]]: the /review specialist is the
  external signal that catches the trade. Without it, the fix author
  cannot self-correct (Huang 2024: "LLMs cannot self-correct reasoning
  yet").

## Falsifier

This pattern is wrong if, within 6 months:
- No fix in the workspace introduces a regression by trading properties
  (then the pattern is rare, not systematic)
- A structural prevention mechanism (layer 1-3) eliminates the class
  entirely (then the fix was to the process, not the code)
