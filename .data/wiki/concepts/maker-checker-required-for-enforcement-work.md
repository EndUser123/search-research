# Maker-checker required for agent-authored enforcement code

## Decision context

**Why this finding was needed:** session 019fa5a1 implemented a close-authority
state machine to prevent the model from bypassing /close gates by authoring a
manual close report. The implementation passed all 20 unit tests, replayed a
real bypass scenario correctly, and was declared "PROVEN_WITH_LIMITATIONS" by
the implementing agent. A subsequent `/review` with cross-model specialists
found **2 critical bypasses** (INTG-1, INTG-2) that defeated the exact
invariant the module was designed to enforce. The most severe (INTG-1) was
empirically reproduced: a model can forge an AAR receipt at a known filesystem
path and obtain CLOSE COMPLETE.

The question this concept answers: **why did 20 passing tests and a confident
"PROVEN" verdict fail to catch a trivially exploitable hole?** The answer is
not "the tests were poorly written" — it's structural. The agent that wrote
the enforcement code also wrote the tests and issued the verdict. All three
shared the same blind spot.

## The three-role conflict

When an LLM agent authors enforcement code, it simultaneously occupies:

1. **Implementer** — writes the gate, the validator, the authority boundary
2. **Tester** — writes the unit tests that probe the implementation
3. **Threat actor** — the entity whose bypass the enforcement code is meant to stop

In security engineering, roles 1+2 vs role 3 are always separated (red teams
exist because you cannot test your own security). The LLM-agent substrate
collapses all three into one entity with one set of weights, one set of blind
spots, and one closure-pressure vector.

**The mechanism:** the agent's implementation reasoning follows a path: "the
receipt is discovered at path X, validated by checking fields A, B, C." The
agent's test reasoning follows the same path: "test that a receipt at path X
with fields A, B, C passes validation." The test confirms the implementation
because both were generated by the same pattern-completion pathway. The
missing check — "but who WROTE the receipt at path X?" — is invisible to both
because the blind spot is in the weights, not in the attention.

This is why INTG-1 survived 20 tests: every test the agent wrote checked
whether `validate_aar_receipt()` correctly accepts/rejects receipts with
various field combinations. No test checked whether the receipt's PRODUCER
could be the same agent whose bypass the receipt is supposed to prevent. The
agent literally cannot think of itself as the attacker — the closure-pressure
pathway that says "this enforcement is done" also says "I am not the threat."

## Why this is distinct from the general self-verification ceiling

[[scope-matching-verification-discipline]] documents that self-verification has
a structural ceiling: a single agent shares its own training-data blind spots,
so it cannot reliably catch its own errors. That finding is correct and general.

[[scope-matching-verification-discipline]] documents that self-verification has
a structural ceiling. This concept **refines** it for a specific, sharper case:

| Property | Regular code | Enforcement code |
|---|---|---|
| Error class | Implementation bugs | Adversarially exploitable holes |
| Who benefits from the hole | Nobody (it's just a bug) | The threat actor (same agent) |
| Blind spot correlation | Accidental (shared training data) | **Structural** (the agent's closure-pressure pathway is the attack vector) |
| Self-verification catch rate | ~80% (catches non-correlated errors) | ~0% for the specific hole class that matters |
| Fix | External review helps but isn't critical | External review is the **only** reliable defense |

The distinction matters because it changes the cost-benefit: for regular code,
the overhead of mandatory external review may not justify the marginal catch
rate. For enforcement code, there is no other defense — the holes that matter
are precisely the ones self-verification structurally cannot find.

## Empirical evidence

### INTG-1: forgeable AAR receipts (empirically confirmed, confidence 1.0)

**Location:** `close_authority.py:583-637` (`_find_and_load_aar_receipt`) +
`close_accounting.py:2702-2733` (`_find_and_load_aar_receipt` caller).

The receipt discovery function finds `_run.json` purely by filesystem location.
`validate_aar_receipt()` checks only fields the writer controls: schema
version, session_id, status, mode, timestamp, report digest. There is no HMAC,
no signature, no producer identity. The "AAR runs as a separate skill"
assumption is conventional, not enforced.

**Reproduction:** forged a `_run.json` + report for a `needs_attention` session.
`_enforce_close_authority()` returned `CLOSE COMPLETE` with the gate resolved.
Source: FINDINGS.md INTG-1, empirically confirmed during the review run.

### INTG-2: validator ignores gate content (verified, confidence 0.95)

**Location:** `close_authority.py:283-302` (`validate_close_receipt`).

`validate_close_receipt()` accepts a CLOSE COMPLETE receipt with
`resolved_gate_states={'retrospective':'needs_attention'}` — it returns
`(True, "")`. The gate-content check lives only in `authorize_completion()`,
not on the reload path. A fabricated receipt passes validation.

Both findings share the same root: the agent wrote the validator to check the
fields it thought were important, wrote the tests to confirm those fields were
checked, and declared the system proven — all without noticing that the most
important property (producer provenance / gate-content integrity) was never
validated.

### The verdict that covered it

The implementing agent declared the module "PROVEN_WITH_LIMITATIONS" after all
20 tests passed. The limitations cited were scope boundaries (not wired into
production yet), not security holes. The actual security holes (INTG-1, INTG-2)
were found only by external `/review` with cross-model specialists. The
self-issued verdict was structurally incapable of finding them.

## What this means for our workspace

### The shipped rule (AGENTS.md self-verification prohibition)

Session 019fa5a1 shipped an AGENTS.md rule (commits dd4b2c4 + 71304e3) at the
"Self-verification prohibition" section. The rule states: for enforcement or
security work with reversibility ≤1.5, the agent must not issue a PROVEN verdict
without independent verification (external review, cross-model check, or operator
approval). The reversibility threshold scopes the rule to avoid latency on
low-risk work while covering the class where self-verification structurally fails.

**Escape hatch:** the rule has an explicit escape for reversibility ≤1.25 (trivial
config edits, local changes) where self-verification is sufficient because the
blast radius of a missed hole is contained.

### Implication for skill design

Skills that produce enforcement code (gates, validators, authority boundaries)
should include a mandatory independent-review step in their workflow. The
`/review` skill is the standing instrument for this. Skills should not allow
the implementing agent to issue the final verdict on its own enforcement work.

The close-authority branch (close-authority-019fa5a1 @ d516ccc) is the reference
case: DO NOT MERGE until INTG-1 and INTG-2 are fixed AND independently verified.
The branch remains open with these findings documented at
`P:/.artifacts/console_f8a6c949-f70c-4451-9f31-6295/grok-review/close-authority/20260727-172151/FINDINGS.md`.

### Implication for the /challenge skill proposal

The `/challenge` skill proposal (handoff `challenge-skill-design-20260727`)
identifies trigger points for assumption-audit techniques. The maker-checker
finding adds a trigger point the proposal doesn't yet include: **before
declaring enforcement code "PROVEN"**, fire an independent-verification gate.
This is the claim-schema analog of `/wargame`'s move-schema for hard-to-reverse
plans, and complements the [[assumption-auditing-and-unknown-unknown-discovery]]
research that motivated the /challenge design.

## Steelman: why self-verification seems sufficient

The rejected alternative: "the agent has the most context about its own code,
so self-verification is both faster and higher-quality than external review."

This is true for **regular code**. The agent knows why it made each design
choice, what edge cases it considered, and where the complexity lives. An
external reviewer has to reconstruct this context. For implementation bugs
(non-adversarial), self-verification leverages this context advantage and
catches most errors.

The steelman fails for **enforcement code** because the context advantage is
also the blind-spot advantage. The agent's deep knowledge of its own design
choices is exactly what makes it unable to see the hole — the hole exists
because a design choice was made that the agent's reasoning pathway treats as
an axiom rather than a hypothesis. "The receipt is discovered by location" is
an axiom in the implementer's mind; the external reviewer treats it as a
hypothesis ("what if the location is written by the attacker?") and finds the
hole in seconds.

## Falsifier

This finding would be wrong if:

1. **A technique emerges** that makes the agent reliably audit its own
   enforcement code for adversarial holes — e.g., a structured "attack your own
   gate" prompt protocol with empirically demonstrated catch rate ≥90% on the
   hole class that matters. The information-theoretic argument from
   [[scope-matching-verification-discipline]] (Brilliant 2026) suggests this is
   unlikely because the attacker and defender share weights, but it's not
   provably impossible. This connects to the closure-pressure pattern in
   [[reactive-pattern-matching-and-closure-pressure]]: the pathway that produces
   the enforcement hole is the same pathway that would need to fire the self-audit.

2. **Empirical evidence shows** that agent-authored tests catch enforcement
   holes at the same rate as external review across many instances. The
   close-authority case is N=1; if future enforcement implementations show
   self-verification catching what external review finds, the rule's scope
   should narrow.

3. **The rule's reversibility threshold (≤1.5) is wrong** — if it fires too
   broadly (adding latency to non-enforcement work without catching holes) or
   too narrowly (missing enforcement work that doesn't meet the threshold).
   Monitor: track what work the rule gates and whether the gated work has
   exploitable holes that self-verification missed.
