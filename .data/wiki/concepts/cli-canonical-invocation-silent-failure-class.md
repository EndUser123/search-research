## Summary

CLIs often have a "canonical" invocation that the help text suggests is correct, but which silently produces wrong results because of host state (config file defaults, OS process spawning rules, flag interactions that only surface at runtime). This is a class of problem, not a one-off. The remedy is runtime smoke-tests, not just static flag review.

## Instances observed this session

### 1. `codex review --uncommitted` — sandbox inheritance (critical)

**Documented behavior:** "Review staged, unstaged, and untracked changes."

**Actual behavior on this host:** `codex review` does NOT accept `-s/--sandbox`. It reads `sandbox_mode` from `~/.codex/config.toml`, which on this host is `danger-full-access`. So every "read-only review" silently runs with full filesystem and network access.

**Fix:** use `codex exec review --uncommitted -c sandbox_mode=read-only -c approval_policy=on-request` instead. The `exec review` subcommand accepts `-c` overrides; the bare `review` shortcut does not.

**Class signature:** the "safe" subcommand variant (`review`) doesn't accept the safety override flag; only the "power-user" variant (`exec review`) does.

### 2. `mmx text chat --message "..." --output json --quiet` — flag interaction (major)

**Documented behavior:** `--output json` returns JSON; `--quiet` suppresses non-essential output.

**Actual behavior:** `--quiet` paired with `--output json` returns **plain text**, not JSON. The `--quiet` flag suppresses the JSON wrapper. The conductor cannot parse what `--quiet` strips.

**Fix:** do NOT combine `--output json` with `--quiet`. Use `--output json` alone.

**Class signature:** two flags that each work correctly in isolation produce a wrong result when combined, and the help text doesn't document the interaction.

### 3. Bare `mmx` on Windows — `.cmd` shim + `CreateProcess` (major)

**Documented behavior:** `mmx` is on PATH; `mmx text chat --message "hello"` should work.

**Actual behavior on Windows:** bare `mmx` resolves to a `.cmd` shim that `CreateProcess` cannot execute directly. The invocation silently fails or hangs when spawned by a process that doesn't shell out through `cmd.exe`.

**Fix:** probe for `node "$env:APPDATA\npm\node_modules\mmx-cli\dist\mmx.mjs"` and use `@("node", $nodeScript)` as the command prefix.

**Class signature:** npm-installed CLIs on Windows have a `.cmd` shim that works in interactive shells but fails when spawned by `CreateProcess`. This affects any npm-installed CLI, not just mmx.

## The pattern

All three share a structure:

1. The CLI's help text suggests invocation X.
2. Invocation X looks correct in code review.
3. Invocation X silently produces wrong results at runtime.
4. The fix is a non-obvious variant (different subcommand, different flag combination, different command prefix).

Static review (reading help text, checking flag names) cannot catch these. Only **runtime smoke-tests** against the actual host environment surface them.

## Detection strategy

- **Smoke-test every canonical invocation** before declaring a skill "done." This session's PR 3 smoke-test caught the `--quiet` and `.cmd` shim bugs that 4 review rounds missed.
- **Probe host config state** (config files, PATH, OS-specific behavior) before documenting canonical invocations.
- **Document the failure mode** alongside the fix, not just the fix. Future readers need to know what goes wrong if they use the "obvious" invocation.
