# Skill catalog scope inconsistency causes cascading read failures

## Decision context

**Why this matters:** The session skill catalog (system-reminder block) is the
primary mechanism agents use to locate skill files. When it reports a wrong
scope, every parallel read in a batch fails, and the agent must fall back to
filesystem search — which is slower, misses gitignored directories, and can
produce false negatives. The catalog is supposed to be the authoritative path
source; when it's wrong, the agent's trust in the catalog is undermined for
all skills, not just the two affected ones.

**The problem observed:** The catalog listed `review` and `refactor` at
workspace scope (`P:\.grok\skills\review\SKILL.md` and
`P:\.grok\skills\refactor\SKILL.md`). Both files don't exist at those paths.
They actually live at user scope (`~\.grok\skills\review\SKILL.md` and
`~\.grok\skills\refactor\SKILL.md`). When the agent read all six primary
skills in a parallel batch trusting catalog paths, two of six reads failed.

**The root cause is unclear:** Either the override was removed at some point
and the catalog + AGENTS.md reference went stale, or it was never created.
Either way, the catalog asserts a path that doesn't resolve.

## Key findings

1. **Two skills affected:** `review` and `refactor` are the only skills in the
   catalog with scope mismatches. All other skills in the catalog have
   correct scope paths.

2. **AGENTS.md has a stale reference:** The line "(repo override
   `P:/.grok/skills/review`)" describes an override that doesn't exist. This
   is a secondary propagation point — anyone reading AGENTS.md for the
   review skill's location gets the wrong path.

3. **The failure mode is insidious:** A single failed read in a parallel
   batch doesn't immediately signal a scope problem — the agent sees a file
  -not-found error and must then search. The batch succeeds for the other 4
   skills, so the agent doesn't realize the catalog itself is wrong until
   it hits the failures.

4. **The fix applied:** 9 stale path references across 5 files were corrected
   to point to user scope (`~/.grok/skills/`). Files changed:
   - `~/.grok/AGENTS.md` — removed "(repo override `P:/.grok/skills/review`)"
   - `~/.grok/skills/refactor/SKILL.md` — canonical self-reference → user scope
   - `~/.grok/skills/review/SKILL.md` — Rule 7 reference → user scope
   - `P:\packages\yt-is\docs\operations\critical-review-2026-07-17.md` — 2 refs
   - `P:\packages\yt-is\docs\operations\refactor-skill-handoff.md` — 4 refs

## What this means for our workspace

- The skill catalog ([[skill-catalog]]) needs a
  scope-validation pass — at minimum, spot-check that every listed path
  resolves. The catalog is auto-generated by `index_skills.py`, so the bug
  may be in the generation logic or in a stale cache.
- The `AGENTS.md` reference to a workspace override for `review` should be
  removed or corrected. If the override was intentionally removed, the
  catalog and AGENTS.md should reflect that.
- Agents should treat catalog paths as `[INFERENCE]` until verified by a
  file-existence check, especially when batching reads. Probing one path
  before fanning out would have caught this immediately.
- This is a generalizable pattern: any auto-generated index that maps names
  to paths is a single point of failure when the mapping drifts from reality.

## Falsifier

- If `index_skills.py` is re-run and the catalog now correctly lists user
  scope for all skills, the root cause was a stale catalog generation bug
  that has since been fixed. In that case, this concept documents a
  transient issue, not a systemic one.
- If the workspace override for `review` is intentionally recreated at
  `P:\.grok\skills\review\SKILL.md`, the catalog scope becomes correct and
  the AGENTS.md reference is valid again.
