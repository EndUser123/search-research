**CORRECTION**: An earlier version of this page (and [[grok-hook-diagnostic-method]])
claimed that user-level command hooks with `.*` matcher didn't dispatch in Grok 0.2.103.
This was based on misreading empty log files as evidence of non-dispatch. The TUI
scrollback annotations showed the hooks DID dispatch — they failed for two specific,
fixable reasons. The matcher and dispatch mechanism both work.

## What Actually Failed (TUI evidence)

After `/hooks → r` reload and a `read_file` probe, the TUI showed:

```
pre_tool_use
  ✗ global/canary-a-pretooluse-fires:pre_tool_use[0].hooks[0] (0ms)
      command not found: C:/Users/brsth/.grok/hooks/canary-scratch/canary-a.sh
  ✗ global/canary-b-deny-honored:pre_tool_use[0].hooks[0] (0ms)
      command not found: C:/Users/brsth/.grok/hooks/canary-scratch/canary-b.sh
  ✗ global/canary-c-pwsh-invocation:pre_tool_use[0].hooks[0] (0ms)
      hook not executed: required env var(s) not set: ${d}, ${env}
```

## Two Distinct Failure Modes

### Failure 1: Stale command path (canaries A and B)

- **Symptom**: `command not found: .../canary-scratch/canary-a.sh`
- **Cause**: The hook JSONs on disk had been updated to point at `P:/tmp/canary/` during
  a cleanup, but Grok was still dispatching the OLD command string from before the reload.
- **What it means**: `/hooks → r` reload may not refresh command-string contents for
  already-loaded hooks, only the discovery list. EVIDENCE_GAP: untested whether a full
  session restart picks up new command strings reliably.
- **Lesson**: when modifying a hook's command field, you may need to restart the session,
  not just press `r`.

### Failure 2: Env-var pre-flight validation (canary C)

- **Symptom**: `hook not executed: required env var(s) not set: ${d}, ${env}`
- **Cause**: Canary C used an inline `pwsh -Command "..."` with PowerShell variable
  syntax like `${d}` and `$env:USERPROFILE`. Grok's hook runner pre-validates `${VAR}`
  references in the command field and refuses to execute if the referenced env var isn't
  set in Grok's own environment at spawn time.
- **What it means**: `${VAR}` in the `command` field is env-var expansion performed by
  Grok BEFORE spawning the hook process, not by the shell that runs the command. Strings
  that look like `${...}` but aren't real env vars cause a hard pre-flight failure.
- **Lesson**: see [[grok-hook-command-env-var-preflight]].

## What This Corrects

Prior claims now retracted:

- ❌ "User-level command hooks don't dispatch in 0.2.103" → they do dispatch
- ❌ "`.*` matcher may not dispatch" → it does dispatch (both failures were A/B which use `.*`)
- ❌ "Read-only tools skip PreToolUse" → **UNVERIFIED**. The canaries failed for
  path/env-var reasons, not tool-class reasons. This hypothesis was based on the
  empty-log misread and has no supporting evidence.

## What Remains Open

- Does PreToolUse fire for read-only tools (`read_file`, `list_dir`, `grep`)? The docs
  say hooks can intercept them, but the canary didn't reach the point of testing this
  because of the path/env failures. Needs a clean re-test.
- Does `/hooks → r` refresh command-string contents, or only the discovery list?
- The TUI annotations are the authoritative dispatch signal; `unified.jsonl` does not
  record hook dispatches at info level. Searching logs for hook evidence is unreliable.
