Original comment in English - Translate to English
Sorry for the delay, been a hectic winter.
You're right, the interchange format could be better defined. To boot, some of the json structure contains tree state, some of it contains visualisation details (e.g. colour). I should have separated those concerns. The open source examples of how it is done right now are in the ros repos:
py_trees_ros_interfaces/BehaviourTree.msg
https://github.com/splintered-reality/py_trees_ros_interfaces/blob/devel/msg/BehaviourTree.msg
 - the tree serialisation, though this is purely for introspection purposes.
NB: Without introducing a really hard constraint mandating behaviours exposing their internal states, it's not possible to have a tree serialisation that can be used for execution. That format also minimises the bandwidth - it only transmits the blackboard delta, since blackboards can get really heavy.
Populating BehaviourTree.msg
https://github.com/splintered-reality/py_trees_ros/blob/devel/py_trees_ros/trees.py#L173
 in-between tree ticks.
Converting BehaviourTree.msg -> JSON
https://github.com/splintered-reality/py_trees_ros_viewer/blob/devel/py_trees_ros_viewer/backend.py#L333
 - relaying the information to the web app
I'll go ahead and create some issues - it would be nice to re-architect some of these interfaces to be more 'standard' and producable from the core py_trees library itself.
