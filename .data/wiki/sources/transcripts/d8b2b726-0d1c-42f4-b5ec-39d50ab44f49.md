How to Set Up and Use Claude Code Agent Teams (And Actually Get Great Results)

Dára Sobaloju

10 min read · Feb 7, 2026

--

If you’ve been using Claude Code for a while, you’ve probably hit the moment where one AI session just isn’t enough. Maybe you’re staring at a codebase that needs a security audit, performance review, and test coverage analysis all at once. Or you’ve got a feature that touches the frontend, backend, and database layer, and you’re tired of context-switching a single session between all three.

 solve this. Instead of one Claude instance doing everything sequentially, you spin up multiple instances that work together in parallel. Each gets its own context window and its own piece of the puzzle. One session acts as the team lead, coordinating the work, while teammates execute independently and can even talk to each other.

The jump from single-session Claude Code to a coordinated team feels like the jump from single-threaded to multi-threaded programming. There’s a learning curve, but once it clicks, you won’t want to go back for anything non-trivial.

This guide covers setup, architecture, practical usage, and the stuff I wish someone had told me before I started.

What You Need Before Starting

Before you dive in, make sure you have:

Claude Code installed and working. If you’re reading this, you probably already have it. If not, grab it from the 

Claude Code repo on GitHub

https://github.com/anthropics/claude-code

.

A terminal multiplexer (for split-pane mode). You’ll want 

tmux

https://github.com/tmux/tmux

 so each teammate gets its own visible pane. More on this below.

An Anthropic API key or a Max subscription. Agent teams use more tokens than a single session because each teammate has its own context window. Keep an eye on 

costs

https://code.claude.com/docs/en/costs

. For research, reviews, and complex features, the extra tokens are usually worthwhile. For routine single-file edits, stick with a single session.

A task that actually benefits from parallelism. Don’t use a team to rename a variable. Use it when you have genuinely independent workstreams.

Enabling Agent Teams

Agent teams are behind an experimental flag, so you need to opt in. Open your 

settings

https://code.claude.com/docs/en/settings

 file (usually  ~/.claude/settings.json ) and add:

{ 
  "env": { 
  "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1" 
  } 
 }

Once this is set, Claude Code gains access to the team coordination tools: creating teammates, assigning tasks, sending messages, and managing the shared task list.

Installing tmux for Split-Pane Mode

You can run agent teams entirely in-process (all teammates share one terminal window), but split-pane mode is worth setting up. Seeing each teammate working in its own pane makes it much easier to monitor progress and catch issues early.

On macOS:

brew install tmux

On Linux (Debian/Ubuntu):

sudo apt install tmux

For other Linux distributions, check the 

tmux installation guide

https://github.com/tmux/tmux/wiki/Installing

.

iTerm2 alternative: If you’re on macOS and prefer iTerm2 over tmux, install the 

it2 CLI tool

https://github.com/mkusaka/it2

 and enable the Python API in iTerm2’s settings. This lets Claude Code create native iTerm2 split panes instead.

One gotcha: split-pane mode doesn’t work with VS Code’s integrated terminal, Windows Terminal, or Ghostty. You need a standalone terminal with tmux or iTerm2.

Once tmux is installed, start a tmux session before launching Claude Code:

tmux new -s my-project 
 claude

Understanding the Architecture

Before you start spawning teammates, it helps to understand how the pieces fit together.

Team Lead: Your main Claude Code session. It creates the team, defines tasks, spawns teammates, and synthesizes results. Think of it as a tech lead who delegates work and reviews output.

Teammates: Each teammate is a separate Claude Code instance with its own context window. They can read and write files, run commands, and communicate with other teammates and the lead. Unlike 

sub-agents

https://code.claude.com/docs/en/sub-agents

 (which only report back to the caller), teammates can message each other directly.

Shared Task List: The team shares a task list with dependency tracking. Tasks can block other tasks, and when a blocking task completes, downstream tasks automatically unblock. Teammates self-claim the next available unblocked task when they finish their current one. File-lock based claiming under the hood prevents race conditions.

Mailbox: An inter-agent messaging system. The lead can message any teammate, teammates can message the lead, and teammates can message each other. This is what makes agent teams fundamentally different from sub-agents.

Config lives at  ~/.claude/teams/{team-name}/config.json  and tasks are stored at  ~/.claude/tasks/{team-name}/ .

Your First Agent Team

The easiest way to get started is to give Claude Code a task that naturally decomposes into parallel work. Here’s a practical example:

Review this codebase for issues. Have one teammate focus on security 
 vulnerabilities, another on performance bottlenecks, and a third on 
 test coverage gaps. Coordinate the findings into a single report.

Claude Code (as the team lead) will:

Create a team with three teammates

Assign each teammate a focused review task

Spawn the teammates, each with context about what to look for

Collect and synthesize the results

You can also be more explicit about team structure if you prefer:

Create an agent team with two teammates. Teammate "backend" should 
 implement the new /api/users endpoint in src/routes/. Teammate 
 "frontend" should build the user profile component in src/components/. 
 They should coordinate on the API contract.

One thing to remember: teammates don’t inherit the lead’s conversation history. Whatever context they need, the lead has to provide in the spawn prompt. My first teammate spawned with zero context about the project and started asking basic questions. Be generous with the initial briefing.

Display Modes: Picking the Right View

Agent teams support three display modes. Picking the right one matters more than you’d expect.

In-process (default in non-tmux terminals): All teammates run inside your single terminal. Use Shift+Up and Shift+Down to switch between teammate views. Works everywhere but can feel cramped since you’re essentially tabbing between sessions.

Split panes: Each teammate gets its own tmux or iTerm2 pane. You can see all of them working simultaneously. This is the way to go for anything with more than two teammates, because you can spot problems as they happen instead of after the fact.

Auto (the default setting): Claude Code detects your environment. If you’re already in a tmux session, it uses split panes. Otherwise, it falls back to in-process.

You can set your preference in settings:

{ 
  "teammateMode": "tmux" 
 }

Or pass it as a flag:

claude --teammate-mode tmux

Key Controls and Features

Once your team is running, a few features make coordination much smoother.

Delegate Mode (Shift+Tab)

Easily the most underappreciated feature. When you toggle delegate mode, the team lead is restricted to coordination only. It can’t write code, run tests, or do implementation work. It can only manage tasks, communicate with teammates, and review their output.

Why bother? Without delegate mode, the lead often tries to do everything itself instead of delegating. If your lead is writing code when it should be coordinating three teammates, flip on delegate mode.

Plan Approval

You can require teammates to submit a plan before they start implementing. The lead reviews the plan and either approves it or sends it back with feedback. It adds communication overhead, but for complex tasks where a wrong approach would waste significant work, it’s a good safety net.

Direct Messaging

Unlike sub-agents (which can only report results back to their caller), teammates can message each other. Your frontend teammate can ask the backend teammate about the API response format directly, without routing everything through the lead.

Task Dependencies

Tasks can declare dependencies on other tasks. A “write integration tests” task can be blocked by “implement the API endpoint” and “build the UI component.” When both blockers complete, the testing task automatically unblocks and the next available teammate picks it up. Complex workflows without micromanaging.

Agent Teams vs Sub-agents: When to Use Which

The answer is simpler than you’d think.

Sub-agents

https://code.claude.com/docs/en/sub-agents

 are for focused tasks where only the result matters. Need to search a codebase for all usages of a deprecated function? Sub-agent. Need to summarize a long file? Sub-agent. The main session spawns it, it does its work, returns the result, done. Lower token cost, simpler coordination.

Agent teams are for work that requires discussion, coordination, or independent decision-making across multiple workstreams. Code review from multiple angles, building features that span layers, debugging with competing hypotheses: these all benefit from teammates that can communicate and self-coordinate.

A good rule of thumb: if you’d handle it with a function call in regular code, use a sub-agent. If you’d need a team meeting in real life, use agent teams.

Real-World Examples

Parallel Code Review

The lowest-friction way to start with agent teams. Spin up three teammates, each reviewing the same PR from a different angle:

Security reviewer: Looks for injection vulnerabilities, auth issues, data exposure

Performance reviewer: Checks for N+1 queries, unnecessary allocations, missing indexes

Test reviewer: Evaluates coverage gaps, edge cases, test quality

The lead synthesizes findings into a single review. What would take one session three sequential passes happens in parallel.

Competing Hypothesis Debugging

Got a bug that could be caused by three different things? Spawn three teammates, each investigating a different hypothesis. They share findings with each other as they go, and often one teammate’s discovery helps another narrow down (or rule out) their theory. Parallel debugging. Surprisingly effective.

The C Compiler Story

Anthropic published a case study about 

building a C compiler with parallel Claude instances

https://www.anthropic.com/engineering/building-c-compiler

. Sixteen Claude agents worked together across nearly 2,000 sessions, consuming around 2 billion input tokens at a cost under $20,000. The result was a compiler that could build a bootable Linux 6.9 kernel on x86, ARM, and RISC-V architectures. They used git-based file locking for coordination, which gives you a sense of the scale these teams can operate at.

Best Practices That Actually Matter

After running agent teams on several projects, here’s what actually moves the needle.

Give teammates rich context in their spawn prompts. They start with a blank conversation. Tell them what the project is, what files matter, what conventions to follow, and what their specific goal is. Skimping on context is the number one reason teammates produce mediocre work.

Size tasks appropriately. Aim for roughly 5 to 6 tasks per teammate. Too granular and you drown in coordination overhead. Too broad and you lose the benefits of parallelism.

Avoid file conflicts. Assign different files to different teammates whenever possible. Two teammates editing the same file simultaneously is a recipe for merge conflicts and wasted work.

Start with research before implementation. Have teammates explore and plan before they write code. This catches architectural mismatches early, before anyone has invested significant work.

Use delegate mode when the lead keeps coding. If you notice the lead doing implementation work instead of coordinating, toggle delegate mode with Shift+Tab.

Pre-approve common operations. Agent teams generate a lot of 

permission prompts

https://code.claude.com/docs/en/permissions

 because each teammate needs approval for file writes, command execution, and so on. Check your permission settings and pre-approve operations you’re comfortable with. This dramatically cuts the number of times you have to click “allow.” Anthropic has guidance on 

enabling more autonomous operation

https://www.anthropic.com/news/enabling-claude-code-to-work-more-autonomously

 that covers this well.

Monitor actively. Split-pane mode isn’t just nice to have. It’s how you catch teammates going off-track before they waste tokens. Steer early and often.

Troubleshooting Common Issues

Teammates not appearing: Press Shift+Down to cycle through teammates in in-process mode. If nothing shows up, verify the task is complex enough to warrant a team. Claude Code might decide a single session is sufficient. Also confirm tmux is installed if you’re expecting split panes.

Too many permission prompts: The most common friction point. Pre-approve common operations in your 

permission settings

https://code.claude.com/docs/en/permissions

. You can also look into 

sandboxing options

https://www.anthropic.com/engineering/claude-code-sandboxing

 for more controlled environments.

Teammates stopping on errors: If a teammate hits an error and stalls, send it additional instructions through the messaging system, or spawn a replacement teammate to pick up where it left off.

Lead shutting down too early: Sometimes the lead wraps up before all teammates finish. Tell the lead explicitly to wait for all teammates to complete before synthesizing results.

Orphaned tmux sessions: If something goes wrong and you end up with leftover tmux sessions, clean them up:

tmux ls 
 tmux kill-session -t <session-name>

Known Limitations

Better to know these upfront than discover them mid-project.

No session resumption for in-process teammates. If the lead session dies, in-process teammates are gone. Split-pane teammates in tmux may survive, but coordination state is lost.

Task status can lag. The shared task list updates aren’t instant. Occasionally a teammate will claim a task that another just finished.

Shutdown can be slow. Cleaning up multiple teammate sessions takes time. Be patient.

One team per session. You can’t run multiple teams from the same lead session.

No nested teams. A teammate can’t spawn its own sub-team.

Leadership is fixed. You can’t transfer the lead role mid-session.

Permissions are set at spawn. All teammates inherit the same permission configuration. You can’t give one teammate more access than another.

Split panes need tmux or iTerm2. No VS Code terminal, Windows Terminal, or Ghostty support yet.

Real constraints, but for the 

common workflows

https://code.claude.com/docs/en/common-workflows

 agent teams are designed for (parallel reviews, multi-layer features, exploration), none of them are dealbreakers.

Final Thoughts

Agent teams are a genuine shift in how AI-assisted development works. Going from “one Claude doing things sequentially” to “multiple Claudes coordinating in parallel” isn’t just faster. Each teammate can go deep on its area without losing context to task-switching, and the results reflect that.

This isn’t magic, though. You still need to be a good tech lead. Define clear tasks, provide rich context, monitor progress, and steer when things drift. The teams that produce the best output are the ones with the most thoughtful human direction.

If you’re running 

Claude Opus 4.6

https://www.anthropic.com/news/claude-opus-4-6

 (the latest model at the time of writing), agent teams feel especially capable. The improved reasoning and instruction-following make coordination smoother and reduce the “teammates going rogue” problem significantly.

Start small. Try a three-teammate code review on your next PR. See how it feels. Then scale up to parallel implementation when you’re comfortable with the coordination patterns. The setup cost is minimal (one settings flag and a tmux install), and the ceiling is high.

Happy building.
