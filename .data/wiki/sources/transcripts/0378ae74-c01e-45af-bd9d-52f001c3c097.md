On a Mac Silicon, a single 

llama-server

 process will outserve most multi-process setups built around it, if its three concurrency knobs are set right.

The three command-line flags are wired together more tightly than their names suggest: 

--parallel

, 

--batch-size

, and 

--ubatch-size

.

Misuse them, and you get out-of-memory errors, evictions, or throughput that flatlines at half the hardware's capability.

Used well, you can serve many concurrent agent requests from one Mac Studio without the operational overhead of a process pool.

This article walks through the parameter semantics, the KV-cache math behind them (including the part of that math that the current generation of hybrid models breaks), the prefix-caching trick that most agent operators leave on the table, and a benchmark methodology you can run on your own hardware.

The benchmark rig in this piece is my Mac Studio M4 Max with 64 GB of unified memory. Sixty-four gigabytes is a useful budget because it is tight enough that the model-size choice still matters, even after the per-token KV pressure of hybrid models has dropped substantially.

The article runs the same parameter sweep against two models, Qwen3.6–27B Q4_K_M and Qwen3.5–9B Q4_K_M, to show how the same knobs behave when weights take a meaningful share of the budget versus when they leave wide headroom.

The disambiguation in the next two sections applies on Linux and CUDA hosts as well. Only the unified-memory budget arithmetic in section two is Mac-specific.

A Note on llama.cpp Support for Hybrid Models

Before the parameter walk-through, one operational caveat. As of May 2026, 

llama.cpp

 support for the Qwen3.5 and Qwen3.6 hybrid lineup is on bleeding-edge HEAD builds, not in stable releases. The hybrid graph (DeltaNet layers interleaved with Gated Attention) is being actively iterated. Recent issues filed against Qwen3.6 builds give the flavor: a thinking-tag parsing regression on the 27B in build 8940 (issue #22398), a tensor-split crash on the 35B variant when launched with 

-sm tensor

 (issue #22058), and a steady stream of smaller graph-code fixes in between. None of that is fatal, but together it makes the case for pinning a known-good commit hash for benchmarking, documenting it in your run notes, and re-testing before bumping. Production is not the place to chase the head of master on a model family whose graph code is two weeks old.

The Three Parameters That Get Confused

llama-server

 has roughly a hundred command-line flags. Three of them control concurrency behavior, and they are not interchangeable.

--parallel

 is the slot count. Each slot is a logical seat in the server, with one request at a time, its own KV-cache region, its own decoding state, and its own conversation history if you use slot persistence. When 

--parallel

 is omitted, llama-server resolves slot count from context size and model defaults; in practice that auto value is rarely what production deployments want, and an explicit number is the right operational choice.

--batch-size

 is the maximum number of prompt tokens the server pulls into one logical forward pass. It governs prefill, the phase where a long prompt is consumed before generation starts. With a 4,000-token prompt and 

--batch-size 2048

, prefill happens in two logical batches.

--ubatch-size

 is the physical batch the GPU actually sees. The logical batch is sliced into micro-batches of 

ubatch-size

 tokens, and each micro-batch is one Metal kernel dispatch. On Apple Silicon this is frequently the parameter that moves prefill throughput, because a larger micro-batch amortizes kernel launch overhead and uses the matmul units more efficiently. The constraint is that 

ubatch-size

 must divide 

batch-size

.

A grouped-query-attention (GQA) note for readers new to the term: modern attention layers share one key-value head across multiple query heads, which is why 

n_kv_heads

 in the math below is much smaller than the total attention-head count. This shrinks the KV-cache footprint substantially. Qwen3.6-27B and Qwen3.5-9B both use Gated Attention with 4 KV heads on their attention layers, dramatically narrower than their 24 and 16 query heads respectively.

What the slot count buys you is the ability to interleave many requests through continuous batching. Decode steps for different requests are merged into the same forward pass, which is where the throughput gain comes from. A single request does not benefit from a high slot count. You only see the win when concurrent traffic actually exists. Increasing 

--parallel

 without giving prefill more tokens-per-pass via 

--batch-size

 and 

--ubatch-size

 just spreads the same throughput across more queues; latency goes up, aggregate tokens per second does not.

KV-Cache Math and Slot Budgeting

--ctx-size

 is a memory budget, not a per-request guarantee. How that budget is divided depends on slot count and the 

--kv-unified

 setting, and the two cases produce very different failure modes.

Case 1: explicit slot count, static partitioning.

 With 

--parallel N

 set explicitly and 

--no-kv-unified

 (or older builds before unified KV became default), 

--ctx-size M

 allocates 

M / N

 tokens per slot. So 

--ctx-size 32768 --parallel 8

 gives each request 4,096 tokens of effective context. If your agent's system prompt is 8,000 tokens, every request truncates or fails. This is the historical default, and the failure mode behind a particular kind of support ticket: the system that ran fine yesterday and started rejecting requests today, after someone bumped the context size or rolled out a longer system prompt.

Case 2: auto slots or

 

--kv-unified

 

on, shared pool.

 The current llama.cpp default for 

--kv-unified

 is "enabled if number of slots is auto." A single shared KV buffer covers the full 

ctx-size

, allocated to requests as they arrive. Heterogeneous request lengths are tolerated more gracefully, because a short request next to a long one borrows from the pool rather than waste an isolated slot allocation. The total budget is still 

ctx-size

; it is just not pre-sliced.

For production, the recommendation is to set 

--parallel

 explicitly so capacity planning stays predictable, and then make a deliberate choice between the static partition (predictable per-slot ceiling) and 

--kv-unified

 (more flexible under heterogeneous load). The internal contradiction in many tutorials, including older versions of this thesis, comes from describing one mode as if it were universal.

The Classical Formula

The KV cache itself is what fills that budget. For each token, the cache stores key and value tensors for every attention layer. The classical approximation:

KV bytes per token ≈ 2 × n_layers × n_kv_heads × head_dim × bytes_per_element


The factor of two is for K and V. 

n_kv_heads

 is the GQA head count, smaller than the attention-head count on modern models. 

bytes_per_element

 is 2 for FP16, 1 for Q8_0, 0.5 for Q4_0.

This formula is correct for dense Transformer architectures, including the Qwen3 generation that preceded the current lineup. For reference, classical Qwen3–32B (64 layers, 8 KV heads, head_dim 128) carries 256 KB of KV per token at FP16, which is the figure most published budget tables for 64 GB Mac Studios still use.

When the Formula Needs an Asterisk

Hybrid architectures break the assumption that 

n_layers

 in the formula counts all layers. Qwen3.6-27B and Qwen3.5-9B are hybrid stacks: each interleaves DeltaNet layers (linear-attention-style recurrent layers) with Gated Attention layers in a 3:1 ratio. The DeltaNet layers carry a small fixed-size recurrent state per slot that is independent of sequence length. They do not grow per token. The classical formula counts them anyway, which inflates the result by 4x.

The corrected version is straightforward: count only the attention layers.

Worked through for the two hybrid models at FP16:

Qwen3.6-27B: 2 × 16 × 4 × 256 × 2 bytes = 65,536 bytes/token ≈ 64 KB/token  
Qwen3.5-9B:  2 ×  8 × 4 × 256 × 2 bytes = 32,768 bytes/token ≈ 32 KB/token


The 27B comes in at 64 KB per token, the 9B at 32 KB. That puts them at a quarter and an eighth of classical Qwen3–32B (256 KB) respectively, and at 2/5 versus 1/5 of classical Qwen3–14B (160 KB). The 27B doubles the attention-layer count of the 9B, and nothing in the Gated-Attention dimensionality (both have 4 KV heads at head_dim 256) compensates for that. So the 27B carries twice the per-token KV cost of its smaller sibling. Both still sit far below the dense Qwen3 generation they replace.

The DeltaNet recurrent state is a separate, modest, sequence-length-independent allocation per slot. It is part of the working set but does not grow as conversations get longer. For a 64 GB budget at the slot counts this article cares about, treating DeltaNet state as a small fixed overhead and concentrating the budget arithmetic on attention-layer KV is the right approximation.

Quantize the cache to Q8_0 and the per-token attention figures halve. The Q4 variants halve them again at the cost of some quality on long-context generation.

The Full Budget on 64 GB

The unified-memory budget on a Mac Studio still adds up the same way:

weights + KV (slots × ctx_per_slot × bytes_per_token) + activations + DeltaNet state + OS overhead  
                ≤ available unified memory


A practical rule of thumb on a 64 GB box keeps the working set at or below roughly 56 GB once 

iogpu.wired_limit_mb

 has been raised. The remainder absorbs activations during prefill and leaves room for the OS and any other process. On macOS, 

sudo sysctl iogpu.wired_limit_mb

 controls how much memory can be wired for GPU use. The default is conservative, and raising it is often necessary even at moderate model sizes.

When a slot's allocation is too tight, the server logs evictions or refuses requests entirely. 

powermetrics --samplers gpu_power

Both are symptoms of the same root cause: the slot budget did not match the workload. With hybrid models on this rig, the more common diagnostic is the GPU running flat at high utilization with aggregate throughput plateauing, which is a bandwidth-or-compute story rather than a memory story.

Prefix Caching for Agent Workloads

The single most underused flag for agent operators is 

--cache-reuse

. The README phrases it precisely: "min chunk size to attempt reusing from the cache via KV shifting, requires prompt caching to be enabled (default: 0)." It is disabled out of the box.

Set it to a token threshold (256 is a common starting point in community tutorials, not an official recommendation), and the server detects when an incoming prompt shares a chunk with a recently processed one and reuses the cached KV slice via shifting. For agent loops, the win is significant. A classification or routing agent with a 2,000-token system prompt that runs 100 requests per minute would otherwise prefill 200,000 tokens per minute that are byte-for-byte identical. With cache reuse active, the prefill cost collapses to the per-request user message and any tool output appended after the system prompt.

The condition is exact byte-equality of the matched prefix. A trailing space, a regenerated UUID, a timestamp injected into the system prompt invalidates the match and forces a full re-prefill. This sounds obvious until you trace why your cache hit rate is zero and discover that the orchestration framework is rebuilding the system prompt with a fresh 

datetime.now()

 on every call. Common offenders include LangChain's 

ChatPromptTemplate

 with 

.format()

 injecting a 

{datetime}

 placeholder, Bedrock-style wrappers that prepend a session identifier, and any middleware that normalizes whitespace inconsistently across calls.

A second caveat applies to sliding-window-attention models. Gemma-class architectures with shared-KV layers currently log "cache reuse is not supported" even with 

-fa

 and 

--swa-full

 enabled (issue #21468 in llama.cpp). For hybrid Qwen3.5 / 3.6 models the relevant question is different: the prefix-caching path on the attention layers behaves like any other attention model, but DeltaNet recurrent state has its own restoration semantics, and that path is exactly the area where the bleeding-edge build caveat from the introduction applies. Verify cache-reuse hit rates empirically on your pinned commit before budgeting on them.

In a single-node setup, cache reuse works across all slots without explicit routing. In a cluster, you also need slot affinity at the load-balancer layer, otherwise a request lands on a different node each time and the cache benefit evaporates. Sticky session routing on the load balancer fixes this. The cluster-routing problem is covered in a planned follow-up article in this series.

Measurement is direct. Every 

llama-server

 chat-completions response includes a 

timings

 object with 

prompt_n

 (tokens actually prefilled) and 

cache_n

 (tokens reused from cache). For an agent with a stable system prompt, 

cache_n

 should approach the system-prompt length on every request after the first. If it does not, you have a prefix invalidation problem, not a cache configuration problem. In streaming mode with 

return_progress

 enabled, the same data appears in 

prompt_progress

total

, 

cache

, 

processed

time_ms

For workloads where you can pin specific prompt templates to specific slots, the 

id_slot

 request parameter gives you explicit control. Pre-warming a slot by sending the system prompt once before traffic starts ensures that subsequent requests routed to that slot are guaranteed cache hits.

A related lever worth knowing exists in recent builds. Host-memory prompt caching (

--cache-ram

 / 

-cram

, default 8 GB since Q4 2025, PR #16391) spills precomputed prefixes to system RAM and re-injects them at slot switch. It is adjacent to 

--cache-reuse

 and can carry the cache across a wider window than the in-flight slots alone.

Limits and When Single-Node Stops Being Enough

A single Mac Studio M4 Max with 64 GB is not infinite. With the per-token KV-cache pressure of hybrid models cut to a quarter (27B) or an eighth (9B) of the previous Qwen3 dense generation, the boundaries that matter have shifted.

Model size versus bandwidth.




As a rule of thumb on a 64 GB box, weights plus the worst-case working set should stay under roughly 56 GB once 

iogpu.wired_limit_mb

 is raised. With Qwen3.6-27B at ~16 GB and Qwen3.5-9B at ~6 GB, weights alone are no longer close to that ceiling. The ceiling is now set by how fast 546 GB/s of memory bandwidth can move weights and activations through the matmul units when many slots are active. A hypothetical 70B-class dense-or-hybrid model at Q4 (around 40 GB of weights) would still load on this rig, but its bandwidth budget per active slot drops sharply, and the realistic concurrency at production-quality TTFT collapses. The current Qwen lineup gives a real example of the next size class up: Qwen3.5-122B-A10B is a sparse-MoE model with 122B total parameters and ~10B active per token, a different bandwidth profile again (large weight footprint, modest active-parameter cost per token). On this hardware tier, anything in the 70B-class neighbourhood is best treated as a low-concurrency model regardless of architecture.

Model choice as a concurrency lever, for different reasons.




On a 64 GB rig running the previous Qwen3 dense lineup, choosing between 14B and 32B was forced by KV pressure: the 32B simply could not afford as many slots. With the current hybrid lineup, both Qwen3.6–27B and Qwen3.5–9B fit comfortably at high slot counts in KV terms. The choice lever moves to compute and bandwidth. The 27B gives you a stronger model with lower aggregate throughput at high concurrency. The 9B gives you a weaker model that saturates the bandwidth ceiling later, so aggregate tokens per second across many slots is higher. State that tradeoff explicitly in your capacity plan; it is no longer a memory decision but a throughput-versus-quality decision.

Context versus concurrency.




This is still a tradeoff, but a softer one than it used to be. At 64 KB per token of attention KV on the 27B, a 64K-context workload costs ~4 GB of KV per slot. That leaves room for roughly eight slots at full context against the working budget on this rig, and considerably more on the 9B at 32 KB per token. The native 262K context of these models becomes the more interesting ceiling for document-analysis use cases, and YaRN-extended ~1M contexts will start to push back into the budget conversation regardless of architecture. Pick context length deliberately for the workload.

Prefill latency on long prompts.




When prompts get into the tens of thousands of tokens, 

--ubatch-size

 becomes the dominant lever. On Apple Silicon, raising it to 1014 or 2048 (when memory permits) often improves prefill throughput substantially, because the matmul units run closer to peak with larger micro-batches.

Speculative decoding (MTP).




Both Qwen3.6–27B and Qwen3.5–9B are trained with Multi-Token Prediction and ship with native speculative-decoding support in their GGUF builds. In 

llama-server

, the 

--spec-*

 flags wire up a draft model whose proposed tokens the target verifies in parallel. On Apple Silicon, MTP can shift the decode-versus-prefill ratio appreciably for chatty agent loops, and it stacks with 

--cache-reuse

 rather than replacing it: the latter compresses prefill, the former compresses decode. One operational caveat specific to hybrid models: DeltaNet's recurrent state has to roll back cleanly when the target rejects a draft chunk, and the rollback semantics in the current hybrid graph code are an active area of iteration. Verify cache-reuse plus MTP on the same pinned commit before relying on the combined throughput in capacity planning.

When to cluster.




When a single node with a sensible 

--parallel

 setting is saturated and aggregate tokens per second has plateaued, horizontal scale is the next step. Multi-process on a single machine is rarely the right answer on Apple Silicon, because two processes contend for the same memory bandwidth and the same GPU. Two nodes behind a load balancer with sticky session routing are the structurally cleaner answer.

Software readiness.




Hybrid model support in 

llama.cpp

 is current but still firming up. Pin builds, document the commit, and re-test on bumps. This is a transient cost that will fade as Qwen3.5 / 3.6 graph code lands in stable releases, but right now it is real.

MLX as an alternative.




For specific architectures and quantizations, MLX outperforms 

llama.cpp

 on Apple Silicon. As a multi-slot continuous-batching server, the MLX ecosystem is less mature today than 

llama-server

. Worth benchmarking on a per-model basis, not worth a default switch.

Conclusion

A single 

llama-server

 process, parameterized correctly, will serve more concurrent agent requests on a Mac Studio M4 Max than most multi-process setups built around it. The leverage comes from reading three flags as a connected system rather than as independent knobs. 

--parallel

 sets the slot count, 

--batch-size

 and 

--ubatch-size

 shape prefill throughput, and 

--cache-reuse

 collapses repeated prefill on stable system prompts. 

--ctx-size

 is a memory budget whose distribution across slots depends on whether you set slot count explicitly and whether 

--kv-unified

 is on. Most of the operational pain in tutorials I see comes from treating any one of those as a default-and-forget setting.

The architectural shift matters too. The KV-bytes-per-token formula keeps working, but for the current hybrid generation it counts only the attention layers, which collapses per-token KV pressure to a fraction of the dense-Qwen3 numbers. On a 64 GB rig running Qwen3.5 / 3.6 hybrids, model choice has shifted from a memory decision to a throughput-versus-quality decision, and the limiting constraint is bandwidth and compute rather than cache budget. None of this is exotic, and it is rarely the first thing tutorials cover. Measure your own configuration, share what you find, and reach for horizontal scale when single-node tuning is genuinely exhausted, not before.
