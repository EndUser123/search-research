Bad News: SessionStart & SessionEnd Blocked by OpenCode SDK 😞

RLabs-Inc/memory

https://github.com/RLabs-Inc/memory

SessionStart

SessionEnd

 - Trigger async memory curation when user exits

The Problem:

 OpenCode SDK 

does not expose these events

 yet.

Open feature request: 

sst/opencode#5409

Only available events: 

session.created

 ,

🔧 Hacky Workarounds for SessionEnd

After deep diving into the codebase and SDK events, here are 

practical workarounds

 that could satisfy 

@RodrigoLuglio

https://github.com/RodrigoLuglio

's memory curation needs:

Option 1: Extended Stop Hook with Configurable Delay ⭐ (RECOMMENDED)

The 

Stop hook already fires on session.idle

 , but it fires immediately. We could extend it with a 

confirmation delay

 - similar to how 

session-notification.ts

 works:

How it works:

Stop hook fires on 

session.idle

Wait N seconds (configurable, e.g., 30-60 seconds)

If no activity during that time → execute memory curation

If activity resumes → cancel the pending curation

Implementation approach:

{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "python3 ~/.claude/hooks/memory_curate.py --mode=delayed_idle --delay=30"
          }
        ]
      }
    ]
  }
}


The memory system could handle the delay internally, or oh-my-opencode could provide a new hook event like 

SessionIdleConfirmed

 that only fires after confirmed inactivity.

Pros:

 Uses existing infrastructure, battle-tested pattern from 

session-notification.ts

Cons:

 Delay means curation happens X seconds after "true" session end

Option 2: Stop Hook + External State File

How it works:

Stop hook writes a timestamp to a state file (e.g., 

~/.claude/session_idle_state.json

 )

External daemon/cron job polls this file every 30 seconds

If idle time > threshold → trigger memory curation

UserPromptSubmit hook clears the state file on new activity

{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {"type": "command", "command": "python3 ~/.claude/hooks/mark_session_idle.py"}
        ]
      }
    ],
    "UserPromptSubmit": [
      {
        "hooks": [
          {"type": "command", "command": "python3 ~/.claude/hooks/clear_idle_state.py"}
        ]
      }
    ]
  }
}


Pros:

 Decouples curation from OpenCode process, reliable

Cons:

 Requires external daemon

Option 3: PreCompact as Session Milestone

Already works today!

 Use PreCompact as a trigger point for 

partial memory curation

:

{
  "hooks": {
    "PreCompact": [
      {
        "hooks": [
          {"type": "command", "command": "python3 ~/.claude/hooks/memory_curate.py --mode=milestone"}
        ]
      }
    ]
  }
}


PreCompact fires when:

Context window is getting full and needs compaction

Session has accumulated significant conversation

Pros:

 Works today, meaningful trigger point, already in oh-my-opencode

Cons:

 Doesn't fire on every session end, only on compaction events

Option 4: Hybrid Approach (Best Coverage)

Combine multiple approaches for maximum coverage:

{
  "hooks": {
    "PreCompact": [
      {
        "hooks": [
          {"type": "command", "command": "python3 ~/.claude/hooks/memory_curate.py --mode=milestone --incremental"}
        ]
      }
    ],
    "Stop": [
      {
        "hooks": [
          {"type": "command", "command": "python3 ~/.claude/hooks/memory_curate.py --mode=idle_trigger"}
        ]
      }
    ]
  }
}


The memory system could:

On 

PreCompact

 : Do incremental curation (extract memories from compacted content)

On 

Stop

 : Mark session as potentially ending, start a timer

External daemon: Finalize curation for sessions that have been idle for X minutes

What oh-my-opencode Could Add (Future Enhancement)

If there's interest, I could implement a new hook event in oh-my-opencode:

SessionIdleConfirmed

 - Fires after X seconds of confirmed inactivity:

{
  "hooks": {
    "SessionIdleConfirmed": [
      {
        "matcher": { "delay_seconds": 30 },
        "hooks": [
          {"type": "command", "command": "python3 ~/.claude/hooks/memory_curate.py"}
        ]
      }
    ]
  }
}


This would be a 

clean abstraction

 over the idle-confirmation pattern, purpose-built for session end detection.

In fact, all the memory system would need is a single 'fire and forget' call to the memory server endpoint /checkpoint with the required information (session id) in order to be able to launch a new oh-my-opencode instance that would resume the session in background with a custom system prompt and that's it. When the user hits crtl+c or any other command that will close the app/end the session, this one single http local call must be made and nothing else....but it need to be really before the session end/app closes, because otherwise, like as I could understand, and please, correct me if I'm wrong, this idle hook can be triggered more than once in the same session, what would end up triggering the memory curation more than once for the same session potentially extracting duplicated memories. Or did I miss anything? We don't need to extend the life of the oh-my-opencode beyond its closing or session ending, just 'fire-and-forget' a local http call that won't reply directly to it, the curation will happen in another instance in background.
