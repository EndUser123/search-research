# The GSD Skills Everyone Misses (I Tested Them)
If you've only ever

used GSD

through its

main workflow,

the discuss, plan,

execute ceremony,

you're using

maybe half of it.

The framework ships

a whole

second layer underneath:

small standalone skills

that don't need

a roadmap, a milestone,

or any of the heavy

setup.

Sketch, fast, debug,

forensics, a pair of

UI commands.

I found them

almost by accident.

I was comparing GSD

against the other

spec-driven tools.

A few videos back

poking through

the command list,

and there they were,

a dozen commands

I'd never run once.

In that comparison

I let GSD

drive itself on --auto

and you never saw

the parts underneath.

This time

I drove

every one of these

by hand

on a real Astro site.

The order you'll see

is the order

I tested them,

including the parts

where I had no clue

what a command did

until I went and

read its source.

A quick thing

first, because

the naming is

a moving target,

the repo has

been renamed.

get-shit-done-redux

is gsd-core on GitHub

now, and at the rate

this stuff changes

it may not be

the last name either,

but the install command

hasn't caught up:

as I'm recording,

what you actually type

is still

npx

@opengsd/get-shit-done-redux@latest,

so don't assume

the repo name matches

the package.

Read the readme

as the source of truth

and grab whatever

command's current

by the time

you're watching.

The slash

commands stay

put through all of it

— /gsd-quick,

/gsd-debug, same names —

and so does

the global

gsd-sdk tooling.

Here's why

any of this moved.

The original project

got rug-pulled.

Back in May,

the project's

top contributor

pushed a commit

titled "WARNING:

This repository

appears compromised" —

then set new issues

and pull requests

to auto-close and lock,

pointing everyone

to a fork.

They spun that fork up

the same day.

Go to the

original repo now

and that warning's

already gone;

it's been swapped

for a clean "GSD

Has Moved" note

that just points

at the fork.

The fork team's own

readme

is blunter about it.

They call it a meme-coin

rug-pull outright,

and say the

former creator

and the old lineage

aren't

part of the project

anymore.

That fork —

now open-gsd/gsd-core —

is the

one that's

actually maintained.

It's run

under the open-gsd

org by people

who say they worked

on the original.

Whether it's exactly

the same crew

I can't confirm,

but it's clearly

where the active

development went.

One thing

I want to be

honest about.

The fork team says

they lost contact

with the

original creator,

TÂCHES,

back around

the start of April.

I can't square that

with what I saw.

On May 7th,

an account under

his name left

a comment on my GSD

comparison video

— five weeks

after the silence

the fork team describes.

I can't be a

hundred percent

sure that

account is really him —

but it's a channel

with thirty-two

thousand subscribers,

not some throwaway,

so it'd

be a strange thing

to impersonate.

And the timing

doesn't fit

a clean

April disappearance.

So I'm not

going to repeat

"he vanished in April"

as fact.

The public

break was really

May 22nd,

not a slow fade.

If you've already got

the old version

installed globally —

for me

it showed up

as a package called

get-shit-done-cc —

Upgrading

just overwrites

it in place.

I'll show

you exactly

what that looks

like next.

The upgrade

itself is boring

and that's exactly

what you want.

I asked Claude

Code to handle it.

It sketched

out a cautious

little plan

— back up the existing

skills first,

then reinstall —

so I let it run.

That backup was Claude

being careful,

not the installer

doing it for me.

When I asked

what the installer

actually does, it

explained: it

just wipes its own

managed files, copies

the new ones on top,

and leaves

any custom skills

you've added alone.

It found the old

get-shit-done-cc

package, swapped it out,

and my skill count

went from 65 to 67.

Two new ones.

Restart Claude Code

and you're current.

Before any of this, on day one,

I ran one more command

that quietly set up

everything

after it:

/gsd-map-codebase.

On a brownfield

project —

an existing codebase

the tool has

never seen —

this is the onramp.

It spawns

four agents in parallel,

each exploring

a different angle

and writing its findings

straight to disk.

One covers

the stack

and integrations.

Another maps

the architecture,

a third handles

conventions and testing,

and the last

one collects

the concerns.

Seven documents

land in a

.planning/codebase

folder,

and the orchestrator

only collects

confirmations,

so your main context

stays clean

while four agents

do the reading.

The document

that earns its keep

is CONCERNS:

a plain

list of the tech

debt and risks

in the codebase.

One of the entries

is the tag-color problem

— the site

draws tag colors

from one data source

and its article data

from another,

so any article living

only in the database

ends up

with inconsistent

colors.

That's the same bug

I later

fixed with quick.

I'd probably mentioned

the color issue

to the model

at some point,

so I won't claim

it discovered it cold.

But the value holds

either way:

the concern gets

written to disk,

where the next command

can read it

instead of relying on me

to remember.

The first skill

I'd already been

leaning on

is /gsd-quick.

I'd used it

earlier that week

to fix a bug

where every tag

on the site

rendered in

the same color.

It traced the data

flow, found the fix,

and seeded

the staging database,

then production.

Yes — I let

Claude access

my production database.

Without backups.

If it had dropped it,

the way it

sometimes likes to,

that would have been

a real cat-astrophe.

No more nicely

generated content

for exotic

React lib lovers.

It didn't,

for the record.

I checked

the colors

actually came through

before it committed

and pushed.

Solid for one command.

When I first ran it

I honestly didn't

know what quick does

under the hood,

so I went and

read the source.

So here's

what's going on

under the hood.

By default

it runs lean —

just a planner

in quick mode

and an executor.

The optional agents

stay off

unless you ask for them:

the research

and discussion

passes,

and a

separate plan-checker.

That's the "skip

optional agents" line

you see when it runs.

You opt

the gates back in

with flags:

--discuss, --research,

--validate, or --full,

which is literally

all three at once.

It reads

your .planning context —

including those

codebase docs

the map just wrote

— drops

a PLAN and a SUMMARY

into a dated quick

folder, and logs

the task in STATE,

not the roadmap.

Which explains

the one weird thing,

or maybe it's the catch.

A change

I thought was trivial,

it treated

like a small project.

The charitable read

is that it really reads

the surrounding context

before touching code.

The honest read

is that quick isn't

always that quick.

Probably some of both.

The bigger experiment

was a dark theme

for the whole site,

and this is where

the standout skill

showed up: /gsd-sketch.

Sketch

makes throwaway HTML

mockups

before it builds

anything.

It asks you

a few taste questions.

What should

the dark theme

feel like?

How should the

blue accent read

against a

dark background?

How do people flip

between modes?

I told it: near-black

and inky,

like GitHub

or Vercel dark.

Brighten the blue.

Auto-detect

the system setting,

but let me override it

by hand.

Then it generated

two to three variants

per screen

as standalone

HTML files,

ran a little web server

so I could click

through them

in the browser,

and let me pick.

I took the flat,

inky one

with hairline borders.

Then I did

the article reading page

the same way

— soft contrast,

high contrast,

tinted code — and chose

the one I liked.

The part

I didn't expect

is the wrap-up.

You run

`/gsd-sketch --wrap-up`

and it doesn't

just save the HTML.

It packages

every decision

you made into a reusable

Claude skill,

written

straight into

your skills folder.

Mine came out

as

`sketch-findings-reactlibs`:

the palette,

the CSS patterns,

the visual direction,

all captured

so the next

build conversation

picks them up

on its own.

Throwaway mockups

that turn into memory

the next build inherits.

I like that a lot.

If you're

getting something

out of this, hit

subscribe — it's

the cheapest way

to keep

the channel going.

And there's a Discord

link in the description.

If you want to argue

about any of this

with me directly.

Next I tried the command

that's supposed

to formalize

the design:

`/gsd-ui-phase`.

It refused.

It needs a

phase context,

and the source

explains why.

It runs a researcher

that writes a UI-SPEC

— a design contract.

The spec

pins down

spacing, typography,

the color split,

the light

and dark tokens,

even the copywriting:

button labels, empty

states, error messages.

Then a checker

reviews it

and either approves it

or blocks

it and sends it back.

It's not a standalone

command, it's a gate

inside the heavy

workflow, slotted

between the discuss step

and the planning step.

So on a quick dark theme

with no phases,

it simply won't run.

So I implemented

the theme with

`/gsd-quick` instead.

It threw a warning

— no roadmap,

no installed agents —

and said

the machinery

was blocked.

The roadmap

part was fair;

the project

had no phases.

But the agents

weren't missing.

They're installed

globally, and `quick`

was only looking

inside the

local project.

When I pushed back

and asked why,

it backed down.

Oh, they're global,

my mistake.

So half of that warning

was a false alarm.

I told it to go

anyway, and it did: it

put the whole recolor

into one central

CSS block

instead of touching

component markup,

made three commits,

and checked the page

with a cURL.

Then the honest part.

It was very confident,

and it was also wrong

in places.

The "dark"

theme still rendered

white in spots.

The logo had black

lettering and vanished

on the dark background,

so I inverted it

in Photoshop — twice,

because a later step

overwrote my version

with the old one.

The search modal

broke on this branch.

And the code-highlight

theme

never actually changed,

no matter what

I asked for.

That's where the last UI

command earned

its place:

`/gsd-ui-review`.

It's a

retroactive audit.

It scores finished

UI against six pillars —

copywriting, visuals,

color, typography,

spacing,

and experience design

— one to four points

each, twenty-four max.

There was no UI-SPEC

to grade against,

so it fell back

to general

six-pillar standards.

It spun up

an auditor agent

and came back

with twenty-one

out of twenty-four,

unhappy about color

and experience

design specifically.

It also caught

a couple of elements

sitting at the

wrong shade

in dark mode,

including one

I'd completely missed.

Three small fixes,

which I had it apply

and commit.

A free second

pair of eyes on work

I thought was

already done.

After all that ceremony,

/gsd-fast is

the opposite,

and it's the

direct answer

to everyone

who watched

the comparison and said

GSD is too slow.

I gave it a small job:

the tags page

only shows

a chunk of the tags,

so add

a load-more button

that pages

through the rest.

Fast didn't

spin up

any subagents

or write

a planning file.

It went straight

into the code.

It added an

ID to the tag list,

wrote the pagination,

and asked

whether a chunk

size of thirty

per click was fine.

I bumped it to fifty.

One shot, done.

The source is blunt

about what

it's for: tasks

you could describe

in one sentence

and finish

in under two minutes —

typos, config

changes,

small refactors,

forgotten commits.

For anything

that needs research

or multiple steps,

you're meant to reach

for quick instead.

The question

I kept asking

myself: is fast

actually faster

than just typing

the same request

into Claude directly?

Reading the source,

the answer is mostly no.

It runs inline in

the current context

with no extra machinery

behind it.

What you really get over

a plain prompt

is the GSD

config around it

and a nudge

to keep the task

small enough

to stay one-shot.

I'd call it a good habit

for the small stuff

rather than something

that does work

a plain prompt couldn't.

The next one is

the skill

I'd actually keep

around: /gsd-debug.

The setup was

a real bug.

That load-more button

I'd just added worked

when I refreshed the

tags page directly,

but if I navigated to it

from somewhere else

on the site,

it did nothing.

Debug doesn't

start guessing.

It opens a session

and interviews

you first —

what you expected,

what actually happened,

any errors,

when it started.

Then it works

the scientific way.

It writes down

a hypothesis,

a test for it,

and what

the result would

mean, and keeps

all of that on disk

as it goes.

Under the hood

it's two agents:

one managing the session

and the checkpoints,

the other

doing

the actual

investigating.

The root cause it found

was a good one.

The load-more logic

lived in a

top-level script

that only runs

on a full page load.

The site uses Astro's

client-side router,

which swaps

in a fresh DOM

when you navigate

without re-running

that script,

so the button lost

its handler.

It moved the binding

into a function

that re-runs

on navigation,

and that was the fix.

The part worth knowing:

the whole

session is saved

as a file

under .planning/debug,

with the

current hypothesis

and the next step

written down.

You can run

/clear, wipe

the context completely,

come back later,

and it picks up exactly

where it left off.

The debugging state

lives on disk,

not in the chat.

The last skill I tried

is the one

I had the least

luck with,

and I'll be honest

about that.

Forensics

is a

read-only post-mortem.

When a workflow crashes

or gets abandoned

and you don't know

where it went wrong,

you point it

at the wreckage

and it goes digging

— through

git history,

the planning

folder, the files

on disk.

It's hunting

for the usual failure

shapes: a loop

that got stuck,

an output

that never got written,

a run that died halfway.

It writes

a report, strips out

any secrets,

and never touches

your code.

My test:

I ran the site's

article pipeline

to publish three

new articles.

It wasn't clean.

The build didn't

seem to register,

and the articles

reported as generated

but never showed up

in production.

So I pointed forensics

at it and asked why.

It wrote a long,

detailed report

and concluded

it wasn't

the bug I'd assumed —

it was caching.

The articles

had been live

in the database

the whole time;

a long cache

was just serving

the old page.

So the dramatic bug

turned out to be a cache

I'd forgotten existed.

Not a great demo,

honestly.

But it shows the shape

of the thing:

when you're staring

at a mess with no idea

where to start,

forensics

gives you a place

to begin.

One footnote: Opus

4.8 had launched

only hours

earlier, and mid-session

I hit a hard

API error

about thinking blocks.

Pure bleeding-edge tax,

and it's already

patched in

Claude Code 2.1.156.

So that's the tour.

No grand verdict

this time,

just a set of skills

I didn't know

were there.

Here's where I landed.

The main GSD workflow,

The full

discuss-plan-execute

pipeline is thorough,

but heavy and slow.

These skills aren't.

Sketch, fast,

debug, forensics,

the UI audit —

each one

stands on its own.

You can drop sketch

into a project

to mock up a redesign,

or run debug

on a real bug,

without committing

to the whole framework

and its ceremony.

That's what

I'd want you to take

from this: cherry-pick

the useful parts.

I do have to

talk about cost,

because that's

the real catch.

GSD isn't

tied to any one model

— run it on

whatever you like,

and the smarter

the model, the better

the results.

The trouble

is that the smart

models are slow,

and a process

built on

a stack of agents

means a lot of waiting.

The long pauses are

what wear you down.

The Fast version of Opus

would fix exactly

that —

same intelligence,

about two

and a half times

quicker.

But I don't turn it on.

The price did

come down recently.

Regular Opus output

is twenty-five dollars

per million tokens;

Fast Opus

used to be a hundred

and fifty

— six times the rate.

It just dropped

to fifty,

so now it's only double.

Cheaper than before,

still not cheap.

The reason I avoid it

isn't the rate, though.

It's that Fast

Opus bills

as extra usage,

on top of your plan

— it doesn't

count against

your subscription

limits.

If it did count

against the limits,

I'd seriously consider

turning it on.

On the

two-hundred-dollar plan

you already get

twenty times the usage,

so the headroom

is there.

But as an extra

charge on top, I don't.

I keep saying it.

Maybe one day.

The skills themselves,

though, are good

to have.

The framework

ships them,

they mostly do what

they promise

— sketch and debug

especially —

and now you know

they're there.

Thanks for watching,

and I hope you picked up

something new today.

As for the cat,

she remains

thoroughly unimpressed

that it took

four parallel agents

to find a bug

she'd have

ignored anyway.
