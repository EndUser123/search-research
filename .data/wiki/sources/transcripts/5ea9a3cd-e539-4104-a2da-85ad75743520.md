[Bug] Stop hook ( 
persistent-mode.mjs
 ) never honors 
stop_hook_active
 , triggering Claude Code's 9-consecutive-block safety override in ultrawork / ralph / autopilot / ultragoal / etc.
Repository:
 Yeachan-Heo/oh-my-claudecode
Affected versions:
 4.14.4 (and earlier — bug pre-exists; verified against 
hooks/scripts/persistent-mode.mjs
 in 4.14.4)
Severity:
 Medium — system gracefully degrades (Claude Code overrides the block and ends the turn), but every persistence mode prints an alarming warning to the user and the OMC 
max_reinforcements
 budget (default 50) is effectively capped at ~9 by Claude Code's safety system.
Symptom
Mid-ultrawork run, Claude Code emits this warning before forcibly ending the turn:
A hook blocked the turn from ending 9 consecutive times — overriding and ending turn.
For Stop/SubagentStop hooks, check stop_hook_active in the input and return success
while it's true. Set CLAUDE_CODE_STOP_HOOK_BLOCK_CAP to raise this limit.

Observed context: this occurred during an active ultrawork run after multiple Stop-hook reinforcements. OMC's reinforcement counter can advance beyond Claude Code's lower consecutive-block cap, so Claude Code force-overrides before OMC reaches its configured reinforcement budget.
Root cause
Claude Code's Stop/SubagentStop hook contract sends a 
stop_hook_active: true
 field in the hook payload when the hook is being re-invoked after a previous 
{decision: "block"}
 — i.e., Claude was already prevented from stopping at least once. Per the official contract, hooks 
must
 return success (allow the stop) when this flag is true, otherwise Claude Code's hard cap ( 
CLAUDE_CODE_STOP_HOOK_BLOCK_CAP
 , default 9) kicks in and force-overrides. 
hooks/scripts/persistent-mode.mjs
 never reads 
data.stop_hook_active
 . A grep over the entire 4.14.4 source tree returns zero matches:
$ grep -rn "stop_hook_active\|stopHookActive\|CLAUDE_CODE_STOP_HOOK_BLOCK_CAP" \
    hooks/ scripts/ docs/
# (no output)

This means every persistence mode — 
ralph
 , 
ultragoal
 , 
autopilot
 , 
ultrapilot
 , 
ultrawork
 , 
ultraqa
 , 
pipeline
 , 
team
 , 
omcTeams
 , 
swarm
 — keeps emitting 
{decision: "block", reason: …}
 on every Stop event until OMC's own 
max_reinforcements
 cap (typically 50) is reached. Claude Code's hard cap of 9 always wins first.
The Stop hook 
does
 correctly short-circuit on several other edge cases (context-limit deadlock — issue 
#213
https://github.com/Yeachan-Heo/oh-my-claudecode/issues/213
, user abort, auth errors, scheduled-wakeup stops, owned async work), so the pattern of "early-return without block" is already established in the file. 
stop_hook_active
 is simply missing from the list. 
hooks/scripts/context-guard-stop.mjs
 (also a Stop hook) self-limits via its own 
MAX_BLOCKS = 2
 guard, and 
code-simplifier.mjs
 uses a per-turn marker file, so neither of those independently trips the cap. The 
SubagentStop
 hooks ( 
subagent-tracker.mjs
 , 
verify-deliverables.mjs
 ) never emit 
decision: "block"
 (grep confirms), so they are not affected.
Reference
Anthropic Claude Code hooks docs, Stop / SubagentStop section:
The 
stop_hook_active
 field will be 
true
 when Claude Code is already
continuing as a result of a stop hook. Check this value or process the
transcript to prevent Claude Code from running indefinitely.
Reproduction
In any project, start ultrawork with a multi-step task list (or any persistence mode: ralph, autopilot, ultragoal).
Let it run. After ~9 turn-end attempts where the hook blocks, Claude Code emits the warning and force-ends the turn.
The OMC 
reinforcement_count
 in 
.omc/state/<mode>-state.json
 will be ~9–11 (not the configured 50).
Suggested fix
Add a 
stop_hook_active
 early-return at the top of 
main()
 in 
hooks/scripts/persistent-mode.mjs
 , alongside the existing guards (around line 895, after 
stateDir
 / 
globalStateDir
 initialization, and before reading mode state files). Minimal patch:
// After: const globalStateDir = join(homedir(), ".omc", "state");

// CRITICAL: Honor Claude Code's stop_hook_active contract.
// When Claude Code re-invokes the Stop hook after a previous block,
// it sets stop_hook_active=true. Hooks MUST return success in that case,
// otherwise CLAUDE_CODE_STOP_HOOK_BLOCK_CAP (default 9) force-overrides
// and the user sees a "hook blocked 9 consecutive times" warning.
if (data.stop_hook_active === true || data.stopHookActive === true) {
  console.log(JSON.stringify({ continue: true, suppressOutput: true }));
  return;
}

Place it 
above
 the persistence-mode dispatch but 
below
 (or alongside) the existing 
isContextLimitStop
 / 
isUserAbort
 / 
isAuthenticationError
 / 
isScheduledWakeupStop
 early-returns to mirror the established pattern.
Behavioral implication
After the fix, 
max_reinforcements
 (default 50) will function as designed — the hook will block on each 
fresh
 turn-end attempt but yield once Claude Code signals re-invocation. This matches how 
ralph_loop
 / 
ultrawork
 are 
supposed
 to keep Claude on task: continue across natural stops, but never spin Claude Code's safety system.
Optional: documentation/config
Mention 
CLAUDE_CODE_STOP_HOOK_BLOCK_CAP
 in OMC docs as a user escape hatch.
Consider lowering the per-mode 
max_reinforcements
 defaults to something near 9–15 since the practical effective cap is the lower of 
max_reinforcements
 and 
CLAUDE_CODE_STOP_HOOK_BLOCK_CAP
 . (Not required for the fix — just clarifies user expectations.)
Tests to add
Unit test for 
persistent-mode.mjs main()
 : input 
{ stop_hook_active: true }
 while 
ultrawork-state.json
 is active → output must be 
{continue: true, suppressOutput: true}
 , 
not
 
{decision: "block", …}
 .
Same test with each of the other modes ( 
ralph
 , 
autopilot
 , 
ultragoal
 , 
pipeline
 , 
team
 , 
ultraqa
 , 
swarm
 ) active.

File audited: 
hooks/scripts/persistent-mode.mjs
 (4.14.4), 1451 lines,

Existing early-returns checked: L899 ( 
isContextLimitStop
 ), L905 ( 
estimateContextPercent ≥ 95
 ), L911 ( 
isUserAbort
 ), L917 ( 
isAuthenticationError
 ), L922 ( 
isScheduledWakeupStop
 ), L927 ( 
hasPendingOwnedAsyncWork
 ), L988 ( 
isSessionCancelInProgress
 ).
data.stop_hook_active
 is referenced 
zero times
 in the entire 4.14.4 tree.
Other Stop hooks ( 
context-guard-stop.mjs
 , 
code-simplifier.mjs
 ) are self-limited and not the cause.
SubagentStop
 hooks ( 
subagent-tracker.mjs stop
 , 
verify-deliverables.mjs

decision: "block"

Additional implementation clues from a local investigation/fix branch:
The important invariant is broader than 
persistent-mode.mjs
 : 
any Stop/SubagentStop hook that can return decision: "block" must yield when the payload has stop_hook_active === true or stopHookActive === true
 . Raising 
CLAUDE_CODE_STOP_HOOK_BLOCK_CAP
 only masks the contract violation.
Primary fix point: add an early 
isStopHookActive(...)
 guard in 
scripts/persistent-mode.mjs
 / generated 
scripts/persistent-mode.cjs
 / 
templates/hooks/persistent-mode.mjs
 , before the mode dispatch returns another block.
Source-level fix point: add 
stop_hook_active
 and 
stopHookActive
 to 
StopContext
 in 
src/hooks/todo-continuation/index.ts
 , export 
isStopHookActive(context)
 , and call it early in 
checkPersistentModes(...)
 in 
src/hooks/persistent-mode/index.ts
 so direct callers and bridge/runtime scripts share the same behavior.
Adjacent Stop hooks worth sweeping too:
scripts/context-guard-stop.mjs
 can block near the context threshold, so it should yield on re-entry before incrementing its own block guard.
scripts/code-simplifier.mjs
 and 
templates/hooks/code-simplifier.mjs
 usually self-limit with a marker, but should still explicitly yield on 
stop_hook_active
 to avoid contributing to the same yellow warning if multiple Stop hooks run in the same turn.
Regression tests worth adding:
src/hooks/persistent-mode/stop-hook-blocking.test.ts
 verifies active persistent modes do 
not
 block when 
stop_hook_active
 / 
stopHookActive
 is true.
src/__tests__/context-guard-stop.test.ts
 verifies context guard yields on Stop-hook re-entry.
src/__tests__/code-simplifier-stop-hook-active.test.ts
 verifies code-simplifier yields on Stop-hook re-entry.
Local candidate-fix verification summary:
targeted Stop-hook tests passed;
build passed;
lint passed with no new errors;
full suite was almost entirely green with one unrelated/pre-existing failure.
One subtle clue: the warning can appear around 
[ULTRAWORK #11/50]
 even though Claude Code says it overrode after 9 consecutive blocks. That mismatch is expected if OMC counts its own reinforcement budget separately while Claude Code enforces a lower consecutive Stop-hook block cap. The fix should make OMC's persistence continue across fresh turn-end attempts while allowing Claude Code's re-entry stop to complete cleanly.
