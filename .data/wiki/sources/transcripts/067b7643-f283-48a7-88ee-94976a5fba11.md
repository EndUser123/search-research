Your AI’s Built-In Safety Net

If you’ve been using Claude Code, you’ve probably felt the tension: you want to give it freedom to work, but not too much. Hooks are the answer

1. What Are Hooks?

Hooks are user-defined shell commands, HTTP endpoints, or AI prompts that execute automatically at specific points in Claude Code’s lifecycle. They let you intercept what the AI is about to do — or just did — and apply your own logic.

💡 Think of hooks as middleware for AI behaviour — not error handling, but programmable guardrails you define once and that run automatically every time.

Hooks give you the power to:

· Block risky or sensitive actions before they happen

· Run validations (type checks, tests, linting) after every change

· Log every action Claude takes for audit trails

· Respond programmatically to AI events without manual intervention

3. PreToolUse: Block Before It’s Too Late

PreToolUse hooks run after Claude creates tool parameters but before the tool executes. This is your first line of defence — inspect and block actions before they happen.

What you can do:

· Protect sensitive files — block writes to .env, secrets, or production configs

· Enforce scope — prevent Claude from touching files outside your project boundary

· Require approval — flag high-risk commands (rm, DB migrations, deploys)

· Modify tool input — auto-correct or sanitise parameters before execution

Real Example: Block rm -rf commands

From the official Anthropic docs — this hook reads each Bash command on stdin and denies it if it matches rm -rf:

#!/bin/bash




# .claude/hooks/block-rm.sh




COMMAND=$(jq -r '.tool_input.command')

if echo "$COMMAND" | grep -q 'rm -rf'; then




jq -n '{




hookSpecificOutput: {




hookEventName: "PreToolUse",




permissionDecision: "deny",




permissionDecisionReason: "Destructive command blocked by hook"




}




}'




else




exit 0  # allow the command




fi

Register this hook in .claude/settings.json:

{




"hooks": {




"PreToolUse": [




{




"matcher": "Bash",




"hooks": [{ "type": "command", "command": ".claude/hooks/block-rm.sh" }]




}




]




}




}

4. PostToolUse: Validate After Every Change

PostToolUse hooks run immediately after a tool completes successfully. This is where automated quality control lives. The hook receives both the tool input (what Claude tried to do) and the tool response (what happened).

What you can do:

· Type checking — run tsc — noEmit after every file change

· Run tests — execute the relevant test suite and feed failures back as context

· Linting — enforce code style automatically after every write

· Logging — record every action Claude takes for audit trails

🔁 Key insight: Claude receives the output of these validators as feedback. If a type check fails, it sees the error and corrects the code automatically — no copy-pasting error messages needed.

Real Example: Run the linter after every file write

{




"hooks": {




"PostToolUse": [




{




"matcher": "Edit|Write",

}




]




}




}

5. The Self-Correcting Feedback Loop

The real power of hooks is what happens when you combine pre and post-hooks. You get a self-correcting feedback loop:

Claude attempts action




│




PreToolUse: Is this allowed?




→ No  → Block + return reason → Claude adapts




→ Yes ↓




Action executes




│




PostToolUse: Is the result valid?




→ No  → Return errors → Claude fixes




→ Yes ↓




Move to next step

You define the rules once. The loop handles enforcement automatically — without any manual intervention from you.

6. Four Types of Hooks

Claude Code supports four hook handler types, giving you flexibility in how you implement your guardrails:

type: “command” — Run a shell script

Fastest, most flexible. Your script gets JSON via stdin and communicates back via exit codes and stdout. Use this for type checks, linting, and blocking dangerous commands.

type: “http” — POST to an HTTP endpoint

Send hook events to your own API or validation service. Great for team-wide policy enforcement or integration with external systems.

type: “prompt” — Ask a Claude model

Send the hook input to a fast AI model (Haiku by default) for intelligent, nuanced evaluation. Returns {“ok”: true/false}.

type: “agent” — Spawn a verifier subagent

A full AI subagent that can use tools (Read, Grep, Glob) to inspect files and verify conditions before returning a decision.

8. Hooks vs. Prompt Engineering

A natural question: why not just tell Claude in the prompt what not to do?

Prompts are instructions. Hooks are enforcement. They serve different roles and work best together.

9. Security Best Practices

⚠ Command hooks run with your full system user permissions. Review and test every hook command before adding it to your configuration.

· Validate and sanitise inputs — never trust hook input data blindly

· Always quote shell variables — use “$VAR” not $VAR

· Block path traversal — check for “..” in file paths

· Use absolute paths — specify full script paths using $CLAUDE_PROJECT_DIR

· Skip sensitive files — never expose .env, .git/, or key files

10. Getting Started — Minimal Day-One Setup

You don’t need to automate everything immediately. Start with the guardrails that would save you the most pain, then expand:

1. Block writes to .env and secrets folders — non-negotiable

2. Run type checks post-write — especially in TypeScript projects

3. Log all file modifications — useful for reviewing what changed per session

Debug hooks with:

claude --debug

This shows which hooks matched, their exit codes, and full output. You can also toggle verbose mode with Ctrl+O inside a session.

Key Takeaway

The most useful thing hooks gave me wasn’t protection from mistakes — it was confidence to let Claude move faster.

When you have a layer that catches bad writes, failed type checks, and scope violations, you can give the AI more latitude without more anxiety. That’s the real unlock.

Hooks aren’t about distrust. They’re about building a system where trust is earned by design.
