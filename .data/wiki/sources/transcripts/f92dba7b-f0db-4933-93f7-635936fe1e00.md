How to Create an AI Agent with the Claude Agent SDK
A complete guide to building production-ready AI agents with custom tools, MCP integrations, and observability
Shinzo Team
February 14, 2026 14 min read
Most LLM integrations stop at text generation. You send a prompt, you get a response, and that's it. But the developer community is rallying behind something much more powerful — AI agents that can autonomously read files, execute commands, search the web, and take actions on behalf of the user. The gap between a chatbot and a true agent has always been the engineering overhead: managing tool execution loops, handling context windows, wiring up external services, and dealing with the non-deterministic nature of LLMs in production.
That's where the Claude Agent SDK comes in. Anthropic recently renamed the Claude Code SDK to the Claude Agent SDK, and for good reason. The same agentic framework that powers Claude Code — one of the most capable AI coding tools available — is now fully programmable in Python and TypeScript. In practice this means you can build production-ready AI agents with built-in file operations, bash execution, 
MCP
https://modelcontextprotocol.io/
 (Model Context Protocol) integrations, and context management without reinventing the wheel.
For the rest of this post, we'll walk you through everything: environment setup, building a working agent, adding custom tools via MCP, and — critically — why you need observability from day one.
What Is the Claude Agent SDK?
The Claude Agent SDK is a developer toolkit designed to build interactive AI agents powered by Anthropic's frontier models. Unlike the standard 
Messages API
https://platform.claude.com/docs/en/agent-sdk/overview
, which gives you low-level control over individual completions, the Agent SDK provides the full agent loop out of the box. It handles tool execution, context management, automatic prompt caching, and session continuity so you can focus on what your agent actually does instead of how it orchestrates each step.
If you're new to the protocol that makes all of this extensible, we'd recommend starting with 
the fundamentals of MCP
https://shinzo.ai/blog/mcp-101-an-introduction-to-the-mcp
 before diving in here.
From Claude Code SDK to Claude Agent SDK
The reason we're explaining the naming is because it matters. Anthropic 
initially released this as the Claude Code SDK
https://www.anthropic.com/engineering/building-agents-with-the-claude-agent-sdk
, positioning it as a programmatic interface for Claude Code's capabilities. But as teams at Anthropic and across the developer community started using it for deep research, customer support automation, data analysis, and a variety of non-coding use cases, the scope clearly outgrew the name. The rename to "Claude Agent SDK" reflects what it actually is: a general-purpose framework for building any kind of autonomous agent.
How Does the Agent SDK Differ from the Messages API?
The core Messages API requires you to manage the entire agent loop yourself. You call the model, check if it wants to use a tool, execute the tool, feed the result back, and repeat until done. With the Agent SDK, Claude manages that loop internally. You provide a prompt and configuration, and the SDK streams messages as Claude reasons, calls tools, observes results, and decides what to do next.
The SDK also ships with built-in tools — Read, Write, Edit, Bash, Glob, Grep, WebSearch, and more — so your agent can start working immediately without you implementing tool execution from scratch. That said, you can extend it with custom tools via MCP, which we'll cover shortly.
Prerequisites and Environment Setup
Before writing any code, let's get the environment ready. The Claude Agent SDK supports both Python and TypeScript. For this guide, we'll use Python, but the concepts are nearly identical in TypeScript.
System Requirements
You'll need Python 3.10 or higher (Node.js 18+ if you're going the TypeScript route), and an Anthropic API key from the 
Claude Console
https://console.anthropic.com/
. The Claude Code CLI is automatically bundled with the Python package, so no separate installation is required.
Installing the SDK and Setting Your API Key
Create a new project directory and install the SDK:
sh Copy
mkdir my-agent && cd my-agent
pip install claude-agent-sdk

Then set your API key as an environment variable. Create a 
.env
 file in your project root:
code Copy
ANTHROPIC_API_KEY=your-api-key-here

Or export it directly in your terminal:
code Copy
export ANTHROPIC_API_KEY="your-api-key-here"

That's it for setup. The SDK handles the rest of the connection plumbing behind the scenes.
Building Your First AI Agent — A Step-by-Step Walkthrough
Now is the perfect time to write some actual code. We'll build a simple agent that can read files, find bugs, and fix them autonomously. This is the same pattern from 
Anthropic's official quickstart
https://platform.claude.com/docs/en/agent-sdk/quickstart
, and it demonstrates the core concepts you'll use in every agent you build.
Creating the Project Structure
First, create a file with some intentional bugs for the agent to work with. Save this as 
utils.py
 in your project directory:
python Copy
def calculate_average(numbers):
    total = 0
    for num in numbers:
        total += num
    return total / len(numbers)


def get_user_name(user):
    return user["name"].upper()

Both functions have edge-case bugs: 
calculate_average
 will crash on an empty list (division by zero), and 
get_user_name
 will throw a 
KeyError
 if the "name" key doesn't exist.
Writing the Agent Loop with query()
Now create your agent script. Save this as 
agent.py
 :
python Copy
import asyncio
from claude_agent_sdk import query, ClaudeAgentOptions, AssistantMessage, ResultMessage

async def main():
    async for message in query(
        prompt="Review utils.py for bugs that would cause crashes. Fix each bug and explain what you changed.",
        options=ClaudeAgentOptions(
            allowed_tools=["Read", "Edit", "Glob"],
            permission_mode="acceptEdits"
        )
    ):
        if isinstance(message, AssistantMessage):
            for block in message.content:
                if hasattr(block, "text"):
                    print(block.text)
        elif isinstance(message, ResultMessage):
            print(f"\nAgent finished: {message.subtype}")

asyncio.run(main())

Run it with 
python agent.py
 , and watch what happens. The agent will read 
utils.py
 , identify both bugs, edit the file with fixes, and explain each change. No manual tool execution on your part.
Understanding Messages and Streaming Output
The 
query()
 function is the main entry point for the 
Claude Agent SDK
https://platform.claude.com/docs/en/agent-sdk/python
. It returns an 
async
 iterator that streams messages as Claude works. Each iteration yields one of several message types: 
AssistantMessage
 (Claude's reasoning or text output), 
ToolUseBlock
 (a tool being called), or 
ResultMessage
 (the final outcome).
The options parameter is where you configure agent behavior. In our example, 
allowed_tools
 restricts Claude to reading, editing, and searching files. The 
permission_mode="acceptEdits"
 setting auto-approves file changes so the agent can work autonomously without prompting you for confirmation on every edit.
You can also pass a 
system_prompt
 to shape the agent's role and behavior, a cwd to set the working directory, and 
max_turns
 to limit how many reasoning steps the agent can take.
How Do You Add Custom Tools to a Claude Agent?
The built-in tools cover file operations and web search, but most production agents need to interact with external APIs, databases, or internal services. This is where custom tools and MCP come in, and it's one of the most powerful aspects of the entire SDK.
Built-in Tools vs. Custom MCP Tools
Built-in tools like Read, Write, Bash, and WebSearch are ready to use immediately — you just include them in 
allowed_tools
 . Custom tools, on the other hand, are Python or TypeScript functions that you define and expose to Claude via in-process MCP servers. They run directly within your application, which means no subprocess management, no IPC overhead, and simpler deployment.
For those who are more technically inclined and want to build standalone MCP servers, take a look at our guide on 
building your own MCP server in TypeScript
https://shinzo.ai/blog/how-to-build-an-mcp-server-in-typescript
.
Building an In-Process MCP Server with Custom Tools
Here's a practical example. Let's say you're building an agent that needs to look up customer data. You can define a custom tool and wire it up with just a few lines of code:
python Copy
from claude_agent_sdk import tool, create_sdk_mcp_server, ClaudeAgentOptions, ClaudeSDKClient

# Define a custom tool
@tool("lookup_customer", "Look up customer details by email", {"email": str})
async def lookup_customer(args):
    # In production, this would query your database
    customers = {
        "alice@example.com": {"name": "Alice", "plan": "Enterprise", "mrr": 2500},
        "bob@example.com": {"name": "Bob", "plan": "Pro", "mrr": 49},
    }
    customer = customers.get(args["email"])
    if customer:
        return {"content": [{"type": "text", "text": f"Customer: {customer}"}]}
    return {"content": [{"type": "text", "text": "Customer not found"}]}

# Create an in-process MCP server
server = create_sdk_mcp_server(
    name="crm-tools",
    version="1.0.0",
    tools=[lookup_customer]
)

# Use it with the agent
options = ClaudeAgentOptions(
    mcp_servers={"crm": server},
    allowed_tools=["mcp__crm__lookup_customer", "Read"],
    permission_mode="acceptEdits"
)

async with ClaudeSDKClient(options=options) as client:
    await client.query("Look up the customer alice@example.com and summarize their account.")
    async for msg in client.receive_response():
        print(msg)

The naming convention for custom tools follows the pattern 
mcp__<server-name>__<tool-name>
 . So a tool named 
lookup_customer
 in a server named crm becomes 
mcp__crm__lookup_customer
 . This makes it straightforward to control exactly which tools Claude can access.
Extending Your Agent with MCP Server Integrations
Beyond in-process custom tools, the Claude Agent SDK supports connecting to external MCP servers. This is where the entire MCP ecosystem opens up — you can connect to databases, project management tools, communication platforms, and more through 
standardized MCP connectors
https://platform.claude.com/docs/en/agent-sdk/custom-tools
.
Connecting External MCP Servers
External MCP servers communicate via stdio (for local processes) or HTTP/SSE (for remote services). Here's how to connect an external filesystem server alongside your custom tools:
python Copy
options = ClaudeAgentOptions(
    mcp_servers={
        "crm": sdk_server,  # Your in-process server
        "filesystem": {      # External MCP server
            "type": "stdio",
            "command": "npx",
            "args": ["-y", "@modelcontextprotocol/server-filesystem", "/tmp/workspace"]
        }
    }
)

You can mix and match SDK servers and external servers in the same configuration. The agent treats them all the same — it just sees a unified set of tools it can call.
Configuring Permissions and Safety Hooks
When you're deploying agents that interact with real systems, security matters. The SDK provides fine-grained permission controls and hook functions that let you intercept tool calls before they execute. This is especially important when following 
MCP server security best practices
https://shinzo.ai/blog/mcp-server-security-guide
 in production environments.
python Copy
options = ClaudeAgentOptions(
    allowed_tools=["Read", "Glob", "mcp__crm__lookup_customer"],
    permission_mode="default",  # Prompts for approval
    can_use_tool=my_permission_callback  # Custom logic
)

You can implement a 
can_use_tool
 callback that applies rate limiting, blocks dangerous operations, or logs every tool invocation for audit purposes. The SDK also supports pre- and post-tool-use hooks for validation and monitoring.
Why Does Your AI Agent Need Observability?
I've seen a lot of developers get excited about building agents, ship a prototype, and then have no idea what's happening when things go wrong in production. AI agents are fundamentally different from traditional software — they're non-deterministic, they make autonomous decisions, and they can fail silently in ways that are incredibly hard to debug without the right tooling.
The Non-Deterministic Problem: Why Agents Fail Silently
Traditional software follows predictable code paths. When something breaks, you get a stack trace. AI agents, on the other hand, might call the wrong tool, hallucinate a response, get stuck in a reasoning loop, or consume far more tokens than expected — all without throwing a single error. According to 
OpenTelemetry's research on AI agent observability
https://opentelemetry.io/blog/2025/ai-agent-observability/
, the non-deterministic nature of agents means telemetry isn't just useful for monitoring — it serves as a critical feedback loop for continuously improving agent quality.
This is exactly why observability can't be an afterthought. The more autonomous your agent, the more you need visibility into what it's actually doing.
What Should You Monitor in a Claude Agent?
At minimum, you should be tracking tool call frequency and success rates, token consumption per session, latency across the agent loop, error rates and failure patterns, and context window utilization. For agents built on MCP, you also want visibility into which MCP tools are being called, how often, and whether they're returning expected results.

Platform developers using Shinzo have transparently tracked over 22,000 MCP server calls per month and easily ported that data to OpenTelemetry for further analysis.

What's Next — Taking Your Agent to Production
Building a working agent is the easy part. Taking it to production is where the real engineering starts.
From Prototype to Production-Ready Agent
A few things change when you move from local development to production deployment. You'll want to implement proper error handling (the SDK provides 
CLINotFoundError
 , 
ProcessError
 , and 
CLIJSONDecodeError
 for catching common failure modes), configure sandboxing to isolate agent processes, set up session management for multi-turn conversations, and define clear boundaries for what your agent can and cannot do.
The Claude Agent SDK supports subagents for parallelizing complex tasks, structured JSON output for integrating with downstream systems, and checkpointing for saving agent progress and enabling rollback during development.
Keeping Your Agent Reliable at Scale
The more your agent does, the more you need to understand what it's doing. We recommend setting up observability from the very first deployment — not after something breaks. Start with 
effortless MCP server analytics with Shinzo
https://shinzo.ai/blog/shinzo-signoz-effortless-mcp-server-analytics
 to get baseline visibility into your agent's MCP interactions, then build custom dashboards and alerts as your use case matures.
The Shinzo TypeScript instrumentation package averages 4,500 downloads per month, which is a strong signal that the developer community sees value in having dedicated MCP observability tooling rather than trying to bolt traditional APM solutions onto agentic workflows.
Wrapping Up
Building an AI agent with the Claude Agent SDK is surprisingly straightforward — install the package, define your tools, write a few lines of async Python, and you've got an autonomous agent that can read, write, search, and execute on your behalf. The real challenge isn't getting it to work. It's keeping it reliable, observable, and safe once it's handling real workloads.
To summarize: start with the official SDK and built-in tools to prototype quickly, extend your agent with custom MCP tools for domain-specific capabilities, and instrument everything with observability from day one.
