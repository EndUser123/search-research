What Claude Code Hooks Actually Are

Think of hooks as tripwires. You plant them at specific points in Claude Code’s lifecycle, and they fire deterministic scripts whenever the AI takes an action. The key word is 

deterministic

. The AI is probabilistic — — it might or might not flag a security issue. A hook always runs. Always enforces. Always blocks when you tell it to.

Claude Code’s hook system now supports 21+ lifecycle events and 4 handler types (command, HTTP, prompt, and agent). For code review, two events matter most:

PreToolUse

 — — fires 

before

 Claude executes a tool (like editing a file or running a command). Return exit code 2 to block the action. The stderr message gets fed back to Claude so it can adjust.

PostToolUse

 — — fires 

after

 a tool call succeeds. Run linters, check for anti-patterns, log what changed.

The exit code contract is simple:

Exit 0:

 Proceed.

Exit 2:

 Block. Stderr becomes Claude’s feedback.

Any other code:

 Proceed, but stderr gets logged.

One important nuance:  PreToolUse  command hooks communicate 

only

 via exit codes. Stdout from these hooks is not read by Claude Code. The  systemMessage  JSON output pattern you will see later is for  PostToolUse  hooks, where it surfaces warnings in Claude's context. Do not mix these up --- the exit code is your only lever for blocking.

This is what separates hooks from prompt-based guardrails. You are not asking the LLM to please maybe check for SQL injection. You are running a bash script that greps for it and hard-blocks the operation if found.

Two matchers on  PreToolUse  --- one for  Bash  commands, one for  Edit  operations. Both route to the same gate script. Two matchers on  PostToolUse  ---  Edit  and  Write  both trigger the post-review checks after code changes land.

The  timeout  field is your safety net. If the hook script hangs, it times out and the operation proceeds. Set this low for pre-checks (10 seconds) and slightly higher for post-checks that run linters (30 seconds).

The PreToolUse Gate: Blocking Dangerous Operations

This is the bouncer. It reads the tool invocation from stdin (JSON), checks for patterns you have defined as dangerous, and either allows (exit 0) or blocks (exit 2) the operation.

#!/usr/bin/env bash 
 # review-gate.sh — PreToolUse hook that blocks dangerous patterns 
 # Exit 0 = allow, Exit 2 = block (message on stderr sent to Claude) set -euo pipefail INPUT=$(cat) TOOL_NAME=$(echo "$INPUT" | jq -r '.tool_name // empty') 
 TOOL_INPUT=$(echo "$INPUT" | jq -r '.tool_input // empty') # ── Bash command checks ────────────────────────────────────────────── 
 if [[ "$TOOL_NAME" == "Bash" ]]; then 
  COMMAND=$(echo "$TOOL_INPUT" | jq -r '.command // empty')  # Block destructive git operations 
  if echo "$COMMAND" | grep -qE 'git\s+(push\s+--force|reset\s+--hard|clean\s+-f)'; then 
  echo "Blocked: destructive git command detected — $COMMAND" >&2 
  exit 2 
  fi  # Block secret file access 
  if echo "$COMMAND" | grep -qE '\.(env|pem|key|secret)'; then 
  echo "Blocked: command accesses sensitive file pattern — $COMMAND" >&2 
  exit 2 
  fi  # Block rm -rf on broad paths 
  if echo "$COMMAND" | grep -qE 'rm\s+-rf\s+(/|~|\.\.)'; then 
  echo "Blocked: dangerous recursive delete — $COMMAND" >&2 
  exit 2 
  fi 
 fi # ── Edit/Write file path checks ────────────────────────────────────── 
 if [[ "$TOOL_NAME" == "Edit" || "$TOOL_NAME" == "Write" ]]; then 
  FILE_PATH=$(echo "$TOOL_INPUT" | jq -r '.file_path // empty')  # Block edits to CI config (require manual review) 
  if echo "$FILE_PATH" | grep -qE '\.github/workflows/'; then 
  echo "Blocked: CI workflow edits require manual review — $FILE_PATH" >&2 
  exit 2 
  fi  # Block edits to lock files 
  if echo "$FILE_PATH" | grep -qE '(package-lock|yarn\.lock|poetry\.lock|Pipfile\.lock)'; then 
  echo "Blocked: lock file edits are not allowed — $FILE_PATH" >&2 
  exit 2 
  fi 
 fi # All checks passed — allow the operation 
 # Exit 0 signals Claude Code to proceed. No stdout needed for PreToolUse hooks. 
 exit 0

What this catches:

Destructive git commands

 — —  git push --force ,  git reset --hard ,  git clean -f . The AI cannot blow away your history.

Secret file access

 — — anything touching  .env ,  .pem ,  .key , or  .secret  files. Credentials stay out of the blast radius.

Dangerous deletes

 — —  rm -rf / ,  rm -rf ~ ,  rm -rf .. . Self-explanatory.

CI workflow modifications

 — — edits to  .github/workflows/  are blocked. Your CI pipeline is too important for unsupervised changes.

Lock file edits

 — —  package-lock.json ,  yarn.lock ,  poetry.lock ,  Pipfile.lock . These should only change via dependency commands, not direct edits.

When the hook blocks an operation, the stderr message flows back to Claude as feedback. The AI sees “Blocked: destructive git command detected” and adjusts its approach — — without you intervening.

The PostToolUse Check: Catching Anti-Patterns After Edits

After Claude edits or writes a file, this script runs language-specific checks and surfaces warnings:

#!/usr/bin/env bash 
 # post-review.sh — PostToolUse hook that runs checks after code changes 
 # Logs what changed, runs linting, flags potential issues set -euo pipefail INPUT=$(cat) 
 TOOL_NAME=$(echo "$INPUT" | jq -r '.tool_name // empty') 
 TOOL_INPUT=$(echo "$INPUT" | jq -r '.tool_input // empty') LOG_FILE="hooks/review.log" 
 TIMESTAMP=$(date -u +"%Y-%m-%dT%H:%M:%SZ") # ── Extract file path ──────────────────────────────────────────────── 
 FILE_PATH="" 
 if [[ "$TOOL_NAME" == "Edit" || "$TOOL_NAME" == "Write" ]]; then 
  FILE_PATH=$(echo "$TOOL_INPUT" | jq -r '.file_path // empty') 
 fi # ── Log the change ─────────────────────────────────────────────────── 
 echo "[$TIMESTAMP] $TOOL_NAME: $FILE_PATH" >> "$LOG_FILE" # ── Run language-specific checks ───────────────────────────────────── 
 WARNINGS="" if [[ "$FILE_PATH" == *.py ]]; then 
  # Check for common Python anti-patterns 
  if grep -n 'import \*' "$FILE_PATH" 2>/dev/null; then 
  WARNINGS+="WARNING: Wildcard import detected in $FILE_PATH\n" 
  fi 
  if grep -n 'except:' "$FILE_PATH" 2>/dev/null; then 
  WARNINGS+="WARNING: Bare except clause in $FILE_PATH\n" 
  fi 
  if grep -n 'eval(' "$FILE_PATH" 2>/dev/null; then 
  WARNINGS+="WARNING: eval() usage detected in $FILE_PATH — potential security risk\n" 
  fi 
  # Run ruff if available 
  if command -v ruff &>/dev/null; then 
  LINT_OUTPUT=$(ruff check "$FILE_PATH" 2>&1 || true) 
  if [[ -n "$LINT_OUTPUT" ]]; then 
  WARNINGS+="LINT:\n$LINT_OUTPUT\n" 
  fi 
  fi 
 fi if [[ "$FILE_PATH" == *.js || "$FILE_PATH" == *.ts ]]; then 
  # Check for common JS/TS anti-patterns 
  if grep -n 'console\.log' "$FILE_PATH" 2>/dev/null; then 
  WARNINGS+="WARNING: console.log left in $FILE_PATH\n" 
  fi 
  if grep -n 'any;' "$FILE_PATH" 2>/dev/null; then 
  WARNINGS+="WARNING: TypeScript 'any' type in $FILE_PATH\n" 
  fi 
 fi # ── Return results ─────────────────────────────────────────────────── 
 if [[ -n "$WARNINGS" ]]; then 
  # Surface warnings as a system message Claude will see 
  jq -n --arg warnings "$WARNINGS" '{ 
  "continue": true, 
  "systemMessage": ("Post-edit review found issues:\n" + $warnings) 
  }' 
 else 
  echo '{"continue": true}' 
 fi exit 0

Notice the  systemMessage  field in the JSON output. When the hook detects issues, it surfaces them as a message Claude will see in context. The operation is not blocked (exit 0,  "continue": true ), but Claude gets immediate feedback: "You just wrote a bare  except:  clause. Fix it."

This is a  PostToolUse  hook --- unlike  PreToolUse , the stdout JSON 

is

 read by Claude Code here. The  systemMessage  gets injected into the conversation context so the AI can self-correct on its next turn.

For Python files, the hook checks for wildcard imports, bare except clauses, and  eval()  usage. If  ruff  is installed, it runs a full lint pass. For JavaScript/TypeScript, it flags leftover  console.log  statements and  any  types.

Every change gets timestamped in  hooks/review.log  --- your audit trail.

Two jobs. The  auto-review  job fires on every PR open or push. The  on-demand  job responds when anyone comments  @claude  on a PR --- asking a specific question, requesting a deeper look at a file, or requesting a re-review after changes.

The prompt is deliberately scoped. It checks four categories — — security, correctness, performance, and error handling — — and outputs in a structured format. The last line matters: 

“If everything looks good, say so — — don’t invent problems.”

 This directly addresses the false positive fatigue that kills adoption. The 45% of developers who cite “AI solutions that are almost right, but not quite” as their top frustration (Stack Overflow 2025) encounter that frustration because tools are incentivized to always find something.

The  --max-turns 5  flag limits how deep the AI goes. For the on-demand job, it gets 10 turns to handle follow-up questions. The  --allowedTools  flag locks down what Claude can do --- it can read diffs and post comments, but it cannot modify code or push changes. This is the security posture the rest of the article advocates.

Every fix follows a pattern: replace implicit trust with explicit validation. Parameterized queries instead of f-strings. Environment variables instead of hardcoded secrets. AST parsing with a whitelisted operator visitor instead of  eval()  on raw input. Specific exception types instead of bare  except: .

The safe math evaluator deserves a note. The  compile + eval  pattern you will see in many tutorials --- even with  {"__builtins__": {}}  --- has known escape vectors via Python's introspection system ( ().__class__.__mro__[1].__subclasses__()  and friends). The AST approach above parses the expression into a syntax tree and only evaluates nodes whose operator type is in an explicit whitelist. No  eval()  call ever touches the raw input. This is the correct pattern for a calculator endpoint.

The  PostToolUse  hook catches the bare  except:  and  eval()  patterns via grep. The GitHub Actions review catches the SQL injection and hardcoded secret via semantic analysis.

What Practitioners Should Do Now

Start with the hooks, not the Actions workflow. The hooks give you immediate value during local development — — every  eval() , every bare except, every hardcoded secret gets flagged before it ever reaches a PR. The GitHub Actions layer is your safety net for what slips through.

Scope your AI reviews narrowly. The tools that fail are the ones that try to review everything — — architecture, style, performance, security, business logic — — in one pass. The prompt in this tutorial checks four specific categories. That is deliberate. AI code review works best as a “second pair of eyes” for patterns it can reliably detect: security vulnerabilities, common bugs, and missing error handling. Repositories using AI-assisted review show 32% faster merge times and 28% fewer post-merge defects when the tool is scoped to what it does well.

Do not remove human reviewers. This bot handles the 80% of routine checks so your human reviewers can focus on the 20% that requires judgment: architecture decisions, business logic correctness, and intentional tradeoffs. The Stack Overflow survey found 75% of developers still prefer asking another person when uncertain about AI outputs. That instinct is correct.

Watch the false positive rate. If your team starts dismissing bot comments without reading them, your scope is too broad. The “cry wolf” effect is the number one reason teams abandon AI code review tools. Tighten the prompt. Add the “don’t invent problems” instruction. Measure signal-to-noise weekly.

Treat hooks as your compliance layer. Every hook invocation is logged with a timestamp. Every blocked operation has a reason. This is your audit trail for SOC 2, for security reviews, for the inevitable “who approved this change” question.

Strategic Takeaways

Hooks are the missing piece between probabilistic AI and deterministic CI/CD.

 They guarantee enforcement regardless of what the LLM decides to do, which is why they belong in every team’s code review stack.

Scope beats sophistication.

 A review bot that checks four categories reliably outperforms one that checks twenty categories unreliably — — the 45% of developers frustrated by “almost right” AI output proves this.

The PreToolUse/PostToolUse split mirrors defense in depth.

 Gate dangerous operations before they happen, then verify the output after — — the same pattern security teams have used for decades, now applied to AI tooling.
