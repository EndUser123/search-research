256 GCM encryption to store all upstream provider keys in SQLite at rest and decryption only happens in memory at the exact moment a request needs to be forwarded the decrypted key is never written events this architecture means that provider specific quirks authentication patterns and response formats are all handled inside the adapter layer and never leak into the routing logic the router does not care which provider it is talking to it just calls the interface and gets back tokens automatic failover is what makes the proxy resilient in practice if the selected provider returns a 429 rate limit error a 5xx server error or times out the router does not surface that failure to the client instead it immediately puts that specific key on a short cool down marks it as temporarily unavailable and retries the request on the next qualifying model in the fallback chain this retry loop runs up to 20 times before the proxy gives up and returns an error to the client in practice with a well-configured chain across multiple providers you're unlikely to exhaust 20 retries under normal usage conditions the failover is completely transparent the client receives a successful response and has no visibility into how many providers were tried before one succeeded the rate limit ledger is what makes the router's decisions accurate rather than optimistic rather than discovering that a key is rate limited by actually hitting a 429 the ledger maintains live counters for every key across all four rate limit dimensions these counters are held in memory for speed and periodically backed to SQLite for persistence across restarts when the router is evaluating whether a key qualifies for a request it checks these counters before making any network call if the counters show that a key is within two requests of its permitted cap the router skips it preemptively and moves to the next option when a 429 does come back from provider that information feeds into the ledger and the key is
