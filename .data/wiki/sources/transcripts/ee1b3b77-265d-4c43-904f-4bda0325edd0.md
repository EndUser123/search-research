# Unified Technical Specification for Claude Code Plugin Lifecycles: Deterministic State Machines, Session Boundary Isolation, and Quality Gate Hook Remediation
Unified Technical Specification for Claude Code Plugin Lifecycles: Deterministic State Machines, Session Boundary Isolation, and Quality Gate Hook Remediation
The operational reliability of agentic software engineering platforms depends on the strict decoupling of deterministic validation systems from the probabilistic reasoning of Large Language Models [cite: 1]. Within the Claude Code ecosystem, this separation is achieved through a deterministic state machine managed by the client execution harness [cite: 1, 2]. Rather than relying on the model to self-evaluate its performance, the harness intercepts lifecycle transitions and executes structured, event-triggered hooks to enforce project standards, verify security parameters, and validate code quality [cite: 1, 3, 4].
This technical specification details the architectural mechanics of Claude Code plugin lifecycles, focusing on deterministic state machines, session boundary isolation, and the structural execution rules of the 
Stop
 hook. It analyzes four critical failure classes that impact multi-turn agentic environments and provides production-grade, zero-drift engineering solutions.

Section 2: Deterministic State Machines & Session Boundary Isolation
The Claude Code harness executes inside an event-driven generator loop, yielding structured state events to the console while processing inputs sequentially [cite: 13]. Although the model's trajectory is non-deterministic, the transition from state to state is managed by a strict state-machine contract [cite: 1].
This contract ensures that tool execution, context compaction, and session termination occur within sandboxed limits [cite: 1, 2, 13].

Failure Class 1: The Identity-Binding Gap (Writer vs. Reader)
Multi-turn agentic workflows frequently require access to the authoritative 
session_id
 to correlate external operations, write to database stores, or validate logs [cite: 10, 14]. However, tools and hooks executed inside the 
Bash
 shell context run in isolated subprocesses where the default environment variables 
CLAUDE_SESSION_ID
 and 
WT_SESSION
 are unpopulated, empty, or untrusted [cite: 15, 16].
While the static template substitution 
${CLAUDE_SESSION_ID}
 is supported inside Markdown skill templates, this substitution occurs exclusively during prompt rendering and is unavailable to background shell environments or decoupled execution scripts [cite: 14, 16, 17].
To bridge this identity-binding gap, orchestrators must exploit the standard input stream of the 
SessionStart
 lifecycle event [cite: 3, 14, 15]. During this initialization phase (the writer phase), the harness passes a JSON envelope to standard input containing the authoritative 
session_id
 [cite: 3, 14, 15].
By reading this stream, an execution hook can capture the true session identifier and persist it to the 
$CLAUDE_ENV_FILE
 [cite: 15, 18]. This temporary file acts as an environment provider; its contents are evaluated and injected into the shell context of all subsequent 
Bash
 tool calls made during the conversation [cite: 15, 18].
To align the writer side with the subsequent reader phase (the validation checks executed during 
Stop
 hooks), the validation script must programmatically reconstruct the file path of the active transcript [cite: 5, 14]. Claude Code stores these transcripts under a project-isolated, slugified directory schema [cite: 5, 6].
The exact file path is calculated using the following structural rule:
\text{Transcript Path} = \text{HOME} + \text{"/.claude/projects/"} + \text{Slugify}(\text{CWD}) + \text{"/"} + \text{Session ID} + \text{".jsonl"}
The directory slug representing the current working directory replaces all non-alphanumeric characters with a hyphen [cite: 5, 6]. For example, a project initiated inside 
/home/node/service-core
 translates to the directory slug 
-home-node-service-core
 [cite: 5].
By mapping this path during 
SessionStart
 and exporting it to the environment file, the reader phase of a 
Stop
 hook can parse the active transcript 
.jsonl
 directly [cite: 5, 6, 14]. This enables the validation gate to verify the history of user prompts and tool actions against the authoritative ID injected by the harness [cite: 5, 14].

Section 3: Hidden Dispatch Surfaces and Frontmatter Duplication
Evaluation Hierarchy and Priority Resolution
As configurations scale, overlapping rules defined globally, project-locally, or inside dynamic skills can cause execution conflicts [cite: 19, 20]. Claude Code resolves these instructions through a multi-tiered evaluation hierarchy [cite: 19, 20, 21].
While standard project configurations (such as permissions and model selections) follow a clean override structure where the highest-priority file replaces the lowest, lifecycle hooks behave differently [cite: 19, 20]. The execution harness uses a 
merged execution model
 for hooks [cite: 20].
When an event fires, the harness aggregates all registered hook handlers across global, local, and plugin scopes, and executes them [cite: 20].
Failure Class 2: Hidden Dispatch Surfaces & Frontmatter Duplication
A critical vulnerability occurs when a project defines global 
Stop
 hooks inside settings files while concurrently loading specialized skills (
SKILL.md
) that contain local 
hooks:
 declarations in their YAML frontmatter [cite: 20, 22].
The loader optimizes context overhead by scanning skill directories at startup, loading only the 
name
 and 
description
 of each skill (capped at approximately 100 tokens per skill) into memory [cite: 23, 24]. When a user prompt matches a skill's description, the full 
SKILL.md
 body and its frontmatter-scoped hooks are loaded on demand [cite: 17, 24, 25].
This lazy loading introduces a hidden dispatch surface [cite: 20, 22]. If a skill contains a localized validation hook while a project-level 
settings.json
 enforces a global 
Stop
 hook, both will execute during a turn termination [cite: 11, 20].
Additionally, many platform versions suffer from an integration bug (Issue #19225) where 
Stop
 hooks defined inside 
SKILL.md
 frontmatter fail to execute natively, even when corresponding 
PreToolUse
 hooks in the same file trigger correctly [cite: 22]. This failure can leave skill-specific assertions unverified [cite: 22].
When background checks run alongside active skill loops, conflicting directives can create an infinite execution loop [cite: 11, 12, 20]. For instance, if a local skill directs the model to format changes using a specific markdown convention, but a global 
Stop
 hook blocks termination because it detects file modifications that have not been compiled, the model will repeatedly attempt to satisfy both rules [cite: 11, 12].
This triggers a cascade of tool calls and prompt re-entries, continuing until it hits the consecutive block ceiling [cite: 26, 27].

The interaction between the Claude Code harness and command-type hooks relies on structured exit-code evaluation and standard output parsing [cite: 1, 3, 11].

Failure Class 3: The Deterministic Evaluation Re-Activation Protocol
When Claude finishes responding, the 
Stop
 event triggers [cite: 1, 3, 11]. The hook evaluates the outcome and returns one of two primary output shapes [cite: 3, 11]:
Approval / Silent Continuation
: Returning an empty JSON object 
{}
 or omitting the 
decision
 field on exit code 0 indicates approval, allowing the session turn to terminate normally [cite: 3, 8, 11].
Deterministic Block
: Returning 
{"decision": "block", "reason": "..."}
 on exit code 0 explicitly prevents stopping, sending the reason string back to the model as feedback to resume work [cite: 3, 11, 12].
The underlying runtime mechanism processes exit codes to bypass the native, in-binary LLM evaluator loop entirely, ensuring deterministic enforcement [cite: 1, 11].
When a command hook exits with 
exit code 2
, the harness intercepts execution immediately [cite: 1, 3, 11]. It discards standard output, captures the standard error (
stderr
) stream, and redirects it directly into the next model turn as a system-level reminder [cite: 1, 3, 11].
This injection forces the model to re-activate [cite: 1, 11]. Because the feedback is fed directly as system context rather than a probabilistic prompt, the model has no choice but to resume execution to satisfy the failing criteria [cite: 1, 11].
To prevent infinite loops during forced continuation, hooks must parse the standard input payload and check the 
stop_hook_active
 (or camelCase 
stopHookActive
) field [cite: 3, 12, 26]. When this field is 
true
, it indicates that the model was already blocked on a previous attempt and is currently trying to exit again [cite: 12, 26].
The hook must evaluate this flag and exit with a code 0 approval [cite: 11, 12, 26]. If it fails to yield, the harness consecutive block cap will override the hook and forcibly end the turn after 9 consecutive blocks [cite: 26, 27].

Section 5: The Stale-Reminder Persistence Loop
Failure Class 4: The Stale-Reminder Persistence Loop
Local validation or checklist hooks (such as checking for untracked database migrations or verifying code formatting) often suffer from a persistence failure [cite: 10, 30].
If a hook dynamically checks a condition and injects reminders or prompt modifications on every turn, the model can become trapped in a 
Stale-Reminder Loop
 [cite: 30]. Even after resolving the issue, the prompt may continue to append the advisory notice on subsequent actions like 
grep_references
 or 
file_deletion
 [cite: 30].
This persistence loop also damages the client's prompt caching mechanics [cite: 30]. Claude Code optimizes API latency and cost by establishing prompt cache boundaries (e.g., 
SYSTEM_PROMPT_DYNAMIC_BOUNDARY
) to keep the session prefix static [cite: 30, 31].
If a custom hook injects variable text, changing tokens, or shifting checklist values directly into historical user prompts turn-over-turn, it introduces 
byte-drift
 [cite: 30].
Turn N:   [Static Prefix Context] [Hook Reminder: "Fix style"] ──► Cache Hit (Prefix Cached)
                                                                       │
Turn N+1: [Static Prefix Context] [Hook Reminder: "Style Fixed"] ──► Cache Bust (Prefix Drifted) [cite: 30]

This byte-drift invalidates the server-side cache [cite: 30]. The engine is forced to re-read and compile the entire conversation history from scratch, causing prompt creation costs to spike by tens or hundreds of thousands of tokens [cite: 30].
To resolve both the persistence loop and prompt-cache invalidation, developers must implement a 
Zero-Drift State Cache
 [cite: 10, 30]. This architectural pattern decouples checklist state tracking from the active conversation history [cite: 10, 30].
Instead of injecting dynamic text into prompts on every turn, the hook maintains an external, session-isolated state file keyed to the active 
session_id
 on disk [cite: 10, 30].
When the validation condition is met, the state file marks the item as 
satisfied
 [cite: 10, 30]. On all subsequent turns, the hook checks this cached value and exits with a static, empty JSON payload 
{}
 [cite: 8, 30]. This maintains perfect byte-stability across history, preserving the prefix cache while preventing the reminder from re-triggering [cite: 30].

Implementation 1: Safe Session Identity Binder and Path Normalizer
This Bash hook runs during the 
SessionStart
 lifecycle event [cite: 3, 11]. It captures standard input, extracts the authoritative session identifier, slugifies the project path, and binds them to the active subprocess environment via 
$CLAUDE_ENV_FILE
 [cite: 14, 15, 18].
#!/usr/bin/env bash
# File: ~/.claude/hooks/session-identity-binder.sh
set -euo pipefail

# Capture standard input JSON payload passed by the Claude Code harness
INPUT_PAYLOAD=$(cat)

# Extract the authoritative session identifier using jq
SESSION_ID=$(echo "$INPUT_PAYLOAD" | jq -r '.session_id // empty')

if [ -z "$SESSION_ID" ]; then
    syslog -s -l err "Claude Code Identity Gate: Failed to acquire session_id from stdin."
    exit 1
fi

# Calculate CWD and create a URL-safe directory slug replacing non-alphanumeric chars
RAW_CWD=$(echo "$INPUT_PAYLOAD" | jq -r '.cwd // empty')
if [ -z "$RAW_CWD" ]; then
    RAW_CWD=$(pwd)
fi

# Sluggify algorithm: replace all slashes and non-alphanumeric values with hyphens
PROJECT_SLUG=$(echo "$RAW_CWD" | sed -e 's/[^a-zA-Z0-9]/-/g' -e 's/-\{2,\}/-/g')

# Build the definitive transcript JSONL path
TRANSCRIPT_PATH="${HOME}/.claude/projects/${PROJECT_SLUG}/${SESSION_ID}.jsonl"

# Persist environment bindings to the session file
if [ -n "${CLAUDE_ENV_FILE:-}" ] && [ -f "$CLAUDE_ENV_FILE" ]; then
    {
        echo "export CLAUDE_SESSION_ID=\"${SESSION_ID}\""
        echo "export CLAUDE_PROJECT_SLUG=\"${PROJECT_SLUG}\""
        echo "export CLAUDE_TRANSCRIPT_PATH=\"${TRANSCRIPT_PATH}\""
    } >> "$CLAUDE_ENV_FILE"
fi

# Return a silent success payload to ensure no user-facing output disruptions
jq -n \
  --arg sid "$SESSION_ID" \
  --arg path "$TRANSCRIPT_PATH" \
  '{
    "hookSpecificOutput": {
      "hookEventName": "SessionStart",
      "additionalContext": "System Identity Enforced. Session ID registered: \($sid). Log Target: \($path)"
    }
  }'

Implementation 2: Deterministic Stop-Hook Quality Gate and Validation Loop
This Python validation script runs during the 
Stop
 event [cite: 3, 11]. It enforces syntax verification and test standards, parses the 
stop_hook_active
 flag to prevent infinite loops, and outputs decision payloads to guide the agent [cite: 11, 12, 26].
#!/usr/bin/env python3
# File: .claude/hooks/stop-quality-gate.py
import json
import sys
import subprocess
from pathlib import Path

def main():
    try:
        # Load the lifecycle event payload from standard input
        input_payload = json.load(sys.stdin)
    except Exception as err:
        sys.stderr.write(f"Validator failure: Failed to parse input JSON: {str(err)}\n")
        sys.exit(1)

    # CRITICAL: Prevent infinite validation loops by checking the continuation state
    if input_payload.get("stop_hook_active") or input_payload.get("stopHookActive"):
        # Exit with approval to break the execution cycle
        print(json.dumps({}))
        sys.exit(0)

    # Define validation commands, timeout limits, and error messages
    validation_pipeline = [
        {
            "command": ["npx", "eslint", "src/", "--max-warnings=0"],
            "timeout": 45,
            "error_msg": "Codebase contains unresolved lint errors."
        },
        {
            "command": ["npm", "run", "typecheck"],
            "timeout": 60,
            "error_msg": "TypeScript compiler verification failed."
        },
        {
            "command": ["npm", "test", "--", "--passWithNoTests"],
            "timeout": 120,
            "error_msg": "Unit tests failed execution."
        }
    ]

    for stage in validation_pipeline:
        try:
            result = subprocess.run(
                stage["command"],
                capture_output=True,
                text=True,
                timeout=stage["timeout"]
            )
            
            # If a check fails, intercept the stop flow and re-activate the agent
            if result.returncode != 0:
                # Capture stderr for context, falling back to stdout if empty
                execution_log = (result.stderr or result.stdout or "")[-500:]
                block_reason = f"{stage['error_msg']}\n\nExecution log:\n{execution_log}"
                
                # Format block decision payload
                decision_payload = {
                    "decision": "block",
                    "reason": block_reason,
                    "systemMessage": "Quality Gate Intercepted. Continuing session to resolve failures."
                }
                
                print(json.dumps(decision_payload))
                sys.exit(0)
                
        except subprocess.TimeoutExpired:
            print(json.dumps({
                "decision": "block",
                "reason": f"Validation step timed out: {' '.join(stage['command'])}",
                "systemMessage": "Compilation timeout exceeded."
            }))
            sys.exit(0)
        except Exception as err:
            # Fall back to exit code 2 if a structural error occurs
            sys.stderr.write(f"Validation hook failure executing {' '.join(stage['command'])}: {str(err)}\n")
            sys.exit(2)

    # All checks passed successfully; allow session turn termination
    print(json.dumps({}))
    sys.exit(0)

if __name__ == "__main__":
    main()

Implementation 3: Zero-Drift Session-Scoped State Cache Manager
This Python implementation provides a file-based checklist tracker to prevent stale-reminder loops [cite: 10, 26, 30]. It stores state in a local JSON file mapped to the active 
session_id
, ensuring that prompts are only injected when a state is unsatisfied [cite: 10, 26]. Once satisfied, the output remains static, protecting the model's system prompt cache bounds [cite: 30, 31].
#!/usr/bin/env python3
# File: .claude/hooks/zero-drift-advisory.py
import json
import os
import sys
from pathlib import Path

# Set up local cache storage inside the project directory
CACHE_DIR = Path(".claude/state_cache")

def resolve_cache_file(session_id: str) -> Path:
    CACHE_DIR.mkdir(parents=True, exist_ok=True)
    return CACHE_DIR / f"session_{session_id}_state.json"

def main():
    try:
        input_payload = json.load(sys.stdin)
    except Exception as err:
        sys.stderr.write(f"Parser failure: Standard input parsing failed: {str(err)}\n")
        sys.exit(1)

    session_id = input_payload.get("session_id")
    if not session_id:
        # Exit silently if no session identity can be found
        print(json.dumps({}))
        sys.exit(0)

    state_file = resolve_cache_file(session_id)
    
    # Initialize cache file if missing
    if not state_file.exists():
        state_data = {"deprecation_warning_satisfied": False}
        state_file.write_text(json.dumps(state_data))
    else:
        try:
            state_data = json.loads(state_file.read_text())
        except Exception:
            state_data = {"deprecation_warning_satisfied": False}

    # If the check has already been satisfied, return an empty payload to protect the cache
    if state_data.get("deprecation_warning_satisfied"):
        print(json.dumps({}))
        sys.exit(0)

    # Perform analysis: search for deprecated internal library calls inside the workspace
    search_path = Path("src/")
    deprecated_calls_detected = False

    if search_path.exists():
        for file_path in search_path.rglob("*.ts"):
            try:
                content = file_path.read_text()
                if "legacyInternalParser" in content:
                    deprecated_calls_detected = True
                    break
            except Exception:
                pass

    # If deprecations are found, inject the reminder once and persist state
    if deprecated_calls_detected:
        state_data["deprecation_warning_satisfied"] = True
        state_file.write_text(json.dumps(state_data))
        
        # Inject the warning context
        print(json.dumps({
            "hookSpecificOutput": {
                "additionalContext": "WARNING: Deprecated method 'legacyInternalParser' detected in src/. Refactor to use 'modernParser' before completing tasks."
            }
        }))
        sys.exit(0)

    # If no issues are found, return empty JSON to ensure prefix stability
    print(json.dumps({}))
    sys.exit(0)

if __name__ == "__main__":
    main()
