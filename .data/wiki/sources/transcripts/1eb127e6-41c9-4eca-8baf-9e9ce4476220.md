The Ralph Wiggum pattern: automation and persistence for coding agents

The Good Programmer

6 min read · Jan 16, 2026

--

Discover how the Ralph Wiggum pattern is revolutionizing coding agent automation, enabling them to work beyond a single session through a cycle of persistent, deterministic iterations.

Press enter or click to view image in full size

The “Ralph Wiggum” pattern is becoming the default infrastructure for anyone wanting to run a coding agent beyond a single session. The name, derived from The Simpsons character known for his naive persistence, captures the essence of the technique: an infinite loop that repeatedly feeds the same prompt to an AI agent, where progress persists not in the model’s context window but in files and git history.

Two main implementations exist today: the original version by Ryan Carson (

snarktank/ralph

https://github.com/snarktank/ralph

), an essential bash script that orchestrates Amp, and 

Ralph TUI

https://ralph-tui.com/

, a complete orchestrator with a terminal interface, plugins for various agents and trackers, and session management. Both derive from Geoffrey Huntley’s insight, who synthesizes the principle as follows: “

The technique is deterministically bad in an indeterministic world. It’s better to fail predictably than to succeed unpredictably.

”

The execution cycle: what actually happens

Ralph operates in five phases that repeat until completion or until an iteration limit is reached.

Task selection.

 The orchestrator queries the tracker (a prd.json file, Beads, or other backends) and selects the highest-priority task with no blocking dependencies. The task must have  passes: false  to be a candidate. This selection is deterministic: no semantic interpretation, just state and dependencies.

Prompt construction.

 The task is transformed into a prompt via Handlebars templates. This is where context injection occurs: acceptance criteria, quality gates, completed dependencies, notes from previous iterations. The template is customizable, and this is the main lever for adapting Ralph to your stack.

Agent execution.

 Ralph spawns a fresh process of the chosen agent (Claude Code, OpenCode, Amp) with the constructed prompt. Output is streamed in real time. The critical point: each iteration is a fresh instance with clean context. Memory between iterations persists only via git history, progress.txt, and prd.json.

Completion detection.

 The agent signals completion by emitting a specific token:  <promise>COMPLETE</promise> . When the agent produces this output, Ralph TUI recognizes the task is complete and moves to the next one. This token-based detection enables fully autonomous operation. No semantic understanding exists here: it's a protocol, a deterministic signal.

Transition.

 The task is marked as completed in the tracker, the session state is saved, and the cycle restarts.

Anatomy of the PRD: specification as contract

The PRD in the Ralph world is not documentation; it’s input for a compiler. The structure must be parseable: user stories with structured IDs (US-001, US-002…), acceptance criteria as verifiable checklists, quality gates as shell commands.

The 

convert

 phase in Ralph TUI does something important: it extracts quality gates from a dedicated section and appends them to the acceptance criteria of each individual story. This means every task carries its own quality checks with it: no “final test” at project completion exists. Quality is atomic, per-task, non-negotiable.

Example of quality gates to include in the PRD:

## Quality Gates 
 These commands must pass for every user story: 
 - `bun run typecheck` - Type checking 
 - `bun run lint` - Linting 
 - `bun run test` - Test suite

Operational setup: from theory to execution

Installing Ralph TUI:

bun install -g ralph-tui 
 cd your-project 
 ralph-tui setup

The interactive wizard detects installed agents, creates the configuration in  .ralph-tui/config.toml , and installs skills for PRD creation.

Creating the PRD:

ralph-tui create-prd --chat

The AI guides you through questions about objectives, scope, target users, and quality gates. Output: a structured markdown file in  ./tasks/prd-<feature>.md .

Converting to executable tasks:

ralph-tui convert --to json ./tasks/prd-my-feature.md

This produces  prd.json  with user stories ready for autonomous execution.

Starting the loop:

ralph-tui run --prd ./prd.json

Ralph selects the first task, constructs the prompt, spawns the agent, monitors output, detects completion, and moves to the next task. It repeats until the backlog is exhausted or the iteration limit is reached.

Advanced configuration

The  .ralph-tui/config.toml  file controls behavior:

tracker = "json" # json | beads | beads-bv 
 agent = "claude" # claude | opencode 
 maxIterations = 10 # safety limit 
 [agentOptions] 
 model = "sonnet" # opus | sonnet | haiku 
 [errorHandling] 
 strategy = "skip" # retry | skip | abort 
 maxRetries = 3

Available trackers cover different scenarios:  json  to start without external dependencies,  beads  for git-backed issue tracking with hierarchies,  beads-bv  for intelligent selection via dependency graph analysis (PageRank, critical path).

Task sizing: where everything is decided

Each PRD item must be small enough to complete within a context window. If a task is too large, the LLM exhausts its context before finishing and produces subpar code.

Properly sized tasks: adding a database column with migration, creating a UI component on an existing page, updating a server action with new logic, adding a dropdown filter to a list.

Tasks to break down: “build the entire dashboard,” “add authentication,” “refactor the API.”

The operational principle is that the task must be completable in a single agent session without quality degradation. If you cannot describe it in two or three sentences, it probably needs to be split.

Persistent memory: AGENTS.md and progress.txt

Ralph maintains two cross-iteration memory channels.

progress.txt

 (or  .ralph-tui/progress.md ) accumulates notes from each iteration. The last N iterations are injected into the prompt via  {{recentProgress}} . This gives the agent context about what has been done without having to reread the code.

AGENTS.md

 is more interesting: after each iteration, Ralph updates AGENTS.md files with learnings. This is crucial because Amp automatically reads these files, so future iterations (and human developers) benefit from discovered patterns, gotchas, and conventions.

Examples of what to add to AGENTS.md: discovered patterns (“this codebase uses X for Y”), gotchas (“don’t forget to update Z when modifying W”), useful context (“the settings panel is in component X”).

Error handling and recovery

Ralph TUI offers three strategies for errors:  retry  for flaky operations (network issues),  skip  for non-critical tasks,  abort  for workflows where any failure is unacceptable.

Session persistence saves state in  .ralph-tui-session.json : current iteration number, task states, iteration history, active tasks for crash recovery. On resume, Ralph resets stuck "in_progress" tasks to "open" and restarts.

When to use Ralph, when not to

Ralph works best for tasks with clear completion criteria and mechanical execution: large refactors, framework migrations, dependency updates, API version bumps across hundreds of files.

It does not work for work requiring nuanced judgment, deep understanding of a large codebase, or architectural decisions. The technique automates mechanical execution, not decisions about what is worth building.

While the Ralph Wiggum loop, like its eponymous character, maintains a cheerful persistence that allows agents to solve complex bugs through pure iteration, autonomy creates a governance vacuum. The risk is what is called “overbaking”: an agent that cannot exit the loop because it must satisfy a completion promise might enter a “sycophancy loop,” attempting to please the user in destructive ways.

The underlying principle

Ralph embodies an “agile but engineered” logic: PRD as parseable specification, stories as atomic verifiable units, epics as scope containers, convert as per-task quality enforcer, prompt templates as repeatable contracts, the COMPLETE token as a deterministic advancement mechanism.

Cognitive work shifts upstream, into the specification. And the specification still requires that act of translation no parser can perform: transforming an intention into a verifiable criterion. Who writes the quality gates? Who decides what “done” means?

Automating the development loop does not eliminate engineering; it concentrates it at a different point in the pipeline.
