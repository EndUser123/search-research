From One-Shot Generation to Multi-Loop Reasoning

TL;DR:

 One-shot LLM code generation fails silently. By introducing iteration loops at different abstraction levels — inner loops for reasoning refinement, outer loops for execution validation — we build AI systems that reason transparently and validate against reality. This article presents NDLI (Nested Dual-Loop Inference), a practical framework combining structured reasoning capture with test-driven validation.

1. Introduction: The Problem with One-Shot Generation

The era of one-shot LLM code generation is ending.

AI coding assistants have a dirty secret: they fail silently. They generate plausible-looking code that compiles, passes a cursory review, and then breaks at runtime. The root cause isn’t model capability — it’s architecture.

Press enter or click to view image in full size

LLMs reason in transient hidden states. These tensor activations hold the model’s “thought process” during generation, but they vanish the moment the forward pass completes. There’s no audit trail. No opportunity for refinement. No way to ask “wait, did I consider that edge case?”

Press enter or click to view image in full size

The result? We’re gambling. Every prompt is a roll of the dice, hoping the model’s single pass captures all requirements, handles all edge cases, and produces correct code. Sometimes it works. Often it doesn’t.

The cognitive gap is real:

 We can validate syntax (does it compile?) but not intent (why did it build this?). We can check if code runs, but not if the reasoning behind it was sound.

What if we could make the model “think twice”? What if we could capture its reasoning, refine it iteratively, and validate it against real execution before delivering code?

This is the promise of iterative inference.

2. LoopCoder: The Research Foundation

Recent research from Beihang University points the way forward.

LoopCoder

 demonstrated that architectural recurrence — weight-shared transformer blocks that iterate internally — dramatically improves code generation. Their approach is elegantly simple: instead of a single forward pass through the transformer stack, the model loops through certain layers twice.

Press enter or click to view image in full size

How It Works

Traditional transformers process input through a stack of layers once:

Input → Layer 1 → Layer 2 → … → Layer N → Output

LoopCoder introduces weight-shared recurrence:

Input → Layer 1 → Layer 2 → [Loop Back] → Layer 1 → Layer 2 → … → Output

The same weights process the representation twice, allowing the model to refine its internal understanding before committing to output tokens.

The Results

The numbers are compelling. IQuest-Coder-V1, built on LoopCoder principles, achieves:

81.4%

 on SWE-Bench (real-world GitHub issues)

87.0%

 on LiveCodeBench

99.4%

 on CRUXEval

These aren’t incremental improvements — they represent a step change in code generation quality.

Press enter or click to view image in full size

The Key Insight

Models benefit from “thinking twice” before outputting. A single forward pass forces the model to commit to token predictions before fully resolving ambiguities in the input. Recurrence gives the model a second chance to refine its internal representation.

But LoopCoder operates at the architecture level. It requires custom model training, specialized infrastructure, and isn’t accessible to practitioners using off-the-shelf models.

The question becomes:

 Can we achieve similar benefits at the application layer, during inference, with any model?

3. The Latent Internal Loop: Capturing Reasoning in JSON

The Latent Loop answers that question: yes, we can implement iteration at inference time without modifying model weights.

The Core Problem

Standard LLM generation is a black box:

Prompt → [Hidden Reasoning] → Code Output

The reasoning happens inside transient tensor activations. Once generation completes, that reasoning is gone. If the code is wrong, we have no way to diagnose 

why

 the model made the choices it did.

Press enter or click to view image in full size

The Solution: Externalize Reasoning

The Latent Loop forces the model to externalize its reasoning into a structured JSON object 

before

 writing code:

Prompt → [Constrained Output] → JSON Reasoning State → Code Output

Press enter or click to view image in full size

Instead of asking the model to generate code directly, we first ask it to produce a structured specification: What are the tasks? Which can I solve? Which need more thought? What questions do I have?

Press enter or click to view image in full size

The Three-Phase Pipeline

Phase 1 — INIT (Decompose)

The model analyzes the task and categorizes subtasks: 
 { 
 "solved_tasks": [ 
 { 
 "name": "display_management", 
 "solution_code": "function updateDisplay() { document.getElementById('display').textContent = displayValue; }" 
 } 
 ], 
 "unsolved_tasks": [ 
 { 
 "name": "power_function", 
 "what_i_know": "Need to compute x^y", 
 "blockers": [ 
 "Is power immediate like sqrt, or deferred like addition?", 
 "What JavaScript function computes power?" 
 ] 
 } 
 ] 
 } Press enter or click to view image in full size

Phase 2 — REFINE (Search & Answer)

For each blocker, the model searches its knowledge and answers:

BLOCKER: “Is power immediate like sqrt, or deferred like addition?”

SEARCH: I know that immediate operations (sqrt, square) take ONE operand…

Deferred operations (+,-,*,/) take TWO operands…

Power x^y takes TWO operands (base and exponent)…

ANSWER: “Power is DEFERRED because it needs two operands.”

The model then moves tasks from unsolved_tasks to solved_tasks as blockers get resolved.

Press enter or click to view image in full size Press enter or click to view image in full size

Phase 3 — GENERATE (Code from Spec)

Only after the reasoning state is complete does the model generate code — now guided by a verified specification rather than raw intuition.

Why This Works

The JSON state acts as 

external working memory

. Unlike transient hidden states:

It persists between LLM calls

It’s human-readable and auditable

It forces categorical thinking (solved vs. unsolved)

It prevents “forgetting” requirements mid-generation

The model can’t hallucinate that it solved a task — either the solution_code field has valid code or it doesn’t.

4. The Ralph Loop: Grounding in Execution

The Latent Loop ensures the model 

thinks

 correctly. But thinking isn’t enough — we need to verify against reality.

The Ralph Loop provides that grounding.

Press enter or click to view image in full size

The Philosophy

“Deterministically bad in an indeterministic world — better to fail predictably than succeed unpredictably.”

Ralph doesn’t trust the model’s self-assessment. It validates generated code against actual execution using real tests.

Press enter or click to view image in full size

Test-Driven Feedback

When a test fails, Ralph converts the failure into actionable feedback:

[PLAYWRIGHT] test_power_function: 2³ expected 8, got NaN

[FEEDBACK INJECTED]

→ “Power function returns NaN. Check: Is pendingOperator

being set correctly? Is operandA stored before entering

exponent? Is Math.pow() being called with correct arguments?”

This feedback becomes context for the next iteration. The model doesn’t just know “something is wrong” — it knows 

specifically

 what failed and can reason about the fix.

BUILD vs FIX Modes

Ralph operates in two modes:

BUILD Mode:

 Generate code from scratch using the full Inner Loop (decompose → refine → generate)

FIX Mode:

 Patch existing code based on test failures. Analyze bugs, propose fixes, apply patches, re-validate.

If a fix causes regression (more tests fail than before), Ralph rolls back to the last working version.

5. NDLI (Nested Double-Loop Inference): The Unified Framework

Nested Dual-Loop Inference combines the Inner Loop (Latent) and Outer Loop (Ralph) into a unified framework.

The Architecture

The Division of Labor

Press enter or click to view image in full size

The Inner Loop is the “mind” — it plans, reasons, and specifies. The Outer Loop is the “hand” — it executes, tests, and validates.

Why Nesting Matters

Neither loop alone is sufficient:

Inner Loop only:

 Produces well-reasoned specifications that may not execute correctly

Outer Loop only:

 Fixes symptoms without understanding root causes

Together, they form a closed-loop system where reasoning informs execution and execution grounds reasoning.

6. The Technical Stack

NDLI is built on practical, accessible tools.

Pydantic: Schema as Cognitive Probe

from pydantic import BaseModel, Field

Press enter or click to view image in full size

The schema isn’t just validation — it’s a 

cognitive probe

. Each field forces the model to articulate a specific dimension of reasoning. min_length constraints prevent lazy responses. description fields guide the model’s understanding.

LM Studio: Forced JSON Output 
 import lmstudio as lms 
 model = lms.llm() 
 chat = lms.Chat(system_prompt) 
 chat.add_user_message(prompt) 
 # Force output to match schema exactly 
 result = model.respond(chat, response_format=ReasoningState) 
 state = ReasoningState(**result.parsed) # Guaranteed valid! Press enter or click to view image in full size

The response_format parameter constrains token generation to produce only valid JSON matching the Pydantic schema. No parsing errors. No hallucinated fields. No “almost valid” output.

State Replacement (Not Accumulation)

Each iteration replaces the previous state entirely:

state = init_state(model) # v1 
 state = refine_state(model, state) # v2 (replaces v1) 
 state = refine_state(model, state) # v3 (replaces v2) 
 code = generate_code(model, state) # uses v3 only Press enter or click to view image in full size

This prevents context bloat. The model always works with a single, authoritative state — not a growing history of previous attempts.

Task-Specific Schema Design

The schema adapts to the domain:

Domain Key Schema Fields 
 Calculator calculator_states, operations, edge_cases 
 Web Scraper target_urls, selectors, pagination_logic 
 API Client endpoints, auth_flow, error_codes

Same Latent Loop methodology, different schema. The schema encodes domain expertise.

7. Early Results & Future Work

What We Observed

Testing NDLI on calculator generation (a deceptively complex task involving state machines, operator precedence, and UI interaction):

16/16 behavioral tests passing

 with Playwright validation

Full audit trail

 of reasoning evolution (state_init.json → state_final.json)

Early convergence

 in many cases — well-designed schemas often yield correct reasoning on first attempt

The trend is clear: capturing LLM internal states in structured JSON for iterative inference improves output quality.

Limitations

We don’t have resources for full benchmarks against standard datasets. Our evidence is empirical, not statistical. The approach adds latency (multiple LLM calls per generation). Schema design requires domain expertise.

Future Directions

Benchmark validation

 on SWE-Bench, HumanEval, and other standard datasets

Schema libraries

 for common domains (web apps, APIs, data pipelines)

Hybrid approaches

 combining architectural recurrence (LoopCoder) with inference-time iteration (NDLI)

Adaptive iteration

 that adjusts loop depth based on task complexity

8. Conclusion: The Schema is the New Prompt

We started with a problem: one-shot LLM code generation fails silently.

We found inspiration in LoopCoder’s architectural recurrence — proof that models benefit from “thinking twice.”

We built NDLI — a practical framework that brings iteration to inference without custom model training:

Inner Loop (Latent):

 Externalize reasoning into structured JSON

Press enter or click to view image in full size

Outer Loop (Ralph):

 Validate against real execution

Together:

 Code becomes a byproduct of verified reasoning, not a gamble

Press enter or click to view image in full size

The key insight isn’t about prompting tricks or model selection. It’s about 

treating reasoning as a first-class artifact

 — something we can capture, inspect, refine, and validate.

The schema is the new prompt. Design it well, and the model’s reasoning follows.
