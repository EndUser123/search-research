TL;DR

Claude Code hooks execute at 12 lifecycle events including PreToolUse (can approve/deny actions) and PostToolUse (run checks after changes).

Three handler types: Command (shell scripts), Prompt (single-turn LLM evaluation), and Agent (subagents with tool access for verification).

PreToolUse is the most powerful security hook: block edits to production files, prevent dangerous commands, enforce review requirements.

Hooks integrate with GitHub Actions and GitLab CI for automated quality gates on AI-generated code.

Cursor (v1.7+) and GitHub Copilot also support hooks, but Claude Code offers the most handler diversity with command, prompt, and agent types.

Hooks are the technical implementation of thread-based engineering checkpoints, automating governance at every tool use event.

Hooks turn your quality standards from documentation into enforcement. Every rule in your CLAUDE.md can become an automated gate that runs before, during, or after Claude modifies your code.

Start simple: Begin with Command hooks for formatting, graduate to Prompt hooks for security, then Agent hooks for deep verification.

Claude Code supports three distinct handler types, each suited to different verification needs:

1. Command Hooks (type: "command")

Shell commands that receive the event's JSON input on stdin and communicate results through exit codes and stdout. These are the most straightforward: run a script, get a pass/fail result.

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "handler": {
          "type": "command",
          "command": "npx prettier --write $FILEPATH"
        }
      }
    ]
  }
}


This runs Prettier on every file Claude edits or writes, enforcing formatting automatically.

2. Prompt Hooks (type: "prompt")

Send a prompt to a Claude model for single-turn evaluation. Use the 

$ARGUMENTS

 placeholder to inject the hook's JSON input data into your prompt text. The model evaluates and returns a decision.

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit",
        "handler": {
          "type": "prompt",
          "prompt": "Review this edit: $ARGUMENTS. If it modifies auth or payments, DENY. Otherwise APPROVE."
        }
      }
    ]
  }
}


Prompt hooks enable intelligent verification without writing shell scripts. The LLM evaluates context-dependent conditions that would be difficult to express as regex patterns or exit codes.

3. Agent Hooks (type: "agent")

Spawn a subagent with access to tools like Read, Grep, and Glob to verify conditions before returning a decision. This is the most sophisticated handler type, enabling deep codebase analysis before approving or denying an action.

Agent hooks are particularly useful for checks that require understanding multiple files or project context, such as verifying that a new API endpoint follows the existing authentication pattern or that a database migration includes required RLS policies.

Production Patterns

Pattern 1: Auto-Format on Every Edit

The simplest and most impactful hook. Every file Claude modifies gets automatically formatted:

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "handler": {
          "type": "command",
          "command": "npx prettier --write $FILEPATH"
        }
      }
    ]
  }
}


You can chain ESLint by changing the command to 

npx prettier --write $FILEPATH && npx eslint --fix $FILEPATH

 .

Why this matters:

 Formatting inconsistencies are one of the top sources of noise in AI-generated code. Auto-formatting eliminates them before you even see the output.

Pattern 2: Protect Critical Files

Block Claude from editing production-critical files without explicit approval:

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit",
        "handler": {
          "type": "command",
          "command": "node scripts/block-critical.js"
        }
      }
    ]
  }
}


The 

block-critical.js

 script reads JSON from stdin and checks the file path against a blocklist:

// scripts/block-critical.js
const fs = require('fs')
const data = JSON.parse(fs.readFileSync('/dev/stdin', 'utf8'))
const blocked = ['src/middleware.ts', 'src/app/api/chat/route.ts', '.env']
if (blocked.some(f => data.filePath?.includes(f))) {
  console.error('BLOCKED: requires manual editing')
  process.exit(1)
}


This prevents Claude from modifying your middleware, AI chat route, or environment files without you explicitly overriding the protection. These are files where a small change can have outsized production impact.

Pattern 3: Security-Aware Dependency Changes

Block new dependency installations without review (directly addressing the 

slopsquatting threat

https://www.pixelmojo.io/blogs/slopsquatting-ai-supply-chain-attacks-defense-guide

):

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "handler": {
          "type": "command",
          "command": "node scripts/block-deps.js"
        }
      }
    ]
  }
}


The 

block-deps.js

 script checks for production dependency installs:

// scripts/block-deps.js
const fs = require('fs')
const data = JSON.parse(fs.readFileSync('/dev/stdin', 'utf8'))
const cmd = data.command || ''
const isInstall = cmd.match(/npm install|yarn add|pip install|pnpm add/)
if (isInstall && !cmd.includes('--save-dev')) {
  console.error('BLOCKED: Production deps require approval.')
  process.exit(1)
}


Pattern 4: Type Check After Edits

Run TypeScript type checking after every file modification to catch type errors immediately:

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "handler": {
          "type": "command",
          "command": "npx tsc --noEmit 2>&1 | head -20"
        }
      }
    ]
  }
}


Pattern 5: Prompt-Based Security Review

Use a prompt hook to evaluate whether edits touch sensitive areas:

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit",
        "handler": {
          "type": "prompt",
          "prompt": "Analyze edit: $ARGUMENTS. Check for: auth, DB, rate limits, payments, secrets. If ANY affected, DENY. Otherwise APPROVE."
        }
      }
    ]
  }
}


This delegates security classification to the LLM itself, which can understand semantic meaning better than regex patterns.

Pattern 6: Notification on Completion

Send a notification when Claude finishes a task, useful for long-running operations:

{
  "hooks": {
    "Stop": [
      {
        "handler": {
          "type": "command",
          "command": "osascript -e 'display notification \"Task complete\" with title \"Claude Code\"'"
        }
      }
    ]
  }
}

Claude Code Hooks: Questions Developers Ask

Common questions about this topic, answered.

What are Claude Code hooks?

Claude Code hooks are user-defined commands, prompts, or agents that execute automatically at specific points in Claude Code lifecycle. They transform best-practice maintenance tasks into enforced rules. Common uses include auto-formatting files after every change, running security scans before edits, executing tests before submissions, and sending notifications when Claude awaits input.

What hook handler types does Claude Code support?

Claude Code supports three handler types: Command hooks (type: "command") run shell commands that receive JSON via stdin and return results through exit codes. Prompt hooks (type: "prompt") send a prompt to a Claude model for single-turn evaluation using the $ARGUMENTS placeholder. Agent hooks (type: "agent") spawn subagents with access to tools like Read, Grep, and Glob for deep verification.

What lifecycle events can hooks attach to?

Claude Code provides 12 lifecycle events. The key ones are PreToolUse (fires before any tool execution, can approve or deny the action), PostToolUse (fires after tool execution for checks and formatting), Notification (when Claude sends notifications), Stop (when Claude finishes responding), and SubagentStop (when subagents complete). PreToolUse is the most powerful because it can block actions.

How do Claude Code hooks compare to Cursor and Copilot hooks?

All three support event-driven hooks with blocking capability. Claude Code differentiates with three handler types (command, prompt, agent) versus command-only for Cursor and Copilot. Claude Code prompt hooks enable LLM-based semantic evaluation, and agent hooks enable deep codebase analysis. Cursor (v1.7+) supports beforeShellExecution, beforeReadFile, afterFileEdit events. GitHub Copilot uses .github/hooks/*.json configuration.

Can hooks run asynchronously without blocking?

Yes. Hooks can be configured to run in the background for non-blocking quality checks. This is useful for longer-running operations like full test suites, comprehensive security scans, and codebase-wide lint checks. Claude continues working while background verification runs, with results reported upon completion.

How do I use hooks for CI/CD integration?

Claude Code supports GitHub Actions and GitLab CI integration. Configure hooks in your CI pipeline to run quality gates (linting, type checking, security scanning) when PRs or MRs are opened. Results post as comments on the PR/MR, and merges are blocked until all gates pass. This ensures AI-generated code meets the same standards as human-written code.

What is a PreToolUse hook and why is it important?

PreToolUse hooks fire before Claude performs any tool action (file edit, command execution, etc.) and can approve or deny the action. This is the most powerful hook for security: blocking edits to production-critical files like middleware or auth routes, preventing dangerous shell commands, and requiring verification before database operations. If the hook returns a deny signal, Claude cannot proceed.

How do prompt hooks work in Claude Code?

Prompt hooks send a prompt to a Claude model for single-turn evaluation. Set the handler type to "prompt" and provide a prompt string using $ARGUMENTS as a placeholder for the event JSON data. The model evaluates semantic conditions (like "does this edit touch authentication logic?") that would be hard to express as regex or shell scripts, making prompt hooks ideal for context-dependent security classification.

How do hooks relate to thread-based engineering?

Hooks are the technical implementation of thread-based engineering checkpoints. Thread-based engineering defines the governance policy (when human review is required), and hooks automate enforcement. PreToolUse hooks block actions that require review, PostToolUse hooks run quality checks, and Stop hooks validate final output. Without hooks, CLAUDE.md rules are advisory. With hooks, they become enforced gates.

Where are hook configurations stored?

Hook configurations live in .claude/settings.json at the project level (applies to all developers in that repo) or ~/.claude/settings.json for user-level defaults (applies across all projects). Project-level hooks take precedence over user-level hooks. Hooks can also be defined in agent and skill frontmatter for scoped automation.

Start simple: Begin with Command hooks for formatting, graduate to Prompt hooks for security, then Agent hooks for deep verification.

Claude Code supports three distinct handler types, each suited to different verification needs:

1. Command Hooks (type: "command")

Shell commands that receive the event's JSON input on stdin and communicate results through exit codes and stdout. These are the most straightforward: run a script, get a pass/fail result.

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "handler": {
          "type": "command",
          "command": "npx prettier --write $FILEPATH"
        }
      }
    ]
  }
}


This runs Prettier on every file Claude edits or writes, enforcing formatting automatically.

2. Prompt Hooks (type: "prompt")

Send a prompt to a Claude model for single-turn evaluation. Use the 

$ARGUMENTS

 placeholder to inject the hook's JSON input data into your prompt text. The model evaluates and returns a decision.

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit",
        "handler": {
          "type": "prompt",
          "prompt": "Review this edit: $ARGUMENTS. If it modifies auth or payments, DENY. Otherwise APPROVE."
        }
      }
    ]
  }
}


Prompt hooks enable intelligent verification without writing shell scripts. The LLM evaluates context-dependent conditions that would be difficult to express as regex patterns or exit codes.

3. Agent Hooks (type: "agent")

Spawn a subagent with access to tools like Read, Grep, and Glob to verify conditions before returning a decision. This is the most sophisticated handler type, enabling deep codebase analysis before approving or denying an action.

Agent hooks are particularly useful for checks that require understanding multiple files or project context, such as verifying that a new API endpoint follows the existing authentication pattern or that a database migration includes required RLS policies.

Pattern 2: Protect Critical Files

Block Claude from editing production-critical files without explicit approval:

{
  "hooks": {

      {

The

// scripts/block-critical.js
const fs = require('fs')

  console.error('BLOCKED: requires manual editing')
  process.exit(1)
}


This prevents Claude from modifying your middleware, AI chat route, or environment files without you explicitly overriding the protection. These are files where a small change can have outsized production impact.

Claude Code Hooks: Questions Developers Ask

Common questions about this topic, answered.

What are Claude Code hooks?

Claude Code hooks are user-defined commands, prompts, or agents that execute automatically at specific points in Claude Code lifecycle. They transform best-practice maintenance tasks into enforced rules. Common uses include auto-formatting files after every change, running security scans before edits, executing tests before submissions, and sending notifications when Claude awaits input.

What hook handler types does Claude Code support?

Claude Code supports three handler types: Command hooks (type: "command") run shell commands that receive JSON via stdin and return results through exit codes. Prompt hooks (type: "prompt") send a prompt to a Claude model for single-turn evaluation using the $ARGUMENTS placeholder. Agent hooks (type: "agent") spawn subagents with access to tools like Read, Grep, and Glob for deep verification.

What lifecycle events can hooks attach to?

Claude Code provides 12 lifecycle events. The key ones are PreToolUse (fires before any tool execution, can approve or deny the action), PostToolUse (fires after tool execution for checks and formatting), Notification (when Claude sends notifications), Stop (when Claude finishes responding), and SubagentStop (when subagents complete). PreToolUse is the most powerful because it can block actions.

How do Claude Code hooks compare to Cursor and Copilot hooks?

All three support event-driven hooks with blocking capability. Claude Code differentiates with three handler types (command, prompt, agent) versus command-only for Cursor and Copilot. Claude Code prompt hooks enable LLM-based semantic evaluation, and agent hooks enable deep codebase analysis. Cursor (v1.7+) supports beforeShellExecution, beforeReadFile, afterFileEdit events. GitHub Copilot uses .github/hooks/*.json configuration.

Can hooks run asynchronously without blocking?

Yes. Hooks can be configured to run in the background for non-blocking quality checks. This is useful for longer-running operations like full test suites, comprehensive security scans, and codebase-wide lint checks. Claude continues working while background verification runs, with results reported upon completion.

How do I use hooks for CI/CD integration?

Claude Code supports GitHub Actions and GitLab CI integration. Configure hooks in your CI pipeline to run quality gates (linting, type checking, security scanning) when PRs or MRs are opened. Results post as comments on the PR/MR, and merges are blocked until all gates pass. This ensures AI-generated code meets the same standards as human-written code.

What is a PreToolUse hook and why is it important?

PreToolUse hooks fire before Claude performs any tool action (file edit, command execution, etc.) and can approve or deny the action. This is the most powerful hook for security: blocking edits to production-critical files like middleware or auth routes, preventing dangerous shell commands, and requiring verification before database operations. If the hook returns a deny signal, Claude cannot proceed.

How do prompt hooks work in Claude Code?

Prompt hooks send a prompt to a Claude model for single-turn evaluation. Set the handler type to "prompt" and provide a prompt string using $ARGUMENTS as a placeholder for the event JSON data. The model evaluates semantic conditions (like "does this edit touch authentication logic?") that would be hard to express as regex or shell scripts, making prompt hooks ideal for context-dependent security classification.

How do hooks relate to thread-based engineering?

Hooks are the technical implementation of thread-based engineering checkpoints. Thread-based engineering defines the governance policy (when human review is required), and hooks automate enforcement. PreToolUse hooks block actions that require review, PostToolUse hooks run quality checks, and Stop hooks validate final output. Without hooks, CLAUDE.md rules are advisory. With hooks, they become enforced gates.

Where are hook configurations stored?

Hook configurations live in .claude/settings.json at the project level (applies to all developers in that repo) or ~/.claude/settings.json for user-level defaults (applies across all projects). Project-level hooks take precedence over user-level hooks. Hooks can also be defined in agent and skill frontmatter for scoped automation.
