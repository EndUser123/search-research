Type-safe AI agents with Pydantic AI: Streaming and multi-agent orchestration
Build type-safe AI agents with Pydantic AI: Streaming responses and multi-agent orchestration on AWS
Overview
This pattern demonstrates how to implement advanced Pydantic AI features on AWS serverless architecture, including basic synchronous agents, real-time streaming responses, and multi-agent orchestration with structured outputs. The pattern covers three core use cases:
Basic Q&A
 with synchronous REST API for simple query-response interactions
Real-time WebSocket streaming
 for improved user experience with token-by-token delivery
Orchestrating multiple specialized agents
 with type-safe structured outputs using AWS Step Functions
The solution uses Amazon Bedrock for LLM inference with streaming support, AWS Lambda for agent execution, Amazon API Gateway for REST and WebSocket APIs, and AWS Step Functions for multi-agent coordination.
Organizations building AI applications need advanced capabilities beyond basic query-response patterns. This pattern addresses common requirements such as implementing type-safe AI agents with Pydantic validation, delivering real-time streaming responses to reduce perceived latency, coordinating multiple specialized agents for complex workflows with validated structured outputs, and implementing enterprise security controls including authentication, rate limiting, and encryption. By combining Pydantic AI's type-safe framework with AWS managed services, teams can build sophisticated AI systems that scale automatically while maintaining strict validation, security controls, and cost efficiency through serverless pay-per-use pricing.
Key Features
Type-Safe AI Agents
: Pydantic AI agents with strict type validation and structured outputs
Real-time Streaming
: WebSocket-based streaming responses using Pydantic AI's  run_stream()
Multi-Agent Orchestration
: Specialized agents with typed outputs coordinated via AWS Step Functions
Enterprise Security
: Cognito authentication, WAF protection, and KMS encryption
Serverless Architecture
: Fully managed AWS services with auto-scaling
Observability
: CloudWatch logging, X-Ray tracing, and custom metrics

Architecture
High-Level Architecture
The solution implements three distinct architectural patterns for different use cases:
1. Basic Q&A (REST API)
User Flow (Basic Q&A)
Step 1: Client Request with Authentication
User authenticates with Amazon Cognito User Pool using username and password to obtain JWT token
User sends POST request to /chat endpoint with JSON body: {"message": "What is AWS Lambda?"}
Request includes JWT token in Authorization: Bearer header
Example: curl -X POST /chat -H "Authorization: Bearer " -d '{"message": "..."}'
Step 2: AWS WAF Security Check
Request passes through AWS WAF attached to API Gateway
WAF applies rate limiting (100 requests per 5 minutes per IP)
WAF blocks malicious requests using AWS Managed Rules (SQL injection, XSS, known bad inputs)
Valid requests proceed to API Gateway with Cognito Authorizer validation
Step 3: API Gateway Processing
Amazon API Gateway receives the request over TLS 1.2+
Cognito Authorizer validates the JWT token (signature, expiration, issuer)
If token is valid, API Gateway invokes Basic Agent Lambda
If token is invalid, expired, or missing, returns 401 Unauthorized
Step 4: Lambda Processing
AWS Lambda Basic Agent receives the request and parses the message
Creates Pydantic AI Agent with system prompt
Calls agent.run_sync(user_message) for synchronous execution
Step 5: Bedrock Inference
Lambda invokes Amazon Bedrock API with Claude 3.5 Sonnet v2 model
Uses cross-region inference profile: us.anthropic.claude-3-5-sonnet-20241022-v2:0
Bedrock generates response based on user query and system prompt
Lambda formats response as JSON: {"message": "...", "model": "...", "timestamp": "..."}
Response sent back through API Gateway to user
2. Real-time Streaming (WebSocket)
User Flow (Real-time Streaming)
Step 1: Authentication
User authenticates with Amazon Cognito User Pool using username and password
Cognito validates credentials and returns JWT tokens (ID token, access token, refresh token)
ID token is used for WebSocket authorization
Step 2: WebSocket Connection Request
User initiates WebSocket connection to wss://.execute-api..amazonaws.com/prod?token=
JWT token passed as query parameter for Lambda Authorizer validation
Request passes through AWS WAF for security checks
WAF applies rate limiting (100 requests per 5 minutes per IP)
WAF blocks malicious requests using AWS Managed Rules (SQL injection, XSS, known bad inputs)
Step 3: API Gateway & Authorization
API Gateway WebSocket API receives connection request
Lambda Authorizer validates JWT token (signature, expiration, issuer)
If token is invalid or missing, connection is rejected with 401 Unauthorized
If token is valid, $connect route is triggered
Step 4: Connection Registration
Connection Manager Lambda is invoked via $connect route
Lambda stores connection ID in DynamoDB connections table
Connection record includes: connectionId, timestamp, userId (from JWT)
Step 5: DynamoDB Storage
Connection data persisted in DynamoDB with TTL enabled (2 hours) for automatic cleanup
Connection Manager returns 200 OK to establish connection
WebSocket connection is now active and ready to receive messages
Step 6: Message Processing & Streaming
User sends JSON message through WebSocket: {"message": "Tell me about serverless computing"}
API Gateway receives message and triggers $default route
Streaming Agent Lambda is invoked (not Connection Manager)
Lambda parses user message and creates Pydantic AI Agent with streaming support
Calls agent.run_stream(user_message) for asynchronous streaming execution
Step 7: Bedrock Streaming & Token Delivery
Lambda invokes Amazon Bedrock API with streaming enabled
Bedrock Claude 3.5 Sonnet v2 generates response token by token
Each token is yielded as it's generated (no waiting for complete response)
For each token received from Bedrock: 
Streaming Agent Lambda sends token to user via API Gateway Management API
Uses post_to_connection() with connection ID
Sends JSON: {"token": "Server", "done": false}
User receives tokens in real-time as they're generated
After all tokens are sent, Lambda sends completion message: {"token": "", "done": true}
If error occurs, sends: {"error": "...", "done": true}
Total streaming time: 30-60 seconds for long responses
3. Multi-Agent Orchestration (Step Functions)
User Flow (Multi-Agent Orchestration)
Step 1: Authentication
User authenticates with Amazon Cognito User Pool using username and password
Cognito validates credentials and returns JWT tokens (ID token, access token, refresh token)
ID token is used for API authorization (valid for 1 hour)
Use scripts/get_token.sh to obtain JWT token
Step 2: WAF Security Check
User sends POST request to /multi-agent endpoint with JSON body: {"message": "Research serverless and analyze costs"}
Request includes JWT token in Authorization: Bearer header
Example: curl -X POST /multi-agent -H "Authorization: Bearer " -d '{"message": "..."}'
Request passes through AWS WAF for security checks
WAF applies rate limiting (100 requests per 5 minutes per IP)
WAF blocks malicious requests using AWS Managed Rules (SQL injection, XSS, known bad inputs)
Step 3: API Gateway Processing
Amazon API Gateway receives the request over TLS 1.2+
Cognito Authorizer validates JWT token (signature, expiration, issuer)
If token is invalid, returns 401 Unauthorized
If token is valid, API Lambda is invoked
Step 4: Multi-Agent API Lambda
API Lambda function receives the request and extracts task from body
Prepares Step Functions execution input with user_id from JWT token
Starts Step Functions state machine execution
Returns 202 Accepted with execution details immediately (async pattern)
Step 5: Step Functions Workflow Initiation
Step Functions state machine starts with execution input:
{  "task" :  " Research serverless and analyze costs " ,  "user_id" :  " <from-jwt-token> " ,  "session_id" :  " session-20260108-123456 " ,  "timestamp" :  " 2026-01-08T12:34:56Z "  }  
Workflow begins by invoking Coordinator Agent Lambda
User receives response with executionArn for status polling
Step 6: Coordinator Agent Analysis
Step Functions invokes Coordinator Agent Lambda
Coordinator receives task and analyzes requirements
Uses Pydantic AI Agent with output_type=RoutingDecision for structured output
Calls agent.run_sync(task) to determine routing
Returns structured decision: agents needed and execution mode (parallel/sequential)
Step Functions Choice State evaluates routing decision
Step 7: Agent Execution (Parallel or Sequential)
Step Functions invokes specialized agents based on Coordinator's decision
Parallel Mode: Researcher and Analyst agents execute simultaneously
Sequential Mode: Researcher executes first, then Analyst processes results
Each agent: 
Receives task-specific input
Creates Pydantic AI Agent with output_type for structured responses
Processes task using domain expertise
Researcher Agent: Gathers information with output_type=ResearchFindings
Analyst Agent: Analyzes data with output_type=AnalysisResult
Parallel execution reduces total time by 50-70% (20s vs 59s sequential)
Step 8: Bedrock Inference
Each agent Lambda invokes Amazon Bedrock API with Claude 3.5 Sonnet v2
Uses cross-region inference profile: us.anthropic.claude-3-5-sonnet-20241022-v2:0
Bedrock generates structured responses based on agent prompts
Researcher returns findings with confidence scores and sources
Analyst returns insights with categories and recommendations
All outputs are type-safe Pydantic models validated at runtime

3. Multi-Agent Orchestration (Step Functions)
Multiple specialized agents with structured outputs coordinated via Step Functions. Supports both parallel and sequential execution modes for optimal performance.
Pydantic AI Features
:
Multiple  Agent  instances with specialized roles
output_type  with Pydantic models for type-safe responses
BedrockConverseModel  for cross-region inference
Agents
:
Coordinator
: Routes tasks to appropriate agents and determines execution mode (parallel/sequential)
Researcher
: Gathers information and research
Analyst
: Analyzes data and provides insights
Execution Modes
:
Parallel Mode
: Independent tasks execute simultaneously (~20-40 seconds, ~37% faster)
Sequential Mode
: Dependent tasks execute in order (~40-60 seconds)
Example
:
#  Get authentication token   export  TOKEN= $( ./scripts/get_token.sh )   #  Submit multi-agent task via REST API (parallel execution for independent tasks)  curl -X POST https:// < api-id > .execute-api.us-east-1.amazonaws.com/prod/multi-agent \ -H  " Authorization: Bearer  $TOKEN "  \ -H  " Content-Type: application/json "  \ -d  ' {"message": "Research the latest AWS Lambda features and separately analyze current cloud computing market trends"} '   #  Submit dependent task (sequential execution)  curl -X POST https:// < api-id > .execute-api.us-east-1.amazonaws.com/prod/multi-agent \ -H  " Authorization: Bearer  $TOKEN "  \ -H  " Content-Type: application/json "  \ -d  ' {"message": "First research the benefits of serverless computing, then analyze the cost implications based on that research"} '   #  Alternative: Direct Step Functions invocation (no authentication required)  python scripts/test_multi_agent.py \ --state-machine-arn  < arn >  \ --task  " Research serverless computing and analyze costs "  \ --test-workflow

Users authenticate with Amazon Cognito User Pool using username/password
Cognito validates credentials and returns JWT tokens (ID token, access token, refresh token)
ID token is included in API requests via  Authorization: Bearer <token>  header
API Gateway Cognito Authorizer validates the JWT token before invoking Lambda functions
Authorization Components
:
Cognito User Pool
: Manages user identities, passwords, and MFA
User Pool ID: Available in stack outputs as  UserPoolId
Client ID: Available in stack outputs as  UserPoolClientId
Password policy: Minimum 8 characters, requires uppercase, lowercase, numbers, and symbols
Account recovery: Email-based password reset
Cognito Authorizer
: Attached to API Gateway REST API
Validates JWT signature using Cognito public keys (JWKS)
Checks token expiration (1 hour validity)
Verifies token issuer matches User Pool
Caches authorization decisions for 300 seconds (5 minutes)
Returns 401 Unauthorized for invalid/expired tokens
Token Validation
: Automatic validation includes:
Signature verification using RS256 algorithm
Expiration time ( exp  claim)
Issuer ( iss  claim) matches Cognito User Pool
Audience ( aud  claim) matches Client ID
Token type ( token_use  claim) is "id"
Example Authentication
:
#  Get JWT token   export  TOKEN= $( ./scripts/get_token.sh )   #  Use token in API request  curl -X POST https:// < api-id > .execute-api.us-east-1.amazonaws.com/prod/chat \ -H  " Authorization: Bearer  $TOKEN "  \ -H  " Content-Type: application/json "  \ -d  ' {"message": "What is AWS Lambda?"} '  
WebSocket API Authorization (Real-time Streaming)
Authentication Flow
:
Users authenticate with Cognito to obtain JWT token
JWT token passed as query parameter during WebSocket connection:  wss://<api-id>.execute-api.us-east-1.amazonaws.com/prod?token=<jwt-token>
Lambda Authorizer validates token and returns IAM policy
Connection is established only if token is valid
Authorization Components
:
Lambda Authorizer
: Custom authorizer function for WebSocket API 
Extracts token from query string parameter
Validates JWT signature and claims using Cognito JWKS
Returns IAM policy allowing/denying connection
Includes user context (user_id, email) in connection metadata
Rejects connections with invalid/expired tokens (401 Unauthorized)
IAM Policy Generation
:
# Allow policy for valid token  {  "principalId" :  user_id ,  "policyDocument" : {  "Statement" : [{  "Action" :  "execute-api:Invoke" ,  "Effect" :  "Allow" ,  "Resource" :  connection_arn  }] },  "context" : {  "userId" :  user_id ,  "email" :  user_email  } }  
WAF Protection
AWS WAF is attached to both REST and WebSocket APIs with the following rules:
Rate Limiting
: 100 requests per 5 minutes per IP address
AWS Managed Rules
: 
Core Rule Set (CRS): Protection against OWASP Top 10 vulnerabilities
Known Bad Inputs: Blocks requests with known malicious patterns
SQL Injection: Prevents SQL injection attacks
Cross-Site Scripting (XSS): Blocks XSS attempts
IP Reputation
: Blocks requests from known malicious IP addresses
Geographic Restrictions
: Optional geo-blocking (configurable)
2. Amazon Bedrock Guardrails
The solution implements Amazon Bedrock Guardrails to ensure responsible AI usage and prevent harmful content generation:
Guardrail Configuration
Guardrail ID
:  <guardrail-id>  (configured in Lambda environment variables) 
Guardrail Version
:  DRAFT  or specific version number
Content Filters
Hate Speech
: MEDIUM threshold
Blocks content promoting hate, discrimination, or violence against protected groups
Filters based on race, ethnicity, religion, gender, sexual orientation, disability
Insults
: MEDIUM threshold
Prevents generation of insulting, demeaning, or offensive language
Blocks personal attacks and derogatory content
Sexual Content
: MEDIUM threshold
Filters sexually explicit content and inappropriate sexual references
Blocks adult content and sexual solicitation
Violence
: MEDIUM threshold
Prevents graphic violence, gore, and violent threats
Blocks content promoting self-harm or harm to others
Misconduct
: MEDIUM threshold
Filters illegal activities, dangerous advice, and unethical behavior
Blocks instructions for harmful or illegal actions
Prompt Attacks
: HIGH threshold
Detects and blocks prompt injection attempts
Prevents jailbreaking and adversarial prompts
Protects against prompt leaking and system prompt extraction
Sensitive Information Filters (PII Detection)
Personally Identifiable Information (PII)
:
Email Addresses
: BLOCK action - Redacts email addresses from inputs/outputs
Phone Numbers
: BLOCK action - Redacts phone numbers (US and international formats)
Social Security Numbers
: BLOCK action - Redacts SSN patterns
Credit Card Numbers
: BLOCK action - Redacts credit card numbers (all major issuers)
Driver's License Numbers
: BLOCK action - Redacts US driver's license numbers
Passport Numbers
: BLOCK action - Redacts passport numbers
Bank Account Numbers
: BLOCK action - Redacts bank account information
IP Addresses
: ANONYMIZE action - Replaces with generic placeholder
MAC Addresses
: ANONYMIZE action - Replaces with generic placeholder
Regulatory Compliance
:
GDPR compliance for EU user data
HIPAA compliance for healthcare information (if applicable)
PCI DSS compliance for payment card data
Topic Filters
Denied Topics
:
Financial advice (investment recommendations, stock tips)
Medical diagnosis and treatment recommendations
Legal advice and interpretation
Political campaign content and endorsements
Cryptocurrency trading advice
Gambling and betting strategies
Topic Detection
: Uses semantic similarity to identify and block denied topics even when not explicitly mentioned
Word Filters
Profanity Filter
: Blocks common profanity and offensive language 
Custom Blocklist
: Organization-specific terms to block (configurable)
Guardrail Application
Guardrails are applied at two stages:
Input Validation
: Before sending user prompts to Bedrock
Validates user input against content filters
Blocks requests containing PII or denied topics
Returns error message if input violates policies
Output Validation
: After receiving model responses
Validates generated content against content filters
Redacts PII from model outputs
Blocks responses containing harmful content
Returns sanitized response to user

:
# Bedrock client with guardrails   bedrock_client   =   boto3 . client ( 'bedrock-runtime' )  response   =   bedrock_client . converse (  modelId = model_id ,  messages = messages ,  guardrailConfig = {  'guardrailIdentifier' :  os . environ [ 'GUARDRAIL_ID' ],  'guardrailVersion' :  os . environ [ 'GUARDRAIL_VERSION' ],  'trace' :  'enabled'   # Enable guardrail tracing for debugging  } )  # Check guardrail action   if   response . get ( 'stopReason' )  ==   'guardrail_intervened' :  # Request blocked by guardrails   return  {  'statusCode' :  400 ,  'body' :  json . dumps ({  'error' :  'Content policy violation' ,  'message' :  'Your request was blocked by content filters'  }) }
