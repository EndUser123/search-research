# Stop Asking Claude Code for Markdown — HTML Makes AI Work Feel 10X Faster
Hey, welcome back. Today we're talking about a weird but genuinely useful shift in Claude Code.

The weirdest productivity upgrade in Claude Code right now is not a new model.

It is asking the model to stop writing Markdown.

And to start writing HTML.

That sounds backwards at first.

Markdown is supposed to be the clean format. It is simple, portable, easy to diff, easy to edit, and every developer already knows how to read it.

HTML sounds like the messy thing we escaped from.

But once an AI agent is doing serious work, Markdown starts to show its age.

Not because Markdown is bad.

Because the thing we are asking agents to produce has changed.

A recent piece by Thariq makes this argument really clearly.

The claim is that Markdown became the default language between agents and humans, but it may not be the best language for complex agent work anymore.

And after using Claude Code for a while, I think that point is stronger than it sounds.

Think about what Markdown was great for.

A README. A checklist. A short design note. A comment that needs bullets, links, and code fences.

For that world, Markdown is almost perfect.

But Claude Code is not just writing short notes.

It is writing implementation plans, architecture specs, research summaries, PR explanations, design explorations, incident writeups, and review artifacts.

Those are not always documents you edit by hand.

That detail matters.

One of Markdown's biggest advantages is that a human can open the file and edit it directly.

But if your real workflow is "ask Claude to update the file," that advantage gets a lot smaller.

The article mentions a very relatable failure mode.

Once a Markdown plan gets past roughly a hundred lines, the author stops reading it carefully.

And honestly, that tracks.

At some point, a Markdown file becomes a wall.

The agent can still write it.

The repo can still store it.

But the human review loop gets weaker, because nobody wants to stare at another giant block of structured text.

That is a real workflow problem.

You see the same thing when an agent tries to visualize something in Markdown.

It starts drawing ASCII diagrams.

It tries to represent color with Unicode blocks.

It describes layout in paragraphs instead of showing layout.

Those tricks are clever.

They are also signs that the format is fighting the job.

If the output needs a diagram, a layout, a comparison table, or a little interaction, Markdown can only fake it.

HTML changes the canvas.

Now the agent can use headings and paragraphs, but also tables, CSS, SVG, images, absolute positioning, canvas, and small bits of JavaScript.

That is a much larger vocabulary for explaining something to a human.

And the point is not "make it pretty."

Pretty is nice, but the real win is compression for the reader.

A flowchart can replace five paragraphs. A side-by-side comparison can replace a long explanation. A highlighted diff can replace a reviewer squinting at raw patches.

This is where the idea starts to click.

If Claude Code creates a plan as an HTML artifact, it can organize the plan visually.

Tabs, sections, callouts, diagrams, code snippets, and links can all live in one thing you can actually inspect.

Sharing also gets easier.

A Markdown file often needs GitHub, an editor, or a rendered preview to look right.

An HTML file can just become a link.

Upload it somewhere, send it to a teammate, and they can open it in a browser.

That sounds small, but it matters.

The chance that someone reads a spec goes way up when the spec feels like a page instead of an attachment.

Most teams do not have a writing problem.

They have a "nobody read the artifact" problem.

HTML also lets the artifact become interactive.

The article gives examples like sliders, knobs, algorithm options, and controls that let a human adjust something instead of describing the adjustment in text.

That is a different kind of collaboration.

The really useful pattern is the copy-back loop.

You adjust the artifact in the browser.

Then the artifact gives you a "copy as prompt," "copy as JSON," or "copy diff" button.

Now your visual edits can go back into Claude Code.

That is the part that feels new.

The HTML file is not a product.

It is not a SaaS app.

It is a disposable interface for one exact decision you are trying to make today.

Claude Code is especially interesting here because it has context.

It can read the local repo, inspect generated files, use git history, and, depending on your setup, pull context from tools like Slack, Linear, browser sessions, or MCP servers.

The article describes asking Claude Code to scan a folder, find generated HTML files, group them by type, and create an HTML overview with diagrams.

That is the difference between a chatbot answering from memory and an agent building from your actual workspace.

That context is what keeps the artifact from feeling generic.

It can be shaped by the actual repository, the actual tickets, the actual diff, and the actual decisions sitting in front of the team.

This is why the use cases are broader than "make me a prettier doc."

One use case is planning and exploration.

Ask for six different onboarding screens, laid out side by side, with the tradeoff of each approach labeled.

Another is implementation planning.

Instead of a plain Markdown plan, ask for an HTML plan with mockups, data flow, important code snippets, risk areas, and review checkpoints.

That makes the plan easier to challenge before the agent starts coding.

Code review is another obvious one.

Markdown can paste a diff, but HTML can show the diff with annotations, severity labels, module diagrams, and a flow explanation next to the code.

For complex PRs, that is a big upgrade.

I like the PR version because it solves a real social problem.

If an agent wrote the code, the reviewer still needs to trust the change.

An HTML explainer can give the reviewer a map before they dive into the raw diff.

Design prototyping is another strong fit.

You can ask Claude to build a tiny HTML playground for a button animation, a checkout flow, a color choice, or a component state.

Then you tune it with controls instead of arguing with adjectives.

Reports and research also fit.

Claude Code can synthesize a repo, issue history, logs, docs, and team context into a report.

In HTML, that report can include diagrams, sections, navigation, and visual summaries that make the whole thing less painful to read.

The most interesting category might be custom editors.

Imagine a one-off board for reprioritizing Linear tickets.

Or a feature flag editor that warns you when a prerequisite flag is off.

Or a prompt tuning page with live examples and a token counter.

That sounds like overkill until you remember the artifact is disposable.

You are not maintaining a new internal tool.

You are asking the agent to create a temporary UI, use it for one decision, then export the result back into your workflow.

There is a trap here, though.

The article warns against turning this into an overbuilt slash command too early.

You do not need a giant system for it on day one.

Just ask for an HTML file and learn where it helps.

That is probably the right starting point.

Use HTML as a medium, not as a religion.

If the task is visual, shared, interactive, or high-stakes, HTML may be worth it.

If it is a tiny note, Markdown is still great.

Now, here is the part I would push on.

HTML may be easier for humans to read, but it can be much more expensive for models to produce.

The artifact gets more readable.

The bill may get bigger.

Markdown is dense.

A heading, a bullet list, and a code fence do not cost much overhead.

HTML brings tags, class names, style blocks, scripts, repeated structure, and sometimes a lot of generated layout code.

That overhead may be totally worth it for a complex review or a planning artifact people will actually read.

But if every brainstorm, every plan, every PR note, and every report becomes HTML, your token budget can start moving in the wrong direction.

This is not a conspiracy claim.

I am not saying Anthropic is being malicious by making HTML look attractive.

I am saying the incentives are worth noticing.

More generated tokens can mean more usage, more cost, and more platform revenue.

That creates a subtle alignment issue.

The model provider benefits when the workflow uses more tokens.

The developer benefits when the output saves enough time to justify those tokens.

Those are not always the same thing.

So the question is not "HTML or Markdown?"

The question is "what is the cheapest artifact that still keeps the human in the loop?"

Sometimes that is Markdown.

Sometimes that is HTML.

Sometimes it is both.

One practical pattern is to ask for semantic content first.

Then ask for an HTML version only when the structure needs visuals, interaction, or sharing.

That keeps you from paying for a beautiful wrapper around a vague plan.

Another pattern is to constrain the artifact.

Ask for minimal CSS.

Ask for no framework.

Ask for no fake data.

Ask for a readable structure that favors diagrams and tables over decorative markup.

For version control, I would be selective.

Generated HTML can be noisy to diff.

If the artifact is a deliverable, commit it.

If it was just a temporary thinking surface, keep the source prompt or a short summary instead.

There is also a security angle.

Do not casually share an HTML artifact that includes sensitive repo details, customer data, internal discussions, or executable JavaScript you have not looked at.

The browser is a great viewer, but it is not magic safety glass.

The interesting part is still the workflow.

My personal take is that the article is directionally right.

Markdown is not going away, but for agent output, HTML is a surprisingly powerful human interface.

It can make specs, reviews, and explorations feel readable again.

The cost critique does not cancel that.

It just keeps the idea honest.

If HTML makes the artifact ten times easier to review, use it.

If it only makes a simple note look fancy, skip it.

The real win is not HTML itself.

The win is getting the human back into the loop.

If a format makes you actually read, question, adjust, and approve the agent's work, that format is doing something valuable.

So try it once.

Ask Claude Code for an HTML artifact on a messy plan or a PR you do not fully understand.

Then watch two things: how much easier it is to review, and how much extra output it took to get there.

That tradeoff is the whole story.

Readable matters.

Cheap matters.

The best developer workflow is the one that respects both.
