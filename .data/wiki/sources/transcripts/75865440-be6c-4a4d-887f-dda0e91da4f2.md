What Claude Code hooks actually are

Thirty-second primer. Claude Code hooks are user-defined shell commands that run at specific points during Claude Code's tool execution lifecycle. They're configured in 

.claude/settings.json

 (project-level) or 

~/.claude/settings.json

 (global), and they let you intercept, validate, or block tool calls before or after they happen.

Think of them as middleware for your AI agent. Every time Claude Code reaches for a tool (running a shell command, writing a file, reading something), your hooks get a say.

Claude Code hooks are middleware for your AI agent. They don't replace git hooks; they govern what Claude does with git.

The critical distinction: 

git hooks

 run when 

you

 use git. 

Claude Code hooks

 run when 

Claude

 uses tools, including git. They complement each other. One set of guardrails for humans, another for the AI.

The architecture: events, matchers, and exit codes

The event lifecycle

Claude Code exposes 12 hook events. For git automation, you'll mostly care about four:

⚠ PreToolUse

 fires before Claude executes a tool. 

This is your gate.

 You can inspect the command, validate it, or block it entirely.

PostToolUse

 fires after a tool completes. Good for notifications, logging, or triggering follow-up actions.

Notification

 fires when Claude produces a notification. Useful for routing alerts.

Stop

 fires when Claude finishes its response. Your chance to run cleanup or summary tasks.

The full event list also includes 

SessionStart

 , 

SessionEnd

 , 

UserPromptSubmit

 , 

PermissionRequest

 , 

PostToolUseFailure

 , 

SubagentStart

 , 

SubagentStop

 , and 

PreCompact

 . For git-related hooks, the four above cover the vast majority of use cases.

Matchers

The 

matcher

 field is a regex string that determines which tool triggers your hook. It supports:

Exact names:

 

"Bash"

 , 

"Write"

 , 

"Read"

Regex patterns:

 

"Edit|Write"

 (matches either), 

"Bash"

 (exact match), 

"mcp__.*"

 (all MCP tools)

For git automation, you'll almost always match on 

"Bash"

 and then inspect the command content inside your hook script.

Exit codes

This is the control mechanism. Your hook script's exit code tells Claude Code what to do:

Exit 0

 means proceed. Everything's fine. Claude Code parses stdout for any JSON output you return.

Exit 2

 means block. Hard stop. For 

PreToolUse

 , Claude Code won't execute the tool call. Whatever you write to stderr becomes the error message fed back to Claude.

Any other exit code

 (1, 3, etc.) means a non-blocking error. stderr is shown in verbose mode and execution continues.

Data flow

Your hook receives JSON on stdin containing metadata and the tool input. For a 

Bash

 tool call, that JSON includes 

tool_name

 , 

tool_input

 (with a nested 

command

 field), 

hook_event_name

 , and other context. You extract the command with 

jq -r '.tool_input.command'

 , decide what to do, and exit accordingly.

Environment variables

Claude Code makes a few environment variables available to hooks: 

$CLAUDE_PROJECT_DIR

 (the project root), 

$CLAUDE_CODE_REMOTE

 (set to 

"true"

 in remote web environments), and 

$CLAUDE_ENV_FILE

 (available in 

SessionStart

 hooks for persisting env vars). Note that the hook event name and tool name are delivered via JSON on stdin (as 

hook_event_name

 and 

tool_name

 fields), not as environment variables.

Your first hook: intercepting git commits

This is the recipe from Anthony's tweet, and it's the best starting point. You want Claude Code to run your linter and type checker before every commit.

Option 1: Inline command in settings.json

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.command' | grep -q 'git commit' && { echo 'Running pre-commit checks...'; bun run lint && bun run typecheck; }"
          }
        ]
      }
    ]
  }
}


Save this to 

.claude/settings.json

 in your project root. That's it. Now every time Claude tries to run 

git commit

 , it first runs your lint and typecheck scripts. If either fails, the commit is blocked.

Option 2: External script (cleaner for complex logic)

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "bash .claude/hooks/pre-commit.sh"
          }
        ]
      }
    ]
  }
}


Then create the script:

#!/bin/bash
# .claude/hooks/pre-commit.sh
​
COMMAND=$(jq -r '.tool_input.command' < /dev/stdin)
​
if echo "$COMMAND" | grep -q 'git commit'; then
  echo "Running checks before commit..."
  bun run typecheck || { echo "Typecheck failed!" >&2; exit 2; }
  bun run lint || { echo "Lint failed!" >&2; exit 2; }
  echo "All checks passed"
  exit 0
fi
​
exit 0


Make it executable:

chmod +x .claude/hooks/pre-commit.sh


The external script approach is better for anything beyond a one-liner. Easier to debug, easier to version control, easier to test on its own.

Exit code 2 is your power move

 

. It blocks the tool call entirely and tells Claude why (via stderr). Exit 0 lets everything through. Any other exit code is a non-blocking warning.

⚠ Again, 

always

 use exit code 2 for hooks where you want Claude Code to 

intervene

 (don't forget!)

Practical recipes: the bookmark-this section

Here are ten copy-pasteable recipes. Each one solves a real problem. I've tested them all. Adapt the paths and commands to your stack.

Branch protection: block force-push to main

#!/bin/bash
# .claude/hooks/branch-protection.sh
COMMAND=$(jq -r '.tool_input.command' < /dev/stdin)
​
if echo "$COMMAND" | grep -qE 'git push.*(--force|-f).*main'; then
  echo "BLOCKED: Force-pushing to main is not allowed." >&2
  exit 2
fi
​
if echo "$COMMAND" | grep -qE 'git push.*(--force|-f).*master'; then
  echo "BLOCKED: Force-pushing to master is not allowed." >&2
  exit 2
fi
​
exit 0


This one's non-negotiable. Claude should never force-push to your primary branch. Full stop.

Auto-format before commit

#!/bin/bash
# .claude/hooks/auto-format.sh
COMMAND=$(jq -r '.tool_input.command' < /dev/stdin)
​
if echo "$COMMAND" | grep -q 'git commit'; then
  echo "Auto-formatting staged files..."
  npx prettier --write $(git diff --cached --name-only --diff-filter=ACM) 2>/dev/null
  git add -u
  echo "Formatting complete"
fi
​
exit 0


Notice this exits 0 even after formatting. It's a pass-through hook; it modifies the staged files but doesn't block the commit.

Enforce conventional commits

#!/bin/bash
# .claude/hooks/conventional-commits.sh
COMMAND=$(jq -r '.tool_input.command' < /dev/stdin)
​
if echo "$COMMAND" | grep -q 'git commit'; then
  MSG=$(echo "$COMMAND" | sed -n "s/.*-m '\([^']*\)'.*/\1/p")
  [ -z "$MSG" ] && MSG=$(echo "$COMMAND" | sed -n 's/.*-m "\([^"]*\)".*/\1/p')
​
  if [ -n "$MSG" ]; then
    if ! echo "$MSG" | grep -qE '^(feat|fix|docs|style|refactor|test|chore|perf|ci|build|revert)(\(.+\))?: .+'; then
      echo "BLOCKED: Commit message must follow Conventional Commits format." >&2
      echo "Expected: type(scope): description" >&2
      echo "Types: feat, fix, docs, style, refactor, test, chore, perf, ci, build, revert" >&2
      echo "Got: $MSG" >&2
      exit 2
    fi
  fi
fi
​
exit 0


This parses the commit message out of the command and validates it against the Conventional Commits pattern. Claude learns fast; after being blocked once or twice, it starts writing properly formatted messages on its own.

Catch secrets before they ship

#!/bin/bash
# .claude/hooks/secret-scan.sh
COMMAND=$(jq -r '.tool_input.command' < /dev/stdin)
​
if echo "$COMMAND" | grep -q 'git commit'; then
  STAGED=$(git diff --cached --name-only)
​
  for file in $STAGED; do
    if [ -f "$file" ]; then
      if grep -qE '(AKIA[0-9A-Z]{16}|sk-[a-zA-Z0-9]{48}|ghp_[a-zA-Z0-9]{36}|-----BEGIN (RSA |EC )?PRIVATE KEY-----)' "$file"; then
        echo "BLOCKED: Potential secret detected in $file" >&2
        echo "Found what looks like an API key or private key." >&2
        exit 2
      fi
    fi
  done
fi
​
exit 0


Pattern matching for AWS keys, OpenAI keys, GitHub tokens, and private keys. It's not exhaustive (use a proper tool like 

gitleaks

 for production), but it catches the obvious mistakes.

Run tests before commit

#!/bin/bash
# .claude/hooks/test-gate.sh
COMMAND=$(jq -r '.tool_input.command' < /dev/stdin)
​
if echo "$COMMAND" | grep -q 'git commit'; then
  echo "Running test suite..."
  npm test 2>&1
  TEST_EXIT=$?
​
  if [ $TEST_EXIT -ne 0 ]; then
    echo "BLOCKED: Tests failed with exit code $TEST_EXIT" >&2
    exit 2
  fi
​
  echo "All tests passed"
fi
​
exit 0


Simple. Effective. Swap 

npm test

 for 

bun test

 , 

pytest

 , 

phpunit

 , whatever your stack uses.

Slack notification on commit

#!/bin/bash
# .claude/hooks/slack-notify.sh
# Use as a PostToolUse hook, not PreToolUse
COMMAND=$(jq -r '.tool_input.command' < /dev/stdin)
​
if echo "$COMMAND" | grep -q 'git commit'; then
  BRANCH=$(git branch --show-current)
  MSG=$(git log -1 --pretty=%B 2>/dev/null)
​
  curl -s -X POST "$SLACK_WEBHOOK_URL" \
    -H 'Content-type: application/json' \
    -d "{\"text\": \"Claude Code committed to *${BRANCH}*: ${MSG}\"}" \
    > /dev/null 2>&1 &
fi
​
exit 0


Configure this as a 

PostToolUse

 hook so it fires after the commit succeeds. The 

&

 at the end of the curl command runs the notification in the background so it doesn't slow things down.

Auto-stage related files

#!/bin/bash
# .claude/hooks/auto-stage.sh
COMMAND=$(jq -r '.tool_input.command' < /dev/stdin)
​
if echo "$COMMAND" | grep -q 'git commit'; then
  # Stage any unstaged .test. files if their source file is staged
  for file in $(git diff --cached --name-only); do
    TEST_FILE="${file%.*}.test.${file##*.}"
    if [ -f "$TEST_FILE" ] && ! git diff --cached --name-only | grep -q "$TEST_FILE"; then
      echo "Auto-staging related test file: $TEST_FILE"
      git add "$TEST_FILE"
    fi
  done
fi
​
exit 0


If you've staged 

utils.ts

 , this automatically stages 

utils.test.ts

 if it exists and has changes. Keeps test files from being accidentally left out.

Block commits to wrong branch

#!/bin/bash
# .claude/hooks/branch-policy.sh
COMMAND=$(jq -r '.tool_input.command' < /dev/stdin)
​
if echo "$COMMAND" | grep -q 'git commit'; then
  BRANCH=$(git branch --show-current)
​
  if [ "$BRANCH" = "main" ] || [ "$BRANCH" = "master" ]; then
    echo "BLOCKED: Direct commits to $BRANCH are not allowed." >&2
    echo "Create a feature branch first: git checkout -b feature/your-feature" >&2
    exit 2
  fi
fi
​
exit 0


File size guard

#!/bin/bash
# .claude/hooks/file-size-guard.sh
COMMAND=$(jq -r '.tool_input.command' < /dev/stdin)
MAX_SIZE=1048576  # 1MB in bytes
​
if echo "$COMMAND" | grep -q 'git commit'; then
  for file in $(git diff --cached --name-only); do
    if [ -f "$file" ]; then
      SIZE=$(wc -c < "$file")
      if [ "$SIZE" -gt "$MAX_SIZE" ]; then
        echo "BLOCKED: $file is $(( SIZE / 1024 ))KB, exceeds 1MB limit." >&2
        echo "Consider using Git LFS for large files." >&2
        exit 2
      fi
    fi
  done
fi
​
exit 0


Review gate with AI-powered code review

#!/bin/bash
# .claude/hooks/review-gate.sh
COMMAND=$(jq -r '.tool_input.command' < /dev/stdin)
​
if echo "$COMMAND" | grep -q 'git commit'; then
  DIFF=$(git diff --cached --stat)
  LINES_CHANGED=$(git diff --cached --numstat | awk '{s+=$1+$2} END {print s}')
​
  if [ "${LINES_CHANGED:-0}" -gt 200 ]; then
    echo "WARNING: Large commit detected ($LINES_CHANGED lines changed)."
    echo "Changed files:"
    echo "$DIFF"
    echo ""
    echo "Consider breaking this into smaller commits."
    # Exit 0 to warn but not block; change to exit 2 if you want to enforce
    exit 0
  fi
fi
​
exit 0


A soft gate. It warns about large commits but doesn't block them. Change 

exit 0

 to 

exit 2

 at the end if you want enforcement.

CLAUDE.md vs hooks: when to use which

I think about Claude Code configuration as a four-layer model:

CLAUDE.md files

 are the context layer. Project conventions, coding standards, architectural decisions. This is where you tell Claude 

how

 to work.

Hooks in .claude/settings.json

 are the enforcement layer. This is where you 

make

 Claude follow the rules. No amount of polite instruction in CLAUDE.md can match a hard 

exit 2

 .

.claudeignore

 is the security boundary. Files and directories Claude should never read or touch.

MCP servers

 are the extension layer. External tool integrations that give Claude new capabilities.

CLAUDE.md is a suggestion. Hooks are a contract. Use CLAUDE.md to explain what you want. Use hooks to enforce what you require.

Git hooks vs Claude Code hooks

These two systems overlap but serve different masters.

Trigger source:

Git hooks:

 Triggered by human git commands in the terminal

Claude Code hooks:

 Triggered by Claude Code's tool calls

Scope:

Git hooks:

 Limited to git events (pre-commit, commit-msg, post-merge, etc.)

Claude Code hooks:

 Can intercept any tool call, including file writes, reads, and arbitrary shell commands

Configuration:

Git hooks:

 Scripts in 

.git/hooks/

 (or managed by husky/lefthook)

Claude Code hooks:

 JSON in 

.claude/settings.json

Sharing:

Git hooks:

Debugging hooks

Hooks fail silently by default. That makes debugging frustrating, and honestly, I hit most of these issues within the first hour of experimenting.

Shell profile issues

Your hook runs in a non-interactive shell. That means 

.bashrc

 , 

.zshrc

 , and their aliases aren't loaded. If your hook calls 

bun

 , 

nvm

 -managed 

node

 , or anything installed via a version manager, use absolute paths:

#!/bin/bash
# BAD: might not find bun
bun run lint
​
# GOOD: use absolute path
/Users/yourname/.bun/bin/bun run lint
​
# BETTER: find it dynamically
export PATH="$HOME/.bun/bin:$HOME/.nvm/versions/node/$(cat $HOME/.nvmrc 2>/dev/null || echo 'v20.0.0')/bin:$PATH"
bun run lint


Matcher gotchas

The matcher 

"Bash"

 matches when Claude uses the Bash tool. But Claude might also use the 

Write

 tool to modify files directly, bypassing your Bash-based hooks entirely. If you're guarding file writes, you need to match on 

"Write"

 as well.

stderr vs stdout

On exit 0, stdout is parsed for JSON output (shown in verbose mode for most events). On exit 2 (blocking), stderr is what gets fed back to Claude as the error message. Make sure your blocking messages go to stderr:

#!/bin/bash
# Capture typecheck output; on failure, send reason to stderr for Claude to see
bun run typecheck 2>&1 || { echo "Typecheck failed!" >&2; exit 2; }

Known issues and workarounds

Session persistence

Hooks are loaded when Claude Code starts a session. If you modify 

.claude/settings.json

 while a session is running, Claude may not pick up the changes immediately. Restart the session to be safe.

Recursion risk

Be careful with hooks that themselves invoke Claude Code or trigger shell commands that match your own matchers. A PreToolUse hook that runs 

git status

 could theoretically trigger another Bash tool call. In practice, Claude Code doesn't re-enter hooks recursively, but keep your hook scripts focused and avoid unnecessary side effects.

Snapshot security

The 

.claude/settings.json

 file is part of your project. Anyone who can modify that file can modify your hooks. Treat it with the same care as your CI configuration. Review changes to it in pull requests. For security-critical hooks that shouldn't be overridable per-project, use a global 

~/.claude/settings.json

 instead.

Performance

Every Bash tool call runs through every matching hook. If you have five PreToolUse hooks matching 

"Bash"

 , all five execute in parallel for every shell command Claude runs, not just git commits. Be mindful of this. Use the 

grep -q 'git commit'

 pattern to bail out early for commands you don't care about.

Treat .claude/settings.json like CI config. Review changes in PRs. Use global settings for hooks that must not be overridden.
