What Claude Code CLI Actually Does

Claude Code is an agentic command-line tool from Anthropic. It reads codebases, edits files, runs shell commands, manages git workflows, and calls external systems through Model Context Protocol (MCP) servers. It does not just suggest code. It executes it.

That is the part most documentation glosses over. Claude Code is not Anthropic's ant CLI, which is a thin API client for chat completions. Claude Code is a terminal binary that takes actions on your machine, your repo, and any service you connect it to. It ships as a standalone CLI, a VS Code extension, a JetBrains plugin, and a GitHub Action.

The practical implications matter. A tool that can run npm install, edit your .env, push commits, and call internal APIs through MCP servers is not in the same security category as an autocomplete plugin. An agent that can run rm -rf is a different security category than an autocomplete tool. That distinction matters the moment Claude Code stops running on one developer's laptop and starts running inside CI pipelines, scheduled jobs, or shared infrastructure.

Keep that framing in mind as you work through the commands and flags below. Most of them are about giving Claude Code more autonomy. The governance question is what stops that autonomy from compounding into risk.

Install Claude Code CLI

Claude Code supports several install paths. Use whichever matches your platform.

macOS and Linux (recommended):

curl -fsSL https://claude.ai/install.sh | bash

Homebrew (macOS):

brew install --cask claude-code

Windows (PowerShell):

irm https://claude.ai/install.ps1 | iex

Windows (WinGet):

winget install Anthropic.ClaudeCode

Anthropic also publishes an npm package:

npm install -g @anthropic-ai/claude-code

Anthropic's current documentation lists npm as a supported install path, and notes that it installs the same native binary as the standalone installer. The native installer script is generally the recommended starting point for new installs, but npm remains a valid option, especially in environments that already standardize on Node tooling. Check the official install page for the latest guidance before pinning a choice in your provisioning scripts.

Prerequisites:

Node.js 18 or higher

An Anthropic account with a Pro, Max, Team, or Enterprise subscription, or a Console API key

A terminal with shell access (bash, zsh, or PowerShell)

Once installed, navigate to any project directory and run claude to start an interactive session. Claude Code will detect the repo context and prompt you to authenticate on first run.

Claude Code CLI Flags for Scripting and Automation

This is the section worth bookmarking. These flags are what turn Claude Code from a chat tool into a scriptable component inside a CI pipeline or shell script.

--print / -p

Non-interactive mode. Claude runs the prompt, writes the output, and exits. Pipe it like any other Unix tool.

claude -p "summarize this repo" > overview.txt

--output-format json

Machine-readable output. Combine with jq or any JSON parser.

claude -p --output-format json "list all TODO comments" | jq '.todos'

--worktree / -w

Runs the session in an isolated git worktree. Useful when you want Claude Code to make changes without touching your active branch.

--allowedTools

Restricts which tools Claude can invoke. This is the most important flag for automation. Pair it with read-only tools when you want Claude to analyze without modifying.

claude -p --allowedTools "Read" "Grep" "Glob" "find auth bugs"

--max-turns

Circuit breaker for runaway agent loops. Limits how many tool-call iterations Claude can perform before terminating. Set conservatively for CI runs.

--agents

Inline subagent definitions. Lets you spawn specialized agents from a CI script without checking in agent config files.

--session-id

Named sessions for tracking work across branches or runs. Useful when you want to resume context later.

Here is a realistic CI snippet that uses these together. A GitHub Action that runs Claude on every pull request to generate a code review comment:

name: Claude code review

run: |

claude -p \

--allowedTools Read,Grep,Glob \

--max-turns 5 \

--output-format json \

"Review the changes in this PR for security issues, missing tests, and unclear naming" \

gh pr comment $ \

--body "$(jq -r '.summary' review.json)"

That workflow is useful. It is also the kind of automation that creates the governance problem we cover later. A CI runner with --allowedTools Read,Grep,Glob is restricted today. If a future engineer adds Bash to that list to fix a test failure, you have just given an LLM shell access to your CI environment. The control plane needs to live outside the pipeline.

Slash Commands and Session Management

Slash commands run inside an active Claude Code session. They control state, configuration, and behavior without leaving the REPL.

Session control

/resume, /continue, /rename, /fork, /clear, /exit

Memory and context

/init initializes a CLAUDE.md file for shared project context

/memory shows or edits session memory

/context displays the current context window

/compact summarizes and shortens context to free tokens

/add-dir adds a directory to the working set

Cost and observability

/cost shows token spend for the current session

/stats prints session statistics

/statusline toggles the live status bar

Configuration

/permissions reviews and modifies tool permissions

/config opens configuration settings

/hooks manages session lifecycle hooks

/mcp manages MCP server connections

/agents lists and switches between configured subagents

Productivity

/export, /extra-usage, /fast, /tasks, /status

Named sessions are underused. Most developers re-explain context every time they start Claude Code. Try this pattern instead:

claude --session-id "feature-$(git branch --show-current)"

Combined with /rename, this makes session history searchable and meaningful when you come back to a feature branch a week later. /cost and /stats are also worth running periodically. Token spend on agentic CLIs adds up fast, and /cost is the only built-in way to see what a single session is consuming.

System Prompt and Permission Flags

Claude Code has four system prompt flag variants for customizing model behavior, plus a permission model that controls when Claude asks before taking an action.

The permission model is the first line of defense. By default, Claude prompts before running shell commands, modifying files, or calling external tools. That prompt-and-confirm flow breaks CI, which is why --dangerously-skip-permissions exists.

Use --dangerously-skip-permissions honestly. It exists because permission prompts make automation impossible. Using it without a sandboxed runner is a production incident waiting to happen. Pair it with --allowedTools and --max-turns to bound the blast radius:

claude -p \

--dangerously-skip-permissions \

--allowedTools Read,Grep \

--max-turns 3 \

"analyze the auth module"

Custom skills can declare their own permission posture in frontmatter. This is the right pattern for shared team skills:

name: security-auditor

description: Audit code without making changes

allowed-tools: Read, Grep, Glob

The takeaway is simple. Tool restriction is the first layer of agent control. It is necessary, but it is not sufficient. The flag lives in the CLI invocation, which means anyone editing the pipeline can change it. Real governance enforces tool boundaries upstream of the developer or the CI script.

Connecting Claude Code to MCP Servers

This is the section most competitor articles skip, and it is where the governance story starts to matter.

claude mcp registers Model Context Protocol servers so Claude Code can discover and call external tools. MCP is the bridge between Claude Code and the systems you actually want an agent to interact with: internal APIs, databases, ticketing systems, observability stacks, and so on.

A simple registration:

claude mcp add my-internal-api \

--transport sse \

--url https://api.internal.example.com/mcp

From there, Claude Code can call tools/list to discover what the server exposes and tools/call to invoke a specific tool.

The practical problem is what most teams do next. MCP servers get exposed with static API keys, basic auth, or no auth at all. The MCP specification moved to OAuth 2.1 for a reason. If Claude Code can call a tools/call method on an internal MCP server, that call needs the same authorization treatment you give a production API. Static keys do not give you per-agent identity, per-tool scopes, or the ability to revoke access when a session ends.

There is also the question of where MCP tools come from. Most internal services are already REST APIs. Rewriting them as MCP servers is wasted work. A better approach is to expose existing APIs as MCP tools through a gateway. Gravitee's Agent Tool Server converts REST APIs into MCP-compliant tools by enabling an MCP entrypoint on any v4 proxy API. You import an OpenAPI spec, flip the entrypoint, and the gateway generates structured tool definitions that Claude Code can discover and invoke. All your existing API policies (auth, rate limiting, logging) still apply.

For a deeper view of how AI gateways and agent gateways relate, see Gravitee's introduction to AI Gateway and Agent Gateway.

The AI Governance Wake-Up Call for Enterprise Teams

For most of the LLM era, governance meant content filters and prompt logging. You watched what the model said, redacted PII, and called it a day. That model breaks the moment an agent like Claude Code can execute shell commands, read your source code, hit your internal APIs, and commit to git.

The risk is no longer a model saying something it should not. The risk is an agent doing something it should not.

What changed in the last twelve months:

Agents run with developer credentials, often with broad git and filesystem access.

MCP servers expose internal systems with static keys and basic auth.

CI pipelines run claude -p against production repos with --dangerously-skip-permissions.

Most security teams have no audit trail of which agent invoked which tool on which resource.

Token spend on LLM APIs is not budgeted anywhere except the credit card statement.

This is the AI governance wake-up call for enterprise teams. The controls that worked for chatbots do not work for agents. Read Gravitee's view on Agentic IAM and the related post on security in multi-agent systems for the longer argument.

The short version: shipping agents without identity, scoped tokens, and tool-level authorization is not an oversight. It is a governance debt that compounds with every new agent, every new MCP server, and every CI pipeline that calls claude -p. The fix is not to slow down agent adoption. The fix is to put the controls in place before the surface area grows past the point of recovery.

Securing Claude Code CLI at Scale

When Claude Code moves from prototype to production, four controls separate teams that can ship safely from teams that cannot.

Agent identity. Stop reusing developer API keys for CI runs. Each agent should have its own identity with OAuth 2.1 and short-lived tokens. Gravitee's Agentic IAM handles this with RFC 8693 token exchange, so user tokens can be exchanged for scoped agent tokens with actor claims. When a user session ends, every delegated agent token is invalidated automatically.

MCP method-level ACLs. Restrict access at the MCP method level (tools/call, resources/read, prompts/list), not just at the HTTP route level. An MCP server exposes one HTTP endpoint, but dozens of tools behind it. Gravitee's MCP Proxy enforces ACLs per agent, per tool, per operation, so an agent restricted to tools/list cannot suddenly invoke tools/call with elevated scope.

LLM guardrails. Token quotas, PII filtering, prompt injection detection, and semantic caching on every call to Anthropic, OpenAI, or Bedrock. The model path needs the same governance you apply to production APIs. For a concrete example, see how semantic caching reduces LLM cost and latency at the gateway.

Unified observability. One dashboard for LLM token spend, MCP tool invocations, and agent-to-agent calls. If you cannot see which agent called which tool on which resource, you cannot answer the audit question. Gravitee covers this in AI observability for enterprise teams.

These controls do not slow developers down. They live at the gateway, not in the agent code or the CI script. Your developers keep running Claude Code the way they already do. The platform team gets identity, authorization, and observability without rewriting a single agent.

Frequently Asked Questions

How do I connect Claude Code CLI to a custom MCP server?

Use claude mcp add 

 to register the server with its transport and URL. For internal APIs, expose them through an Agent Tool Server that converts OpenAPI specs into MCP-compliant tools rather than building a custom MCP server from scratch. This keeps your existing API governance (auth, rate limiting, logging) in front of the agent.

What are Claude Code CLI rate limits?

Limits depend on your Anthropic subscription tier (Pro, Max, Team, Enterprise) or your Console API plan. Inside a session, monitor consumption with /cost and /stats. For team deployments, do not rely on provider-side limits alone. Enforce token quotas at an AI Gateway so you can apply per-team or per-agent budgets and get one view across providers.

How do I configure Claude Code CLI for a team?

Check in a CLAUDE.md file at the repo root for shared project context. Use --allowedTools and skill frontmatter to enforce read-only or scoped behavior in CI. For organization-wide policy (authentication, PII redaction, audit logging, tool-level ACLs), route Claude Code traffic through an AI Gateway. That keeps governance out of individual repos and pipelines.

Is --dangerously-skip-permissions safe in CI?

Only inside a sandboxed runner with no production credentials. Pair it with --allowedTools to restrict the toolset and --max-turns to bound the blast radius. Even then, treat it as a last resort. A sandboxed runner with shell access can still leak data through MCP server calls if those servers are not properly secured.

How do I debug a failed Claude Code session?

Run claude logs 

 to see recent output. Check /hooks for misconfigured hook scripts. For automated runs, log the JSON output from --output-format json and parse for error fields. If the failure involves an MCP server, check the server logs for authorization errors. Static-key auth failures are one of the most common causes of silent MCP errors in CI.

How is securing Claude Code different from securing a normal API client?

A normal API client makes predictable calls. An agent decides what to call at runtime based on a prompt. That means you need authorization decisions that adapt to context (which user, which agent, which tool, which resource), not static role-based access. It also means you need observability that maps agent intent to actions, not just HTTP traces. This is why Agentic IAM exists as a category separate from human IAM.
