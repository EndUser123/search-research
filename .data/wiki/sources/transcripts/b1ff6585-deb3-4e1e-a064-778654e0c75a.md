I switch shells often but prefer to do it on my own terms. While exploring Claude code this week (in beta) I thought I would share some of the setup snags I encountered setting up on Windows the way I want (invoking from Powershell).

The general getting started is here: 

Claude Code overview — Anthropic

https://docs.anthropic.com/en/docs/agents-and-tools/claude-code/overview

Setting up WSL (npm, node and claude-code)

Claude's instructions for wsl (Windows Subsystem for Linux) are fairly straight-forward though gloss over packages and paths which will be the focus of this article.

You need wsl and we can check we have it installed and a running container like this (for installation, consider sources like: 

Install WSL | Microsoft Learn

https://learn.microsoft.com/en-us/windows/wsl/install

):

wsl --list -v
  NAME              STATE           VERSION
* Ubuntu-24.04      Running         2
  docker-desktop    Stopped         2


First snag I hit was that Claude code didn't want to install in wsl, I noticed I could run “ 

npm — version

”, but not “ 

node — version

” in wsl, so checked where these were resolving. The which command is helpful here — we want both to point to a linux version deployed to “/usr/bin/…” and not a windows version via “/mnt/c/…” .

user@host:~$ which npm
/usr/bin/npm
user@host:~$ which node
/usr/bin/node


My npm command was pointing to “mnt/c/…” so installing in the container was the next step via “ 

sudo apt install npm nodejs

”. If like me, you forgot your wsl user password change it by running wsl as root and then updating the user password (i.e. run “ 

wsl -u root

” and then “ 

passwd [[username]]

” before continuing).

user@host:~$ sudo apt install npm nodejs
Reading package lists... Done
Building dependency tree... Done
Reading state information... Done
npm is already the newest version (9.2.0~ds1-2).
nodejs is already the newest version (18.19.1+dfsg-6ubuntu5).
0 upgraded, 0 newly installed, 0 to remove and 176 not upgraded.


The $PATH can sometimes be a bit fiddly and the container resources should be listed first. For npm in the below example we can see that when calling npm you get the one in /usr/bin/npm (preferred), but that it exists in multiple places. If you have unexpected behavior, consider pruning the /mnt/c/… bits off your path you don't expect to use and see if that helps.

user@host~$ which npm
/usr/bin/npm
user@host:~$ whereis npm
npm: /usr/bin/npm /usr/share/npm /mnt/c/Program Files/nodejs/npm 
    /mnt/c/Users/user/AppData/Roaming/npm/npm /usr/share/man/man1/npm.1.gz


Claude still wasn't happy to install and was complaining that it couldn't write in the node global packages directory. Rather than use sudo to install (which almost always turns into sudo to run and therefore should be avoided at all cost), I updated the user “global packages” and store them somewhere we own instead of the lib directory.

For this example we are creating a new .npm-global area, and configuring npm to use this folder for global/default packages. In line with the guidance for installing Claude code I've also set os to linux. Use “ 

npm config list

” to help verify.

mkdir -p ~/.npm-global/lib
npm config set prefix '~/.npm-global'
npm config set os linux


Ensure the .npm-global folder is added to $PATH automatically by appending something like this to your shell init script like ~/.profile:

# set PATH to include npm-globals if exists
if [ -d "$HOME/.npm-global/bin" ] ; then
    PATH="$HOME/.npm-global/bin:$PATH"
fi


And reset your shell to include the new path:

user@host:~$ source ~/.profile
user@host:~$ echo $PATH
/home/user/.npm-global/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:...


Finally, we can install claude-code:

npm install -g @anthropic-ai/claude-code
claude


Running claude for the first time will run the setup. Click the link and follow directions then copy/paste the key back in the shell. This all stays inside the wsl user space so changing directories later maintains the same API access which is great.

PowerShell

I often open PowerShell by default and considering the above, you can't simply run claude from the location you are in. That said, we can invoke wsl directly and tell it to then run claude:

PS C:\Users\user\source\repos\myrepo> wsl -e bash -c "source ~/.profile && claude"

This is great — but I'm not going to type * 'wsl -e bash -c “source ~/.profile && claude*' every time so let's hide that away in Powershell so we just run 

claude

 like in wsl.

We can achieve this by adding a function and making it available on every shell via our $PROFILE (like we did with the node bin directory via ~/.profile in wsl). $PROFILE doesn't exist by default but once created will be referenced (use $PROFILE to avoid path guesswork):

PS C:\path> Test-Path $PROFILE
False
PS C:\path> New-Item -Path $PROFILE -ItemType File -Force
    Directory: C:\Users\user\OneDrive\Documents\WindowsPowerShell
Mode                 LastWriteTime         Length Name
----                 -------------         ------ ----
-a----        22/04/2025     12:29              0 Microsoft.PowerShell_profile.ps1


With the file available (blank) we can add the following claude function:

function claude { wsl -e bash -c "source ~/.profile && claude" }


To skip opening the file in notepad, just copy/paste the below:

Add-Content -Path $PROFILE -Value "function claude { wsl -e bash -c ""source ~/.profile && claude"" }"


To test our new function, we can open a new terminal and verify it exists:

PS C:\Users\user> get-command claude
CommandType     Name                                               Version    Source
-----------     ----                                               -------    ------
Function        claude


Putting it all together

Now that we have claude-code configured on wsl and our claude function in PowerShell, we can open a new PowerShell window, navigate to our code folder and simply call claude:

PS X:\src\project> claude
