Summary

Running a hybrid 

attention + DeltaNet (linear-attention / SSM)

 model via 

llama-server

 with 

cache_prompt: true

 in a multi-turn tool-using conversation produces outputs where individual digits are silently dropped from numeric tokens and from variable-name substrings. The 

same final-turn prompt

, replayed as a 

single fresh request

 against a freshly-restarted 

llama-server

 with an empty prompt cache, produces correct output on every run. The corruption is reproducible and deterministic-ish (it hits different cells on different runs but is consistently present in the cached-state path, and consistently absent in the fresh path).

This is a 

distinct symptom from the performance regression in #20225

 (full re-prefill every turn) and the crash in 

#20222

https://github.com/ggml-org/llama.cpp/issues/20222

 ("Chunk not found"). Those issues at least fail loudly. This one produces plausible-looking but numerically wrong output with no log warnings.

This looks like a state-management bug in how 

llama-server

 saves and restores the recurrent (linear-attention / SSM) state across requests when the common-prefix point between the new prompt and the cached prompt is not at the end of the cached sequence — i.e. when the host application mutates the middle of the message history between turns. A candidate low-level cause is the 

copy_cell

 bug identified in PR 

#20700

https://github.com/ggml-org/llama.cpp/pull/20700

 ( 

ggml_view_1d

 receiving byte count instead of element count during recurrent state checkpoint/restore), which affects all checkpoint/restore operations on recurrent state. 

Maintainers: please confirm whether this fix has landed in or before build 84ae843 .

 If not, that may be the patch.

The hybrid architecture is the relevant factor. The model has both standard attention layers (with positional KV cache) and DeltaNet layers, which maintain a single rolling recurrent state vector with no positional indexing. Resuming a conversation from a cached prefix of length N requires restoring the recurrent state as of token N — this is the path that appears to be buggy.

Reproduction

The bug was observed in a real application: a data-analysis tool loop where the model issues 

search_variables

 / 

execute_python

 / 

task_tracker

 tool calls across ~25 rounds, and between rounds the host application 

mutates the middle of the message list

 in two ways:

After 

store_result

 , the host replaces a previous 

role=tool

 message (a large 

search_variables

 output) with a short stub string.

After every round, the host removes any previous 

user

 -role 

[RESULT_PERSIST]

 message and re-appends an updated one at the end.

Both mutations move the common-prefix point (between the cached tokens and the new prompt's tokens) backwards from the tail into the middle of the sequence. Over ~22 such mutations, state drift accumulates. In the final-answer turn, the model generates a markdown report where ~1 in 10 dense digit sequences has a dropped digit.

Hypothesis

llama-server

 with 

cache_prompt: true

 reuses the longest common prefix between the cached token sequence and the incoming prompt's tokens. For standard attention layers this is straightforward — keep the K/V tensors for the prefix, prefill the new suffix. For DeltaNet / linear-attention / SSM layers it is not: there is no per-position cache, only a rolling recurrent state. To "resume" at the end of a prefix of length N you need the recurrent state 

as of token N

.

When the common-prefix point moves backwards (e.g. from token 18,900 in the previous cached prompt to token 14,200 in the new one, because the host mutated a message at ~token 14,200), the server must restore the recurrent state from a checkpoint and replay the new suffix forward. We suspect either:

The restore uses a snapshot at the wrong token position, or

The restore is numerically imprecise due to the 

copy_cell

 byte-vs-element-count bug identified in PR 

feat: MTP support for dense Qwen 3.5 with FastMTP vocabulary trimming #20700

https://github.com/ggml-org/llama.cpp/pull/20700

, or

Not all per-layer DeltaNet state is fully reset before the replay.

Small drift on each restore accumulates across 20+ rounds, and by the final turn the recurrent state is enough off that dense-digit-sequence generation (where the model needs to hold a numeric value in state across 5+ output tokens) produces single-token dropouts. Attention-heavy tokens (short words, structural markup) are unaffected; tokens whose correct generation depends heavily on the DeltaNet layers' recurrent state (sustained numeric sequences, repeating-digit patterns, long identifier substrings) are where drift shows up.

Candidate fix: 

copy_cell

 in 

llama-memory-recurrent.cpp

PR 

#20700

https://github.com/ggml-org/llama.cpp/pull/20700

 identifies a bug where 

ggml_view_1d

 in 

copy_cell

 receives a byte count instead of an element count, corrupting all recurrent state checkpoint/restore operations. This would produce exactly the kind of off-by-N recurrent state that causes low-level per-token drift without an obvious crash. 

Is this fix present in or before 84ae843 ?

"9"

 ), or

"8."

 ).

_llamacpp_chat_stream

 ; deltas are now accumulated verbatim. Both 

qwen-chat-api

 and 

qwen-chat-api-internal

 restarted.
