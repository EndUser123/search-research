Architecture Plan: Handoff Context Preservation Enhancement

Context

The handoff V2 system (P:/packages/handoff) preserves context across session compactions. The transcript 03-19-2025 -

 

handoff 0.txt demonstrates the symptom: the AI had to be corrected 3 times about "prompting enhancements" because the

 

handoff only captured the last user message, not the conversation context where the user clarified what they meant.

Root Cause: extract_last_substantive_user_message() in transcript.py (lines 662-753) only extracts the LAST substantive

 

user message, losing:

User's refinements and clarifications

Conversation history about what the task actually is

Context about why earlier interpretations were wrong

Current Architecture Analysis

Current Design (What Works)

V2 envelope schema: Structured handoff with checksums, evidence validation, status tracking

Multi-terminal safe: Session-scoped (not terminal-scoped), no shared mutable state

Evidence freshness: Content hash verification detects stale files

Bridge tokens: Decision continuity across compactions

Quality scoring: Handoff quality assessment

Current Gap (What's Missing)

The goal field is too narrow:

Current: Single line from last user message

goal = extract_last_substantive_user_message(transcript_path)

Example result: "Continue current task (meta-discussion filtered)"

This loses the conversation thread where the user refined the task 3 times.

Solution Options (Verbalized Sampling)

Option A: Structured Conversation Summary (RECOMMENDED)

Approach: Add LLM-generated conversation summary to handoff envelope

Design:

Add new field conversation_summary to V2 envelope (alongside goal)

Generate summary using LLM with structured prompt:

User's original intent

Key clarifications and refinements

Constraints and decisions

What NOT to do (anti-goals)

Summary is concise (~300-500 tokens) vs full transcript (~10k+ tokens)

Store summary in envelope, reference full transcript via transcript_path

Tradeoffs:

Favors: Context preservation, accuracy, reduced user corrections

Sacrifices: Slightly higher compaction time (LLM call)

ISO 25010: +Maintainability (clearer context), -Performance Efficiency (LLM latency)

Why This Is Optimal:

Matches industry best practice: "summarize, don't dump"

Preserves clarifications without full transcript bloat

Structured format prevents ambiguity

Can be generated during PreCompact (parallelizable)

Option B: Expanded Goal Extraction (Multi-Line)

Approach: Extract last N user messages instead of just last 1

Design:

Modify extract_last_substantive_user_message() to capture last 3-5 messages

Join with newlines into multi-line goal

No LLM call required (pure extraction)

Tradeoffs:

Favors: Simplicity, no LLM latency

Sacrifices: Less structured, may include meta-discussion noise

Why Not Optimal:

Still misses clarifications buried in assistant responses

Multi-line goal is less structured than summary

May include irrelevant backtracking


--------------------------------------------------------------------------------


Option C: Full Transcript Reference

Approach: Always include full transcript in restore prompt

Design:

During restore, read full transcript from transcript_path

Inject last 1000 lines into restore message

No summary generation

Tradeoffs:

Favors: Maximum context retention

Sacrifices: Token cost, restore latency, complexity

Why Not Optimal:

Violates "summarize, don't dump" principle

High token cost (~10k+ tokens per restore)

Slower session starts


--------------------------------------------------------------------------------


Option D: Hybrid Recent Window + Summary

Approach: Combine verbatim recent messages with summary

Design:

Keep last 10 user messages verbatim

Add LLM-generated summary of older context

Inject both into restore prompt

Tradeoffs:

Favors: Best of both worlds (recent detail + old context)

Sacrifices: Higher complexity, more fields to maintain

Why Not Optimal:

Overkill for the observed problem

Recent messages already in transcript (redundant)

More complex than Option A
