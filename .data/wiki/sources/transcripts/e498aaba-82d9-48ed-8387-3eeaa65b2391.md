You asked Claude to understand a complex codebase last week.

Before it answered, something happened you didn't notice.

Claude didn't read your files directly. It spawned a separate AI instance — with its own isolated context window, its own tool restrictions, its own model — to explore your codebase. That agent read, searched, and mapped every relevant file, then sent back a clean summary. The 20,000 tokens of file content it consumed? Gone. Never touched your main conversation.

Claude answered using the summary.

You saw one response. Behind the scenes, two AI instances coordinated to produce it.

This is Claude Code's subagent system — and it has been running automatically in your sessions since you installed it. Most developers have never consciously worked with it. The ones who have are building development pipelines that make single-agent workflows look primitive.

And two months ago, a developer reverse-engineered Claude Code's binary and found something Anthropic had built but wasn't talking about. Something that changes everything.

More on that in a minute.

🧠 The Core Problem Subagents Solve

First, understand the architecture — because without it, subagents seem like unnecessary complexity.

Every file Claude reads enters your context window. Every search result, bash output, error message, explored directory — it accumulates. By the time Claude finishes understanding your codebase, your context window is 40% full of exploration noise that has nothing to do with the actual task you wanted done.

The context window degradation covered in our last post — the “Lost in the Middle” problem — gets dramatically worse when one agent tries to do everything.

Subagents solve this by isolation.

A subagent is a completely separate AI instance with its own context window. It does the messy work — reads 50 files, searches 200 functions, runs 20 bash commands — and returns only its final answer to your main conversation. The noise stays inside the subagent. Your main context sees one clean paragraph.

The one-line definition:

 

Subagents are isolated AI workers that absorb context pollution so your main conversation stays sharp.

The context savings are measurable. A thorough codebase exploration that would consume 35,000–50,000 tokens in your main context returns as a 2,000–4,000 token summary. One subagent run recovers nearly an hour of context capacity.

🤖 The Built-In Subagents Already Running In Your Sessions

Claude Code ships with built-in helper agents that fire automatically. You've never configured them. You've never invoked them. They've been running every session.

The Explore Subagent — Your Silent Code Reader

Triggers automatically when:

 Claude needs to search or understand code without making changes.

What it has:

 Read, Grep, Glob, Bash (read-only operations only) 

What it doesn't have:

 Edit, Write — intentionally locked out

Three thoroughness levels Claude chooses based on task complexity:

quick

 — targeted function or file lookup

medium

 — module-level understanding

very thorough

 — comprehensive codebase analysis

When you ask 

“how does the authentication flow work?”

 — Claude doesn't scan files itself. It dispatches Explore with 

very thorough

 . Explore maps your entire auth system and returns a structured summary. Your context receives that summary, not 30,000 tokens of raw file content.

The detail almost nobody writes about:

 Explore runs on 

Haiku

, not Sonnet. File reading and searching are mechanical operations that don't need frontier reasoning. Haiku handles them at roughly 80% lower cost. Claude Code has been doing model routing under the hood since day one.

The Plan Subagent — Your Informed Architect

Triggers automatically when:

 You enter plan mode and Claude needs to understand your codebase before proposing an approach.

When you say 

“I want to add real-time notifications to this app”

 and Claude enters plan mode — it doesn't write a plan immediately. The Plan subagent first reads your existing architecture, checks similar patterns, reviews your data model. Claude receives that research and proposes an approach that actually fits your codebase. No cargo-culting patterns that don't work with your stack.

The Documentation Lookup Subagent

Claude Code's own system prompt includes a built-in documentation workflow that uses a subagent whenever you ask 

“can Claude Code do…”

 or 

“does Claude Code have…”

 — it dispatches a subagent to look up the answer rather than relying on potentially stale training data.

This is Anthropic eating their own cooking. They use subagents to keep Claude Code accurate about Claude Code.

📁 Building Your Own — The Complete File Format

Custom subagents are Markdown files with YAML frontmatter. Here's the 

complete

 field reference — not the simplified version most tutorials show:

---
name: code-reviewer           # Required. Used for invocation and display.
description: "..."            # Required. This is how Claude decides when to delegate.
model: sonnet                 # sonnet | opus | haiku | inherit (default: inherit)
tools: Read, Grep, Glob       # Allowlist. Omit to inherit ALL tools from main session.
disallowedTools: Write, Edit  # Denylist. Alternative to tools allowlist.
permissionMode: default       # default | acceptEdits | bypassPermissions (use with caution)
maxTurns: 30                  # Max tool calls before agent stops. Default: unlimited.
skills:                       # Pre-inject skills into agent context at startup.
  - api-conventions
  - error-handling-patterns
hooks:                        # Agent-specific hooks (converted to SubagentStop events).
  Stop:
    - type: command
      command: ./scripts/notify.sh
color: red                    # UI color for visual distinction. Optional.
---
Your system prompt goes here in Markdown.


The fields that matter most and why:

 

**tools**

 

vs

 

**disallowedTools**

 — These are not equivalent. 

tools

 is an allowlist — the agent can only use what you specify, nothing else. 

disallowedTools

 is a denylist — the agent inherits everything and you block specific tools. If you omit both, the agent inherits every tool from the main session including all MCP servers. Be intentional. Tool sprawl is how agents do unexpected things. 

**permissionMode**

 — Three options that most guides skip entirely:

default

 — agent asks for permission just like normal Claude Code

acceptEdits

 — agent auto-approves file edits without asking (faster for write-heavy agents)

bypassPermissions

 — skips all permission checks entirely. Use only in sandboxed environments. If the parent session uses 

bypassPermissions

 , it overrides the subagent setting — you cannot restrict it further. 

**maxTurns**

 — This is the safety brake most developers forget. Without it, an agent with a complex task can run 200+ tool calls, burning through tokens and potentially doing unexpected things. Set 

maxTurns: 50

 for most agents. Set 

maxTurns: 100

 for deep research agents. Set it intentionally. 

**skills**

 — This is the feature almost nobody has written about. You can inject Skill content directly into a subagent's context at startup — not "make it available," but actually pre-load it. The subagent starts knowing your 

api-conventions

 and 

error-handling-patterns

 without having to discover and load them during execution.

skills:
  - api-conventions      # Full SKILL.md content injected at startup
  - error-handling-patterns


Combined with the Skills system from Day 2 of this series — this means every specialized agent you build starts with exactly the domain knowledge it needs. No discovery phase. No context burned on loading. Just immediate expertise.

🎯 The Description Field — The Most Important Line You'll Write

Everything else in your subagent config is implementation. The description field is the brain.

Claude reads every agent's description when deciding whether to delegate. It matches your request against all available descriptions and routes accordingly. A bad description means the agent never fires. A great description means it fires precisely when needed.

Weak description:

description: A code reviewer for TypeScript


Claude has no idea when to use this vs. just reviewing code itself.

Strong description:

description: Expert TypeScript and React code reviewer. Use proactively 
  after any code generation or modification task. Invoke when reviewing 
  PR changes, auditing new components, or checking recently modified files.
  Reviews for type safety, security vulnerabilities, and performance issues.


Three things make this work: specificity about 

what

 it does, the phrase 

“Use proactively”

 (directly from Anthropic's official docs — it significantly increases automatic delegation rate), and clear 

when

 conditions.

You can also invoke any agent explicitly by name:

Use the code-reviewer agent on the authentication module


Bypasses matching entirely. Guaranteed invocation regardless of description quality.

💡 The One Architecture Insight That Changes Everything

Here's the thing that the AntStack field guide identified — and it's the single most common point of confusion in all of Claude Code's documentation:

The file format for an agent and a subagent is identical.

Same YAML frontmatter. Same Markdown body. Same 

.claude/agents/

 directory.

The distinction is not in the file. The distinction is in the call site — who invokes it and in what context.

When you run 

claude --agent code-reviewer

 , that same file becomes your entire main session — Claude Code running as the code reviewer persona, with those tools and that system prompt, for the whole conversation.

When Claude delegates to 

code-reviewer

 from your main session, that same file runs as a child instance with an isolated context window.

Same file. Two completely different execution modes. The architectural implication: you design the file around the agent's expertise and constraints. The role it plays — orchestrator or worker — is determined at runtime, not at file creation.

This composability is intentional. You can promote a worker subagent to an orchestrator or demote an orchestrator to a worker without touching its definition.

**code-reviewer.md**

---
name: code-reviewer
description: Expert code reviewer for TypeScript, React, and Node.js.
  Use proactively after any code generation or modification. Invoke when 
  checking new components, reviewing PR changes, or auditing modified files.
tools: Read, Grep, Glob, Bash
model: sonnet
maxTurns: 40
---
You are a senior code reviewer. When invoked, run `git diff HEAD` to 
identify what changed, then review every modified file.
Check for:
- TypeScript type errors or unsafe `any` usage
- Missing error handling on async functions  
- Security issues: unvalidated inputs, exposed secrets, injection vulnerabilities
- Performance problems: unnecessary re-renders, N+1 queries
Output format - always in this order:
1. Critical (must fix - blocks merge)
2. Warnings (should fix)
3. Suggestions (nice to have)
4. One thing done well
Include filename and line number for every issue. Do NOT make changes.


**debugger.md**

---
name: debugger
description: Root cause analysis specialist. Use proactively when any 
  error occurs, tests fail, or behavior doesn't match expectations. 
  Always invoke BEFORE attempting a fix — never fix without diagnosing first.
tools: Read, Edit, Bash, Grep, Glob
model: sonnet
maxTurns: 60
---
You are an expert debugger specializing in root cause analysis.
Rule: Never fix what you haven't confirmed. Form a hypothesis. Test it. 
Then fix.
Steps:
1. Capture exact error message and stack trace
2. Find the specific file and line causing the issue
3. Read surrounding code for context
4. Form and test your root cause hypothesis
5. Implement the minimal fix that addresses root cause
6. Verify with the relevant test
Report: root cause, evidence, fix applied, how to prevent recurrence.


**security-auditor.md**

---
name: security-auditor
description: Application security specialist. MUST BE USED before any 
  commit touching auth, payments, user data, API endpoints, or database 
  queries. Checks OWASP Top 10 vulnerabilities.
tools: Read, Grep, Glob
model: sonnet
maxTurns: 50
permissionMode: default
---
You are an application security engineer. Audit for:
- Hardcoded secrets or API keys
- SQL injection (string interpolation in queries)
- Unvalidated user input in dangerous functions
- Missing auth/authorization checks on routes
- Exposed internal error details in responses
For each finding:
- Severity: Critical / High / Medium / Low
- File and exact line number
- What the vulnerability enables
- Specific fix with code snippet
If any Critical findings exist, state clearly: DO NOT MERGE.


**test-writer.md**

---
name: test-writer
description: Test generation specialist. Use proactively after implementing 
  any new function, component, or API endpoint. Generates comprehensive 
  test suites matching existing project patterns.
tools: Read, Write, Bash, Grep, Glob
model: haiku
maxTurns: 80
---
Before writing any tests:
1. Read 2-3 existing test files to understand conventions
2. Identify the testing framework
3. Use existing tests as templates
Write for every function/component:
- Happy path (expected inputs and outputs)
- Edge cases (boundaries, empty inputs, null)
- Error cases (invalid inputs, timeouts, failures)
After writing: run the tests. Fix any failures before completing.
Report: tests written, passing count, coverage percentage.


**researcher.md**

---
name: researcher
description: Technical research specialist. Use when Claude needs external 
  documentation, library comparisons, or best practice guidance. Runs 
  parallel research and returns concise structured findings.
tools: Read, Grep, Glob, WebFetch, WebSearch
model: haiku
maxTurns: 30
---
You are a technical researcher. Your output goes to another agent.
Be concise and structured - not conversational.
For any research topic:
1. Search official documentation first
2. Find the most recent relevant version
3. Identify common mistakes and gotchas
4. Find one working example
Output (under 400 words total):
- Key finding (1-2 sentences)
- Official source URL
- Working code example
- One gotcha to avoid


🪝 SubagentStart and SubagentStop — The Hooks Nobody Uses

From the Hooks post — you know hooks fire at specific moments. Two hook events are specifically designed for subagent workflows that most developers haven't touched yet.

SubagentStart

 — fires when a specific subagent begins

SubagentStop

 — fires when any subagent finishes

{
  "hooks": {
    "SubagentStart": [
      {
        "matcher": "db-agent",
        "hooks": [
          {
            "type": "command",
            "command": "./scripts/setup-db-connection.sh"
          }
        ]
      }
    ],
    "SubagentStop": [
      {
        "hooks": [
          {
            "type": "command", 
            "command": "./scripts/cleanup-and-log.sh"
          }
        ]
      }
    ]
  }
}


Real use cases:

SubagentStart on db-agent:

 automatically set up database connection before the agent runs, tear it down after

SubagentStop on security-auditor:

 automatically log every security audit to a file with timestamp

SubagentStop on any agent:

 pipe results to a queue file and print the next suggested command in the main session — this is how production pipeline automation works

The SubagentStop + queue pattern is how developers build actual software pipelines: 

pm-spec

 agent finishes → SubagentStop fires → hook reads queue → prints "Use architect-review agent on [spec]" in the main transcript → Claude sees it and runs the next stage. Reproducible, automated, no manual handoffs.

📐 The 3–4 Agent Rule — More Agents Doesn't Mean More Output

Here's the counterintuitive insight from experienced Claude Code users: 

more subagents often makes you less productive.

When you have 20 agents defined, you spend cognitive overhead deciding which one is right for each task. The routing friction adds up. The value of automatic delegation depends on Claude having a small, clear set of agents to choose from.

The practical limit most developers have settled on: 

3–4 active subagents for any given project.

Pick your highest-value agents for the codebase you're working on. For a TypeScript/React app: 

code-reviewer

 , 

debugger

 , 

test-writer

 . Three agents. Every task fits one of them cleanly. Auto-delegation works reliably. No routing confusion.

Add more agents as your workflow matures and you identify gaps. Don't install 20 agents on day one and wonder why Claude keeps picking the wrong one.

🔴 The Hidden Feature Anthropic Built But Didn't Announce

On December 18, 2025, a developer did something delightfully meta: they used Claude Code to read Claude Code's own source code.

Running strings analysis on the binary revealed 

TeammateTool

 — a fully-implemented multi-agent orchestration system with 13 distinct operations. Feature-flagged off. No documentation. No announcement.

On January 24, 2026, Mike Kelly packaged it into 

claude-sneakpeek

 and published it. Within hours: 281 points on Hacker News, 207 developers debating whether this was the future of development or a dangerous step too far.

What they found: 

Swarms mode

 — now officially called 

Agent Teams

.

Instead of talking to a single AI coder, you talk to a 

team lead

 that doesn't write code. It plans and delegates. When you approve the plan, it enters delegation mode and spawns a team of specialists who:

Share a live task board with dependencies

Work in parallel as teammates

Message each other to coordinate

Anthropic then officially released it on February 5, 2026.

Enable it:

// .claude/settings.json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}


Use it:

claude
> Build a REST API with authentication, rate limiting, and tests.
> Use a team of specialists for this.


Claude creates the plan, spawns specialists, coordinates their work. You approve or redirect.

The rough edges you need to know before using it:

The team lead sometimes implements instead of delegating. Tell it explicitly: 

“Wait for your teammates to complete their tasks before proceeding.”

 Or use delegate mode with 

Shift+Tab

 to restrict the lead to coordination-only tools.

Session resumption for in-process teammates doesn't work. 

/resume

 and 

/rewind

 don't restore active teammates — if you resume a session, the lead may try to message teammates that no longer exist. Spawn fresh ones.

Task status can lag. Teammates sometimes fail to mark tasks completed, blocking dependent work. Check manually if a task seems stuck.

One team per session. Teammates cannot spawn their own teams. This is deliberate — preventing infinite recursion and runaway cost.

The honest assessment:

 Agent Teams is experimental for real reasons. For production work with a deadline — stick with custom subagents, which are stable and battle-tested. For exploring and prototyping on non-critical projects — Agent Teams shows you where AI-assisted development is heading.

The pattern Addy Osmani documented: start with research and review tasks (clear boundaries, no code changes), then cross-layer features (frontend, backend, tests each owned by a different teammate), then large refactors. Each step increases coordination complexity — learn it incrementally.

📊 The Complete Decision Map — Subagents vs Slash Commands vs Skills vs Agent Teams

You now have four ways to extend Claude Code's behavior. Here's when to use each:

Feature Use when Runs in Key trait 

Slash Commands

 You trigger a workflow manually Main conversation Explicit, on-demand 

Skills

 Claude needs specialized expertise passively Main conversation Always-available knowledge 

Subagents

 Task needs isolation, tool restriction, or clean context Isolated context window Automatic delegation 

Agent Teams

 Complex multi-domain task needing parallel specialists Multiple isolated contexts Team orchestration

The decision in plain language:

Repeating a workflow? → Slash Command

Domain knowledge Claude should always apply? → Skill

Task that produces context pollution or needs tool restrictions? → Subagent

Complex project needing parallel specialists who coordinate? → Agent Teams (experimental)

Most of what you need day-to-day is subagents. Agent Teams is for when a task is complex enough to genuinely benefit from parallel specialists — not just because parallel sounds impressive.
