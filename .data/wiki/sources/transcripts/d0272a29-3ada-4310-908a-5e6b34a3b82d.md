How NOT to Use AI: The Traps Software Engineers Fall Into

Ishwar Rimal

5 min read · Sep 26, 2025

--

Press enter or click to view image in full size Generated by Gemini

Like many of you, I’ve jumped headfirst into using LLM tools — Copilot, Gemini, you name it. And make no mistake, they’ve been massive productivity boosters, helping me churn through daily tasks faster than I ever thought possible.

While these tools have undoubtedly supercharged my workflow in countless ways, I’ve also noticed a few habits — both in myself and others — where we push them too far, often doing more harm than good.

Today, I will list down those things that I feel should be avoided in your daily work while utilizing the power of LLM.

Here we go:

1. Taking help of LLM for code review

I know what you’re thinking, but hear me out. First, let me ask you a question: When was the last time you commented in a PR that the function could have a time complexity of N Square?

If you are a seasoned human reviewer, the answer is probably 

“almost never,”

 unless that piece of code is running on a massive dataset or is a known performance bottleneck. You have the context to know that for an array of five items, O(n2) is perfectly fine and often simpler to read than an optimized O(n) solution.

LLMs, however, are 

idealists

. They are trained on a vast ocean of “perfect” code and best-practice guides, and they will meticulously point out issues that are technically correct but practically irrelevant. They flag:

Theoretical Efficiency:

 Highlighting an O(n2) loop even when the input size is negligibly small (n<10).

Superfluous Refactoring:

 Suggesting an abstract class or a new helper function for logic that is used only once, increasing complexity for no real gain.

When you copy an LLM’s review comments, you are introducing 

review fatigue

 and slowing down the very process the AI was supposed to accelerate. It dilutes the critical feedback (security, logic) with noise (minor nits).

2. Writing the entire technical requirements document with LLM

Though it sounds tempting, that you explain your feature request to an LLM and ask it to write a technical document for it, I’ve seen it do more harm than good. You end up writing so many things that it becomes impossible to handle all those things suggested by the LLM.

The LLM will generate an exhaustive document full of theoretical best practices, complete with sections for logging, metrics, error handling, and future scalability that you never actually planned for the initial scope. This isn’t helpful; it’s a form of digital procrastination.

Instead of forcing you to think through the one critical path, it lets you generate a long, impressive-looking document that serves only to overwhelm your team and bloat your sprint backlog with “non-negotiable” items. The real work is defining the 

minimum

 viable solution, which requires a human filter.

3. Generating Code for Complex, Non-Standard Business Logic

LLMs are brilliant for boilerplate, data mapping, and using common libraries — tasks where the solution is well-represented in the training data.

However, when you ask it to generate code for your most complex, custom business logic — the non-standard rule that makes your product unique — you are setting yourself up for failure. The LLM will confidently produce code that is syntactically perfect but subtly 

logically incorrect

 because it lacks the deep, tribal knowledge of your codebase and business rules.

Debugging code that you didn’t write, which already looks plausible and complex, is significantly harder and more time-consuming than just writing the correct, clear logic yourself from the start. Use the LLM to write the surrounding infrastructure; keep the core logic human-driven.

4. Using LLMs as a Replacement for Debugging and Root Cause Analysis

We’ve all been there: a mysterious bug appears, and instead of using a debugger or writing a print statement, we copy the error message and the surrounding code into an LLM and ask it to fix it.

While this works for simple errors, relying on it for complex issues skips a critical part of a software engineer’s job: 

building mental models.

 By letting the LLM provide a potential fix (often with a confident-sounding explanation), you bypass the process of deep analysis and experimentation that builds your understanding of the system’s failure modes. You fix the symptom, but you miss the root cause, ensuring the same class of bug will appear again later. The debugger is a superior tool for teaching you how your code actually works.

A Human Filter is Always Required

These and many more points illustrate why you should be 

careful while blindly trusting the result of an LLM

. Of course, these models are capable of generating 100% correct, functional code or detailed documentation, but that’s not the ultimate measure of quality.

Ultimately, it’s for 

you, the software engineer

, to decide if the output is the 

best

 solution for the current situation. The AI provides an answer; you provide the 

context

, the 

pragmatism

, and the 

strategic judgment

 to ensure the code is not just correct, but clear, maintainable, and appropriate for the team’s needs.

Practical Tips for Utilizing LLMs

The LLM is a tireless pair programmer; the final decision on what constitutes a valuable, non-bloating change remains the human engineer’s responsibility. Don’t stop using the tools, but always apply the human filter.

Always Review and Fully Understand Everything:

 Never blindly accept an LLM’s output. Treat its code and suggestions as a draft. You must be able to explain the generated code line-by-line and own it fully.

Learn to Discard Out-of-Scope Suggestions:

 If the LLM suggests an architectural change or a deep refactor that is far outside the immediate scope of your work, use your judgment and discard it. Your goal is to ship the feature, not start a new, unscheduled project.

Don’t Over-Engineer:

 If an LLM suggests a complex optimization that increases code complexity but only offers a trivial performance gain, be ruthless and discard it. Prioritize 

clarity and maintainability

 over marginal theoretical efficiency.

Avoid Nitpicking in PR Comments:

 When reviewing with the help of an LLM, only include comments that you would have written yourself. If it’s a minor style/formatting issue, let your automated linter handle it. 

Do not put comments on a PR that you would not do otherwise for nitpicking.

 Focus your human energy on logic, security, and architecture.

We have to remember a basic truth: the LLM is a powerful tool, but it’s not a seasoned engineer with good judgment. It’s fast and it checks all the rules, but it completely misses the important context — things like 

project priorities

, the 

real-world cost of a code change

, and whether an issue is a serious bug or just a tiny, perfect detail.

When we stop thinking for ourselves and just follow its long lists of suggestions — like writing huge documents or letting small comments slow down a PR — we kill our momentum. Your real value as an engineer isn’t just taking an answer; it’s using your 

human judgment

 to make sure the code is not just right, but is the 

clearest, simplest, and most fitting solution

 right now. Use the AI to work faster, but you must always stay in control.
