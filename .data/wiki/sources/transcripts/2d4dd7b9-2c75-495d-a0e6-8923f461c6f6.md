A few weeks ago, my AI tools setup felt settled.

Most days I am bouncing between full stack work, cloud stuff, and mobile. One moment I am deep in NestJS and TypeScript, the next I am wiring something in AWS, and later I am staring at a SwiftUI screen wondering why state is doing that thing again. So when someone says “try a new tool,” my first reaction is usually: please no.

But I kept hearing the same phrase from dev friends and Twitter people who definitely ship faster than me:

“You should try Claude Code.”

I ignored it for a bit because I already use ChatGPT daily for brainstorming and Cursor for implementation. That combo covers a lot.

Still, curiosity won. I tried Claude Code on real tasks for a week, hit a bunch of confusing moments, and then something clicked. After a few days, I was genuinely impressed. This post is everything I wish I knew on day one so you can skip my trial and error and start getting value immediately.

Why Claude Code When I Already Have ChatGPT and Cursor

Here's the honest answer: I was not looking for another chatbot.

I wanted a tool that is better at:

Reading a real codebase, not just a pasted snippet

Reasoning across multiple files

Helping me plan changes before I break something important

Acting like a senior engineer who actually asks “what's the architecture here?”

Cursor is amazing at execution. ChatGPT is great at breadth. Claude Code, at least for me, became the tool for structure and planning. And the biggest surprise is that it helped me learn NestJS architecture faster than random docs doomscrolling.

The Mental Model That Made Claude Code Click

Claude Code works best when you treat it like:

A repo aware teammate, not a command line toy

A planning assistant, not a code generator

If you ask it to “build the whole feature end to end,” it can try, but the real magic is when you use it to:

Understand the current structure

Decide where code should live

Write a plan that keeps you honest

Then implement, usually in Cursor, with fewer surprises

The Prompt System That Unlocks Claude Code

Claude Code has a official way to do reusable prompts rather than keeping a prompts.md file.

There are three main pieces that matter in practice.

1) Skills (Slash Commands)

Skills are reusable prompts you trigger like a command.

They live in: 

~/.claude/skills/

Each skill is a 

.prompt

 file

You trigger it with: 

/skill-name

Example: create a review skill.

File:

 

~/.claude/skills/review.prompt

---
name: review
description: Review code for bugs, performance, and best practices
---
Please review the following code for:
- Potential bugs
- Performance issues
- Best practices
- Readability
Output:
1) Findings (grouped by severity)
2) Suggested fixes
3) Any tests I should add


Then in Claude Code, run:

/review


Paste the code, or tell it which file or folder you want reviewed.

A Skill for Robust Testing

This one saved me a lot of time because it forces Claude to think like a QA engineer.

File:

 

~/.claude/skills/test-plan.prompt

---
name: test-plan
description: Generate a robust test plan and example tests
---
Create a robust testing plan for the change.
Requirements:
- Identify critical paths and failure modes
- Add unit tests for pure logic
- Add integration tests for request/response flows
- Include edge cases and negative tests
- Suggest what should be mocked and what should not
Output:
- A short test plan
- A list of test cases
- Example code snippets for the most important tests
Context:
- If this is a NestJS project, prefer Jest and one integration test using supertest


Trigger it with:

/test-plan


2) Project Specific Prompts with 

CLAUDE.md

CLAUDE.md

 lives in your project root and gets auto loaded when you work in that directory.

This is where you put repo rules like:

Use TypeScript

Follow ESLint rules

Keep controllers thin and move logic to services

Write tests for features

Here is a practical NestJS flavored example:

# CLAUDE.md
## Project Guidelines
- Language: TypeScript
- Framework: NestJS
- Controllers must be thin
- Business logic goes in services
- Prefer policy helpers for authorization rules
- Add unit tests for services
- Add at least one integration test for key endpoints


If you want Claude to behave consistently, this file matters more than any single prompt.

3) Personal Memory with 

MEMORY.md

There is also a persistent memory file that can carry across conversations for a specific project: 

~/.claude/projects/<project-path>/memory/MEMORY.md

This is where you can keep notes like:

We use Prisma

We deploy on AWS

Prefer this folder structure

Do not change public endpoints without updating clients

I treat 

MEMORY.md

 like a tiny notebook that keeps Claude from forgetting how my project works.

Bonus: MCP Servers

If you are already in the MCP world, Claude Code can also load prompts and tools from MCP servers configured in 

~/.claude/mcp.json

 .

That is more advanced, but the idea is simple: you can bring your own tools and prompt workflows into Claude Code.

Plan Mode: The Part That Actually Taught Me NestJS Architecture

The biggest wow moment for me was not code generation.

It was plan mode.

Plan mode is where Claude Code feels like a senior engineer who:

Asks the annoying questions you should ask

Breaks work into steps

Helps you avoid turning your codebase into spaghetti

Here's the kind of prompt I used while working on a typical NestJS feature:

We have a NestJS API with roles: admin, staff, user.
Goal: Add an endpoint to update an organization's settings.
Rules:
- admin can update only their org
- staff can update only a subset of settings
Please propose:
1) Module layout
2) Where to put authorization logic (guard vs service vs policy)
3) DTO structure
4) A step by step plan to implement with minimal risk


Claude would respond with a structured plan that usually covered:

Which module should own the feature

How to keep controllers thin

How to centralize authorization decisions

Where DTO validation should happen

A Practical Authorization Pattern (That Kept My Controllers Clean)

A pattern that worked well:

Guards do authentication and attach the user context

Service layer enforces the business rule: can this actor do this action

A small policy helper makes the service readable and testable

Here's the important part: this is also the kind of structure Claude Code naturally pushes you toward in plan mode, because it prefers a single place to reason about permissions.

// policies/org.policy.ts
export function canUpdateOrgSettings(input: {
  role: 'admin' | 'staff' | 'user';
  userOrgId: string;
  targetOrgId: string;
}): { allowed: boolean; reason?: string } {
  const { role, userOrgId, targetOrgId } = input;
  if (role === 'admin' && userOrgId === targetOrgId) return { allowed: true };
  return { allowed: false, reason: 'Insufficient permissions' };
}
// org-settings.service.ts
import { ForbiddenException, Injectable } from '@nestjs/common';
import { canUpdateOrgSettings } from '../policies/org.policy';
@Injectable()
export class OrgSettingsService {
  async updateSettings(params: {
    actorRole: 'admin' | 'staff' | 'user';
    actorOrgId: string;
    targetOrgId: string;
    payload: Record<string, unknown>;
  }) {
    const decision = canUpdateOrgSettings({
      role: params.actorRole,
      userOrgId: params.actorOrgId,
      targetOrgId: params.targetOrgId,
    });
    if (!decision.allowed) {
      throw new ForbiddenException(decision.reason);
    }
    // Persist changes (Prisma, etc.)
    return { ok: true };
  }
}


Why this is worth calling out:

Your permission rules become plain code you can unit test

Controllers stay boring and thin

Claude Code can reason about it easily because the policy function is deterministic

Multi Agent Workflows (Without Going Full Sci Fi)

You do not need a “100 agents” setup.

But splitting responsibilities can help when the task is big.

A simple mental model:

Architect Agent: proposes structure and boundaries

Refactor Agent: focuses on code cleanup without breaking behavior

Test Agent: suggests test cases, failure modes, and edge cases

How to actually run this in practice

Even if you are not literally starting separate agent processes, you can run it as a workflow by giving Claude clear phases.

Example prompt:

We are going to do this in three passes.
Pass 1 (Architect): propose the module layout and flow.
Pass 2 (Refactor): list safe refactors with minimal behavior change.
Pass 3 (Test): produce a robust test plan with example unit and integration tests.
Wait for my confirmation between passes.


If you want it to run in one go:

Act in three roles: Architect, Refactor, Test.
Return three sections in that order.
For each section, include:
- Assumptions
- Steps
- Risks


This makes the output more structured and less one giant blob of advice.

Model Choice on the Minimum Pro Plan: Sonnet 4.5 vs Opus 4.6

I made a rookie mistake early on: I assumed I should always use the best model.

In practice, if you are on the minimum Pro plan, you will get the best day to day experience by:

Defaulting to Sonnet 4.5

Escalating to Opus 4.6 only when you truly need it

What Sonnet 4.5 handled perfectly for me:

Plan mode for backend features

Architecture reviews

TypeScript refactors

Explaining unfamiliar parts of the codebase

When I'd consider Opus 4.6:

Deep architectural trade offs

High risk refactors where you want extra reasoning

Hard debugging sessions where you keep going in circles

Think of it like:

Sonnet is the daily driver

Opus is the power tool

10 Things You Can Try in Claude Code This Week

Here are ten concrete things you can do to get value fast.

1) Generate a plan before touching code

Ask for a step by step plan. Then implement.

2) Ask it to explain a module like you're rejoining the project

This is incredible for returning to code you wrote months ago.

3) Review your module boundaries

Ask it to identify files that are doing too much and suggest a cleaner structure.

4) Refactor a service without changing behavior

Use a safe refactor skill and insist on constraints.

5) Improve authorization without fat controllers

Use a policy helper plus service enforcement.

6) Create a 

CLAUDE.md

 in 15 minutes

Then refine it over time.

7) Build a few reusable skills

Start with 

/review

 and 

/test-plan

 .

8) Use Claude as a PR reviewer

Ask it what feels risky, unclear, or inconsistent.

9) Intentionally switch models

Start with Sonnet 4.5. Escalate to Opus 4.6 only if needed.

10) Ask “what would you change if you owned this repo?”

This prompt is strangely effective for surfacing architecture issues.

How I'm Using Claude Code With Cursor and ChatGPT

My workflow after this week looks like:

ChatGPT: explore ideas, brainstorm approaches, write drafts

Claude Code: plan the change, reason about architecture, keep structure clean

Cursor: implement quickly and iterate

Claude Code did not replace anything. It filled a gap.

Common Pitfalls (So You Don't Repeat My Mistakes)

Expecting Claude Code to build the whole feature perfectly

Not giving it 

CLAUDE.md

 and then wondering why answers are inconsistent

Overusing the biggest model and burning your limits

Skipping plan mode and jumping straight to code

Conclusion

After a week, Claude Code earned a permanent spot in my daily workflow, especially for planning, architecture, and those moments when you are staring at a repo thinking, “Where do I even start?” If you are on the minimum Pro plan, I would default to Sonnet 4.5 for almost everything and treat Opus 4.6 like an escalation tool for deep reasoning or high risk refactors. Going forward, I plan to keep using Claude Code alongside Cursor and ChatGPT.

I also want to explore Codex next. I have heard enough good things that it deserves a real trial, and I plan to write more articles about Claude and other AI tools as I use them in real projects. Stay tuned.
