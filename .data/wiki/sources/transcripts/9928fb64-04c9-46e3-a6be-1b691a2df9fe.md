A Practical Guide for Platform, Security, Developer, and DevOps Teams on AWS

Every AI coding tool eventually hits the same wall: it helps you write code faster inside an editor, but the moment you close the tab, it forgets everything — your architecture decisions, your naming conventions, your CloudFormation patterns, your IAM policies. The next session starts from zero.

Claude Code is built differently. It runs in your terminal, reads your entire codebase, executes shell commands, remembers your project’s context across sessions, and integrates directly into your CI/CD pipelines. It can query your AWS environment, reason about your infrastructure state, and act on it — via the CLI, headless scripts, or GitHub Actions.

You are not chatting with an assistant. You are working with an agent who understands your AWS workloads and can take action across them.

This blog walks through concrete, production-grade use cases for four engineering personas on AWS —

Part 1 — How Claude Code Remembers Your Project

Press enter or click to view image in full size

Before diving into use cases, you need to understand the memory model. This is what separates Claude Code from a glorified autocomplete — especially on AWS, where every project has its own account structure, region topology, naming conventions, and tagging standards.

The problem: every session starts fresh

Claude Code’s context window resets between sessions. Without a memory system, you spend the first five minutes of every session re-explaining your VPC layout, your Lambda patterns, your deployment pipeline, and your cost-center tags. Across a team of 20 engineers and 40 microservices, this compounds fast.

Two complementary memory mechanisms

Claude Code solves this with two systems, both loaded automatically at the start of every session:

Mechanism Who writes it What it stores Scope 

CLAUDE.md

 You AWS standards, IaC conventions, CLI commands, constraints Project, team, or global 

Auto memory

 Claude itself Learned preferences, corrections, AWS patterns Per-user, per-project

Neither is a magic prompt injection. Claude treats them as context, not enforced configuration. The more specific and concise your instructions, the more consistently Claude follows them.

CLAUDE.md — Your AWS Project’s Persistent Brain

CLAUDE.md  lives in your repository root. Claude reads it at the start of every session — locally, in headless scripts, and inside GitHub Actions CI runs.

Bootstrap it automatically:

cd your-aws-project 
 claude 
 /init

/init  analyses your codebase, discovers your build system, infers your stack, and generates a starting  CLAUDE.md . Refine it once; it applies everywhere.

A well-crafted CLAUDE.md for an AWS microservice:

# order-processor-service 
 ## AWS Context 
 - Account: 123456789012 (non-prod) / 987654321098 (prod) 
 - Primary region: ap-south-1 (Mumbai), DR: ap-southeast-1 (Singapore) 
 - Deployment target: ECS Fargate on existing VPC (vpc-0abc1234) 
 - Message broker: Amazon SQS + SNS fanout 
 - Database: Amazon RDS PostgreSQL 15 (Multi-AZ in prod) 
 - Secrets: AWS Secrets Manager (never hardcode, never use SSM Parameter Store for secrets) 
 - Observability: CloudWatch Container Insights + X-Ray tracing enabled 
 ## Stack 
 - Python 3.12, FastAPI, SQLAlchemy (async), Alembic 
 - Tests: pytest + moto for AWS service mocks, coverage threshold: 85% 
 - Container: Docker, base image: public.ecr.aws/our-org/python-base:3.12 
 ## Commands 
 - Build: `docker build -t order-processor .` 
 - Test: `pytest tests/ -v --cov=app` 
 - Deploy (non-prod): `aws ecs update-service --cluster dev-cluster --service order-processor --force-new-deployment` 
 - Logs: `aws logs tail /ecs/order-processor --follow` 
 ## IaC Standards 
 - Terraform only - no CDK or CloudFormation in this repo 
 - Provider: hashicorp/aws ~> 5.0, pinned in versions.tf 
 - State backend: S3 (s3://our-org-tfstate-ap-south-1) + DynamoDB lock table 
 - Required tags on every resource: Environment, Team, CostCenter, ManagedBy=terraform, DataClassification 
 - No wildcard (*) IAM actions - ever 
 - S3 buckets: versioning=true, public access blocked, SSE-S3 minimum 
 ## What NOT to do 
 - Never use us-east-1 unless explicitly told to 
 - Never store credentials in code - use IAM roles and instance profiles 
 - Never create security groups with 0.0.0.0/0 ingress except on ports 80/443 
 - Do not modify .terraform.lock.hcl manually

This file is committed to source control. Every developer, every CI job, and every automated workflow inherits the same AWS standards — without any additional configuration.

Scoped Memory: Global, Project, and Subdirectory

CLAUDE.md files can exist at multiple levels. More specific locations always take precedence:

~/.claude/CLAUDE.md ← Personal AWS CLI profile, preferred region 
 your-project/CLAUDE.md ← Service-level standards, shared with team 
 your-project/.claude/rules/ 
  ├── iam-policies.md ← Loaded when working on IAM resources 
  ├── terraform-aws.md ← Loaded for /infra/ work 
  └── lambda-patterns.md ← Loaded for /functions/ work

For large AWS projects with multiple Terraform root modules, Lambda functions, and CDK stacks, scoped rules keep context lean — Claude only loads subdirectory rules when it reads files in those directories.

Auto Memory — Claude Learns Your AWS Preferences

Type  #  at the start of any message to fast-save a preference mid-session:

# always use ap-south-1 as the default AWS region 
 # our ECS task definitions use awsvpc network mode 
 # never use t2 instance types — use t3 or graviton (t4g) instead 
 # our Lambda functions always use ARM64 architecture for cost savings

These are automatically saved to the most relevant CLAUDE.md. Browse everything with  /memory  in the interactive terminal.

Settings and Hooks — Enforce AWS Standards at the Tool Level

The  .claude/settings.json  hooks layer runs shell commands at specific lifecycle points. Use this to enforce AWS hygiene automatically:

// .claude/settings.json 
 { 
  "hooks": { 
  "PostToolUse": [{ 
  "matcher": "Edit|Write", 
  "hooks": [{ 
  "type": "command", 
  "command": "if echo \"$CLAUDE_FILE_PATHS\" | grep -q '\\.tf$'; then terraform fmt \"$CLAUDE_FILE_PATHS\"; fi" 
  }] 
  }], 
  "PreToolUse": [{ 
  "matcher": "Bash", 
  "hooks": [{ 
  "type": "command", 
  "command": "if echo \"$CLAUDE_TOOL_INPUT\" | grep -qE 'aws .*(delete|destroy|terminate|drop)'; then echo '{\"block\": true, \"message\": \"Destructive AWS commands require explicit human confirmation.\"}' >&2; exit 2; fi" 
  }] 
  }] 
  } 
 }

This auto-formats every Terraform file Claude touches and blocks any destructive AWS CLI command ( delete ,  destroy ,  terminate ) until a human explicitly runs it.

Security note:

 Hooks in 

.claude/settings.json

 execute automatically when Claude opens a project. Only open repositories you trust. Inspect hook configurations from third-party repos the same way you review third-party GitHub Actions workflows.

Persona 1 — The Developer

Pain point

Writing boilerplate AWS Lambda handlers, mocking DynamoDB and S3 in tests, tracing a bug across SQS → Lambda → RDS, keeping IAM policies aligned with actual code usage — these are hours every week that produce no user-facing value.

Use Case 1.1 — Issue-to-PR: Fix a Lambda Timeout Bug

A user reports: 

“Order processing Lambda times out when the SQS queue has more than 500 messages in a batch.”

 A developer mentions  @claude  in the GitHub issue:

@claude investigate and fix this Lambda timeout. The function is in 
 /functions/order-processor/. Check SQS batch size, Lambda concurrency 
 limits, and the RDS connection pool config.

Claude traces the SQS event source mapping, finds the batch size set to 500 with a 30-second Lambda timeout and a synchronous RDS call per message, corrects the batch size to 10, adds connection pooling via RDS Proxy, updates the  batchWindow  to reduce API calls, and opens a PR with an explanation. The developer reviews the diff and merges.

Use Case 1.2 — Generate Lambda + Infrastructure Together

A developer needs a new Lambda function with its full AWS wiring. Instead of piecing together three separate tools:

claude -p "Create a new Lambda function called 'invoice-generator' that: 
 - Triggers from an SQS queue named 'invoice-requests' 
 - Reads order data from DynamoDB table 'orders' 
 - Writes generated PDFs to S3 bucket 'invoices-bucket' 
 - Stores the S3 key back in DynamoDB 
 - Uses ARM64 architecture and Python 3.12 
 - Reads DB credentials from Secrets Manager 
 Include: 
 1. The Lambda handler in /functions/invoice-generator/ 
 2. Terraform module in /infra/modules/invoice-generator/ 
 3. IAM role with least-privilege policies (no wildcard actions) 
 4. pytest tests using moto to mock DynamoDB, S3, and Secrets Manager 
 5. CloudWatch log group with 30-day retention"

Because CLAUDE.md already has your tagging standards, state backend config, and architecture preferences, the output is on-standard from the start — not a starting point that needs 30 minutes of cleanup.

Persona 2 — The DevOps Engineer

Pain point

ECS deployments failing silently. CloudFormation stacks stuck in  UPDATE_ROLLBACK_FAILED . CodePipeline stages that need a human to read through 800 lines of CloudWatch logs to understand what went wrong. Terraform state that has drifted from reality.

Use Case 2.1 — Auto-Diagnose and Fix ECS Deployment Failures

When an ECS service fails to stabilise after a deployment, instead of paging an engineer:

# .github/workflows/ecs-deploy-fix.yml 
 name: Auto-Fix ECS Deployment Failure 
 on: 
  workflow_run: 
  workflows: ["Deploy to ECS"] 
  types: [completed] 
 jobs: 
  diagnose-and-fix: 
  if: ${{ github.event.workflow_run.conclusion == 'failure' }} 
  runs-on: ubuntu-latest 
  permissions: 
  contents: write 
  pull-requests: write 
  steps: 
  - uses: actions/checkout@v4 
  - name: Configure AWS credentials 
  uses: aws-actions/configure-aws-credentials@v4 
  with: 
  role-to-assume: ${{ secrets.AWS_DEPLOY_ROLE_ARN }} 
  aws-region: ap-south-1 
  - uses: anthropics/claude-code-action@v1 
  with: 
  anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }} 
  prompt: | 
  The ECS deployment just failed. Do the following in order: 
  1. Run: aws ecs describe-services --cluster ${{ vars.ECS_CLUSTER }} --services ${{ vars.ECS_SERVICE }} 
  2. Run: aws logs tail /ecs/${{ vars.ECS_SERVICE }} --since 15m 
  3. Check stopped task details: aws ecs describe-tasks with the stopped task ARN 
  Identify the root cause (OOM kill, missing env var, bad health check, 
  IAM permission denial, image pull failure). Fix the Terraform or 
  application config and open a PR with a clear explanation. 
  claude_args: "--max-turns 20"

Claude reads the CloudWatch logs, identifies the stopped task reason (e.g.,  CannotPullContainerError  due to a missing ECR permission), patches the IAM role in Terraform, and opens a PR — before a human engineer even opens their laptop.

Persona 3 — The Security Engineer

Pain point

Security is always a downstream checkpoint on AWS. A publicly-accessible S3 bucket found in production, a Lambda function with  iam:*  permissions, a security group open to  0.0.0.0/0  on port 5432 — these are expensive mistakes. Traditional SAST tools catch code-level issues but miss IAM misconfigurations, S3 bucket policy flaws, and business logic vulnerabilities in serverless architectures.

Use Case 3.1 — Security Review on Every PR, AWS-Aware

# .github/workflows/security-review.yml 
 name: AWS Security Review 
 on: 
  pull_request: 
  types: [opened, synchronize] 
 jobs: 
  security: 
  runs-on: ubuntu-latest 
  permissions: 
  pull-requests: write 
  steps: 
  - uses: actions/checkout@v4 
  - uses: anthropics/claude-code-action@v1 
  with: 
  anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }} 
  prompt: | 
  Run a security review of the changes in this PR with AWS context. 
  For application code: check OWASP Top 10 - SQL injection, SSRF, 
  command injection, hardcoded AWS credentials or ARNs. 
  For Terraform/IaC: check for - 
  - IAM policies with wildcard (*) actions or resources 
  - S3 buckets with public access enabled or missing encryption 
  - Security groups with 0.0.0.0/0 on non-HTTP ports 
  - Lambda functions without resource-based policy restrictions- RDS instances without encryption at rest or Multi-AZ in prod 
  - Secrets stored in SSM Parameter Store instead of Secrets Manager 
  - Missing CloudTrail or VPC Flow Logs on new accounts/VPCs 
  Post findings as inline PR comments with severity (critical / high / 
  medium / low) and a concrete remediation snippet for each issue. 
  claude_args: "--max-turns 10" 


Real validation:

 Anthropic’s own engineering team uses this pattern in production. The GitHub Action caught an SSRF vulnerability in a credential proxy and an RCE via DNS rebinding — both in new features, before merge.

Use Case 3.2 — IAM Policy Least-Privilege Analysis

IAM is where AWS security gets subtle. Overly broad permissions compound across services:

# Pull the current IAM role policy and analyse it 
 aws iam get-role-policy \ 
  --role-name order-processor-task-role \ 
  --policy-name order-processor-policy | \ 
  claude -p "Analyse this IAM policy against the Lambda function code in 
  /functions/order-processor/. Identify: 
  1. Permissions granted but never used by the code 
  2. Resources specified as '*' that could be scoped to specific ARNs 
  3. Any missing condition keys (aws:SourceArn, aws:SourceAccount) 
  that should restrict cross-service invocation 
  Output a least-privilege replacement policy with ARNs scoped to 
  our ap-south-1 account (123456789012) and add inline comments 
  explaining why each permission is required."

Use Case 3.3 — CVE Triage Across Lambda Functions

When a critical CVE drops affecting a Python or Node.js package, you need blast-radius analysis across your entire Lambda portfolio — fast:

#!/bin/bash 
 # triage-lambda-cve.sh 
 CVE_PACKAGE="cryptography" # example: CVE in the cryptography Python package 
 AFFECTED_VERSION="<41.0.0" 
 for dir in functions/*/; do 
  fn_name=$(basename "$dir") 
  echo "Scanning $fn_name..." 
  claude -p "Check $dir/requirements.txt (or package.json). 
  Is '$CVE_PACKAGE $AFFECTED_VERSION' present? 
  If yes: current version, patched version, migration effort 
  (drop-in / minor changes / breaking changes), and blast radius 
  (what data or AWS services does this function access?). 
  Output as JSON." > "triage/${fn_name}.json" 
 done 
 # Aggregate results 
 claude -p "Read all JSON files in /triage/. Produce a priority-ordered 
 remediation plan: which Lambda functions to patch first based on 
 data sensitivity and blast radius. Output as a markdown table."

Use Case 3.4 — Pre-Commit Hook: Block AWS Credential Leaks

// .claude/settings.json 
 { 
  "hooks": { 
  "PreToolUse": [{ 
  "matcher": "Write|Edit", 
  "hooks": [{ 
  "type": "command", 
  "command": "grep -rE '(AKIA[0-9A-Z]{16}|ASIA[0-9A-Z]{16}|aws_secret_access_key\\s*=\\s*[\"\\x27][^\"\\x27]{40}[\"\\x27])' \"$CLAUDE_FILE_PATHS\" && echo '{\"block\": true, \"message\": \"AWS credential pattern detected. Use IAM roles and Secrets Manager.\"}' >&2 || true" 
  }] 
  }] 
  } 
 }

This matches AWS access key ID patterns ( AKIA* ,  ASIA* ) and secret access key patterns. Claude cannot write a file containing them. The block fires before the edit is applied.

Encode your AWS golden path once in a global CLAUDE.md. Every developer gets on-standard infrastructure without filing a ticket:

Part 3 — Production Hardening on AWS

Before wiring Claude Code into your AWS pipelines, apply these safeguards.

Use OIDC for GitHub Actions → AWS authentication

Never store long-lived AWS access keys in GitHub Secrets. Use IAM OIDC with temporary, auto-rotated credentials:

- name: Configure AWS credentials 
  uses: aws-actions/configure-aws-credentials@v4 
  with: 
  role-to-assume: arn:aws:iam::123456789012:role/GitHubActionsClaudeRole 
  role-session-name: ClaudeCodeSession 
  aws-region: ap-south-1

Attach a trust policy scoped to your specific repository and workflow:

{ 
  "Condition": { 
  "StringEquals": { 
  "token.actions.githubusercontent.com:sub": 
  "repo:your-org/your-repo:ref:refs/heads/main" 
  } 
  } 
 }

Scope Claude’s IAM role to least privilege

Create a dedicated IAM role for Claude Code workflows. For read-only tasks (drift detection, security review), attach only read permissions:

# Terraform: IAM role for Claude Code GitHub Actions 
 resource "aws_iam_role_policy" "claude_readonly" { 
  name = "ClaudeCodeReadOnly" 
  role = aws_iam_role.claude_code.id 
 policy = jsonencode({ 
  Version = "2012-10-17" 
  Statement = [ 
  { 
  Effect = "Allow" 
  Action = [ 
  "ecs:Describe*", "ecs:List*", 
  "logs:Describe*", "logs:Get*", "logs:FilterLogEvents", 
  "iam:Get*", "iam:List*", 
  "ec2:Describe*", 
  "s3:GetBucketPolicy", "s3:GetBucketAcl", 
  "ce:GetCostAndUsage" 
  ] 
  Resource = "*" 
  } 
  ] 
  }) 
 }

For deployment workflows, scope write permissions to specific ECS services, ECR repositories, and S3 buckets by ARN — never  Resource: "*"  on write actions.

Pin the action to a commit SHA in production

# Development: anthropics/claude-code-action@v1 is fine 
 # Production: pin for supply-chain security 
 uses: anthropics/claude-code-action@<full-commit-sha>

Never auto-merge Claude’s output

Claude proposes; humans approve. Enforce branch protection rules so no automated PR bypasses a required review — especially for any workflow that touches Terraform applying to production accounts.

Set max-turns to control blast radius and API cost

claude_args: "--max-turns 5" # Quick PR security review 
 claude_args: "--max-turns 15" # ECS bug diagnosis and fix 
 claude_args: "--max-turns 25" # Multi-module drift detection

The right starting point: pick the one workflow that costs your AWS team the most time. For most teams, that is either PR security review (catching IAM misconfigs before they reach production) or CI failure diagnosis (getting a root cause without paging an engineer). Start there, measure the impact, then expand.
