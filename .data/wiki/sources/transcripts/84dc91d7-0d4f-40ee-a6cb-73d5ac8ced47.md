Typifying 1000 Python files with Ruff + Claude

Yair Morgenstern

5 min read · Dec 7, 2025

--

Use Ruff “ANN” rules with exclusions to target specific folders

Use static tools to infer what types we can — pyrefly + infer-types + autotyping

Let claude code run ruff to find the types it has yet to add

Parallelize claude with xargs to speed up and limit context collisions

Background

I work in a 10-year-old Python codebase, which is mostly untyped. As time goes on and those that wrote the code move on to other things, this leads to confusion regarding data inputs and outputs, which both causes bugs and leads to longer dev time, since “understanding what’s going on” takes up a larger portion of time.

In a pre-LLM world I saw this as an unsolvable problem — since the effort required to fix things is so large, no one would actually do it or allow for it to be done in lieu of other work. In a post-LLM world, we can throw money at it to save us money in the long-term.

Methodology

The most important thing is to 

stop the bleeding

 — to disallow new code to be untyped.

Since our code is already linted with Ruff, to do this we can utilize Ruff’s ‘ignore’ rules:

Add “ANN” to Ruff’s ‘select’ to add annotation rules check

Exclude all files except one specific folder with  "!yourFolder/**" = ["ANN"]

Tell claude to run ruff to find errors, and add types to fix those errors, looping until success

Commit this change — this folder is now a type-only zone

Since Ruff exclusion rules allow for multiple folders, you can build up your type-only zones with e.g.  "!{folderA/**,folderB/**}" = ["ANN"]

What about static tools?

Most type-checking tools — 

Mypy, Ty, Pywright

— don’t add types.

To supplement this, it seems many large companies have written their own tool to add python types: 

MonkeyType, RightTyper, PyAnnotate

, etc. But, they all assume that you 

run

 the code to generate runtime types, and then annotate using that. This is because 

dynamic languages 

can’t be properly

 statically typed correctly. 

Meanwhile, I’m sitting on a huge codebase where I don’t know how to run most of the code there — that’s not my use-case.

In our use-case, we’re not going for 100% correctness — we want “good enough” that allows us to add the ruff lint check to avoid the future!

https://github.com/orsinium-labs/infer-types

 is a tool that actually 

does

 do a lot of the work — in an example folder I took, it reduced 3000 ruff annotation errors to 2200 — that’s 26% of the work, time and tokens, done instantly! But it only annotates return types, and not input parameter types.

https://github.com/JelleZijlstra/autotyping

 is another tool that does similar work — running it after infer-types, I only get another 2% off, but that’s still worth the time for a simple  python3 -m autotyping “velocity/velocity/analytics/attributes” — bool-param — int-param — float-param — str-param

I only discovered 

https://pyrefly.org/en/docs/autotype/

https://pyrefly.org/en/docs/autotype/

Parallelizing Claude

With 1000 files to type, we have to parallelize. Luckily, this is a case where

Each file is roughly self-contained,

Ruff can run on each file to find only its inputs,

And the outputs don’t conflict with one another.

This lends itself neatly to a bash solution:

#!/bin/bash 
 # Usage: ./parallel_claude.sh <folder> 
 # Example: ./parallel_claude.sh ./src 
 MAX_JOBS=5 
 if [ $# -ne 1 ]; then 
  echo "Usage: $0 <folder>" 
  echo "Example: $0 ./src" 
  exit 1 
 fi 
 FOLDER="$1" 
 if [ ! -d "$FOLDER" ]; then 
  echo "Error: Directory '$FOLDER' does not exist" 
  exit 1 
 fi 
 # Function to run claude on a single file 
 process_file() { 
  local file="$1" 
  local PROMPT=" 
  You are working on $file 
  - First, check with 'pre-commit run ruff' on the file, if there are any problems with it - if not, exit. 
  - When adding types to a file: 
  - Assume python 3.11 for types and syntax (e.g. list and not List, “| None” syntax instead of Optional, no “from __future__ import”) 
  - <repo-specific rules ommited for example> 
  - use object instead of Any, but try to avoid Any where possible. 
  - No need to specify '| None' on typeddicts 
  - No need to add typings on single string / int / list consts 
  - Do not use “if TYPE_CHECKING” conditional imports 
  " 
  echo "Processing: $file" 
  claude -p "$PROMPT" 
  echo "Completed: $file" 
 } 
 # Export the function so it can be used by parallel processes 
 export -f process_file 
 # Find all files in the folder and run claude with max 5 parallel jobs - to not overload Claude's API 
 find "$FOLDER" -name "*.py" -not -path "*/__pycache__/*" -type f -print0 | xargs -0 -n1 -P"$MAX_JOBS" -I{} bash -c 'process_file "$@"' _ {} 
 echo "All files processed!"

Note that since Claude tends to say “eh, good enough” after a certain amount of work, you may need to clean up with a final catch-all prompt. In my example, I was left with 111 errors out of 2160 for the final cleanup.

Is It Any Good?

Half a year ago, the answer was “no”. A lot has changed since then.

Now, Claude is 

good

 at recognizing base types — bool, int, str, list, dict, etc.

It is 

relatively competent

 at recognizing when custom classes are used, by searching for the functions called on the classes.

It 

does not

 handle custom data structures well — types which should ideally be represented by a TypedDict get lumped together as  dict[str,Any]  which — while excluding base types — doesn’t help us understand what’s actually there.

What’s next?

Adding types is one of the highest ROI tasks I can think of in a codebase for LLMs. Types are IDE-friendly documentation that doubles as error-checking (Pycharm knows when you’re returning something wrong) and triples as a firm basis for code rewrites.

Ensuring that the types propagate correctly between functions was out of scope of this mission, but could easily be added by switching out Ruff for Ty. The question is one of cost-effectiveness: Would I pay 1000$ to have the codebase pass Ty checks as well as just have annotations? I think yes.

As time passes and token costs decrease, I expect untyped legacy codebases to be a thing of the past. And that, to me, is an absolute win.
