Problem Statement

Feature request: Persistent state across context compaction

The Problem

When Claude Code compacts context mid-session, it loses track of project state, in-progress work, decisions made, and what it was doing. For long sessions on complex projects, this means Claude asks "what are we working on?" after every compaction — sometimes multiple times per session.

This is the single biggest friction point for power users. Context compaction is necessary (windows are finite), but the information loss is not.

Proposed Solution

What I Built

I wrote 

MemoryForge

https://github.com/marolinik/MemoryForge

 — a zero-dependency memory layer that hooks into Claude Code's lifecycle to survive compaction cycles. 780 lines of Node.js, 3 hooks, 6 MCP tools.

The core mechanism is a 

compaction survival loop

:

Session starts ───> Hook reads .mind/ ───> Briefing injected into context
     ^                                              |
     |                                              v
     |                                        Work happens
     |                                              |
Hook re-injects <─── Context compacted <─── Hook saves checkpoint
briefing (source=compact)


SessionStart

 hook reads state files from 

.mind/

 and injects a briefing via 

additionalContext

Claude works, context grows

PreCompact

 hook fires, saves a checkpoint to 

.mind/checkpoints/latest.md

Context compacts

SessionStart

 fires again with 

source=compact

 — hook detects this and re-injects the full briefing plus the checkpoint

The result: Claude picks up exactly where it left off after compaction. No "what were we doing?" moment.

State is stored in four human-readable Markdown files ( 

.mind/STATE.md

 , 

PROGRESS.md

 , 

DECISIONS.md

 , 

SESSION-LOG.md

 ), queryable via MCP tools mid-session.

The API Stability Question

This entire system depends on 

undocumented behavior

 of Claude Code's hook system:

SessionStart fires after compaction with source=compact

 — This is the critical signal that tells my hook "context was just lost, re-inject everything." If this event stops firing, or the 

source

 field changes, the survival loop breaks silently.

additionalContext in hookSpecificOutput is injected into Claude's context

 — This is how the briefing gets into the model's working memory. If the return contract changes, briefings stop appearing with no error.

PreCompact fires before compaction with time to write files

 — My hook needs enough time to read state and write a checkpoint before compaction proceeds. If the timeout is too short or the event stops firing, checkpoints are lost.

SessionEnd fires on exit

 — Used for activity tracking and auto-generated session summaries. Less critical, but still part of the loop.

None of these are documented as stable API. I'm building on implementation details that could change in any CLI update.

The Request

Can these hook behaviors be stabilized or documented?

Specifically:

 return path

I'm not asking for new features — just stability guarantees on behavior that already exists and works.

Why This Matters Beyond MemoryForge

The compaction survival loop is a 

general primitive

. Any tool that wants to maintain state across compaction needs these same guarantees:

Project management tools that track tasks across sessions

Code review tools that remember review context

Learning/tutoring tools that track student progress

Any MCP server that needs to restore state after compaction

If the hook API is stable, an ecosystem of tools can build on it confidently. If it's not, every tool is one CLI update away from silent failure.

Alternative Solutions

Alternative: Native Support

If Anthropic is planning to solve compaction memory loss natively (which would be ideal), I'd love to know. MemoryForge exists because the gap exists — if the gap closes, the tool becomes unnecessary, and that's a good outcome.

Either way, we are running MemoryForge today within our 50+ engineers using Claude Code which is evidence that this problem is real and worth solving, whether externally or internally.

We built a PreCompact hook that saves session state to an external memory system (CLI-based, git-backed markdown with YAML frontmatter) before compaction occurs. On session resume after compaction, a SessionStart hook queries this external store and injects a lean context summary into the fresh context window.

It works, but the restored context is a summary — not the actual conversation. What we lose on compaction:

What was tried and failed

: The summary captures outcomes, not the debugging path. An agent that just spent 20 minutes diagnosing a connection issue loses that diagnostic reasoning.

Nuanced mid-task decisions

: "I chose approach A over B because of X" gets compacted to "using approach A." The rationale disappears.

Partial results

: If compaction hits mid-task, intermediate state is lost unless the agent explicitly persisted it before the compaction trigger.

We also built a 

.claude/rules/

 system specifically because rules auto-load every session and survive compaction unconditionally, unlike conversation context. Critical operational knowledge (team trust policies, memory CLI syntax, session lifecycle checklists) was moved INTO rules files because that was the only reliable way to ensure it persisted across compaction boundaries. The fact that we migrated knowledge out of conversation context and into rules to survive compaction tells you what's missing from the compaction system itself.

What would help most

: Let us mark specific messages or tool results as "pin: do not compact." Not everything — just the critical anchors. A pinned message survives compaction verbatim, not summarized. This would let agents protect key decisions, partial state, and diagnostic paths without externalizing everything to disk.

MemoryForge is the right instinct. PreCompact

 hook: saves session state to a markdown checkpoint

SessionStart

 hook with 

source=compact

 detection: re-injects the briefing

A 3-tier memory architecture: session-state (raw), indexed summaries, full entries

A 

.claude/rules/

 layer that auto-loads critical context (15+ rule files)

MEMORY.md as an overflow index — but it truncates at ~200 lines, so we maintain a separate index file

The 

source=compact

 behavior you're depending on — we depend on it too. It's the keystone of the whole survival loop. If that field goes away or changes semantics, several agents go dark in mid-session without knowing why.

Your API stability ask is exactly right. Document 

source

additionalContext

 as canonical injection path, and 

PreCompact
