remember the brainrote IDE

https://vibingwithai.substack.com/p/the-responsible-way-to-use-the-time

) and even stranger naming conventions, so this wouldn’t be the first time something serious arrived wearing a name given to a character with the personality traits of simple-mindedness, innocence, and often nonsensical behaviour.

Now it represents more than a character.

This Ralph is a technique.

A deliberately plain one, if you look at it.

As Geoffrey Huntley, the person who came up with the whole Ralph way of running coding agents in the loop, put it simply:

In its purest form, Ralph is a Bash loop. A technique that is deterministically bad in an undeterministic world.

while :; do cat PROMPT.md | claude-code ; done

Straightforward:

keep running forever, take whatever is written in  PROMPT.md , feed it into a coding agent, let it do the work, then start over.

while :;  means “keep going”

PROMPT.md  is where the specs and instructions live

claude-code  is the coding agent

the loop repeats until the specs are satisfied or you stop it

A way of running a coding agent repeatedly against written specifications until the expected outcomes are met. The intelligence is expected to come from clear, granular specifications and verifiable outcomes.

Nothing about it is sophisticated if you come from a dev-world background.

Nothing about it is new.

And that’s exactly why it makes it easier (not so much in practical terms from the outset, but in theoretical terms, unless, of course, you are one of those courageous non-techies venturing into this new world of AI-assisted software creation) for a non-techie to grasp the idea of coding agents that can be spawned from one of those AI-infused integrated coding tools, especially the terminal or the command line (the often black screen you see developers toiling in).

That detail matters less because there is nothing special about the loop itself.

It is just a software development technique that performs a task repeatedly based on predefined conditions.

It is just doing something repeatedly.

Like playing a song on repeat.

This time, it is about running coding agents repeatedly.

Iteratively.

It works when the coding agent is given granular, testable specs and allowed to work through them repeatedly until the expected outcomes are met.

That’s it.

And when something fumbles, it will definitely fail, because it is all about running coding agents that depend on models that are, by design, stochastic, again and again until the defects are identified and resolved “through various styles of prompts”.

Every programmer recognizes this pattern.

You receive a list of features from the Product Manager (PM) that need to be implemented, along with various constraints.

You determine the best approach to fulfil the PM’s requirements, write code according to your designed system, which you consider the optimal solution, and then execute the code to observe how it functions.

You see how it works and where it falls short.

You tweak some lines of code or do a complete refactor by throwing away the code you have already written, depending on how far off your initial implementation is from the expected result.

You run it again.

You run a test and then run it again.

Until it is foolproof.

You keep doing this until the code perfectly aligns with the expected product behaviors initially defined by the PM (some detours along the way may also need to be addressed).

The only difference now is that coding agents are maturing to the task, being wired with large language models capable of handling coding tasks over a long horizon.

And if they have to engage with a tool, that won’t be a problem.

The latest models can operate a range of tools, from the terminal to the GUI, such as a browser.

Ralph rides the wave of model improvements encapsulated in modern coding agents.

These agents can now operate autonomously for extended periods, invoke tools without supervision, modify files, run tests, recover from failures, and resume work using artifacts (a shared source of truth between the human and the AI) saved to disk (your computer’s storage device).

Here is the perfect short video from Google explaining what artifacts are:

When those capabilities are combined with predefined, granular specs, iteration no longer collapses at every lingering turn. Instead, you can brace for failure at every iteration point in advance with custom prompts designed to identify recommended routes that avoid contacts which could first lead to failure.

After all, we are dealing with non-deterministic systems in LLMs.

How are we finding ourselves in such fertile ground for such a technique?

Well, the models have improved at long-running tasks.

The models have improved in tool use.

Earlier, they drifted.

They had no way of knowing whether what they generated worked because they couldn’t test it in a real environment.

So they confidently guessed (the beauty of being probabilistic by design, you could say).

Oh, I almost forgot. They declared success prematurely. Even if you keep running them to do the same tasks, the repetition revealed nothing, as there was nothing concrete to measure against in a practical environment.

That has changed.

In case you haven’t been paying attention, I have a two-part series on model improvements (no, they are not focused on benchmarks from the various leaderboards) and on how these improvements have been crystallizing across some widely used CodeGen platforms, particularly AI-assisted coding tools.

Back to Ralph Wiggum, “the software engineer.”

In a Ralph-style setup, plans live outside the agent.

Specifications live outside the agent.

Verification lives outside the agent.

Each run begins by reading the same constraints and producing work that can be checked against them. The conditions are the guardrails for the true north of the product you are collaborating on with AI.

If the output does not meet the specs, the agent continues. It tries a different approach and checks whether it works by giving it a swing, now that the large language models powering the coding agents are capable of tool use.

Ralph doesn’t fix unclear thinking. It keeps going until the gaps can’t be ignored, and that’s usually too late.

If you do not have a shared picture of your build-to-be with the LLMs powering the coding agents you spawn under the Ralphing paradigm, then you are lost.

If the specs are underspecified, iteration produces noise.

If verification is weak, iteration lingers for no functional purpose.

If intent is muddled, iteration amplifies the confusion.

Ralph does not fix any of that.

The agency-control trade-off is a must-have.

How your products should be scaffolded is up to you.

It will definitely remain so for the foreseeable future.

Coding models are not yet capable of fully replacing human developers.

There are a number of variables in the equation that support that argument. I won’t be going into them here now.

If you’re unclear about what your build should look like and how it should be scaffolded, Ralphizing your way to a product that reflects the nuances of the user experience and the architectural needs will remain a pipe dream, regardless of how many coding agents you involve in Ralphizing.

Picture Ralph Wiggum contemplating your seemingly nonsensical implementation idea.

Different Approaches to Ralphizing

Press enter or click to view image in full size

From multiple perspectives, different practitioners are developing different flavours of Ralphizing agentic coding workflows that involve coding agents capable of operating over extended periods, handling tools on the fly when necessary, and functioning without human involvement.

Here are five of them I have stumbled on so far, in no particular order.

Anthropic’s Ralph Wiggum Plugin: Implementation of the Ralph Wiggum technique for iterative, self-referential AI development loops in Claude Code.

Here is this development methodology based on continuous AI agent loops, as the team at Anthropic tried to capture from Geoffrey Huntley’s initial idea in Claude Code.

https://vibingwithai.substack.com/p/the-responsible-way-to-use-the-time

Clayton Farr’s Ralph Playbook- A comprehensive guide to running autonomous AI coding loops using Geoff Huntley’s Ralph methodology. 

Adds structure without changing the core idea. Requirements are separated from planning. Planning is separated from execution. Specs and plans become explicit artifacts that the agent consumes on every run. The repetition stays the same. The clarity improves. 

Here is Clayton Farr’s Ralph Playbook

https://github.com/ClaytonFarr/ralph-playbook

.

Here is another fork of 

Clayton Farr’s Ralph Playbook for Geoffrey Huntley’s Ralph Playbook by ghuntley

 — Three Phases, Two Prompts, One Loop. Ralph as a practice, more than a system. 

Check out the GitHub repo by ghuntley to learn about these individual steps, which are considered the optimal way by ghuntley.

https://github.com/ghuntley/how-to-ralph-wiggum

The snarktank’s Ralph Implementation Approach — This implementation leans toward reuse.

 It treats Ralph as a general automation primitive that can be applied across projects. The goal is not philosophical purity, but portability. 

Check out snarktank’s GitHub repo here to learn about this unique approach.

https://github.com/snarktank/ralph?tab=readme-ov-file

And then there is Ralph Orchestrator by Mikey O’Brien- An improved implementation of the Ralph Wiggum technique for autonomous AI agent orchestration — “

The orchestrator is a thin coordination layer, not a platform. Agents are smart; let them do the work.” 

Here is the GitHub repo for this implementation of Ralph.

https://github.com/mikeyobrien/ralph-orchestrator?tab=readme-ov-file

Ralphy by michaelshimeles -An autonomous AI coding loop that runs AI assistants (Claude Code, OpenCode, Codex, or Cursor) to work through tasks until everything is complete. 

Here is the GitHub repo for Micky’s implementation of Ralp.

https://github.com/mikeyobrien/ralph-orchestrator?tab=readme-ov-file

All of these implementations point to the same conclusion, differing only in which approach is best for achieving the end result without babysitting the Ralphized coding agents.

The breakthrough is that coding agents can now execute against granular specs for long enough while interacting with a real developer environment, dealing with artifacts generated on the fly, to keep the record straight over longer iteration build processes.

Just yesterday, I wrote about the parallelisation effort the Cursor team is experimenting with to run multiple coding agents capable of handling long-horizon tasks.

In closing, I said what I have always said:

Instead of chasing the hottest, trendiest AI-infused coding platforms and tools, focus on learning the foundational literacies of speaking Dev so you can explain what and why, and develop an architectural awareness of how modern software products are wired.

With these two foundational skills under your belt, you can effortlessly communicate with the coding agents, play your part, and define a shared picture of your build with the LLMs that power the very coding agents you spawn to handle the actual build workflow.

You can only adopt the technique, fondly called Ralph after Ralph Wiggum, the recurring fictional character from the animated television show 

The Simpsons

, if you can manage the complexity of software development.

After all, the LLMs only abstracted the part that 

was never the bottleneck

https://ordep.dev/posts/writing-code-was-never-the-bottleneck

.

If you are one of those who have no idea how software products are scaffolded and can’t tell what is what or how components integrate with one another to deliver which features under which conditions, then what the coding agents generate will definitely outstrip your ability to understand it.

In that case, Ralphizing your build process is not for you.

Ralph is here to dispel the illusion that vague intent will somehow resolve itself now that the models are getting good.

Write the spec clearly. At a granular level.

And then it gets Ralphed:

Coding agents go through it.

Iterate through different implementation paths.

Test to see if it works. If it does, keep an artefact that reflects the implementation and move on to the next task. If not, circle back on it.

It is not as if this is an unheard-of technique. Software developers go through the same cycle at every stage of their development workflows.

That is not a new idea but a new way of building with AI- Ralphizing- software being developed by autonomous coding agents without stopping halfway through for a break, out of boredom, laziness, a mental block, or to attend to a vice.

However, your role remains.

You need to have clarity about your build at a granular level.

After all, it is only the tools that have changed, but the “

fundamental requirement for engineering rigor has never been higher,
