CLAUDE.md Is a Suggestion Box. Hooks Are Law.

How hooks fit in

If you’ve used Claude Code long enough, this has happened to you. Claude modified the exact files you told it not to touch. You had it in CLAUDE.md: “

Never modify `services/_shared/models/` without approval

.” Claude read it. Claude acknowledged it. Then Claude modified `services/_shared/models/` anyway — because the immediate task seemed more important than your rule.

In Part 1

/@kumaran.isk/stop-using-claude-code-like-a-chatbot-19aab259a7ee

, we covered why this happens — CLAUDE.md loads as a user message, not a system prompt. It’s influential but not enforced. When the immediate task pulls Claude in a different direction, your rules lose.

Hooks solve this. They’re shell scripts that Claude Code runs before or after Claude executes a tool. Claude doesn’t decide whether to run your hook — Claude Code runs it automatically. If the hook exits with code 2 on a blockable event, the action is blocked. Claude never gets the chance to proceed.

CLAUDE.md defines rules so Claude understands intent. Hooks enforce rules so intent alone isn’t enough.

 You need both. CLAUDE.md without hooks is a suggestion box. Hooks without CLAUDE.md are enforcement without understanding.

I spent weeks writing increasingly detailed CLAUDE.md files before I set up my first hook. Once I added hooks, Claude couldn’t break the rules even if it wanted to — the shell script blocks the action before Claude gets a chance to execute it.

The distinction that matters most

Before you wire up your first hook, understand this: `

PostToolUse

` is non-blockable. It fires after Claude writes a file. Sounds like the right place to block bad writes, but it isn’t. By the time `

PostToolUse

` fires, the file has already been written. Exit code 2 from a `

PostToolUse

` hook sends the output (warning) as context to Claude — it doesn’t undo the write.

To block before execution, use `

PreToolUse

`. That’s the distinction that determines whether your hook enforces a rule or sends a warning after the fact. Use `

PostToolUse

` for logging, linting, pattern detection or any post tasks — not blocking.

Lifecycle Events: Two Categories

Claude Code fires hooks at over 20 defined lifecycle points. Here are the 13 that cover every category you’ll use in practice. The key property for each one: does exit code 2 actually block anything?

Blockable Events — Exit 2 Stops the Action

Non-Blockable Events — Exit 2 Sends a Warning, Nothing More

The mental model is simple. `PreToolUse` blocks. `PostToolUse` warns. Everything else follows from that.

Exit Codes: Three Numbers That Control Everything

Two things to get right: 

write to stderr, not stdout

 — Claude Code reads stderr as the message to display. And 

exit 2 on non-blockable events becomes a warning

 — if you exit 2 from `

PostToolUse

` expecting to block a write, the write stands.

Four Essential Hooks to Wire Up First

These are the patterns I run in every Claude Code project. They cover the most common failure modes.

1. Block Dangerous Bash Commands (PreToolUse)

#!/bin/bash




INPUT=

(cat)  
CMD=

(echo "$INPUT" | jq -r '.tool_input.command // empty')




BLOCKED=("rm -rf /" "curl.*| bash"




"git push --force.*main" "> /dev/sda" "mkfs")

for pattern in "

{BLOCKED\[@\]}"; do  
if echo "

CMD" | grep -qi "$pattern"; then




echo "BLOCKED: $pattern" >&2




exit 2




fi




done




exit 0




```

Wire it in `.claude/settings.json`:

```json




{




"hooks": {




"PreToolUse": [{




"matcher": "Bash",




"hooks": [{




"type": "command",




"command": ".claude/hooks/block-bad-bash.sh"




}]




}]




}




}

The `

matcher

` field filters by tool name. `

Bash

` catches all shell commands. You can also match `

Write

`, `

Edit

`, or any other tool. Omit `matcher` to apply the hook to all tools.

Test your hook before deploying: `

echo ‘rm -rf /’ | .claude/hooks/block-bad-bash.sh

`. A hook that always exits 2 blocks all Claude tool use. Tune `

BLOCKED

` patterns to your project — overly broad patterns create more friction than they’re worth.

Known caveat (as of early 2026):

 `

PreToolUse

` exit 2 reliably blocks 

Bash

 tool calls, but there are open bugs 

#13744

https://github.com/anthropics/claude-code/issues/13744

,

 

#26923

https://github.com/anthropics/claude-code/issues/26923

 where it doesn’t always block `

Write

`, `

Edit

`, or `

Task

` (subagent) calls . For those tools, the more reliable enforcement path is using `

hookSpecificOutput

` with `”

permissionDecision

”: “deny”`. Check the Claude Code issues before depending on exit-2 blocking for non-Bash tools.

2. Context Injection (UserPromptSubmit)

#!/bin/bash




BRANCH=

(git rev-parse --abbrev-ref HEAD 2>/dev/null)  
RECENT=

(git log --oneline -5 2>/dev/null)

cat << EOF




## Session Context (auto-injected)




- Branch: $BRANCH




- Date: $(date '+%Y-%m-%d %H:%M')




- Recent commits:




$RECENT




EOF

Output from this hook is prepended to every prompt Claude sees. Claude always knows the branch. You never type it again. This eliminates an entire class of “

wrong branch

” mistakes with zero effort.

3. Session Resume Protocol (SessionStart)

#!/usr/bin/env bash




# session-start.sh

CONTENT="## SESSION RESUME PROTOCOL (hook-injected)

Context may have been reset. BEFORE any other action:




1. Run TaskList — check for pending/in_progress tasks




2. If tasks found → present status summary before starting new work




3. If no tasks → ready for new work"

s="

{CONTENT//\\\\/\\\\\\\\}"  
s="

{s//\"/\\\"}"




s="

{s//

'\n'/\\n}"




printf '{"hookSpecificOutput":{"hookEventName":"SessionStart","additionalContext":"%s"}}' "$s"




exit 0

Two rules: output must be valid JSON with `

additionalContext

` — plain text is ignored. Always exit 0 — non-zero blocks the session from starting.

4. AI-Pattern Detection (PostToolUse)

#!/usr/bin/env bash




INPUT=

(cat)  
FILE=

(echo "

INPUT" | jq -r '.tool\_input.file\_path // empty')  
\[ -z "

FILE" ] && exit 0




[ ! -f "$FILE" ] && exit 0

if grep -qE "raise NotImplementedError|TODO: implement" "$FILE"; then




echo "WARNING: Stub detected in 

FILE" >&2  
fi  
if \[\[ "

FILE" != *test* ]]; then




if grep -qE "jest\.mock|unittest\.mock" "$FILE"; then




echo "WARNING: Test fixtures in prod file" >&2




fi




fi




exit 0  # warn only, never block writes

This is `

PostToolUse

`, so it’s always exit 0. The warnings feed back into Claude’s context — Claude reads “

stub detected

” and fixes the stub in the next turn without you saying anything. Pattern detection, not enforcement. That’s what non-blockable events are for.

The Rules Architecture: When CLAUDE.md Gets Too Long

A mature CLAUDE.md can grow to 600–900 lines. At that size, you hit a real problem: the “lost-in-middle” effect. LLMs attend less to content buried in the middle of long contexts — in long-context retrieval benchmarks, rules in the middle consistently show lower recall than rules at the top or bottom. Your error handling policy at line 612 is functionally weaker than the same policy at line 12.

The fix is three layers:

Layer 1 — CLAUDE.md as executive summary

 (150–250 lines). Tech stack overview, reference to each rules file, skill/agent routing table, common commands.

Layer 2 — `.claude/rules/` domain files

 (150–350 lines each). `

core-behaviors.md`, `code-standards.md`, `first-principles.md

`, project-specific constraints. Claude Code loads every `.md` file in `

.claude/rules/

` automatically.

Layer 3 — `lessons.md` as live correction log.

 When you correct Claude, the mistake goes here in a four-line format: what happened, what should have happened, the rule, and the date. At three recurrences, promote it to the matching domain file and delete from lessons.

The reference pattern in CLAUDE.md:

## Core Behaviors




> Defined in `.claude/rules/core-behaviors.md`




> (always loaded). Say "understood" then proceed.

This keeps CLAUDE.md under the attention threshold. Every rule lives in a focused file where it gets full recall weight.

Data-Driven Rules: The 10+ Rule Pattern

Once you have more than ten enforcement rules, editing bash scripts to add each one doesn’t scale. The rule engine pattern moves rules into markdown files and loads them at runtime.

Each rule file:

---




name: No Hardcoded Colors (Angular)




applies_to: Write|Edit




file_pattern: "*.ts|*.html"




severity: warning




---




## Pattern




\`\`\`regex




#[0-9a-fA-F]{6}|rgb\(|rgba\(




\`\`\`




## Message




Use daisyUI semantic classes, not raw hex/rgb.

To add a new rule: create a new file. No script editing. The engine finds all rule files, parses frontmatter, filters by `

applies_to

` and `

file_pattern

`, evaluates the regex, and emits warnings or exits 2.

One rule per file. One engine to run them all. That’s the pattern that scales.

Autonomous Loops: Making Claude Iterate Until Done

The `

Stop

` event is blockable. A hook that exits 2 on `

Stop

` prevents Claude from finishing — it feeds a new prompt back instead. Claude iterates on a task until a verifiable completion condition is met.

A state file `

.claude/loop.local.md

` controls the loop:

---




active: true




iteration: 1




max_iterations: 10




completion_promise: "all 47 tests pass"




---




Fix failing tests in auth module. Run pytest




after each change. Continue until all tests pass.

This is a pattern you implement in your own hook — `

` isn’t a built-in Claude Code tag, it’s just a marker your hook script watches for in Claude’s output. Claude must output `

all 47 tests pass

` — exact string match — to exit the loop. Always set `

max_iterations

`. Without it, a stuck loop burns tokens indefinitely. I set the default at 10. Haven’t needed to raise it yet.

Key Takeaways

PostToolUse is non-blockable

 — exit 2 sends a warning, not a block. Use `

PreToolUse

` to block before execution.

CLAUDE.md is advice. Hooks are law.

 CLAUDE.md can be overridden by pushback; hooks run at the shell level regardless.

 block dangerous bash (`

PreToolUse

`), context injection (`

UserPromptSubmit
