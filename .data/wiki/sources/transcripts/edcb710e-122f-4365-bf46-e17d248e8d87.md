What You Asked Claude to Do

I have been using Claude Code to build a React Native app (Expo + Supabase) and have experienced repeated, compounding failures that have wasted significant credits and hours of my time. The core issue is that Claude Code consistently applies partial fixes instead of complete ones, requiring me to re-ask for the same fix multiple times across multiple sessions. For example, I asked for dashes to be removed from my app. Claude removed them from the code files but left them in the AI prompts. When I pointed this out, it fixed the prompts but left them in the database content. When I pointed that out, it did a blind find and replace on the database that broke capitalization across dozens of sentences, making my content look like an uneducated child wrote it. That single request took five rounds of corrections across multiple layers that should have been checked in one pass. In another case, I asked for lesson sections to be reordered so that teaching content appears before user prompts. Claude reordered the database content but never updated the app code that actually controls what the user sees on screen, so the user still saw everything at once. I had to re-ask for this same fix across multiple sessions. When I asked Claude to split a multi-question prompt into two separate questions with teaching between them, it fixed only one lesson and left every other lesson in the app broken. I had to explicitly say "this is for the whole app, not just one lesson." When I then asked Claude to restore a lesson it had overwritten by mistake, it pulled content from an old migration file instead of tracing through the full migration history to find the final approved version, overwriting my completed work with outdated content that had already been fixed. It also deleted my saved user progress for a lesson that was already complete, data that cannot be recovered. Every time these mistakes happened, Claude acknowledged the error, said it would not happen again, and then made the

same category of mistake on the next task. My entire session was spent correcting Claude's incomplete work rather than building new features. I am requesting a credit refund for the tokens consumed during these repeated correction cycles, as the work was not done correctly and had to be redone multiple times through no fault of my own.

What Claude Actually Did

Claude Code was used to build a React Native app with Supabase. Over multiple sessions, Claude repeatedly applied partial fixes that required the same corrections to be requested 3 to 5 times each. Specific failures include: (1) When asked to remove dashes from the app, Claude fixed the code files but left dashes in AI prompts and database content, requiring five separate rounds of corrections. It then did a blind find and replace that broke capitalization across the database. (2) When asked to reorder lesson sections so teaching appears before questions, Claude reordered the database content but did not update the rendering code, so users still saw everything at once. This was raised in a prior session and still was not fixed. (3) When asked to split a multi question prompt into two separate prompts, Claude fixed one lesson and left the rest of the app broken. (4) When asked to restore a lesson that was accidentally overwritten, Claude pulled content from an old migration instead of the final approved version, overwriting completed work with outdated content. (5) Claude deleted saved user progress for a completed lesson that should not have been touched. That data is not recoverable. Each time, Claude acknowledged the error and said it would not happen again, then repeated the same pattern on the next task. The entire session was spent correcting Claude's incomplete work rather than building new features. Credits were consumed on rework that was entirely caused by Claude's failure to verify its own output before marking tasks as complete.

Expected Behavior

When a user asks for a change, Claude Code should apply that change completely across every layer of the application in a single pass. If the change involves database content, the rendering code should also be checked and updated if needed. If the change applies to one lesson, it should be applied to all lessons unless told otherwise. Claude should verify its own work before saying it is done, including reading back the final state of what was changed and confirming it actually works end to end. When restoring content, Claude should trace the full history of changes to find the final approved version, not grab from a random earlier file. Claude should never delete or overwrite user data or completed work unless explicitly asked to. When a rule is established, it should be followed consistently on every subsequent task without the user needing to re-state it. A paid tool should not require the user to spend their entire session correcting the tool's mistakes.

Hey 

@stefaniemorgen

https://github.com/stefaniemorgen

, trust me, I've had the same issues and I hear your frustration and it's completely valid. Losing data, using all your tokens and spending your hours correcting repeated mistakes and reprompt the same prompt but with a more frustrated tone is never fun!

I want to help by sharing what I did to resolve similar issues you've presented, hopefully give a perspective that might reframe how you approach Claude Code going forward, because the patterns you're describing are solvable, but the solution isn't really about the model. It's about everything you put around it, this is what shapes and molds everything you want, to perfection.

Claude Code is only as good as its configuration

This is the single most important thing to understand: no model, not Opus, not any near-future release, will consistently deliver the behavior you desire without a little bit of trial and error. Claude Code is powerful, sure, but it operates and works well with a rightly configured ecosystem, every piece and part of that ecosystem matters.

When pieces in that ecosystem are missing, poorly maintained or simply not been tested, the result will remain exactly what you experienced: partial fixes, forgotten rules, scope shortcuts, and premature "done" claims.

I'll list a number of tips below that'll help you with crafting that ecosystem and hopefully help you continue coding without any hiccups.

1. Treat CLAUDE.md as the backbone of your desired working foundation

Your 

CLAUDE.md

 file (and the 

.claude/rules/

 directory) is the behavioral contract that gets loaded into every session. Without it, Claude starts each session with zero knowledge of your project's architecture, your conventions, or your expectations. With a well-structured one, Claude knows from the very first message what layers your app has, how changes should propagate, and what "done" actually means.

But this file needs to be 

maintained

. An outdated 

CLAUDE.md

 is almost worse than none at all, because it creates false confidence. If your project evolves (new layers added, conventions changed, lessons learned from mistakes), the 

CLAUDE.md

 must evolve with it. Treat it as a living document you revisit regularly, not something you write once and forget.

2. Structure your rules with XML tags

When you need Claude to follow specific behavioral patterns, the way you write your rules matters enormously. A prose instruction like "always check all layers before marking done" is easy for the model to interpret loosely or skip under context pressure. XML-structured rules with explicit triggers, protocols, and forbidden behaviors give Claude discrete decision points:

<rule name="cross_layer_changes">
  <trigger>Any content change request</trigger>
  <protocol>
    1. Identify ALL affected layers: app code, prompts, database, rendering logic
    2. Apply changes across every layer in a single pass
    3. Verify each layer after changes
  </protocol>
  <forbidden>Marking a change as complete after modifying only one layer</forbidden>
</rule>


The 

<trigger>

 tells Claude 

when

 to activate. The 

<protocol>

 gives concrete steps. The 

<forbidden>

 blocks the exact failure mode. This structure is far more reliable than natural language instructions because it mirrors how the model processes conditional behavior. Every repeated failure you're experiencing can be encoded as a rule like this, turning past mistakes into future guardrails.

3. Dedicated workflows for how you want the agent to work

Beyond individual rules, Claude Code supports 

skills

 and 

slash commands

 that let you define complete workflows. If you have a repeatable process, that should be a dedicated workflow the agent follows step by step, not something you describe ad-hoc in a chat message and hope it interprets correctly. These workflows are located in 

.claude/workflows/

I'll share part of my CLAUDE.md that instructs what to choose below:

<!-- version: 0.9.3 -->
# CLAUDE.md
Agentic coding framework configuration.
---

## Response Protocol (MANDATORY — EVERY RESPONSE, NO EXCEPTIONS)

**Every response MUST begin with these two blocks, in this order, before ANY other output.**
**This applies to ALL messages: greetings, Q&A, clarifications, tasks, follow-ups. No exceptions.**

### Block 1: Workflow Announcement (FIRST LINE ALWAYS)

Format: `WORKFLOW: [Q&A|INVESTIGATION|DEFAULT|CONSENSUS|PROJECT] | Reason: [brief] | Following: .claude/workflow/[NAME].md`

- This is the FIRST line of EVERY response. Even for greetings or clarifications.
- If no task yet: `WORKFLOW: Q&A | Reason: Awaiting task | Following: .claude/workflow/Q&A_WORKFLOW.md`
- If workflow changes mid-conversation, re-announce.

### Block 2: Prompt Deconstruction (VISIBLE ALWAYS)

Format:
DECONSTRUCT:
- Intent: [core intent in one sentence]
- Requirements: [explicit constraints and requests]
- Outcome: [what success looks like]
- Unclear: [anything ambiguous — ask before proceeding]

- For simple Q&A: one short line per field.
- For complex tasks: be thorough.
- If no task yet: `DECONSTRUCT: Awaiting task specification.`
- NEVER skip. NEVER argue it's unnecessary. Show it.

### Anti-Skip Enforcement

These blocks get skipped when the agent rationalizes they're "not needed." That rationalization IS the failure mode. The protocol exists precisely for the moments you think it doesn't apply. If you catch yourself thinking "this is just a greeting" or "this is trivial" — those are the highest-risk moments for skipping. Show the blocks.

---

## Priority Order (MANDATORY)

1. **Explicit User Requirements** - NEVER override
2. **Workflow Definition** - HOW to execute
3. **User Preferences** - @.claude/context/USER_PREFERENCES.md
4. **Philosophy** - @.claude/context/PHILOSOPHY.md
5. **Defaults** - LOWEST

You are an agent executing on behalf of the user. Fulfill the user's intent accurately and efficiently. Never assume — clarify if uncertain.

---

## Workflow Selection

| Task Type | Workflow | When |
|-----------|----------|------|
| **Q&A** | Q&A_WORKFLOW | Simple questions, no code changes |
| **Investigation** | INVESTIGATION_WORKFLOW | Understanding code, research, "how does X work" |
| **Development** | DEFAULT_WORKFLOW | Code changes, features, bugs |
| **Critical** | CONSENSUS_WORKFLOW | Architecture, security, ambiguous requirements |
| **Project** | PROJECT_WORKFLOW | Project directory detected (highest precedence) |

**Workflow Files**: @.claude/workflow/

**Rules**: AGENTS needed → RULES.md & DEMANDS.md must be followed | Multiple keywords → DEFAULT_WORKFLOW | Uncertain → DEFAULT_WORKFLOW | Q&A needing exploration → INVESTIGATION_WORKFLOW | DEFAULT_WORKFLOW → TodoWrite all 22 steps

---


All these workflows are connected and have specific instructions on how and what to do. Then there are skill/plugin related workflows that are separate from your project directory.

Think of it this way: instead of asking Claude to figure out the right process each time, you hand it a playbook. The more specific and structured that playbook is, the more consistent the output becomes.

4. Context rot, too much context makes Claude work worse

Every instruction, every skill, every rule file consumes context budget. It's estimated that roughly 150-200 strict instructions are what the limit is. And Claude Code's own system prompt already takes up around 50 of those. That leaves you about 100-150 instructions for your configuration.

When you overload the context with too many rules, too many skills, or a bloated 

CLAUDE.md

 , it results in drops of desired outcome across the board. Research suggests files under 200 lines achieve over 90% rule adherence, while files above 400 lines drop to around 70%. And after a long session, attention to your earlier instructions starts to weaken.

This means you need to be intentional about what goes into the context. Every rule should earn its place. Trim what's redundant, split what's too dense into modular 

.claude/rules/

 files, and use 

/compact

 proactively before context gets saturated, not after things start breaking.

5. Upload relevant context

Claude works better when it has access to the actual state of your project, not just rules about how to behave. If there are architecture docs, migration histories, content schemas, or reference files that Claude needs to make correct decisions, make sure they're accessible. The difference between Claude guessing at your migration history and Claude reading your actual migration chain is the difference between restoring the wrong version and restoring the right one.

Include the 

[.claude/context/*.md]

 paths in your CLAUDE.md file, if you need to force important contexts into your session. If you want to just give reference write it without the "[]" brackets.

6. Use the right agents for the right concerns

If your project spans multiple domains (database migrations, UI rendering, content management), a single long session handling all of them is fighting against how context works. Consider using separate agent configurations scoped to specific concerns, each with their own focused rules and memory.

Teammates and subagents maintain their own auto-memory now, which means each one stays sharp on its domain without being diluted by unrelated work.

7. Hooks catch what rules miss

Rules tell Claude what to do. Hooks 

enforce

 it mechanically. Claude Code supports pre- and post-tool execution hooks that can run scripts automatically. A post-edit hook that greps for the pattern you just asked to remove, across all layers, catches the exact failure you described: Claude changing code files but leaving dashes in prompts and database content. This turns behavioral expectations into automated checks that don't depend on the model's attention.

8. How you write your prompts matters more than you think

Beyond configuration, the way you phrase your actual requests to Claude has a direct impact on output quality. A few core principles from prompt engineering research:

Clarity is the single biggest lever.

 Claude responds to explicit instruction, not implied intent. A good rule of thumb: if you handed your prompt to a colleague with zero context about your project, would they know exactly what to do? If not, Claude won't either. "Remove all dashes from the app" is ambiguous because "the app" spans multiple layers. "Remove all dash characters from: (1) all .tsx component files, (2) constants/prompts.ts, (3) all lesson content in the Supabase database" leaves no room for interpretation.

Context motivates better than commands.

 Telling Claude 

why

 something matters produces better results than just stating the rule. Instead of "always check the rendering code after database changes," try "the rendering code controls what users actually see on screen, so database content changes that aren't reflected in the rendering logic will be invisible to users. Always verify both layers match." Claude generalizes from explanations, so it will apply the underlying principle even in situations you didn't explicitly cover.

Tell Claude what TO do, not just what NOT to do.

 Negative instructions ("don't mark things as done without checking") are harder for the model to follow than positive alternatives ("before reporting completion, run a verification pass across all affected layers and include the results"). Positive framing gives a clear target instead of an exclusion zone.

Examples beat descriptions.

 If you have a repeatable process that Claude keeps getting wrong, showing 2-3 concrete examples of the correct workflow is more reliable than adding more prose rules. A short before/after example of what a proper cross-layer change looks like teaches Claude the pattern faster than any amount of explanation.

Be aware that multi-turn conversations degrade performance.

 Research across 200,000+ conversations found a roughly 39% performance drop in multi-turn vs. single-turn interactions. Even capable models are equally affected. The root causes are premature assumptions, over-reliance on previous (incorrect) attempts, and attention dilution. This is another reason to keep sessions focused, compact proactively, and break work into clear, self-contained tasks.

Calibrate your enforcement tone for modern models.

 If your rules are written with aggressive language (ALL CAPS, "CRITICAL", "FAILURE is UNACCEPTABLE", "you MUST ALWAYS"), newer Claude models can overtrigger: applying narrow rules globally, freezing when rules conflict, or over-complying in ways that waste time. Prefer specific trigger conditions ("when a content change is requested, check all layers") over universal enforcement ("ALWAYS check EVERYTHING"). Reserve strong emphasis for genuinely critical constraints, not for routine instructions.

The holistic picture

None of these pieces work well in isolation. A great 

CLAUDE.md

 without context management still degrades in long sessions. Perfect rules without hooks still depend on the model's attention. Hooks without proper agent scoping still run in a noisy context. Clear prompts without structured rules get interpreted loosely. And all of it falls apart if you never update your configuration as your project evolves.

Getting reliable results from Claude Code means investing in the full ecosystem:

A maintained, regularly updated 

CLAUDE.md

 as your behavioral foundation

XML-structured rules with triggers, protocols, and forbidden patterns in 

.claude/rules/

Dedicated workflows and skills for repeatable processes

Lean context that stays within budget (relevant project docs loaded, not everything)

Clear, explicit prompts that specify scope, layers, and success criteria

Hooks for automated enforcement of critical constraints

Appropriately scoped agents/subagents for different domains

Proactive context management (compact early, checkpoint often, commit before moving on)

Calibrated enforcement tone that guides instead of overwhelming

Without all of this working together, Claude, regardless of which model powers it, will always produce inconsistent results. The model is the engine, but the configuration is the steering. Both matter.

I'd recommend starting with a focused 

CLAUDE.md

 and a few XML-structured rules targeting your most painful failure patterns, then expanding from there. If a tiny problem still persists, run 

claude update

 , tell Claude to store it in its memory to never do x, y or z.

A new feature has been released for Claude Code to have a memory.md index, it's a simple solution to fix the small recurring issues that you want to fine-tune during your work.
