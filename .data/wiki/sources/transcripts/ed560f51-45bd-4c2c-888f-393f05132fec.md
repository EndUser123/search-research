, I covered the foundational mistakes that cause agents to fail before they even start: the monolithic mega‑prompt, linear‑everything thinking, invisible state, all‑or‑nothing autonomy, and passing “as‑is” content through the model.

This article continues that discussion with a focus on scale traps — the patterns that emerge once you introduce tools, multiple agents, and production constraints. These are the issues that surface in real deployments: latency spikes, cost blowups, debugging blind spots, and “agents” that aren’t really agents at all.

The objective of this article is twofold:

To call out advanced anti‑patterns that appear when agents meet tools, multi‑agent routing, and enterprise SLAs.

To provide practical counter‑patterns you can implement so your system remains fast, observable, and reliable at scale.

❌ Anti‑Pattern #7: Tool Soup

(Too many tools, ambiguous tools, or overlapping tools)

Giving an agent a large, undifferentiated toolbelt hoping it will “figure it out” fails predictably. In fact, if we indiscrimately add all tools from 

multiple MCP servers, we can expose 100+ tools

 without realizing the impact.

In deployments with 50+ MCP tools, tool definitions consume ~72K tokens upfront — 

60% of a 128K context window before any work begins

. Worse, these definitions repeat 

every conversation turn

. A 4-turn conversation burns 288K tokens on tool definitions alone, creating both 

cost explosion (up to 400%)

 and context exhaustion.

Why the pattern fails

Context window exhaustion (tool definitions consume 60%+ of context before work begins)

Argument mismatch: models hallucinate arguments by mixing schemas from similar tools

Decision ambiguity from overlapping/redundant capabilities

Increased planning tokens, latency, and resulting in inconsistent behavior

A better architecture: Curate and Specialize

Cluster tools by capability; expose only what’s needed per task

Abstract variants behind parameterized tools; use semantic naming

Specialize: give agents different tool subsets (roles enforce clarity)

MCP servers:

 Explicitly select tools per agent (watsonx Orchestrate enforces this)

Large catalogs (50+ tools):

 Use dynamic retrieval, not upfront loading

Evidence:

Gorilla API-Bench

 (Patil et al., 2023): Tool selection accuracy degrades sharply as catalogs grow from dozens to hundreds. Hallucination rates scale with toolbelt size. (

arXiv:2305.15334

) | 

Anthropic (2025–2026)

: Tool definitions can consume 50,000+ tokens. (

Anthropic Docs

)

❌ Anti‑Pattern #8: Tool Data Overload

(Tools returning megabytes of data when only a summary is needed — also known as “The Firehose Effect”)

Tools returning far more data than needed cause 

“Agentic Drift”

 — agents start strong but become incoherent as conversations progress. Common culprits: database dumps instead of filtered results, binary data (images, PDFs), massive JSON payloads, or verbose metadata. Agents cannot process random binary data, and even structured data becomes unusable at tens of thousands of tokens per response.

Why the pattern fails

Context window exhaustion and cost explosion from verbose tool output

Prefill latency (seconds spent “reading” before generating)

Attention dilution (90% context = raw dump weakens focus)

Agent confusion and hallucinations from high noise-to-signal ratio

Binary data unreadable (base64 images, PDFs)

A better architecture: Filter an the Source

Filter at tool layer:

 Return only needed fields/records; use pagination/filtering at source

Binary data:

 Extract text (OCR, PDF parsing) or metadata before returning

Summaries:

 “Found 1,247 records. Top 5: …” not full dumps

Artifact Pattern:

 Write large datasets to sandbox; return summary; agent peeks selectively

Streaming/chunking:

 Return table of contents or excerpts; let agent request sections

Unmodifiable tools:

 Use sub-agent as data processor/filter

Principle:

 Tools = intelligent filters, not firehoses. Agent’s job = reasoning, not parsing.

Evidence:

Liu et al. (2023)

: “U-shaped” accuracy curve — agents recall beginning/end of context but struggle with middle. More context ≠ more intelligence. (

arXiv:2307.03172

)

❌ Anti‑Pattern #9: Agent-Washing

(Tools Disguised as Agents: “Our agent answers FAQs from a vector store.” That’s a tool.)

“Agents” that do exactly one thing — run a retrieval query, call a single API, or summarize text — are just tools wrapped in expensive reasoning loops. 

Rule of thumb:

 If there’s only one reasonable action, it’s a tool, not an agent.

“Agent-Washing”

 takes a perfectly good function or RAG pipeline and wraps it in unnecessary planning overhead, adding latency and cost without capability. If the path from input to output is a straight line, an agentic loop just generates expensive latency.

Why the pattern fails

Reasoning Tax: planning loops double/triple token count and latency for deterministic operations

Prefill overhead: processing entire agent prompt before calling API

Higher variance and harder testing/maintenance than simple functions

A better architecture: Tools Before Agents

Decision Matrix (3 questions):

 Three Questions Before Using an Agent:

Is the tool selection dynamic? Does the model need to choose between 5 different ways to solve the problem?

Is the path conditional? Does the second step depend entirely on the unpredictable output of the first?

Is there a feedback loop? Does the model need to look at its own output and “try again”?

If the answer to all three is “No,” it should be a Tool/Flow, not an Agent.

Alternatives:

Deterministic workflows for predictable steps

Hard-coded routing with classifier

Stateless execution for single-purpose tools

Expose deterministic capabilities as MCP tools, not agents

Quick aid:

 One path → Tool/Workflow | Multiple actions → Agent | Fixed sequence → Workflow | Open-ended → Agent + tools

Evidence:

ReAct

 (Yao et al., 2022): “Reasoning Tax” — ReAct loops double/triple token count for simple tasks. (

arXiv:2210.03629

) | 

Toolformer

 (Schick et al., 2023): Models can call tools directly without agent framework. Deterministic calls have lower variance. (

arXiv:2302.04761

)

❌ Anti‑Pattern #10: Trust Before Verify

(Using agents, tools, and MCP servers without understanding their behavior)

Teams deploy components — agents, MCP servers, third-party tools — into production without verifying behavior. When failures occur (bad outputs, latency spikes, cost surges), you need answers: What happened? Why? How to fix it? Without observability, you can’t answer.

Many public MCP servers fail basic security and operational audits

 — lacking idempotency, containing prompt injection, or requesting excessive permissions. [

MCP Security Studies done by Endor Labs

https://www.endorlabs.com/learn/classic-vulnerabilities-meet-ai-infrastructure-why-mcp-needs-appsec

]

Compounding risk:

 Tool Soup + Blind Trust creates massive attack surface. Connecting unverified MCP servers means adding 100+ tools AND dozens of security vulnerabilities simultaneously.

Why the pattern fails

Security:

 Prompt injection in tool descriptions, malicious tool behavior, supply chain attacks

Observability:

 Opaque MCP servers, black box agents, no audit trails, irreproducible behaviors, mystery costs/timeouts

Operational:

 Destructiveness, non-idempotency (double charges from retries), monolithic responses, hidden side effects, undocumented edge case behavior

A better architecture: Verify Before Trust

For your own agents:

Trace every step: prompts, models, tool calls, inputs/outputs.

Version prompts, tools, and model selections.

Visualize the plan: timeline, state transitions, decision points.

Log cost and latency per step and per run (planner vs tools vs post‑processing).

For external components (MCP servers, third-party agents):

Audit before adoption:

 Review the implementation. Does it provide logs, traces, or telemetry? Is its operational behavior documented?

Test operational characteristics:

Is the tool idempotent? Can it be safely retried?

Is it destructive? Does it require approval gates?

What side effects does it have? (notifications, state changes, cascading actions)

What does it return? (filtered data or full dumps)

Wrap with instrumentation:

 Add a monitoring layer that captures inputs, outputs, latency, and errors for every external call.

Test in isolation:

 Run the component in a sandboxed environment with test data. Observe its behavior under normal and failure conditions, and when called multiple times.

Demand transparency:

 If a component can’t explain its decisions, document its side effects, or provide audit trails, don’t use it in production.

Add safety controls:

 For destructive or non-idempotent tools, add approval gates, rate limits, or dry-run modes.

Maintain fallbacks:

 Have alternative implementations ready if the external component becomes unreliable or unmaintainable.

When teams add observability and understand operational behavior, reliability improves immediately — not because models changed, but because the system’s characteristics are known and controlled. This applies doubly to external components: if you can’t observe it and don’t understand how it behaves, you can’t trust it.

Evidence:

OWASP Top 10 for Agentic Applications 2026 — ASI02

: Agents can misuse legitimate tools via prompt injection, misalignment, or unsafe delegation. Tool definitions via MCP servers create supply chain vulnerabilities (ASI04). Maps to T2 Tool Misuse, T4 Resource Overload, T16 Insecure Inter-Agent Protocol Abuse.

❌ Anti‑Pattern #11: Happy Path Engineering

(Building only for success: no retries, no dead‑end handling, no graceful degradation)

Agents fail in production when tools malfunction — timeouts, exceptions, inconsistent outputs — triggering cascading errors and task abandonment. 

Root cause: training pipelines optimize only for success

, never exposing agents to the failures dominating real-world usage.

Real systems fail constantly, yet most agents assume tools always work. 

Agents trained only on happy paths become brittle

 — they’ve never seen timeouts, malformed responses, or learned to distinguish “retry” from “escalate.” When tools fail, they loop indefinitely, hallucinate alternatives, or silently quit.

Why the pattern fails

Training on success only (failures filtered as “bad data”)

No failure recovery patterns (can’t distinguish retry vs. escalate)

Cascading reasoning errors from single tool failure

One-size-fits-all retry logic ignoring failure types

Silent failures and no graceful degradation

A better architecture: Design for Failure

Recovery trees per failure class (timeout → backoff, 4xx → escalate)

Fallback tools/flows, dead-end detection, partial re-planning

Evidence:

PALADIN

 (Sept 2025): Without recovery logic, agents achieve <50% success (sometimes ❤0%) when tools fail. Baseline Recovery Rate: 32.8%. With failure injection training: 89.7%. Failure recovery must be explicitly trained. (

arXiv:2509.25238

)

❌ Anti‑Pattern #12: Multi‑Agent Chaos

(No roles, no coordination, no shared state)

More agents create coordination problems, not intelligence. Without clear roles and state sharing, agents duplicate work, contradict each other, or bounce control indefinitely.

Why it fails

No coordinator/routing policy, shared state, or termination rules

Overlapping tool access and authority

A better architecture: Coordinate with Clear Roles

Role specialization, coordinator/routing rules, shared state with invariants

Termination criteria, least-privilege tools per agent

Roles:

 Technical (capability-based) or Business (domain expertise)

Avoid micro-agent overkill:

 Start broad, split only with evidence

Evidence:

MAS-FIRE

 (Feb 2026): Multi-agent chaos creates semantic failures that propagate silently. Stronger models don’t uniformly improve robustness — architecture matters. Iterative, closed-loop designs neutralize 40%+ of faults vs. linear workflows. (

arXiv:2602.19843

https://arxiv.org/html/2602.19843

)

❌ Anti‑Pattern #13: Responsiveness Afterthought

(Fast use cases, slow architectures)

Use cases demanding sub-second or single-digit-second responses fail with nested planning loops, multi-agent handoffs, and heavy retrieval chains.

Why it fails

Planner invoked too often, multiple unnecessary model calls

Over-retrieval and agents where deterministic functions suffice

A better architecture: Performance First Design

Design for latency budgets upfront (300–800ms, 1–3s, 5–8s tiers)

Minimize planner invocations, precompute/cache, inline simple logic

Parallelize calls, short-circuit on high-confidence answers

Evidence:

Google Research

: 53% of mobile users abandon sites >3 seconds. Agent architectures with 5–10s response times fail UX requirements. Latency = first-class constraint. (

Google Support

https://support.google.com/adsense/answer/7450973?hl=en

)

❌ Anti‑Pattern #14: Unbounded Execution Cost

(No cost limits, no budgets, no awareness of accumulating inference costs)

Costs accumulate across small decisions: oversized models for simple steps, repeated retrieval, re-planning loops, and unbounded tool exploration.

Why it fails

No cost awareness, no caching, oversized models, excessive summarization

A better architecture: Make Cost Visible

Cost-aware planning with cost/benefit heuristics

Caching (retrieval, intermediate results, facts)

Right-size models (small/fast for routing, heavy where needed)

Summarize only when needed; prefer structured state

❌ Anti‑Pattern #15: Demo-Grade Agent in Production

(Building a demo agent with off-the-shelf frameworks, testing only on your laptop, and assuming it’s production-ready)

A common pattern in early agent adoption is building a prototype using frameworks like LangGraph, Langflow, LangChain, or even managed platforms. The agent works well in personal testing — handling the happy path scenarios you’ve tried on your laptop — and the assumption becomes: “This is ready for users.”

In most cases, it isn’t.

The problem isn’t the frameworks themselves — they’re powerful tools for building agents. The problem is that 

teams build and test for the demo, not for production reality

. Personal testing on a laptop with curated inputs doesn’t reveal the reliability and scale issues that emerge when real users interact with the system.

Why it fails

Testing gaps:

 No multi-user, adversarial, digression, mind-changing, red-teaming, or edge case testing. Personal testing covers <10% of input space.

Reliability gaps:

 No conversation repair, ambiguity handling, safety guardrails, undo/rollback, or graceful degradation.

Scale gaps:

 No concurrency model, resource management, observability at scale, failure isolation, production optimizations, or MCP/A2A integration.

Infrastructure gaps:

 Missing network scalability, storage/database, horizontal/vertical scaling, caching, context compression, and performance optimization.

Maintenance burden:

 Teams spend more time on infrastructure than agent capabilities. Hidden cost: months of work that mature platforms provide out of the box.

A better architecture: Use Production Agent Platforms

Test for production:

 Multi-user, adversarial, digression, mind-changing, red-teaming, edge cases

Build reliability:

 Conversation repair, ambiguity handling, guardrails, undo/rollback, graceful degradation

Use trusted platforms:

 For example, IBM watsonx Orchestrate provide reliability, testing, concurrency, observability, MCP/A2A, failure handling, enterprise features

Custom when:

 Unique requirements (rare), dedicated team, validated scale needs, testing resources

Decision:

 (1) Tested beyond laptop? (2) Built reliability? (3) Platform meets 80%? (4) Team for scale? (5) Calculated TCO?

Most teams: custom agent platform / custom agent control plane is typically not worth the cost vs. mature platforms.

Evidence:

Forrester 2025

: 75% of firms building custom agentic architectures will fail. Failure due to underestimating infrastructure complexity, reliability engineering, and testing — not technical capability. (

Forrester Blog

)

Closing Thoughts

At small scale, agents can seem magical. At enterprise scale, architecture wins. Tool catalogs must be curated. Agents must be observable. Failure must be designed, not discovered. And every decision — autonomy, cost, latency — should be intentional.
