Problem Statement

Every tool invocation in Claude Code appends its full output to the conversation context. As the session progresses, the context window fills up with stale tool outputs — test results, build logs, file listings, diffs, grep outputs. This is the single biggest practical issue with long Claude Code sessions.

The community plugin 

context-mode

 tries to solve this by intercepting tool calls 

before

 execution via PreToolUse hooks and redirecting them to a sandbox where output is indexed for BM25 keyword search. This works in isolation but has significant limitations:

BM25 search is keyword-based and dumb

 — it can't reason about what's relevant to the current task. If you run 

pytest

 and 2 of 1400 tests fail, BM25 can't extract just the failures unless you know the exact keywords to search for.

PreToolUse interception breaks subagents

 — the hook redirects 

Read

 → 

ctx_execute_file

 , but background subagents can't prompt for interactive permission approval on the redirected tool. Every denial message points to another tool that's also denied, creating a circular permission block:

Hook says "don't use Read, use ctx_execute_file" → subagent tries ctx_execute_file → denied

Hook says "don't use Bash, use ctx_execute" → subagent tries ctx_execute → denied

Every tool redirects to another denied tool → subagent gives up

It's solving the wrong problem

 — the issue isn't the tool call itself, it's the output size. We don't want to prevent the call, we want to handle the result intelligently.

Proposed Solution

Add a 

PostToolUse hook

 that can intercept large tool output and auto-delegate summarization to a lightweight agent before the output enters the main context.

Flow:

Tool runs normally, produces output

PostToolUse hook fires, checks output size against a configurable threshold

If over threshold → automatically spawn a lightweight agent with the full output + current task context

Agent returns a focused summary of only what's relevant

Summary replaces the raw output in the main context window — the raw output never touches the conversation

This could be exposed as:

A setting like 

autoSummarizeLargeOutput: true

 with a configurable line/token threshold

A new hook type ( 

PostToolUse

 ) that plugins can implement

Both — a built-in handler plus the hook type for custom implementations

What the hook needs:

Access to the full tool output (to check size and pass to an agent)

Ability to replace/transform the output before it enters the conversation

Ability to spawn an agent for summarization

This would also enable other useful PostToolUse plugins beyond just output summarization

Why agent-based PostToolUse is better than all of these:

Prevention > cleanup

 — it's cheaper and simpler to never add the bloat than to compress it later

Agent summarization is task-aware

 — unlike BM25 or generic compression, the agent knows what the current task needs and extracts only that

No risk of losing important info during compaction

 — the agent summarizes with full task context at the moment of output, not later when conversation state has moved on

No circular permission issues

 — the tool runs normally, the hook processes the output, no tool redirection needed

Priority

High - Significant impact on productivity

Performance and speed

Use Case Example

Scenario 1: Parallel PR review

Running a PR review with 4 parallel subagents (code reviewer, test analyzer, error handling auditor, simplification reviewer)

Each agent needs to read a 1000-line diff + several source files

When agents return results, each result can be 200-500 lines of structured findings

After 2-3 PR reviews in one session, the context is bloated with old tool outputs from earlier reviews

With PostToolUse agent delegation: each large output gets auto-summarized to ~50 lines of relevant findings before entering context. Session stays fast through multiple reviews.

Scenario 2: Test output

Running 

pytest

 with 1400 tests passing and 2 failing. Today the full output (hundreds of lines of dots, warnings, and collection info) enters context. With this feature, an agent extracts just the 2 failures and relevant tracebacks — maybe 20 lines instead of 500.

Scenario 3: Build logs

Running a build command that produces 300 lines of output. Only the errors matter. Agent returns "Build failed: 2 errors in src/auth.py (line 45: missing import, line 89: type mismatch)" instead of the full log.

Additional Context

Environment:

 We use Claude Code CLI extensively with subagents for parallel code review, test execution, and codebase exploration. The subagent pattern (spawn agent → agent does work → returns summary) is already the best workaround for context management, but it requires manually creating a specialized agent for every possible large-output scenario. The proposed PostToolUse hook would generalize this pattern into the platform.

This is one of the most impactful problems for long sessions. A PostToolUse hook for output summarization doesn't exist natively, but you can approximate it:

1. PostToolUse hook that truncates large outputs and saves the full version:

#!/bin/bash
# ~/.claude/hooks/output-compressor.sh
# Save full output to file, return summary to context

INPUT=$(cat)
TOOL=$(echo "$INPUT" | jq -r '.tool_name // empty')
OUTPUT=$(echo "$INPUT" | jq -r '.tool_output.stdout // empty')
OUTPUT_LEN=${#OUTPUT}

# Only process large outputs (>5000 chars)
if [ "$OUTPUT_LEN" -gt 5000 ]; then
  # Save full output to a retrievable file
  FULL_FILE="/tmp/claude-output-$(date +%s)-$TOOL.txt"
  echo "$OUTPUT" > "$FULL_FILE"
  
  # Log a pointer
  echo "Large output ($OUTPUT_LEN chars) saved to $FULL_FILE" >&2
  echo "Use 'Read $FULL_FILE' if you need the full output." >&2
  
  # For test outputs specifically, extract failures
  if echo "$OUTPUT" | grep -qiE 'FAIL|ERROR|failed'; then
    echo "--- Failures found ---" >&2
    echo "$OUTPUT" | grep -A 2 -iE 'FAIL|ERROR|failed' | head -20 >&2
  fi
fi

exit 0


This doesn't prevent the full output from entering context (PostToolUse is informational), but it creates a breadcrumb for the model to know where the full data lives.

2. CLAUDE.md strategy for output-heavy sessions:

## Context Conservation
For commands that produce large output:
- Use `| head -50` or `| tail -20` to limit output at source
- For test runs: `pytest --tb=short -q` instead of verbose mode
- For grep: add `| head -20` to limit results
- For git log: use `--oneline -10` not full log
- For file listings: use Glob tool (deduplicated) not `find` (verbose)

If you need full output, save to a file first:
  pytest > /tmp/test-results.txt 2>&1
Then read only the relevant parts.


3. PreToolUse hook that auto-pipes large-output commands:

#!/bin/bash
# ~/.claude/hooks/auto-limit-output.sh
# Automatically add output limits to known verbose commands

INPUT=$(cat)
TOOL=$(echo "$INPUT" | jq -r '.tool_name // empty')

[ "$TOOL" != "Bash" ] && exit 0

CMD=$(echo "$INPUT" | jq -r '.tool_input.command // empty')

# Detect verbose commands without limits
case "$CMD" in
  "npm test"*|"pytest"*|"cargo test"*)
    if ! echo "$CMD" | grep -qE '\|.*head|\|.*tail|--tb=short|-q|--quiet|>'; then
      echo "Tip: This test command may produce large output." >&2
      echo "Consider adding '| tail -50' or redirecting to a file." >&2
    fi
    ;;
  "find "*|"grep -r"*|"rg "*|"git log"*)
    if ! echo "$CMD" | grep -qE '\|.*head|--oneline|-n |--max-count'; then
      echo "Tip: This search command may produce large output." >&2
      echo "Consider adding '| head -30' to limit results." >&2
    fi
    ;;
esac

exit 0


The fundamental issue is that PostToolUse hooks can inform but can't modify the output that enters context. The most effective approach is prevention: CLAUDE.md rules + PreToolUse nudges that encourage the model to limit output at source before it hits context. The file-save pattern (save full output, read selectively) is the closest thing to a summarization pipeline you can build with current hooks.
