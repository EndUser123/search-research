# The REAL reason Pi is better than Claude Code or Codex
You may have heard developers switching to this new coding agent harness called Pi,

which is a minimal and extensible way to work with coding agents that you might prefer to

Claude Code, Codex, or even OpenCode. There are a lot of reasons why,

but I'm going to zero in on one feature for managing conversation history, called /tree.

I'm going to compare it to how you might manage conversations in Claude Code or Codex

and talk about why this is just a better way to work with agents. I have my terminal pulled up here

with a Codex conversation. Everything I say also applies to Claude Code, by the way.

This was more of an exploratory prompt, where I was trying to set up an end-to-end testing solution

so that when my agent is working on a desktop app, it can actually check its work.

I just asked a question on how to do this. And the way that I use Codex is very lazy.

I don't use planning mode. I don't save architecture documents.

I just have a long conversation about what I want to build. Then, if we arrive at a point

that feels buildable, I ask it to implement whatever we're doing. So that's what I did here.

It came back with a couple options, gave me what it thought was the best step-by-step solution,

and then I went with its recommendation to implement this CLI package that we're trying to build.

It reached something that worked pretty well. It also verified how the solution works.

But I realized through reading the implementation that it might be a lot simpler if we built it

as an MCP server instead of what I was using here, which is an extension.

So I thought, how do I go back to the previous plan we built and explore that other option?

There are a few ways you can do this. The first option is to just talk to the agent directly.

"I'm not sure I agree with this implementation. It might be simpler as an MCP server.

Can you go explore that?" This works well enough, but you end up with the problem of context pollution.

I don't really want it to know everything it did with the Pi extension.

I just want it to start fresh and explore a new solution. So now I could reach for forking.

This is available in every major harness. Claude Code has /branch. In Codex, it's called /fork.

The mechanics are very simple. It takes whatever you're currently talking about

and forks it over to a new copy. That way, you still have this thread

that you can revisit at any time, but now we have a new thread where we can work on a separate solution.

This also gives me the freedom to go over to a new worktree

and work inside this forked version of the conversation. This works well enough,

but it still doesn't solve some of the fundamental issues I mentioned. First off,

we can't do anything with the context when we fork. It just copies it all over wholesale.

Ideally, I would roll back to where we were discussing the planning document earlier,

which is up here, and start the conversation from this point rather than wherever we currently were.

And really, the only way to achieve that is to be very defensive while prompting with an agent

and trying to predict, will this be a point that I need to fork from in the future?

If I had been super smart up front, I would have saved this to a separate markdown file,

or at this point, I would have run slash fork so I could create multiple conversation threads.

But that requires a lot of upfront thinking. I prefer to just prompt through a solution,

and if I realize I need to roll back a few steps and start over, have some mechanism to do that.

As you can imagine, this is where Pi comes into the picture. Here I have another conversation

I was working on with the Pi agent earlier. Let's say I wanted to do the same sort of thing.

I want to roll back a few prompts in the past to where we were deciding on an architecture doc,

and we had a fork in the road with multiple options we wanted to explore.

If I want to roll back to that fork in the road, I can do so using /tree.

This is a bit like fork, but deciding where you want to fork from.

You can see here that you have access to every call and response in the conversation,

down to the tool calls as well. You can go through all of them individually.

You can also use the left and right arrows to page through. We can see here, right at the top

of this conversation, is when we worked on our initial architecture plan.

If I want to roll all the way back to here and explore a new solution,

I can just select this inside the tree, with an option to summarize as well.

If you want to compact all of the context or add a custom prompt describing,

"This solution didn't work, and now we want to explore a new one," you can do all of that.

I personally just leave it on no summary and roll back to this point.

If you roll back to a specific prompt, it also places whatever prompt you wrote at that point in time

straight in the prompt box. It's literally a Wayback Machine for your agents.

Here, I decided to roll back to the agent's response to that architecture doc

and describe a new direction I want to go down. Then you can continue on with the agent from this point.

Another beautiful thing about tree is that it doesn't rewrite your history

whenever you resume from a previous point. If we look at the tree that's created,

we can see all the branching that has happened in this conversation.

We can see where we got our initial architecture document.

We can see where we branched off to describe a new direction,

and we can see the original thread that we had going. We can create forks in the road in the past.

That way, we don't lose any of the progress we made. All of the history is preserved.

This is powerful because you don't have to plan out when you save architecture diagrams

or when you're going to fork off and explore different options. You can just move forward

as far as you want to go and then branch off later. It's the grug-brain approach.

Another cool aspect is how you can roll back to tool calls as well as agent prompts.

I've started using this whenever I need to debug the meta behavior of an agent,

like when it makes a confusing tool call. Maybe it was trying to do a curl and I realized,

"Oh, we don't have the web search extension installed. Let me set that up."

Or in this conversation, where it reached for my create-worktree skill

and created a worktree off a directory that I did not expect.

I could start a new conversation and ask about it, but I realized I could also use /tree

and roll back to a specific tool call that I thought was problematic.

This is the one that surprised me. I can click into that and ask the agent

why it decided to make that tool call at this fork in the road.

"Why did we create a worktree off of the other working directory?

I would expect this to create a worktree off of the main branch always.

Update the skill if we need to." In many ways, this is similar to how you would use

/side or /btw in Codex or Claude Code,

where you have a question that's unrelated to your main chat thread,

but you still want to bring in as much context as possible from that main chat thread

so the agent can answer that question. Here, the agent patched its skill file

to always branch off of main. Now I can go back to the main conversation I was having.

I can hit the arrow key a couple times, move ahead, and now I'm back to the main thread.
